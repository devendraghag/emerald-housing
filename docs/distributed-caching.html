Distributed caching

Step 1 | Learn the words

What is a distributed cache?

A cache is a fast copy of data used to avoid repeated database reads. A distributed cache is a separate service that multiple application instances can access. Here Redis is shared storage, not a Java map inside one Society Service process.

  • Pod: one running Society Service instance in Kubernetes.
  • Cache key: lookup name such as a flat UUID.
  • Cache owner: service responsible for what is stored and how it is refreshed.
  • Source of truth: authoritative data; here it is Society PostgreSQL.
  • Invalidation: delete cached copy after its source changes.
  • TTL: time-to-live; expiry duration for an entry.
  • Eventual consistency: a read can briefly be old, then converge after invalidation or expiry.
Analogy: PostgreSQL is the official building register. Redis is a shared photocopy at reception. Every receptionist pod reads the same copy. Society Service is responsible for replacing it when the official register changes.
Step 2 | Why share the cache?

Local copies can disagree

Pod APrivate copy may be stale
Pod BMay have another copy
Shared RedisBoth pods use the same keys

If Pod A handles a write, Pod B's private in-memory cache would not automatically know. Both Society pods instead use Redis. Evicting a key through one pod makes the deletion visible to the other.

Remember: Redis shares values and key deletion across pods. It does not broadcast application events or make SQL and cache operations atomic.

Step 4 | See the deployment

Shared by app pods; disposable as data

Society Pod ARead/write cache
Society Pod BSame Redis endpoint
redis-cacheOne Redis deployment
PostgreSQLSource on miss

Kubernetes sets SOCIETY_CACHE_REDIS_HOST=redis-cache. Society Service has two replicas. Cache Redis has one replica, an emptyDir volume, and AOF disabled. Redis restart can lose cache entries; the app repopulates from PostgreSQL.

Availability boundary: manifests do not define Redis replicas/failover or persistent cache storage. Cache is shared across Society pods, but Redis itself is one endpoint.

Step 6 | Follow an HTTP read

Example: list floors

GET /api/v1/floors → FloorController → FloorService.getFloors()
→ @Cacheable("societyFloors", key="all")
→ hit: return cached list
→ miss: query PostgreSQL, then put response in Redis
RequestLoad balancer selects pod
CheckPod reads shared Redis key
HitDeserialize and return
MissLoad DB and fill cache

@Cacheable is on the service method, not in the controller. A Redis per-key distributed load lock reduces duplicate DB loads if pods miss together. TTL eventually expires entries even when invalidation is missed.

Step 7 | Follow an update across pods

Flat write and cache invalidation

1. WriteSociety updates PostgreSQL
2. EventFlat ID and floor numbers
3. CommitTransaction commits
4. EvictListener deletes Redis keys
5. ReloadAny pod reads current row

FlatCacheInvalidationListener runs with @TransactionalEventListener(AFTER_COMMIT). The Spring event is local to the pod handling the write; its listener deletes keys in shared Redis. Other pods see the deletion without receiving that event.

If a flat moves floors, both floor-list keys are evicted. Its negative lookup is removed too. Floor writes evict related lists through @CacheEvict.

Crosses pods: Redis key deletion. Does not cross pods: Spring event itself. No Kafka invalidation topic is used.
Step 8 | Understand consistency

Eventual, not strict, consistency

  • After a normal DB commit, listener evicts shared keys; next read should reload committed data.
  • Between commit and eviction, concurrent readers may briefly see old cache data. DB and Redis operations are not atomic.
  • If Redis is unreachable during eviction, an old key may remain until TTL expiry.
  • Direct SQL updates do not fire service events; cache can stay stale until expiry/manual clearing.
  • Redis restart removes copies; PostgreSQL business records remain and refill the cache.

Describe this as cache-aside with after-commit invalidation and TTL fallback. It is eventual consistency, not linearizable or strongly consistent behavior.

Step 10 | What if Redis fails?

Fallback has a bound

After Redis error, that Society process bypasses Redis for five seconds and loads from PostgreSQL. A semaphore limits fallback loads to 16 concurrent operations per pod; excess requests fail fast and are counted.

Bypass/semaphore are per pod. Aggregate fallback may approach this limit times pod count. The distributed load lock is in Redis and only works while Redis is reachable. Society's Kubernetes cache Redis uses maxmemory 128mb, allkeys-lru, ephemeral storage, and no persistence. Under memory pressure Redis evicts keys by LRU; it is not durable business storage.

Step 11 | Operate and verify

Developer checks

  1. Confirm Society uses redis-cache, not separate redis.
  2. Read the same cacheable value through different Society pods and check it is shared.
  3. Update a flat through Society Service; confirm affected keys are evicted after commit and next read has current data.
  4. Watch cache lookup, DB-load, Redis failure, and lock-timeout metrics in Actuator/Prometheus.
  5. In development, restart Redis and confirm requests repopulate entries.
  6. For direct SQL edits, expect TTL refresh unless cache is cleared.
Metrics and Prometheus scraping exist, but Grafana has no dedicated cache hit-rate panel. A high hit rate alone does not prove faster endpoints; compare endpoint/Redis latency and database load.
Step 12 | Know what is not promised

Tradeoffs

  • Redis durability or high availability: manifest has one ephemeral Redis cache pod.
  • Atomic DB commit plus Redis eviction.
  • Spring events distributed across pods; shared Redis deletion provides visibility.
  • Automatic awareness of direct SQL or another service's writes.
  • Every API response cached; only selected Society floor/flat reads are cached.
  • Strict read-after-write for all concurrent calls in the commit/eviction interval.

Outbox, CDC, versioned keys, or uncached strong reads are possible future choices, not current behavior.

Step 13 | Interview practice

Developer-level explanation

“Society Service uses Redis as a distributed cache for selected floor and flat reference reads. PostgreSQL is the source of truth and Society Service owns cache population/invalidation. Two Society pods share one Redis endpoint, so values and evictions are visible across them. Spring Cache annotations apply per-cache TTLs, typed JSON serialization, a versioned key prefix, TTL jitter, and a Redis load lock to reduce duplicate DB loads. On flat writes, an in-process event triggers an after-commit listener which deletes affected keys in shared Redis. The event itself is not broadcast to other pods/services. Consistency is eventual: service writes invalidate promptly, TTL bounds missed invalidation, and Redis outage falls back to bounded DB loads. This Kubernetes Redis deployment is single-instance and ephemeral, not durable or highly available.”

Follow-up questions

How does Pod B know Pod A changed data?

It does not receive the Spring event. Pod A's listener deletes the key in shared Redis; Pod B then misses and reloads PostgreSQL.

Does Redis own the business data?

No. PostgreSQL is authoritative; Redis holds disposable copies.

Is this strongly consistent?

No. It is eventual; a brief commit/eviction interval exists and missed eviction can persist to TTL.

What if SQL is edited directly?

No service event runs, so cache can remain old until expiry/manual invalidation.

How could invalidation be made reliable across services?

Use outbox or CDC, or make Society Service the required write path. Neither is implemented here.
