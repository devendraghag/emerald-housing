Step 1 | Understand the problem

Why protect a service from a failing dependency?

Suppose Member Service needs Society Service to verify a flat. If Society becomes slow or unavailable, each Member request may wait, fail, and immediately send another request. Under load, this can hold request resources and add more work to an already unhealthy dependency.

A circuit breaker watches calls to one dependency. When failures or slow responses become frequent enough, it temporarily rejects calls locally. This gives the dependency time to recover and prevents repeated work from piling onto it.

Electrical analogy: a breaker trips when a circuit is unsafe. Here it trips when recent dependency calls show that continuing normal traffic is likely to waste time and capacity.
Step 2 | Learn the state machine

Closed, open, and half-open

ClosedCalls pass through; outcomes are recorded.
OpenCalls fail fast without contacting Society.
Half-openA limited number of probe calls check recovery.
Closed againSuccessful probes restore normal traffic.
  • Sliding window: recent calls used to calculate health.
  • Failure rate: failed calls divided by recorded calls after the minimum sample count.
  • Slow-call rate: calls slower than a configured duration divided by recorded calls.
  • Open wait: how long the breaker waits before recovery checks.
  • Fast failure: the caller receives a local error; Society is not contacted.

The breaker is not a retry, timeout, or fallback. Those are separate controls.

Step 3 | Find the feature in this codebase

Member Service protects Society Service lookups

The feature is implemented in Member Service, not as a global gateway filter. The SocietyClient wraps two Society HTTP operations in the same named resilience instances:

  • getFlat(UUID) reads a flat for membership workflows.
  • noticeFlatOptions() reads the minimal directory used to select notice audiences.

Both share the breaker name societyFlatLookup, and also share retry and bulkhead instances. The breaker is local to one Member Service process. Every Kubernetes replica keeps its own state and metrics; one pod opening its circuit does not directly open another pod's circuit.

Scope: this does not automatically wrap all HTTP calls in the repository. Gateway routes to Society, session validation clients, AI provider calls, and database interactions are not all using this SocietyClient breaker.
Step 4 | Follow a real call

From business operation to remote response

Membership / notice business flow
  -> SocietyClient.getFlat(...) or noticeFlatOptions()
  -> Retry.decorateSupplier(...)
       -> CircuitBreaker.decorateSupplier(societyFlatLookup)
            -> Bulkhead.decorateSupplier(societyFlatLookup)
                 -> RestClient HTTP call to Society Service
  -> deserialize and validate result
  -> return success or map failure to a safe dependency exception

The retry wrapper is outermost. Each retry executes the breaker and bulkhead again, so each physical HTTP attempt is evaluated separately. Each attempt gets its own breaker admission decision.

After an HTTP response, SocietyClient validates required fields and the requested flat ID. A successful HTTP status with an invalid body becomes a 502 dependency error, and may count against the breaker under its exception predicate.

Step 5 | Read configured transitions

What makes the circuit open?

  1. The breaker starts closed and evaluates a count-based window of 10 recorded calls.
  2. It waits until at least 5 calls have been recorded before evaluating failure and slow-call rates.
  3. It opens if failure rate reaches 50%, or slow-call rate reaches 60%. A call taking at least 2 seconds is considered slow.
  4. While open, it automatically transitions toward half-open after 15 seconds.
  5. Half-open allows at most 2 probe calls. Probe outcomes determine whether it closes or opens again according to Resilience4j behavior.

The code logs state transitions with the breaker name and source/destination state. This supports event correlation, but is not an alert by itself.

Window size and minimum calls differ: five calls are enough to make a decision, while up to ten recent calls form the evaluation window.

Step 7 | Understand failure classification

Exceptions have an explicit predicate

The configured recorder accepts only SocietyDependencyException values with status 500 or above. Therefore:

  • Mapped Society 502/503/504 errors and timeouts qualify.
  • Expected domain outcomes such as flat-not-found 404, invalid request 400, or conflict 409 do not count as breaker failures.
  • Bulkhead rejection is not a Society dependency failure and is not counted by this predicate.

When the breaker rejects a call, SocietyClient maps CallNotPermittedException to status 503 and code SOCIETY_CIRCUIT_OPEN. Bulkhead saturation maps separately to SOCIETY_CAPACITY_EXCEEDED. There is no cached or synthetic fallback value: callers receive an error.

Retries can amplify breaker accounting: one logical operation may produce up to three physical failures and contribute three outcomes. The retry stops if the breaker itself rejects an attempt, because that rejection is not classified as a retryable dependency exception.

Step 8 | Review test coverage

What tests currently establish

SocietyClientResilienceTest.circuitOpensAfterPhysicalFailuresAndClosesAfterSuccessfulHalfOpenProbe uses WireMock to return 503 twice with a two-call test window. It confirms opening, fast failure with SOCIETY_CIRCUIT_OPEN without another HTTP request, then a successful probe that closes the circuit after the dependency recovers.

The same test class verifies that a saturated one-call bulkhead rejects extra work without issuing a second HTTP request. Other client tests cover transient retry, permanent-error non-retry, timeout-to-504 mapping, and invalid response handling.

Coverage verdict: the essential closed-to-open-to-recovery path and fail-fast behavior are tested. The breaker test uses test-specific thresholds, not the production configuration bean.

Coverage not demonstrated by current tests

  • Production property binding and the exact production thresholds in an application-context test.
  • Opening specifically due to slow-call rate or testing the exact two-second boundary.
  • Half-open rejection above probe capacity or reopening after a failed probe.
  • Metrics binder output and circuit metric exposition at /actuator/prometheus.
  • Breaker behavior across replicas or under live Kubernetes traffic.
Step 9 | Follow the metrics

Instrumentation exists; dashboard coverage is limited

SocietyResilienceConfiguration.resilience4jMeters binds Resilience4j circuit-breaker, retry, and bulkhead metrics to Micrometer. Member Service exposes Prometheus through Actuator. Its Kubernetes Deployment annotates pods for scraping at /actuator/prometheus, and the Prometheus Kubernetes scrape config discovers annotated pods.

SocietyClient also adds custom metrics: timer emerald.society.flat.lookup records one physical flat-lookup attempt, and counter emerald.society.flat.lookup.timeouts counts timed-out attempts. The timer stops inside getFlatOnce, so it is per attempt, not the total elapsed time across retries.

Step 10 | Operate and interpret

Practical incident walkthrough

  1. Identify the Member Service pod and time range. Breaker state is process-local, so compare pods individually.
  2. Check Society call failures and slow-call behavior. Use correlation IDs and Member logs to connect requests with downstream outcomes.
  3. Look for the transition log and breaker metrics tagged with societyFlatLookup.
  4. While open, expect a 503 SOCIETY_CIRCUIT_OPEN and no Society HTTP request for rejected attempts.
  5. Check Society health and latency before changing thresholds. Half-open probes are permitted after the configured wait.
  6. Confirm recovery and normal calls. If one pod behaves differently, inspect its config, network path, and local metrics.

Tune only after comparing downstream latency, errors, request volume, traffic per pod, retry amplification, and caller timeouts. A small minimum-call count can react to little data; a large window or threshold can react too slowly.

Step 11 | Know the boundaries

What this implementation does not do

  • State is in memory per Member Service replica, not shared across pods.
  • It does not serve stale or cached data while open; it returns a 503 dependency error.
  • It protects the configured Society flat lookup and notice-directory calls, not every downstream integration.
  • Retry wraps the breaker, so each attempt is counted separately and can encounter an open breaker.
  • Slow-call duration is a health signal, not a hard timeout. HTTP transport timeouts are separate.
  • Metrics are registered and scrape config exists, but no repository Grafana breaker panel or alert was found.
  • Focused tests do not prove production property binding, metric exposition, or deployment-wide behavior end to end.
Step 12 | Explain it in an interview

Developer-level answer

“Member Service uses Resilience4j around its Society flat and notice-directory calls. The named breaker, societyFlatLookup, has a ten-call count window, five minimum calls, a 50 percent failure threshold, a 60 percent slow-call threshold at two seconds, a fifteen-second open wait, and two half-open probes. It records mapped Society dependency errors with status 500 or above, excluding expected 4xx outcomes. Retry wraps the breaker, so every physical attempt is evaluated. If open, the client returns a 503 SOCIETY_CIRCUIT_OPEN error; there is no fallback data. Circuit-breaker, retry, and bulkhead metrics are registered through Micrometer and Prometheus scraping is configured. Focused tests prove opening, fast rejection, and recovery, but do not test production property binding, slow-call opening, or metric exposition. Grafana has no dedicated breaker panel, and each Member pod has local state.”

Likely follow-up questions

Why does each pod have its own breaker?

Resilience4j registries live in the application process. Shared state would require distributed coordination, which this code does not configure.

Are retries counted as one failure or several?

Several. Retry invokes the breaker for each attempt, and each attempt outcome is recorded independently.

Why exclude 404 and 409?

They can be valid business outcomes or caller-specific errors, not evidence that Society is unhealthy. The predicate records only mapped dependency exceptions with status 500 or above.

What happens when it opens?

The client fails locally with 503 and code SOCIETY_CIRCUIT_OPEN. It does not contact Society and does not provide fallback data.

How is slow-call rate different from a timeout?

The breaker uses two seconds as a health threshold. The HTTP client has separate transport limits: two seconds to connect and three seconds to read.

What would you add to improve confidence?

Add tests for production property wiring, slow-call opening, half-open rejection/reopening, and Micrometer exposition. Then create a Grafana panel and alert based on per-pod breaker state and failure/slow-call trends, after checking the actual Prometheus series.

Does an open circuit mean the dependency is definitely down?

No. It means this pod observed enough qualifying failures or slow calls to stop normal traffic temporarily. The issue could be transient or isolated to that pod's path.
