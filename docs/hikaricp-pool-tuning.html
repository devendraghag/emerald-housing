Step 1 | Start with database connection basics

What is a connection?

A database connection is a live communication channel between a service and PostgreSQL. Opening a new one for every query is expensive, so services keep a set of reusable connections ready.

ServiceNeeds to run a SQL query
ConnectionA channel to PostgreSQL
PoolShared supply of reusable channels
ReturnConnection goes back for another request

Think of a pool like checkout counters. A request borrows a counter, completes its database work, and releases it. If every counter is occupied, new requests wait.

Step 2 | Learn HikariCP terms

What the pool settings mean

  • Maximum pool size: most connections this pool may open.
  • Minimum idle: idle connections Hikari tries to keep ready.
  • Connection timeout: how long a request waits to borrow a connection before failing.
  • Validation timeout: maximum time to check a connection is alive.
  • Idle timeout: when an excess idle connection may be removed.
  • Max lifetime: maximum lifetime of a connection before Hikari retires it.
  • Pool wait/acquire time: time spent waiting to obtain a connection.
  • Pending borrowers: threads currently waiting for a connection.
More connections are not always faster. Too many connections can overload PostgreSQL, increase memory use, and add contention. Tune the total across every pod and service, not one pod in isolation.

Step 4 | Follow a request to the pool

How one SQL call obtains a connection

HTTP requestCalls a service operation
TransactionRead/write intent is established
Routing datasourceChooses writer or optional reader pool
HikariCPBorrows a pooled connection
PostgreSQLExecutes SQL
ReleaseConnection returns to pool when transaction work ends

The routing datasource sends normal transactions to the writer. A transaction marked read-only can go to the reader when that optional pool is enabled; otherwise it falls back to the writer. A LazyConnectionDataSourceProxy delays taking a real connection until transaction read-only status is known.

Writer and reader each have their own Hikari pool. Their maxima are separate connection budgets. Hikari is created as a real bean, so Spring Boot/Micrometer can report pool metrics for the configured datasources.

Step 5 | Calculate the connection budget

Pool size multiplies by replica count

Kubernetes currently starts two pods for each service. HPAs allow Member Service up to 3 replicas and Society Service up to 4 replicas. Both deployments set maxSurge to 1 for rolling updates.

Member DB writer3 max pods x 8 = 24 connections
Society DB writer4 max pods x 8 = 32 connections
If reader is enabledMember 3 x 4 = 12; Society 4 x 4 = 16 to replica DBs

These are configured maxima at HPA scale limits, not the number opened immediately; minimum idle is 1 per active pool. A rolling update can temporarily add a surge pod, so leave extra headroom. Also count migration jobs, admin tools, other applications, and any shared clients against each database's connection limit.

Capacity check: compare the sum of per-pod pool maxima with each database's max_connections and reserve capacity for maintenance and other clients. Member and Society have separate database URLs, so calculate each database budget independently.
Step 6 | Measure pool wait and saturation

Metrics already flow to Prometheus

Member and Society services expose Actuator metrics and Prometheus. Their Kubernetes pods carry scrape annotations; the Prometheus config discovers annotated pods every 15 seconds. The Grafana service overview already graphs active Hikari connections by application, pod, and pool.

To diagnose waiting, inspect these Hikari metrics (exact availability depends on the datasource binder and active pool):

Check which series exist in Prometheus before relying on a query. The dashboard currently shows active connections; wait/pending series can be queried in Prometheus even if a dedicated Grafana panel is not present.

The Actuator /metrics endpoint is restricted to ADMIN or SOCIETY_ADMIN. Prometheus scrapes /actuator/prometheus; service security permits this endpoint, while Kubernetes network policy should limit who can reach it.
Step 7 | Tune only after observing a bottleneck

Read several signals together

  1. Run a repeatable representative load profile; record request rate, database latency, pool metrics, and database CPU/connection usage.
  2. If pending borrowers and acquisition wait rise while active stays at max, identify whether queries/transactions are slow or pool capacity is insufficient.
  3. Check PostgreSQL CPU, locks, I/O, and max_connections before increasing pool size. A saturated database can get worse with more clients.
  4. Shorten transaction scope and optimize queries before increasing connections when connections are held too long.
  5. Change the environment-backed pool max gradually, then repeat the same workload and compare latency, pending, DB load, and errors.
  6. Set a service-wide budget using HPA maximum replicas and rolling-update surge, not only the current pod count.

Connection timeout of 2 seconds means a request fails rather than waiting indefinitely. It is not the same as a database query timeout or a transaction timeout.

Step 8 | Operate and diagnose

Where to inspect this at runtime

  • Prometheus: query the Hikari series by app, pod, and pool; Prometheus scrapes every 15 seconds.
  • Grafana: open the Emerald Housing Service Overview and inspect the existing Active Hikari connections by Pod panel.
  • Actuator metrics: an authenticated administrator can query a named metric using the service's /actuator/metrics/{metric-name} endpoint.
  • Environment: Kubernetes ConfigMap provides pool defaults; deployments may override them through environment variables.
  • Database: compare pool wait with PostgreSQL connections, active queries, locks, and resource saturation.

Use one load profile before and after a change. Changing pool sizes based only on the number of threads or current traffic can hide query/database bottlenecks.

Step 9 | Know the current limits

What is included and what is not

  • Hikari writer/read pool configuration, environment overrides, datasource routing, Actuator/Prometheus exposure, pod scraping, and an active-connection Grafana panel are already present.
  • No automatic pool-size optimizer is configured. Values are explicit defaults and must be tuned from observed load and database capacity.
  • The member and society HPAs scale on CPU, not pending database connections. A pool bottleneck may not trigger HPA scaling.
  • The dashboard includes active connections but no dedicated acquisition-wait or pending panel. Prometheus queries above are available as an operational approach; add panels if operators need them on the dashboard.
  • Replica pools are disabled in the checked-in Kubernetes config. Enabling them needs a real replica URL, credentials, and an independent connection budget.
  • Metrics and a 15-second scrape interval may miss very short spikes. Use application traces or database telemetry for deeper investigation.
Step 10 | Interview practice

Developer-level explanation

"Member Service and Society Service create Hikari writer pools with maximum size 8 and minimum idle 1, and optional reader pools with maximum size 4. Pool values are environment-configurable. A routing datasource selects the reader only for read-only transactions when replicas are enabled; otherwise reads use the writer. Actuator exposes metrics and Prometheus scrapes the service pods. Grafana already shows active Hikari connections. To tune, I would inspect active/max, pending borrowers, and connection acquisition time alongside database CPU, locks, and connection limits. I would calculate the budget using each service's maximum pod count and rolling-update surge, then change one setting and rerun the same load test. The HPA currently scales on CPU, not pool saturation, and there is no automatic pool tuner."

Likely follow-up questions

Does a larger pool always increase throughput?

No. The database may become overloaded by more concurrent clients. More connections can increase contention, memory use, and context switching.

What does pending mean?

Threads are waiting for a connection because all available pool connections are currently borrowed.

How do you estimate pool wait?

Use the acquire timer's cumulative sum divided by its count over a time window, or inspect the acquire timer directly. Ensure the metric exists in the target Prometheus scrape.

Why count pods in the pool budget?

Every pod owns its own pool. Scaling replicas multiplies the possible connections to the database.

What is the difference between writer and reader pools?

Writer connects to the primary database. When replica routing is enabled, read-only transactions can use the separate reader pool and replica URL.
