Step 1 · Before opening the code

What pagination means

Suppose a building has 20,000 flats. If an API sends every flat for every screen refresh, the server must load and serialize a huge result, the network carries it all, and the browser must keep it in memory. Pagination means asking for a manageable slice at a time.

Page numberThe position of a slice. This project numbers from zero: page 0 is the first page.
Page sizeThe maximum number of rows requested, such as 20.
OffsetHow many matching rows come before this page. Page 2 at size 20 has offset 40.
Sort orderThe order in which rows are arranged before selecting a slice.
CursorA continuation bookmark identifying where the previous batch ended.
Count metadataThe total matching rows/pages, when the endpoint calculates and returns them.
Simple analogy: a directory is a thick book. Page-number pagination says “open page 4.” Cursor pagination says “continue after the last name I just read.” Both avoid handing over the entire book at once.
Step 2 · Understand the problem

What changes when a list grows?

Without paginationAPI asks for every matching row
→
More workDatabase, service, network, and browser handle more data
→
With paginationRequest asks for a bounded batch
→
Predictable responseClient fetches more only when needed

Pagination controls the number of returned rows per request. It does not by itself make a filter fast, create a missing database index, or guarantee that every endpoint in an application is paginated.

Project review result: core member, flat, membership-history, account, owner, and family browse flows have bounded routes. Some legacy and workflow lists remain unbounded; see the coverage table.
Step 3 · What this project already has

Build order: request contract, validation, query, response

  1. HTTP routes: controllers expose page routes, and member/flat controllers also expose cursor routes.
  2. Safe request rules: PageRequests.of(...) checks that page is non-negative, size is 1–100, sort field is allowed, and direction is asc or desc.
  3. Bounded database access: directory query code sets the offset and maximum rows. It also adds an ID tie-breaker so rows with the same primary sort value have a stable order.
  4. Response mapping: page responses include content and page metadata. Cursor responses include items, a continuation cursor, and hasNext.
  5. Client usage: the portal uses page routes for the main member, flat, family, and owner directories.

This feature is already implemented for these routes. This documentation update does not add or change pagination behavior.

Step 4 · Follow an actual request through the code

Example: list the first 20 members

GET /api/v1/members/page?page=0&size=20&sortBy=createdAt&direction=desc
1 · BrowserSends page, size, sort, optional search/status
→
2 · GatewayRoutes the API request to Member Service
→
3 · ControllerMemberController.getPage reads query parameters
→
4 · ServiceMemberService.searchPage validates and delegates
→
5 · QueryDirectoryQueries.page builds bounded query plus count
→
6 · DatabaseReturns selected rows; API maps them to response DTOs

Put simply: the controller does not fetch every member and trim the list in Java. The service passes paging instructions to the query layer, and the database applies the requested offset and maximum result size.

In DirectoryQueries.page, JPA calls setFirstResult(offset) and setMaxResults(pageSize). For page 0 and size 20, offset is 0 and the result is capped at 20. A separate count query computes totalElements for the response. The actual database SQL syntax is generated by the JPA provider and database dialect.

Where does the index fit? Pagination says how many rows to return and where to start. A suitable database index can help find and order those rows efficiently. Pagination itself does not create an index; indexes are managed separately through database schema migrations.
Step 5 · Learn page-number pagination

Page 0, page 1, and the response

For size=20, page 0 asks for rows 1–20; page 1 asks for rows 21–40. In general, offset = page × size.

GET /api/v1/members/page?page=0&size=20
GET /api/v1/members/page?page=1&size=20

The member page response is a PageResponse: content, page, size, totalElements, totalPages, sortBy, and direction. Filters such as search and status are applied to both the page query and the count query.

Sort fields are allow-listed by each service before the query is built. The query appends the row ID as a tie-breaker. For example, if two members have the same createdAt, the ID still gives them a deterministic order.

Why cap size at 100? It prevents a caller from asking for a huge “page” that defeats the purpose of pagination. Invalid page, size, sort, or direction inputs are rejected rather than silently accepted.
Step 6 · Learn cursor pagination

Use a bookmark for continued browsing

Offset pagination may become more expensive for very deep pages because the database can need to pass over earlier matching rows. For member and flat directories, this project also provides cursor routes ordered by createdAt and id.

GET /api/v1/members/cursor?limit=20
GET /api/v1/members/cursor?limit=20&after={nextCursor}
First callNo cursor; get up to 20 members
→
Extra rowQuery asks for 21 to detect another page
→
ResponseReturn 20 items and hasNext=true
→
Next callSend nextCursor as after

The cursor encodes the last row’s timestamp and ID plus a hash representing the query/access scope. It is URL-safe Base64 encoded, which makes it opaque-looking but not encrypted. Limits are capped at 100. Cursor pagination uses its fixed ordering; it does not provide arbitrary sort choices. Membership histories currently have page routes, not cursor routes.

Step 8 · How a developer operates and reads it

Try a request and interpret the result

Use an environment where the app is running and pass the required authentication for that route. Example member requests:

GET /api/v1/members/page?page=0&size=20&sortBy=createdAt&direction=desc
GET /api/v1/members/page?page=1&size=20&sortBy=createdAt&direction=desc
GET /api/v1/members/cursor?limit=20
  • Use page and size when a UI needs numbered pages and total counts.
  • Use the returned page metadata to render page controls and know the number of matches.
  • For cursor browsing, pass the returned nextCursor as after on the next request.
  • If the API rejects a request, check page ≥ 0, size 1–100, allowed sort field, and direction.
  • For performance analysis, inspect the generated SQL and database execution plan; a bounded result alone does not prove the query is fast.
Step 9 · What it does not guarantee

Limits and practical next steps

  • Deep offsets: high page numbers can still cost work. Prefer cursor traversal for long sequential member/flat browsing.
  • Count query: page metadata includes totals, which requires a count query and may be costly for complex filters.
  • Concurrent changes: records can be inserted or removed between page requests, so offset pages may shift. Cursor continuation is more stable for traversal but is not a frozen snapshot.
  • Indexes: pagination limits result size; review indexes for filter and sort columns using actual query plans.
  • Coverage: migrate callers away from unbounded legacy routes and add bounded variants for growing workflow collections where needed.
  • Different route implementations: JPA directory pages return page metadata, while some raw SQL routes return only a list. Consumers should not assume all responses share one shape.
Step 10 · Explain it in an interview

Developer explanation

“I reviewed pagination in Emerald Housing. The member and flat directories expose page-number endpoints with a maximum size of 100, validation for page and sort input, deterministic ordering, and page metadata. The JPA query applies offset and max results in the database query, while a count query supplies total metadata. For deeper member and flat traversal, cursor endpoints use createdAt and ID, fetch limit plus one to determine whether more results exist, and return a continuation cursor. The portal uses bounded routes for its main directories. I also found legacy full-list routes and some workflow collections without pagination, so the feature covers core browsing but not every collection API.”

Likely follow-up questions

Does the controller itself paginate the Java list?

No. The controller forwards the requested page to the service. The query layer applies the offset and maximum result count in JPA or SQL, so the service does not load the full list and slice it afterward.

Why validate page size?

A maximum prevents clients from requesting an enormous response and defeating the resource bound. The shared page helper permits sizes from 1 through 100.

Why add ID to the sort?

The primary sort value can be identical for multiple rows. ID supplies a deterministic tie-breaker so page boundaries are less likely to reorder arbitrarily.

Why use a cursor instead of page numbers?

Cursor traversal resumes after a known key and avoids increasingly large offsets. In this implementation it is available for member and flat directory traversal.

What does limit plus one accomplish?

If the client asks for 20, the query fetches up to 21. The extra row indicates that a next page exists; it is removed from the returned 20 items.

Does pagination make the query fast automatically?

No. It bounds the result returned. Query predicates, sort, indexes, database load, and count-query cost still matter and should be checked with execution plans and metrics.
