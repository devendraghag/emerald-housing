Step 1 · Understand the idea

What pagination means

Imagine the Emerald Housing directory has thousands of flats. A screen usually needs only a small group at a time. Pagination asks the database for a bounded group instead of loading the whole directory into the service and trimming it in Java.

Directory dataMany matching rows
→
RequestWhich page or where to continue?
→
DatabaseReturn a bounded group
→
API responseRows plus navigation information
Page numberWhich numbered batch to retrieve. This project starts at page 0, the first page.
Page sizeThe maximum number of rows requested in one numbered page.
OffsetHow many matching rows come before the requested page: page number x page size. Page 2 with size 20 skips 40 rows.
LimitThe maximum rows returned in a cursor batch. In this project, cursor limit is between 1 and 100.
FilterA condition that chooses which rows qualify, such as member status or flat floor. Filters are applied before counting and pagination.
SortThe order matching rows are arranged in before the database selects the batch.
Total elementsThe number of rows matching the filters. Page responses include this count.
Total pagesHow many numbered pages are needed for all matching rows at the chosen page size.
CursorA continuation token that marks where to resume when requesting the next batch.
One example: with 45 matching flats and a page size of 10, there are 5 total pages. Page number 2 has offset 20 and returns up to 10 rows. A cursor request instead uses a limit (for example, 10) and the returned cursor to continue.
Key distinction: pagination limits the rows returned. It does not automatically make the database query fast, add indexes, or mean every list endpoint is paginated.

More specific notes: the Society flat directory page/cursor routes support search, status and floor filters. The member directory supports search and status. Membership history has page and cursor routes from either member or flat perspective. Account, owner and family cursor alternatives use their existing filters and access rules. Their cursor implementation is in each controller/service, separate from the shared directory query helper.

Page and cursor responses are intentionally different. A page returns totals and sort information. A cursor response returns items, nextCursor and hasNext. Consumers should use the contract for the route they called.

Step 3 · Trace a real page request

Member directory: HTTP request to PostgreSQL

GET /api/v1/members/page?page=0&size=20&sortBy=createdAt&direction=desc&status=ACTIVE
1 · ClientSends page, size, sort and optional filters
→
2 · MemberControllergetPage(...) reads parameters
→
3 · MemberServicesearchPage(...) applies service flow
→
4 · PageRequestsValidates bounds and allowed sort
→
5 · DirectoryQueriesBuilds content and count queries
→
6 · PostgreSQLReturns the bounded rows and count
→
7 · ResponseMaps entities to DTOs and page metadata

The query helper uses JPA Criteria and calls setFirstResult(offset) and setMaxResults(size). It separately runs a count query with the same filters. Hibernate translates these instructions into SQL for the configured database; the guide does not assume a hard-coded LIMIT/OFFSET spelling.

MemberController.getPage └─ MemberService.searchPage ├─ PageRequests.of(page, size, sortBy, direction, allowedSorts) └─ DirectoryQueries.page(search, status, ..., pageable) ├─ Criteria query: filters + ORDER BY + offset + max results ├─ Count query: same visibility and filters └─ PageImpl → PageResponse<MemberResponse>
Why this matters: loading the whole list and calling subList() would still transfer and hold all matching rows. Here the page bounds are passed to the database query.
Step 4 · Learn page-number pagination

Page number, size, offset and metadata

For 45 matching rows and size 10, there are five pages. Pages start at zero. Page 2 has offset 2 × 10 = 20, so it starts after the first 20 matching rows.

Page 0Rows 1–10
Page 1Rows 11–20
Page 2Rows 21–30
Page 3Rows 31–40
Page 4Rows 41–45
GET /api/v1/members/page?page=2&size=10&sortBy=createdAt&direction=desc

The shared response record in each service contains:

{
  "content": [ /* this page's DTOs */ ],
  "page": 2,
  "size": 10,
  "totalElements": 45,
  "totalPages": 5,
  "sortBy": "createdAt",
  "direction": "desc"
}
Response fieldMeaning
contentRows for the requested page, mapped to API DTOs
pageZero-based current page
sizeRequested page size
totalElementsTotal rows matching the current filters and access rules
totalPagesNumber of pages calculated from count and size
sortBy, directionRequested sort configuration

Internally, PageRequests.of constructs Spring Data Pageable/PageRequest. The custom query returns a Spring Data Page, and PageResponse.from(...) maps its content while retaining the metadata used by this API.

Validation: page must be non-negative, size must be 1–100, the sort field must be on that route’s allow-list, and direction must be asc or desc. The helper rejects invalid requests with the application’s invalid-page error.

Stable page order: the member and flat directory page queries append id ASC after the requested sort. If two rows have the same createdAt or flatNumber, the ID breaks the tie deterministically.

Step 5 · Learn cursor pagination

Continue from the last row instead of skipping a large offset

A cursor is a bookmark for sequential browsing. Member and flat directory cursor queries use the fixed order createdAt ASC, id ASC. Membership-history cursor endpoints also exist; check MembershipService for their exact ordering and validation.

GET /api/v1/members/cursor?limit=20&status=ACTIVE
GET /api/v1/members/cursor?limit=20&status=ACTIVE&after={nextCursor}
Request 1No after token
→
QueryFetch at most limit + 1 rows
→
TrimReturn up to limit; extra row means more exists
→
ResponseItems + hasNext + cursor
→
Request 2Pass cursor as after

For a page size of 20, the query asks for up to 21. If it gets 21, the service returns 20, sets hasNext=true and encodes the last returned row as the next cursor. If there are no more rows, nextCursor is null.

Cursor position = (createdAt, id) └─ next batch condition: createdAt > lastCreatedAt OR (createdAt = lastCreatedAt AND id > lastId) └─ ORDER BY createdAt ASC, id ASC

The cursor also carries a hash of the query and access scope, including filters and identity/role scope. Reusing a cursor with different filters or a different access scope is rejected as INVALID_CURSOR. It is URL-safe Base64 encoded, which is not encryption. Cursor limits are 1–100.

Page-number approachCursor approach in this code
Can jump to a requested page; includes total countsContinue from prior result; no total count in CursorPage
Uses requested sort allow-list and offsetUses fixed ordering and a continuation token
Deep offsets may require more database workUses last key values; suited to sequential browsing
Rows can shift between requests when data changesLess sensitive to offset shifts, but not a frozen snapshot
Step 6 · Understand what is being paged

Filters, permissions, safe sorting

The query is not simply “take rows 1–20.” It first selects the rows visible to the caller and matching filters, orders that result, then applies page bounds.

Access scopeCan this caller read these records?
→
FiltersSearch, status, floor where supported
→
OrderAllow-listed field + direction + ID tie-breaker
→
WindowOffset and size, or cursor and limit
Rule in current directory queriesWhy it matters
Member reads apply the member-access policy; a resident is restricted to their own member record.Page counts and content must describe data the caller may see.
Society flat reads are constrained to the Emerald society; residents are restricted to their own flats.A filter must not expand visibility across societies or residents.

Member and Society page queries apply the same predicates to their count query. Society flat page/cursor queries fetch the related floor as part of the query for response mapping.

Step 8 · Think about production behavior

What pagination helps with—and what it does not solve

ConcernWhat happens in this designPractical response
Huge responsePage size and cursor limit are capped at 100.Keep bounded routes as the preferred choice for growing directories.
Deep page numberOffset grows with page number; query rejects offsets above Java’s integer range and tells callers to use cursor pagination.Use cursor traversal when the user is moving forward through many results.
Total count costPage queries execute a separate count query; cursor responses do not contain totals.Choose cursor when total pages are not needed; measure complex filtered counts.
Concurrent inserts/deletesOffset boundaries can move between requests. Cursor continuation is less affected by offsets, but does not create a cross-request snapshot.Choose the navigation contract that fits the user workflow and consistency needs.
Query speedA small result still may require scanning many rows or sorting; pagination does not create indexes.Inspect generated SQL, query plans, metrics and existing migration-managed indexes.
Changing orderDirectory pages append ID as a tie-breaker; cursor order is fixed by its key tuple.Keep a deterministic order for reproducible page boundaries.
Do not claim a measured speedup from pagination alone. To prove performance, compare representative data, SQL plans, database work and API latency. This guide documents query behavior, not benchmark results.
Step 9 · Know the boundaries

Implemented coverage and remaining unbounded routes

The repository includes bounded directory, membership-history, account, owner and family routes. Cursor alternatives now cover the growing lists that previously only had offset-based access. Compatibility list/page routes remain for existing clients. Floors stay page-based because the domain limits them to floor numbers 1–99.

Step 10 · Practice explaining the implementation

Interview questions and answers

How does pagination work in Emerald Housing?

The Member and Society services expose page-number routes for member, flat and membership-history data. Controllers pass parameters to services; helpers validate page, size, sort and direction; JPA query code applies offset and max results. Page routes also run a count query and return a project-specific PageResponse. Directory cursor routes use a fixed createdAt/ID order and return items with continuation information.

Does the application load every row and then split the list?

Not for the directory page query implementation. The JPA query receives the offset and maximum result size via setFirstResult and setMaxResults. Some separate compatibility endpoints still return whole lists, so choose the bounded route when browsing potentially large data.

What is the difference between the page response and cursor response?

PageResponse includes content, page, size, totalElements, totalPages, sortBy and direction. CursorPage includes items, nextCursor and hasNext, without total counts or arbitrary sort parameters.

Why does the page query need a count query?

The API returns totalElements and totalPages, so it needs the total number of matching rows. The directory query helper executes a count query using the same filters and access predicates. Counting can be expensive on large or complex datasets.

Why is ID appended to the requested sort?

Many records can share the primary sort value. ID gives a consistent tie-break order, which makes page boundaries deterministic for a given dataset.

What does limit plus one do in the cursor query?

If the requested limit is 20, the query fetches at most 21 rows. The extra row tells the service that more data exists. The service returns only the first 20 and sets hasNext.

Can a cursor be reused with different filters?

No. The directory cursor includes a hash for the filters and access scope. If the token is malformed or belongs to a different scope, the API reports INVALID_CURSOR.

Is the cursor encrypted?

No. It is URL-safe Base64 encoded and includes the position plus a scope hash. Base64 is encoding, not encryption; clients should treat the token as opaque.

Does pagination guarantee a fast query?

No. It limits returned rows. Filters, sort order, indexes, data distribution, count work and database load still matter. Use query plans and production-like measurements to assess performance.

What happens with a very high page number?

Large offsets may be costly. The directory helper also rejects offsets larger than Integer.MAX_VALUE and directs the caller to cursor pagination for deep browsing.

Does every list route use pagination?

No. The repository has bounded directory and membership-history routes plus compatibility routes that return lists. Pagination coverage must be checked endpoint by endpoint.

How would you explain the design in one minute?

“We use page endpoints when clients need numbered navigation and total counts, and cursor endpoints for sequential browsing. The services validate bounds and query inputs, enforce access filters in the database query, and apply the row limit there rather than slicing a full result in memory. Page queries include a matching count query; cursor queries fetch one extra row to determine whether another batch exists. Pagination controls result size, but I still check query plans and ensure callers use bounded endpoints.”
