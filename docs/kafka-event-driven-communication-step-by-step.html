Step 1 | Learn why services use messages

Synchronous call versus event message

With a synchronous HTTP call, service A asks service B for an answer and waits. This is useful when A cannot continue without B's result. It also couples the request to B's availability and response time.

With event-driven communication, a producer records that something happened. A consumer processes that fact later. The producer can finish its own transaction without waiting for notification fan-out. The consumer can scale or recover separately, but the result arrives later and duplicate delivery must be handled.

An event is a durable announcement, not a remote method call. It says what happened; consumers decide what work follows.
Step 2 | Learn event-driven concepts

Producer, topic, key, consumer group

  • Producer: serializes and sends an event.
  • Topic: named log that stores related events.
  • Key: groups related messages and determines partition placement; here the domain object's ID is used.
  • Consumer: reads messages and applies its own work.
  • Consumer group: identifies one logical subscriber. Multiple groups can independently consume a topic.
  • Eventual consistency: the event's downstream effect may appear after the producer's database commit.

Messages may be delivered again. Good consumers make database effects idempotent, commonly by recording a stable event ID.

Step 4 | Identify business events

Events represent committed domain changes

  • Community notices: when a notice status changes to PUBLISHED, the service creates CommunityNoticePublished.
  • Lost and found: workflow changes publish event types for publication, resolution, claim submission, and qualifying flat reassignment when the report is already published or claim-received.

The event is created from the business operation and handed to its publisher. The publisher's publish method inserts the event envelope into the corresponding outbox table. It does not immediately invoke listener code or ask the consumer for a response.

The triggering database update and outbox insert share the service transaction. If that transaction rolls back, the event is not left behind as a false announcement.

Step 5 | Read the event contract

Versioned JSON envelope and entity key

Both Java event records include:

  • eventId — stable UUID for deduplication.
  • noticeId or reportId — aggregate/entity identifier.
  • eventType and actorId — action name and initiating account.
  • occurredAt — business occurrence time.
  • schemaVersion — currently 1.
  • timestamp and correlationId — envelope timestamp and request correlation.

Publisher sends the serialized event as a string and uses notice/report ID as the Kafka key. Topics currently have one partition, so all keys in each topic share that partition; the key is still useful for preserving the domain identity and for future partitioning.

No schema registry is configured in the checked-in code. Schema compatibility is currently maintained through the JSON record shape and explicit schemaVersion field.
Step 6 | Understand reliable publishing

Database outbox closes the dual-write gap

Service transaction
  -> update notice/report row
  -> insert event into PostgreSQL outbox
  -> commit both together
  -> HTTP response returns

Scheduled outbox dispatcher
  -> claim pending rows using FOR UPDATE SKIP LOCKED
  -> send JSON event to Kafka with entity ID as key
  -> wait for broker send result
  -> delete the outbox row after success
  -> retain and retry after failure

The scheduled dispatchers poll every second by default and claim up to 50 rows with a 180-second lease. SKIP LOCKED lets multiple Member Service instances claim separate rows. The publisher uses a claim token when deleting or releasing a row.

The send uses KafkaTemplate.send(...).get(): the business request does not wait for Kafka, but the background dispatch worker waits for the send acknowledgement before deleting the outbox row.

Step 7 | Understand consumer responsibilities

Consumers create recipient-specific notification rows

Each listener parses the event JSON, then inserts (flow,eventId) into kafka_processed_events with a uniqueness check. If the event ID has already been processed for that flow, the listener records a duplicate metric and returns.

For a new event, the listener selects eligible admins and current residents/family members based on active accounts, memberships, flat/audience rules, and actor exclusion. It inserts rows into community_notice_notifications or in_app_notifications. The listener's database transaction makes the processed-event marker and notification writes commit together.

This is database notification fan-out, not an email/SMS delivery. Other endpoints later read those persisted notifications.

Step 8 | Understand delivery guarantees

At-least-once delivery with idempotent effects

  • Producer settings include acks=all, Kafka producer idempotence, 10 send retries, and a 120-second delivery timeout.
  • If a send fails, the outbox row remains, its attempt count increases, its claim is released, and a later scheduled poll can try again.
  • If Kafka accepted a record but the process crashed before outbox deletion, the row can be sent again. Duplicate events are expected and consumer event-ID deduplication protects the database effect.
  • Listener failures are retried twice after the first delivery, each with a 1-second fixed backoff. Persistent errors are sent to a corresponding .DLT topic.
  • Consumer offset commit and PostgreSQL transaction are not one distributed transaction. Deduplication covers a database commit followed by a crash before offset acknowledgement.

The practical contract is at-least-once message delivery with idempotent notification writes, not a claim of exactly-once processing across PostgreSQL and Kafka.

Member Service uses KAFKA_BOOTSTRAP_SERVERS with default localhost:9092. Local compose runs a single-node Kafka 4.0 KRaft broker; E2E compose also defines a single Kafka broker. Consumer auto-commit is disabled and record-level acknowledgement is configured.

One partition constrains parallel consumption and ordering is topic-wide. One replica means the checked-in topic shape is not durable across broker loss. Production must choose partition count, replication, retention, security, and monitoring based on deployment requirements.

Step 10 | Operate and interpret

Follow queue depth and failed records

Useful Member Service metrics include outbox rows waiting by flow, sent/consumed/failed counters, and duplicate counts. Interpret them together:

  • Growing kafka.outbox.waiting suggests broker connectivity or scheduled dispatch is not keeping up.
  • Outbox send failures should correspond with retained rows and increased attempt counts.
  • Consumer failures move to DLT after configured retries; inspect DLT payload and headers before replay.
  • Duplicate counters can indicate expected redelivery after crash/rebalance or a repeated producer dispatch.
  • Compare consumer lag and notification creation volume to distinguish a publisher backlog from a slow consumer.

docs/kafka-operations.md describes inspecting DLT topics and replaying selected JSON records to the original topic. Consumers dedupe by event ID; intentional reprocessing requires reviewing/removing the processed-event row first.

Step 11 | Decide where event-driven communication fits

Use events for facts and deferred side effects

Good candidates are work that can happen after the main state transition, does not need to return a result to the caller, and can tolerate eventual consistency. Notification fan-out fits that shape.

Keep synchronous calls for work whose answer is required before the business operation can commit or return. This project uses HTTP for Society flat validation in membership flows and for session validation. Replacing those with an event would require a different request/reply or saga contract, correlation state, timeout handling, and compensation rules.

  • No Kafka producer/consumer was found in Society Service or AI Service for cross-service business integration.
  • No general event bus, schema registry, Kafka Streams topology, or request/reply topic is configured.
  • Outbox polling retries indefinitely; no max-attempt quarantine or exponential poll backoff is defined.
  • Topic partitions/replicas are small development defaults and limit throughput and fault tolerance.
Step 12 | Interview preparation

Developer-level explanation

“Kafka event-driven communication in this repository is used by Member Service for asynchronous notification fan-out. Notice publication and selected lost-and-found transitions update business data and insert a versioned event envelope into PostgreSQL outbox tables in the same transaction. A scheduled dispatcher claims rows in batches with SKIP LOCKED, sends JSON to Kafka keyed by notice/report ID, and deletes only after the broker acknowledges. Member Service listeners in separate consumer groups use eventId deduplication and transactionally create recipient notification rows. Producer reliability settings, consumer retries, DLT topics, and metrics support recovery. It is at-least-once delivery with idempotent database effects. Kafka is not currently the general service-to-service communication mechanism: Society validation and session checks remain HTTP, and Society cache invalidation is an in-process Spring event.”

Likely follow-up questions

Are the producer and consumer different services?

Not in these flows. Both Kafka publishers and listeners are in Member Service, although they are decoupled by Kafka topics and can run on different Member Service instances.

Why do we need the outbox?

It commits the event-to-publish with the business update, preventing a database success plus lost event if Kafka is unavailable.

Can an event be delivered more than once?

Yes. A publisher may send successfully and crash before deleting the outbox row. Consumer deduplication makes repeated processing safe for notification rows.

Does the HTTP request wait for listener completion?

No. It waits for its database transaction, including the outbox insert. Kafka dispatch and notification generation happen later.

Why keep Society validation synchronous?

The business operation needs the Society response to decide whether to proceed. Notification fan-out has no result needed by the request.

Is this exactly once?

No. The system uses at-least-once delivery and idempotent database effects; there is no atomic transaction spanning Kafka and PostgreSQL.

What limits production scale?

Each topic is declared with one partition and one replica, and outbox sends are sequential with a blocking acknowledgement wait. Production sizing and broker durability need explicit design.
