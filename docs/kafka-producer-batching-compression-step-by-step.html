Kafka producer batching and compression, from zero

1. Learn the basics first

A Kafka producer sends records to a topic. Each record has a key and value. Kafka groups records for a partition into a batch and sends a request to a broker.

  • batch.size: the target maximum space allocated for a batch per partition; it is not a promise that every batch reaches this size.
  • linger.ms: how long the producer may wait briefly for more records before sending a partially filled batch.
  • compression.type: compression codec applied to batches sent to Kafka.

Batching can reduce request overhead. Compression can reduce bytes sent and stored, at the cost of CPU. These settings trade latency, CPU, request rate, and network/storage use. They should be judged with producer metrics under representative traffic.

Before this change: producer reliability settings existed (acks=all, retries, and idempotence), but batch size, linger, compression, producer-side measurements, and an enqueue-before-wait batch flow were not configured/implemented.

2. What the project already had

Community notice and lost-and-found event publishing uses PostgreSQL outboxes. Each scheduled dispatcher claims up to 50 rows and sends to its Kafka topic. The Kafka topics currently each have one partition. A single key per event is the notice/report ID.

The outbox already exposed waiting-row depth and successful/failed message counters. The Member Service Actuator endpoint is scraped by Prometheus, and Grafana already had service panels. However, senders waited synchronously for each event’s broker acknowledgement before sending the next event. That serialized the sends and left little opportunity to fill producer batches.

Both publishers follow the same approach. Enqueuing multiple records before waiting allows Kafka’s producer to batch records for the same partition during the configured linger window. With the current one-partition topics, all sends for a topic can share that partition’s batches.

4. What was changed, step by step

Step 1 — queue the claimed batch

Each dispatcher now serializes the claimed rows and calls KafkaTemplate.send for each row, retaining the returned future alongside its event. It does not wait between sends.

Step 2 — wait for per-record acknowledgement

After enqueueing, the dispatcher awaits each future. For each successful send it deletes only that event row using the matching event ID and claim token, then increments the existing per-flow sent counter.

Step 3 — preserve failure recovery

If serialization, enqueue, or acknowledgement fails for one event, that event’s attempts count increments, its claim is released, and the existing failure counter/log is emitted. Other queued sends still get their results processed independently.

Step 4 — set tunable starting defaults

The producer now uses a 32 KiB batch target, a 5 ms linger window, and LZ4 compression. Environment variables can override each setting. These are conservative starting values to measure, not a benchmark-proven optimum.

Step 5 — sample Kafka client metrics

A scheduled component reads the shared producer’s native metrics through KafkaTemplate.execute, selects the Kafka metric families for batch size, records per request, compression rate, and record size, then publishes Micrometer gauges.

Step 6 — display the evidence

Grafana now shows average batch bytes, compression ratio, and records per request per pod, alongside the existing sent/consumed and consumer lag signals. Compare these over a representative workload before changing values.

7. Read the signals together

  • Records/request rises and batch size rises: producer is combining more work into broker requests; check that publish latency remains acceptable.
  • Compression ratio falls below 1: batches are being reduced on the wire; compare network bytes and producer CPU to decide whether the saving is useful.
  • Batch size stays close to one record: traffic may be too sparse to fill batches, events may be large, or the linger window may be too short for this workload.
  • Outbox depth rises: compare sent rate, failed sends, Kafka availability, and scheduling; producer batching alone cannot fix a slow broker or producer outage.
  • Records/request improves but p95 event delay worsens: batching may be trading latency for throughput; adjust linger or revert based on the service’s event freshness requirement.

For example, the conceptual PromQL is kafka_producer_records_per_request_avg{namespace="emerald-housing"}. Use Grafana’s pod dimension to compare instances. Pair it with rate(kafka_messages_sent_total[5m]), outbox waiting depth, publish failures, CPU, and broker/network telemetry.

8. How to tune safely

  1. Capture a baseline under representative event volume before changing configuration: throughput, publish latency, batch size, records/request, compression ratio, CPU, and outbox depth.
  2. Change one setting at a time. Compare linger.ms for latency/batch fill, then batch.size for memory and batching, then compression codec for network/CPU trade-offs.
  3. Test both a sparse workload and a burst. A value that works for a burst can add unnecessary delay at low traffic.
  4. Keep producer reliability settings intact while tuning batching. This project uses acks=all, idempotence, retries, and a delivery timeout.
  5. Compare before/after using identical load and environment. Keep the change only if it improves the targeted objective without violating event freshness, CPU, memory, or error limits.
  6. Document the winning settings with workload and broker context; do not generalize a single local run to production.

Compression is most useful when batches contain repeated/compressible data. Tiny single-record batches can show little benefit or even overhead. This repository has not run a producer benchmark, so the configured values are measurable defaults rather than proven performance improvements.

9. Reliability boundaries to preserve

The outbox remains the durable source for event intent. A row is deleted only after its own send future acknowledges successfully. Failed sends release the row for a later attempt. Enqueueing many sends before waiting does not change this per-row completion rule.

Producer idempotence reduces duplicates from producer retries but does not eliminate outbox replay duplicates if Kafka acknowledges and the process fails before the database row is deleted. Consumers still deduplicate by event ID. Batching and compression do not create a distributed PostgreSQL/Kafka transaction.

Failure nuance: a large queued batch can have multiple in-flight sends. The dispatch code handles each future separately, but a process crash can leave every claimed row to be recovered after its claim lease expires. Verify lease duration and delivery timeout remain compatible when changing these settings.

10. Verification performed

The Member Service compiled and the focused Kafka producer metric extraction test passed. That test verifies averaging matching producer metric entries and ignoring metrics with other names. The existing outbox-to-Kafka Testcontainers integration test was selected to check the asynchronous publisher path, but it was skipped because no Docker environment was available.

The Grafana dashboard JSON parsed successfully and the observability Kustomize build succeeded. These checks validate code compilation, the calculation helper, and dashboard structure. They do not measure real compression ratio, batch fill, throughput, or latency against a live broker.

11. Limits and next evidence

  • No checked-in load-test results establish that 32 KiB, 5 ms, and LZ4 are optimal for this application.
  • The new metrics are sampled every 15 seconds and are producer-client averages, not per-message timing or exact per-topic throughput.
  • Kafka metric availability and labels can vary by client version and activity. Confirm exported values rather than assuming every gauge is populated.
  • Current event topics each have one partition, limiting parallel broker-side consumption, though producer batching can still reduce request overhead.
  • Outbox sends are now queued in batches of up to 50, bounded by the existing SQL claim batch. Very large increases can raise producer memory and in-flight work.
  • Grafana panels show producer samples by pod but there is no automated tuning controller or alert tied to these values.
  • Load testing against a live Kafka broker is still required before claiming throughput or bandwidth improvement.

12. Interview preparation

60-second explanation

“The Member Service publishes events from two transactional outboxes. Previously the dispatcher waited for each Kafka acknowledgement before submitting the next event, which limited producer batching. It now queues the claimed batch first and then awaits each future; each outbox row is still deleted only after its own broker acknowledgement. We configured a 32 KiB batch target, 5 ms linger, and LZ4, all overridable through environment variables. A scheduled sampler reads Kafka’s native batch-size, records-per-request, compression-rate, and record-size metrics into Micrometer and Grafana. These are starting values, not benchmark-proven wins; we would validate them with representative traffic while watching latency, CPU, outbox depth, and delivery errors.”

Likely follow-upAnswer
Why enqueue before waiting?It lets multiple records reach the Kafka producer buffer together so the producer can batch records for a partition. The dispatcher still waits for each event’s own result before deleting its row.
What does linger trade?A short delay can increase batch fill and reduce request overhead; it can also add latency when traffic is sparse.
Why LZ4?It is a fast compression codec suitable as a starting point for event traffic. The compression ratio and CPU cost must be measured for actual payloads.
Does compression always reduce bytes?No. Small or incompressible batches may have little benefit or overhead. Check the measured ratio and network/broker bytes.
Does producer idempotence make the whole flow exactly once?No. It covers producer retry semantics. PostgreSQL outbox deletion is separate, so replay can still republish after a crash; consumer event-ID deduplication remains necessary.
How do you prove the tuning helped?Run comparable representative workloads before and after, then compare throughput, records/request, batch size, compression ratio, publish latency, CPU, network, and outbox backlog.
