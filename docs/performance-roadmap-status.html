Recommended next steps

  1. Pick key user journeys (for example member lookup, flat directory, membership creation, notice/lost-found flow) and define representative data volume and concurrency.
  2. Add one repeatable load tool (#2/#57) with warm-up, steady-state, ramp, and teardown phases; keep secrets and destructive test data controlled.
  3. Record a baseline: request rate, p50/p95/p99 latency, error rate, CPU/memory, pool saturation/wait, SQL/query counts, Kafka consumer lag, and cache hit/miss.
  4. Run a separate stress test (#3) only after the baseline is stable. Identify the first constrained resource and observe recovery after load stops.
  5. Change one variable at a time (query/index, pool, cache, consumer, CPU/memory), repeat the same scenario, and retain changes only when the outcome improves without unacceptable errors or staleness.
  6. Turn on trace export deliberately in a test/target environment and confirm spans actually reach Tempo; the checked-in default is disabled.
  7. Document results: environment, commit, workload, data shape, configuration, before/after percentiles, and known limitations. Source presence is not a benchmark result.

There are no new application features in this audit. The purpose of this page is to correct status claims and make the evidence trail navigable.

Interview-ready summary

Short answer: “Emerald Housing already has a solid set of performance building blocks: pagination and selected cursor APIs, Redis caching, Hikari configuration, Resilience4j around a downstream Society read, Kafka outbox/idempotency flows, consumer-lag/producer metrics, JFR capture tooling, and Kubernetes resource/HPA manifests. The key gap is proof: I would not call the system performance-tuned until I run repeatable representative load and stress scenarios, confirm trace/metric collection, inspect query plans, and compare before/after results. Several capabilities are deliberately scoped rather than global.”

Likely follow-up: What would you do first?

Establish an API workload baseline with realistic data and report p95/p99 latency, throughput, errors, and resource saturation. Then isolate the bottleneck using metrics/traces and SQL plans. Avoid tuning several settings at once.

Likely follow-up: Does “HPA included” mean it scales?

No. The HPA manifest is only a desired policy. The cluster needs the metrics API, matching pod resources, and observable traffic. Validate scale-up, scale-down, and request latency under load.

Likely follow-up: Does “Kafka lag metric included” mean lag is optimized?

No. It means lag can be observed for configured consumers. Optimization requires workload evidence and controlled changes to processing time, concurrency, partitions, batch sizes, and downstream capacity.

Likely follow-up: Why not enable every cache or parallel call?

They can add staleness, invalidation complexity, memory pressure, connection contention, and retry/load amplification. Add them only where measurement shows a bottleneck and where semantics remain safe.
