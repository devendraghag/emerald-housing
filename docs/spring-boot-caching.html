Step 1 | Start with the basic problem

Why cache?

A repeated read normally travels from application to database and back. A cache keeps a temporary copy so repeated requests can return sooner and avoid repeated database work.

No cacheRequest → PostgreSQL → response
Cache hitRequest → Redis → response
Cache missRedis miss → PostgreSQL → save copy → response

PostgreSQL remains the source of truth. Redis contains disposable response data that can be reconstructed.

Step 2 | Learn Spring Cache words

What the annotations mean

  • @EnableCaching switches on Spring's cache interception support.
  • @Cacheable checks the named cache/key before invoking a method. On a miss, the method runs and its result is cached.
  • @CacheEvict removes one key or all entries after a successful method call, based on its options.
  • Cache name groups related values; key distinguishes individual entries within that cache.
  • sync=true asks the cache provider to synchronize a value load for the same key; this project also adds a Redis lock across pods.
Spring annotations are applied through Spring's proxy/interceptor mechanism. Calls entering the bean through the Spring proxy receive caching behavior; a self-call from one method to another method on the same object can bypass proxy advice.
Step 3 | Find where caching is enabled

SocietyCacheConfiguration is the entry point

SocietyCacheConfiguration is a Spring @Configuration class annotated with @EnableCaching. It implements CachingConfigurer, allowing the project to provide its own CacheManager, CacheResolver, and cache error handler rather than accepting only framework defaults.

Boot startsFinds configuration bean
@EnableCachingRegisters cache interceptors
Service callInterceptor reads cache annotations
ResolverSelects Redis-backed cache or bypass manager

So the call sequence is controller → Spring service proxy/interceptor → cache resolution → service body only when needed. The controller itself does not perform Redis commands.

Step 4 | Understand CacheManager and CacheResolver

How this project builds Redis caching

The redisCacheManager bean creates a Spring Data Redis RedisCacheManager. It declares four allowed caches: floor list, flat by ID, all flats, and flats by floor. Each gets a typed JSON serializer and its own TTL. Unknown cache names are disabled instead of being created dynamically.

The configuration also applies a versioned key prefix, disables null caching, enables cache statistics, and marks the manager transaction-aware. A custom CacheResolver wraps each cache to add lookup metrics, load-lock behavior, and Redis failure handling. During the local Redis bypass window, it returns a NoOpCacheManager cache so the service loads from PostgreSQL.

Typed serialization matters: a Redis byte/string value has to come back as the expected DTO or DTO list, not an untyped generic object.

Step 6 | Trace one endpoint end to end

Example: GET /api/v1/flats/by-floor/2

On a miss, FlatService.listByFloorNumber loads the floor and flat rows, maps them to response DTOs, and returns the list. The body records database-load metrics. The caching interceptor stores the successful result with its TTL. With sync=true and the custom per-key Redis lock, multiple Society pods coordinate a miss and recheck Redis before doing the database load.

GET /api/v1/flats/by-floor/2
  -> controller calls service
  -> cache key societyFlatsByFloor / 2
  -> hit: service body skipped

Step 7 | Trace mutations and invalidation

Cache doesn't update itself when PostgreSQL changes

Flat writes publish FlatReferenceChangedEvent. The FlatCacheInvalidationListener handles it after transaction commit and deletes the flat-by-ID, all-flats, impacted floor-list, and negative-cache keys. Floor create/update methods use @CacheEvict(allEntries=true) for related caches. Flat activation uses a broad cache eviction annotation.

After an entry is removed, the next cacheable read misses, executes the service loader, and writes the new value. This is eviction-and-reload behavior, not a database change automatically propagating into Redis.

Transaction-aware manager plus after-commit event listener help avoid invalidating cache data before the database transaction succeeds. Redis and PostgreSQL still are not one atomic transaction.
Step 8 | Review security and special cases

Why some reads intentionally bypass caching

The all-flat and by-floor caches only activate when @societyAccess.staff() is true. That prevents the staff list cache from being reused for resident-scoped results. The flat controller also chooses uncached FlatService.get(id) for the internal authority SERVICE_MEMBER_FLAT_READ; its code comment says the assignment validation must read the primary to avoid read-replica lag false negatives.

Paginated, cursor, and search methods have many changing inputs and are not annotated. Caching them safely would require all filters, page/cursor, sort, tenant and authorization dimensions to be represented in the key and invalidated correctly. The current code leaves them uncached.

A separate SocietyNegativeCache stores short-lived “flat not found” markers. It is custom Redis code rather than a Spring @Cacheable method, and flat changes remove the marker.

Step 9 | Locate the configuration values

Redis connection and per-cache lifetime

  • application.yml provides environment-backed Society Redis host/port/password, 500 ms connection/command timeouts, and Lettuce pool limits.
  • TTL defaults in the manager: floors 10 minutes, flat-by-ID 2 minutes, all-flats and flats-by-floor 5 minutes. TTL jitter defaults to 30 seconds.
  • Negative-cache TTL defaults to 30 seconds. Load-lock defaults: wait 2 seconds, lease 30 seconds, retry 25 ms.
  • Kubernetes config points Society Service to redis-cache; the Redis cache is separate from other Redis uses.
  • Startup floor warmup is enabled by default and can be disabled with SOCIETY_CACHE_WARMUP_ENABLED.

TTL jitter randomly shortens the configured TTL. Configuration validates that TTL and lock durations are positive and jitter is smaller than TTL.

Step 10 | Observe Spring caching

Measure whether it helps

SocietyCacheMetrics exposes cache lookups by cache/outcome, lookup duration, database load counts and duration, Redis failures, fallback rejections, load-lock timeouts, negative lookups, and warmup results. Actuator exposes metrics/Prometheus; Prometheus scrapes Society pods. Grafana currently has no dedicated cache panel.

  • Compare hit and miss rates per cache.
  • Compare cache lookup duration to database loader duration.
  • Check endpoint latency and DB load before claiming improvement.
  • Look for Redis errors, fallback and lock timeouts when misses rise.
Post-lock cache rechecks are not counted as separate lookups, so the reported hit ratio is an operational measure rather than every Redis read performed internally.
Step 11 | Know the implementation limits

What it does not claim

  • Not all services or endpoints use Spring caching; only selected Society reference reads do.
  • Redis is a disposable cache, PostgreSQL remains authoritative.
  • Consistency is eventual: an old value can be observed around commit/eviction or if invalidation fails, bounded by TTL where entry remains present.
  • Cache metrics do not prove faster user-visible response by themselves.
  • Spring method caching is proxy-driven; self-invocation can bypass annotations.
  • The Redis Kubernetes deployment is a single ephemeral cache instance, not a durable HA cluster.
Step 12 | Practice the interview answer

Developer explanation

“Society Service enables Spring caching in SocietyCacheConfiguration using @EnableCaching and a custom RedisCacheManager. The manager declares typed caches with per-cache TTLs, a versioned key prefix, null caching disabled, and transaction awareness. Cacheable service methods cover selected floor and flat reference reads. On a hit, Spring's interceptor skips the method body; on a miss, the repository-backed service method runs and its DTO result is cached. Staff conditions prevent some shared list caches from applying to resident views. Flat changes evict affected keys after commit, while floor writes use CacheEvict. There is a custom resolver/wrapper for metrics, Redis fallback, and a cross-pod load lock. Pagination/search and internal primary-read validation remain uncached. This is targeted Spring Cache usage, not a global cache for the whole application.”

Likely follow-ups

What does @Cacheable do on a hit?

It returns the cached value and skips executing the annotated method body.

What happens on a miss?

The method executes, reads from PostgreSQL, and Spring stores the returned value under the cache/key.

Why a custom CacheResolver?

It selects instrumented Redis caches or a no-op cache during bypass and wraps cache behavior with metrics and a load lock.

Why condition on staff?

To avoid reusing a shared staff list result for a different caller scope.

Why avoid caching every endpoint?

Some results depend on identity, pagination, filters, or primary database consistency. Incorrect keys/eviction could return wrong or stale data.

Does @CacheEvict make Redis and the DB transaction atomic?

No. Transaction-aware behavior and after-commit events align timing, but they do not form a distributed atomic transaction.
