Step 1 | Learn what the name means

What is Caffeine?

Caffeine is a Java in-memory cache library. A cache entry lives in the memory of one running Java process. It can make a lookup very fast because the app does not need a network call to Redis or PostgreSQL.

  • Local / in-memory: data belongs to one process and disappears when that process restarts.
  • Per-pod copy: each Kubernetes pod has its own cache contents.
  • Maximum size: a bound that keeps the local cache from growing forever.
  • Expiry: entries are removed after a configured duration or access policy.
  • Invalidation: local entries must be removed or refreshed when the source data changes.
Analogy: Redis is a shared bookshelf in a building lobby. Caffeine is a small personal notepad kept by each receptionist. The notepad is quicker to check, but each receptionist can have different notes.
Step 2 | Determine the actual status

Caffeine is not currently implemented

Repository inspection found no Caffeine dependency or Caffeine cache configuration. Society Service uses Spring's cache abstraction with Redis. There are no code changes adding a local cache in this feature.

The requested condition is to add Caffeine only when a hot dataset is measured and per-pod differences are acceptable. Cache hit/miss and lookup-latency instrumentation exists, but repository files do not provide observed production measurements showing Redis as a bottleneck. Adding a second cache without that evidence would introduce memory use and more invalidation paths without demonstrated benefit.

Decision: do not add Caffeine now. Continue using the existing shared Redis cache, and collect/inspect the current measurements before reconsidering a local layer.
Step 3 | Understand the cache already in the project

Society uses shared Redis caching

SocietyCacheConfiguration enables Spring caching and builds a RedisCacheManager. Selected floor and flat reference reads use @Cacheable; write paths evict affected keys. Two Society pods use the same Redis service, so entries and evictions are shared across those pods.

Flat by IDsocietyFlatById, default TTL 2 minShared response lookup.

PostgreSQL remains the source of truth. The Redis cache has TTLs, invalidation, hit/miss and latency metrics, a load lock, and a bounded DB fallback on Redis failure. Caffeine would be an additional layer, not a replacement for those responsibilities by default.

A local cache is not automatically faster overall. If Redis is already fast and the database is not pressured, Caffeine may add complexity with little measurable improvement.
Step 5 | Picture a future two-level read

Only if measurements justify it

Request to Pod ACheck local Caffeine
Local hitReturn immediately
Local missCheck shared Redis
Redis missLoad PostgreSQL and fill lower layers

If implemented as a two-level cache, each pod would check its own Caffeine first, then Redis, then PostgreSQL. A value filled on Pod A would not automatically appear in Pod B's local cache. Pod B would discover updates through explicit invalidation, short local TTL, version checks, or by eventually missing its local entry and reading Redis again.

request -> local Caffeine hit? return
        -> local miss -> shared Redis hit? fill local, return
        -> Redis miss -> PostgreSQL, fill Redis + local, return

This is a design illustration only. The project currently has no Caffeine layer and no local cache fill/invalidation flow.

Step 6 | Collect evidence before adding it

Questions the measurements must answer

  1. Which specific cache name/key family receives enough repeated reads to be “hot”?
  2. How much time does Redis lookup add compared with endpoint and database time?
  3. What is the hit ratio per cache, and what are the p50/p95 lookup durations?
  4. Do bursts of cache misses cause meaningful database load or service latency?
  5. Can the data safely be stale for a small, explicit local TTL?
  6. Can every write or external change invalidate every pod, or is TTL-based divergence acceptable?
  7. How much heap can every pod allocate without increasing GC pressure?

Use existing society.cache.lookups, society.cache.lookup, database-load metrics, Redis memory metrics, and endpoint latency together. The Grafana overview has no dedicated cache panel today, so inspect Prometheus/Actuator metrics and run representative traffic. Do not infer “hot” from the existence of a cache annotation alone.

Step 7 | Understand local-cache risks

Per-pod data can diverge

  • Pod A may serve its local value while Pod B has already refreshed a newer value.
  • Existing flat invalidation is executed by the pod handling the write, then deletes shared Redis keys. It does not broadcast an event to clear another pod's local Caffeine cache.
  • A local TTL bounds staleness but does not guarantee immediate read-after-write visibility across pods.
  • Every pod allocates its own memory; replica count multiplies total cache memory.
  • More memory can increase garbage collection and heap pressure, offsetting latency benefit.
  • Redis outage fallback behavior would need careful design if a local cache is placed in front of it.

These tradeoffs are why the task says local differences must be acceptable before adding Caffeine.

Step 8 | Decide whether a dataset is a fit

Good and poor candidates

Read requiring primary DB correctnessNoLocal cache would violate the need to check current primary state.

Society's small floor list may look like a candidate by shape, but it is already in Redis and is not proven Redis-bound. The flat lists may change and must respect caller scope. Neither is enough reason to add Caffeine without workload results.

Step 9 | If evidence arrives, use a safe rollout plan

Implementation steps for a future change

  1. Record baseline hit rate, Redis lookup latency, endpoint latency, DB load, heap, and GC under repeatable traffic.
  2. Choose one dataset with high reuse and accepted maximum local staleness. Document its data owner and write sources.
  3. Add the Caffeine dependency and a bounded cache configuration: maximum size/weight, expire-after-write, and stats.
  4. Decide whether it fronts Redis or replaces a cache path. Do not accidentally create two independent Spring CacheManager beans without explicit cache routing.
  5. Make cache keys include every result-changing and security-relevant dimension.
  6. Define cross-pod invalidation or an explicit local TTL/staleness contract for every mutation path.
  7. Expose per-cache local hit/miss/eviction metrics and compare with the baseline.
  8. Run multi-pod tests: read, update on pod A, read on pod B, Redis outage, restart, and memory-pressure behavior.
  9. Roll out gradually and remove the layer if latency does not improve or heap/GC/staleness worsens.
Do not merely add spring-boot-starter-cache or a Caffeine dependency and assume it becomes a second level. This project already supplies a custom Redis CacheManager/resolver; cache-manager selection and invalidation need explicit design.
Step 10 | How to operate it if added later

Success criteria

Success means lower end-to-end latency or database/Redis pressure under the same workload, while memory use, GC, and stale reads stay within agreed limits. Monitor per-pod local hit rate, local eviction count, cache size, heap/GC, Redis hit rate, database loads, and endpoint latency. Compare pods independently because local hit rates can differ.

Current repository status: Caffeine metrics/configuration do not exist, so the existing Redis cache metrics cannot be described as Caffeine measurements.

Step 11 | Interview practice

Explain the decision clearly

“Caffeine is a local JVM cache, while our current Society cache is Redis shared by the application pods. I did not add Caffeine because this optional optimization requires measured hot data and an acceptable per-pod staleness contract; the repository has Redis hit/latency instrumentation but no checked-in production measurements showing Redis is the bottleneck. A second cache would need a bounded size, short TTL, security-safe keys, cross-pod invalidation or documented staleness, and new per-pod metrics. I would establish a baseline, test one suitable dataset under multi-pod traffic, and keep the layer only if end-to-end latency improves without unacceptable heap/GC or consistency costs.”

Likely follow-ups

Why would Caffeine be faster?

It serves values from the same JVM's memory without a Redis network round trip.

What is the main difference from Redis?

Redis is shared across pods; Caffeine is local to each process. Local values can differ and disappear on restart.

Why not add it to the floor list now?

The list is already cached in Redis, and there is no evidence Redis latency is the bottleneck. Adding a local copy creates a cross-pod invalidation gap.

How would Pod B learn a value changed on Pod A?

It would need explicit invalidation broadcast or a local TTL/version check. Redis eviction alone does not clear Caffeine memory.

What metrics matter?

Local hit/miss/evictions, cache size, Redis latency/hit ratio, endpoint latency, DB loads, heap, and GC, measured under representative traffic.
