JPA fetch optimization

Step 1 | Learn the basics first

What is JPA doing?

JPA is the Java standard used by this project to map Java entities to relational database tables. Hibernate is the JPA provider that builds and runs SQL for those entities and queries.

  • Entity: Java representation of a database row, such as FlatEntity.
  • Relationship: a link between entities, such as a flat's floor.
  • Lazy: related data is loaded only when code accesses it.
  • Fetch join: load a related entity together with the root entity in the query.
  • DTO projection: select the fields needed for an API response and construct the response object directly.
  • Entity graph: metadata telling JPA which related fields a query should load. This project does not use @EntityGraph in the inspected flat read paths.
Analogy: an entity is a folder for one row. A relationship is a pointer to another folder. Fetch optimization chooses which folders to bring now, so response mapping does not keep returning to the database.
Step 2 | Understand why fetch choices matter

Load enough data for the response, not every possible relationship

The flat response needs a floor number. FlatEntity maps its floor relationship as lazy. If the query returns 20 flats and the mapper then loads each floor separately, it may trigger an N+1 query pattern. If the query loads every relationship whether needed or not, it can transfer unnecessary data and make joins complex.

Too littleRoot rows only, then extra lazy queries
Targeted fetchRoot rows plus needed floor data
Too muchUnneeded relationships and duplicated result rows

The project uses targeted retrieval: it selects FlatResponse directly for certain list routes and fetches the floor association for entity-based directory page/cursor queries.

Step 3 | Find the relationship in this codebase

FlatEntity and FloorEntity

FlatEntity has scalar floorId plus a lazy JPA association named floor. The API's FlatResponse includes floorNumber, so several read paths need the floor's number.

FlatEntity.floorId  -> flats.floor_id
FlatEntity.floor   -> @ManyToOne(fetch = LAZY)
FloorEntity.floorNumber -> value returned in FlatResponse

The problem is not “always make associations eager.” The decision is made per read path according to what that response needs.

These techniques can solve similar loading needs, but they return different shapes and have different trade-offs. Choose the smallest fetch plan that meets the response contract.

Step 5 | Trace the DTO projection path

Flat list query returns response objects directly

The unpaged GET /api/v1/flats calls FlatService.list(), which invokes FlatRepository.findAllResponsesByFlatNumberAsc(). The repository query constructs FlatResponse and joins the floor to read floorNumber.

select new FlatResponse(
  flat.id, flat.flatNumber, flat.floorId,
  floor.floorNumber, flat.status, flat.version)
from FlatEntity flat
join flat.floor floor
ControllerFlatController.list()
ServiceFlatService.list()
RepositoryJPQL DTO projection joins floor
APIAlready-built FlatResponse list

Because the repository returns DTOs rather than FlatEntity objects, the service does not later navigate a lazy floor relation for each flat. The page projection method findAllResponses(Pageable) uses the same DTO approach and has a separate count query.

Step 6 | Trace the entity fetch-join path

Directory page and cursor queries return entities

The portal's GET /api/v1/flats/page is handled by FlatController.page, which calls FlatService.searchPage. That service delegates to DirectoryQueries.page. The Criteria query calls:

root.fetch("floor", JoinType.INNER);

The result is FlatEntity rows with the floor relationship already loaded. FlatService maps each entity to FlatResponse and reads flat.getFloor().getFloorNumber() without one additional query per row.

Request/api/v1/flats/page?page=0&size=20
QueryCriteria query fetches floor
DatabaseContent SQL joins floor
MappingRead floorNumber from fetched entity
ResponsePageResponse with flat DTOs and totals

The cursor query in DirectoryQueries also fetches floor before FlatService maps cursor items. By-floor page requests use the same DirectoryQueries page method with a floor filter.

Count query: the page response needs totalElements/totalPages, so the code runs a count query too. That is one predictable extra query per page response, not one query per flat.

Step 8 | Understand the configuration

Lazy loading and SQL diagnostics

Both member-service and society-service configure spring.jpa.open-in-view: false. This discourages hidden database access during web response serialization after service work completes. In society-service, spring.jpa.show-sql is controlled by the JPA_SHOW_SQL environment variable and defaults to false.

  • Keep entity relationships lazy by default when broad eager loading is unnecessary.
  • For each list endpoint, choose a DTO projection or targeted fetch plan for fields the response actually needs.
  • Enable SQL logging locally when diagnosing generated queries, then turn it back off after investigation.
  • Inspect actual SQL and query counts; annotations and code intent do not alone prove runtime behavior.
Step 9 | Verify the behavior

What a developer should check

  1. Call the flat list, page, cursor, and by-floor routes with multiple records.
  2. Verify each FlatResponse contains the correct floorNumber.
  3. Count SQL statements: list projection should retrieve joined DTO data; page/cursor should have joined content data; page additionally has its count query.
  4. Check there are no repeated floor selects that increase with the number of flat rows.
  5. Review the database plan and response latency for realistic data sizes.

Repository inspection confirms the projection and fetch joins are present. No dedicated query-count assertion was found in the inspected source tests, so runtime query-count measurement is not claimed here.

Step 10 | Learn the limits

What this optimization does not mean

  • It does not make every relationship eager. Only floor is fetched where the flat response needs it.
  • Fetch joining multiple to-many collections can multiply result rows and complicate pagination. This use is a to-one floor relationship.
  • DTO projections are useful for response reads but do not return managed entities for updates.
  • A fetch join reduces round trips; it does not guarantee the database query has a good execution plan.
  • Entity graphs are a valid JPA tool but are not used in the inspected paths.
  • Future response fields that navigate lazy relationships should trigger a fresh query-count review.
Step 11 | Interview practice

Explain the design clearly

"I inspected how flat reads need the floor number. FlatEntity maps floor as a lazy many-to-one. The unpaged list uses a JPQL DTO projection that joins floor and returns FlatResponse directly. The page and cursor flows return entities, so DirectoryQueries uses a targeted Criteria fetch for floor before FlatService maps each row. The by-floor list loads the floor once and reuses its number. This avoids per-flat lazy loads without making the entire entity graph eager. Open Session in View is disabled, so required data must be fetched within the query/service work. I would still verify SQL counts and plans at runtime; I found no dedicated query-count test."

Likely follow-up questions

Why use a projection on one route and fetch join on another?

The unpaged list can directly return a response DTO. The paged/cursor query also applies dynamic filters, access predicates, sorting, and cursor logic, so it returns entities and fetches only the needed floor relationship.

Why not mark floor EAGER?

Eager loading affects every use of FlatEntity, including code that may not need the floor. A targeted fetch plan keeps loading specific to read paths that need it.

Is one count query an N+1?

No. It is a fixed query needed for page totals. N+1 grows with each returned entity.

What is an entity graph?

A JPA fetch-plan declaration that names relationships to load for a query. This repository's inspected flat paths use projections and Criteria fetch joins instead.

How would you prove the optimization?

Use SQL/query-count instrumentation on realistic multi-row data, check the related data is joined, and inspect the actual database plan.
