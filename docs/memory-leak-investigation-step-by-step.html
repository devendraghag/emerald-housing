Memory leak investigation, from zero

Learn what a memory leak looks like, what memory signals already exist in this project, and how to investigate safely using repeatable load and Java Flight Recorder. 1. Learn the concepts first

A memory leak in a managed-language application is usually an object-retention problem: objects remain reachable after the application no longer needs them, so garbage collection cannot reclaim them. A heap that grows during warm-up is not automatically a leak. A leak hypothesis is stronger when the post-GC live set keeps increasing across comparable workload cycles.

Heap is only one part of process memory. Container RSS also includes thread stacks, direct buffers, metaspace, JIT code cache, JVM structures, native libraries, and other native allocations. A rising container working set with stable heap points toward a different investigation than a rising old-generation live set.

Healthy caches and bounded per-session state can grow to a working level and then stabilize. The key question is whether retained state has a bound, a useful lifetime, and an owner that removes it.

Useful distinction: memory leak detection is not the same as an OOM alarm. An OOM or pod restart is a late symptom. Compare time series and retained heap behavior before the failure.

4. Recognize patterns before calling something a leak

Observed patternPossible explanationNext check
Heap rises during warm-up, then reaches a plateau.Expected cache/JIT/class loading or normal working-set growth.Continue a steady workload long enough to see repeated GC cycles; compare plateau across equivalent runs.
Post-GC heap baseline rises across repeated equal workload windows.Potential retained-object growth.Compare object types and retainers across heap snapshots; correlate with caches, sessions, queues, and request mix.
RSS rises while heap metrics stay relatively flat.Native/direct memory, thread stack growth, mapped files, or process-level behavior.Inspect thread count, container memory, direct buffers, native libraries, and OS/process metrics.
Memory jumps with traffic rate and falls after load stops or cache expiry.Load-proportional working set, buffered work, or cache growth.Check queue/backlog depth, cache size/TTL, and whether usage returns to baseline after a controlled drain.
One pod grows but peers do not.Pod-specific traffic skew, local cache/cardinality, or a local resource leak.Compare per-pod request counts, cache state, restarts, heap metrics, and JFR recordings.

5. Investigate step by step

Step 1 — establish a baseline

Record the exact image tag, Java version, pod name, memory request/limit, JVM flags, replica count, current traffic mix, and service health. Save RSS/working set, heap used/committed, GC activity, CPU, restarts, and request rate before the test.

Step 2 — define repeatable load

Use a non-production workload with the same endpoints, payload sizes, data, concurrency, and duration across runs. Include a warm-up period, steady state, and a quiet/drain period. Avoid changing replicas or cache settings during the comparison.

Step 3 — inspect trends

Plot memory by pod over time. Separate heap used from container memory; compare heap after natural GC cycles, not just the highest instantaneous heap sample. Do not trigger forced GC on a production service to make a chart easier to read.

Step 4 — capture JFR during the same workload

Use scripts/profiling/record-jfr.ps1 as described in the JFR guide. Run load before the recording rollout and keep it active through the recording window. Check the JFR summary to see which allocation and GC events were recorded.

Step 5 — narrow the owner

Look for allocation types, repeated allocation sites, long-lived collections, maps keyed by user/request IDs, unbounded queues, listener registrations, ThreadLocals, and per-conversation state. Distinguish expected bounded caches from retained objects that lack an eviction or lifecycle rule.

Step 6 — use a heap dump only when justified

A heap dump can contain user and session data and can be close to the live heap size. Prefer an isolated non-production reproduction. Plan disk, storage, access control, and transfer before enabling it.

Step 7 — validate a fix

Change one suspected owner/lifecycle, repeat the same load, and compare post-GC live-set trend, RSS, GC behavior, latency, throughput, errors, and restarts. A lower heap at one instant is not sufficient evidence.

6. Use JFR in this repository

The existing capture script adds a bounded -XX:StartFlightRecording=settings=profile startup option to one selected Kubernetes Deployment, writes the file under the existing writable /tmp, copies it to the workstation, then removes the temporary override. It supports Gateway, Member, Society, and AI Service deployments. The profile includes JVM start-up as well as load; account for that when interpreting the time range.

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\profiling\record-jfr.ps1 `
  -Deployment member-service -DurationSeconds 300 -Context docker-desktop

jfr summary .\artifacts\jfr\<pod>-emerald-member-service.jfr
jfr print --events jdk.ObjectAllocationSample,jdk.GarbageCollection,jdk.GCHeapSummary `
  .\artifacts\jfr\<pod>-emerald-member-service.jfr

Allocation samples can suggest where objects are created. They do not prove an object is retained; short-lived allocations can be high without a leak. For retention, compare heap dumps or live-object histograms captured at equivalent phases, and use a heap-analysis tool to inspect dominators and reference paths.

Operational effect: the script rolls the target Deployment when enabling JFR and again when restoring defaults. Use a safe environment and confirm the recording file is copied before the pod is replaced.

7. Heap dumps: useful, expensive, and not enabled by default

No -XX:+HeapDumpOnOutOfMemoryError, HeapDumpPath, jcmd capture helper, or heap-dump storage workflow was found in the project configuration. The app images are JRE-based and run with read-only root filesystems; only the mounted /tmp is writable. The ephemeral volume has no explicit storage limit in these Deployments.

Do not add automatic heap dumping casually: a large dump can exhaust ephemeral storage, contain sensitive member/session data, and increase node pressure during an OOM incident. If the organization decides to enable it, design the destination, storage cap, retention, access, encryption, and transfer workflow first, then validate in staging.

For a controlled heap dump, compare snapshots from equivalent workload phases with a supported JDK diagnostic tool or profiler in a suitable environment. Look at retained size and reference paths, not only object counts. This repository does not ship a heap-dump analyzer or an in-container JDK diagnostic tool.

9. Operational response checklist

  1. Confirm the affected pod/service, time range, image, and whether memory is heap, RSS, Redis, or another resource.
  2. Check restarts and Kubernetes OOM events alongside the memory trend; a restart resets process-local measurements.
  3. Compare equivalent pods and load. Check whether traffic, cache cardinality, or backlog changed.
  4. Capture JFR and metrics under controlled load. Store artifacts securely and avoid committing dumps/recordings.
  5. If a dump is needed, use a preplanned bounded, access-controlled path and a staging reproduction when possible.
  6. Form one retention hypothesis, fix its lifecycle, and repeat the same workload to prove the trend stabilizes.
  7. Document evidence, rollout impact, data handling, and rollback. A memory leak should not be declared from a single sample or one high-water mark.

10. Gaps and limitations in this repository

  • No automatic leak detector, threshold alert, or leak incident runbook existed before this guide.
  • Prometheus scrapes pods with the configured annotations only when the optional observability overlay is running; AI lacks these annotations.
  • No dedicated JVM memory/GC Grafana dashboard or checked-in leak alert rule was found.
  • The JFR workflow creates profile recordings but does not create heap dumps or analyze retained-object graphs.
  • JFR settings and sampling can miss rare allocation/retention behavior; longer controlled soak tests may be required.
  • Heap dumps are not enabled by default, and the repository has no secure dump storage/retention process.
  • Local JFR smoke verification is not evidence that a live service has a leak or is leak-free.

12. Interview preparation

Developer-level explanation

60-second answer: “A Java memory leak usually means objects remain reachable after their useful lifetime. I diagnose it by comparing equivalent workload periods and looking for a rising post-GC live set, while separating Java heap from container RSS and native memory. In this project, Java 21 containers size heap at 75% of the cgroup-aware memory, Actuator exposes metrics, and an opt-in JFR script can capture allocation and GC samples during controlled load. JFR allocation samples are not a retained-object graph, and the project does not have automatic leak alerts or heap-dump analysis enabled. If trends justify it, I would capture secure snapshots in staging, inspect dominator/reference paths, fix the retaining owner, and repeat the same load to verify memory stabilizes.”

Likely follow-up questions

How do you distinguish a leak from normal cache growth?

Check whether the cache has size/TTL bounds and whether memory reaches a stable plateau after warm-up and equivalent request cycles. Compare retained objects and cache cardinality over time rather than a single heap measurement.

Can a GC log or JFR profile prove a leak?

It can provide evidence of rising post-GC live data or allocation behavior, but retained-object analysis usually needs comparable heap snapshots and reference paths.

Why can container RSS rise while Java heap is flat?

Thread stacks, direct/native buffers, metaspace, code cache, native libraries, or mapped memory can grow outside the Java heap.

Why not always enable HeapDumpOnOutOfMemoryError?

The dump can be large, sensitive, and consume the remaining ephemeral storage during an already critical event. Define destination, capacity, security, and retention first.

What does the repository's JFR script capture?

A bounded startup recording with the JDK's profile settings on a selected deployment, then copies per-pod files from writable /tmp. It restarts pods and does not itself generate load or analyze retained objects.

How do you prove the fix worked?

Repeat the same traffic, data, duration, image/resource conditions, and compare post-GC live-set trend, RSS, GC behavior, latency, throughput, errors, and restarts. The memory trend should stabilize without moving pressure elsewhere.
