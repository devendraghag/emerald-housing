Object creation optimization, from zero

Learn what allocation pressure is, follow how request data becomes response objects in this project, and use the existing JFR workflow to decide whether object creation is actually a bottleneck. The guiding rule is the feature itself: optimize only after a representative profile identifies pressure.

1. Learn the concepts first

Allocation is creating objects such as DTOs, lists, strings, map entries, framework wrappers, and request/response buffers. The JVM garbage collector is designed to reclaim short-lived objects, so “the code creates many objects” is not automatically a performance problem.

Allocation pressure matters when measured object creation causes a meaningful cost: high allocation rate, more GC CPU or pauses, excessive memory bandwidth, or heap churn that harms latency/throughput. The relevant question is usually bytes allocated per request or operation and which allocation sites account for that cost.

Retained memory is different. A leak keeps objects reachable; allocation profiling shows where objects are created, not necessarily why they remain live. For retention questions, use the separate memory-leak investigation guide.

Do not optimize by style alone. Replacing records, streams, immutable collections, or straightforward mapping with mutable reuse can reduce clarity and introduce aliasing/thread-safety bugs without reducing measured cost.

For a paged Member response, MemberService.getPage validates the requested page through PageRequests, queries a Spring Data page, maps each item with MemberService::toResponse, and returns PageResponse. The record DTO and response list are allocations, but paging bounds how many items this request maps.

Society's FlatService.page similarly obtains a bounded page and maps query results to FlatResponse. A cache hit on selected paths can bypass database result mapping, while a cache miss still constructs the response objects before storing/returning them.

5. Profile before changing code

The existing script captures JFR with settings=profile for a chosen Kubernetes deployment and saves a bounded recording. It restarts that deployment when enabling and restoring JVM options; use a safe environment. Follow the JFR step-by-step guide.

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\profiling\record-jfr.ps1 `
  -Deployment member-service -DurationSeconds 300 -Context docker-desktop

jfr summary .\artifacts\jfr\<pod>-emerald-member-service.jfr
jfr print --events jdk.ObjectAllocationSample .\artifacts\jfr\<pod>-emerald-member-service.jfr

Run a representative endpoint mix at the expected concurrency. Record build/image, pod resources, dataset, warm-up, throughput, p50/p95/p99 latency, CPU, GC activity, and the load window. Compare allocation samples for recurring types/call sites; sampled events are not a complete census of every allocation or a retained-object graph.

Interpretation: high sampled allocation does not alone prove a bottleneck. Look at allocation rate per useful operation, GC cost, heap/latency behavior, and whether a code path runs frequently enough to matter.

6. Step-by-step investigation

Step 1 — choose one operation

Pick a high-volume request or job with a measurable latency/throughput objective. Avoid profiling a mixture where the expensive path cannot be identified.

Step 2 — capture the baseline

Use the same build, data, pod limits, cache state, concurrency, and workload for repeatable runs. Save JFR and load-generator output together with the run metadata.

Step 3 — identify the allocation source

Inspect JFR allocation samples and the call path. Decide whether allocation is from application DTO mapping, JSON/HTTP, ORM hydration, framework internals, or a dependency. Avoid optimizing code that contributes little to total cost.

Step 4 — state a concrete hypothesis

Example: “This unpaged response builds thousands of DTOs and lists on every request; a bounded projection/page will reduce bytes allocated per request.” The hypothesis should specify expected behavior and correctness constraints.

Step 5 — make one focused change

Possible changes include bounding an endpoint result, avoiding duplicate intermediate collections, selecting only required columns, caching stable reference data, or reducing repeated serialization/conversion. These are candidate approaches, not claims that this repository currently needs them.

Step 6 — re-run and compare

Repeat the identical workload and compare allocated bytes/operation if available, allocation samples, GC CPU/pause, throughput, p99 latency, errors, and correctness. Keep the change only if it improves the measured goal without harming readability or behavior.

8. Measure and verify the result

For a candidate change, compare the baseline and candidate under the same representative workload. Capture at minimum:

  • Requests/operations per second and p50/p95/p99 latency;
  • allocation samples and, where available, allocated bytes per operation;
  • GC frequency, pause time, and GC CPU;
  • heap/RSS and container OOM/restarts;
  • functional correctness, response shape, ordering, authorization, and error behavior.

Existing functional tests protect API behavior but do not establish allocation improvement. The repository contains no JMH benchmark or checked-in before/after allocation profile for this feature.

9. Gaps and limitations

  • No representative JFR allocation profile or allocation benchmark is checked in.
  • No explicit object pool, reusable DTO layer, or allocation-specific memory setting is configured.
  • JFR allocation samples are sampled evidence; they do not report every object or explain why an object remains reachable.
  • Current pagination and caches help bound/reuse selected data paths but do not optimize every allocation site.
  • Record DTO creation and JSON serialization are normal API costs; reducing them can complicate API correctness.
  • Optimizations measured on one endpoint, JVM, data shape, and cache state may not transfer to other paths.

10. Interview preparation

Developer-level explanation

60-second answer: “Object creation optimization should follow allocation evidence. Emerald Housing has an opt-in Java Flight Recorder workflow using the JDK profile settings, but there is no representative allocation report or allocation benchmark checked in, so no allocation-driven code rewrite is justified. The API code maps query results to immutable record DTOs; Member and Society bound paged responses to 100, and cursor paths bound result limits. Society also caches selected reference/flat responses, which avoids repeated database mapping on cache hits but has its own costs. I would profile one representative operation, identify the dominant allocation call site, make one focused change such as bounding output or removing a redundant intermediate collection, then compare allocation per operation, GC, throughput, p99 latency, and correctness under the same load. I would not add object pools or mutable reuse just because objects are being created.”

Likely follow-up questions

Are many short-lived objects always bad?

No. Modern JVMs collect many short-lived objects efficiently. They matter when measured allocation rate creates material GC/CPU/latency cost.

Does JFR allocation sampling count every object?

No. It samples allocation events according to the recording settings. It helps locate patterns but is not a complete allocation census.

Why not pool DTOs?

DTOs are request-specific and often immutable; pooling can create shared mutable state, synchronization, retained memory, and lifecycle complexity. Use only if a profile and benchmark show a clear benefit.

Does pagination optimize allocation?

It bounds the number of records and response DTOs produced for the page request. That limits per-request work, but does not prove each individual allocation is cheaper.

How is allocation pressure different from a memory leak?

Allocation pressure concerns how quickly objects are created and collected. A leak concerns objects that remain reachable and retained beyond their useful lifetime.

What evidence would justify a code change?

A repeatable profile identifies a costly allocation site under representative load, and a controlled before/after run improves allocation per useful operation or a related service objective without correctness or memory regressions.
