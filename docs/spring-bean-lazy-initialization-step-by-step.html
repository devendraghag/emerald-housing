1. Learn the bean lifecycle terms first

A Spring bean is an object managed by the application context. With normal singleton initialization, Spring creates and wires singleton beans while the context starts. A bean marked lazy is created when something first requests it instead of during normal startup.

Global lazy initialization defers most eligible singleton beans. Per-bean lazy initialization marks selected beans with @Lazy. Lazy beans can still be created during startup if an eager bean depends on them; laziness delays creation only while the dependency graph allows it.

This is different from lazy data access. Delaying a physical database connection or lazily loading a JPA relationship does not mean Spring delayed creation of the repository, service, or other singleton bean.

Two numbers matter: time until the Pod becomes Ready and latency/memory on the first request that triggers a lazy bean. A shorter startup can simply move work from startup to the first user.

Spring's eager singleton dependency graph can still pull a lazy bean into startup when a non-lazy bean needs it. 5. What a controlled experiment would look like

No lazy setting has been added. If a startup benchmark shows the context is a bottleneck, a test-only or staging experiment could compare normal initialization with Spring Boot's global property:

# Hypothetical experiment only; not currently set in this repository
SPRING_MAIN_LAZY_INITIALIZATION=true

Or mark only a proven optional bean with @Lazy. Avoid enabling both global and per-bean changes in the same experiment; the smaller change is easier to attribute. Keep the normal configuration as the control run.

Before applying the experiment, identify whether the expensive startup time comes from Spring bean construction, database migrations, Society warm-up, or AI embeddings. A bean-level setting will not automatically optimize non-bean startup tasks.

6. Measure startup and memory impact

  1. Choose the exact interval: container process start to Pod Ready, or JVM start to Spring's final Started log. Record both when possible.
  2. Repeat cold starts with the same image, node, resource limits, dependency availability, database schema state, Redis state, and configuration.
  3. Measure startup duration and RSS/heap immediately after readiness, after the same idle interval, and after a representative first request.
  4. Run first requests for important routes and record latency, errors, and whether they trigger provider connections, cache loading, migrations, or index building.
  5. Exercise rarely used routes too. Deferred failures can remain hidden if only health endpoints are called.
  6. Compare eager and lazy runs over multiple repetitions; report median and tail startup/first-use behavior, not one run.

The repository's JFR capture workflow can capture JVM events from startup, but it restarts the selected Deployment and its profile recording is not itself a Spring bean-creation timeline. Correlate JFR with application logs and readiness transitions.

Memory must be compared at equivalent points. A lazy context may appear smaller before the first request simply because some beans have not been created yet; measure after the same route mix and warm-up duration too.

8. Operational walkthrough

  1. Check rollout events and logs to identify whether time is spent in JVM/Spring startup, Flyway, cache warm-up, AI embedding calls, or external dependency waits.
  2. Record the current eager baseline and the first-request latency for the service's important routes.
  3. Try one targeted lazy setting in a non-production experiment only when an unused/expensive bean is identified.
  4. Verify startup probe, readiness checks, database migration, cache warm-up semantics, and AI index state remain correct.
  5. Exercise all routes, including rarely used ones, and monitor first-call errors, latency, resource peaks, and downstream connection spikes.
  6. Compare after equal workload/warm-up intervals. Revert if cost was merely moved to request handling or if failures become harder to detect.
Current behavior to operate: Member and Society readiness requires dependencies listed in their health groups; Society warm-up can be disabled with SOCIETY_CACHE_WARMUP_ENABLED=false, but that changes first-request cache behavior and is not a bean-lazy switch. AI readiness checks Spring readiness state only and does not prove the FAQ vector store is populated.

9. Gaps and limitations

  • No global spring.main.lazy-initialization setting or production @Lazy annotation was found.
  • No eager-versus-lazy startup or memory benchmark was found.
  • Startup work includes Flyway, a Society ApplicationRunner, and AI indexing; these have different lifecycle semantics.
  • The Society and Member JDBC proxy and JPA lazy associations are not Spring bean lazy initialization.
  • Lazy initialization can move wiring/provider errors to the first route use and shift latency to users.
  • Startup probes define failure tolerance, not the actual duration or a startup objective.
  • The JFR profile capture workflow does not by itself explain Spring bean construction phases.

10. Verification and implementation status

Repository inspection searched all service application configuration and production source for global lazy initialization, @Lazy, eager startup runners, Flyway, and lazy JDBC/JPA usage. It confirmed that Spring bean lazy initialization is absent, while separate lazy data-access behaviors exist.

This task adds the feature-specific learning and measurement guide only. No application setting or bean annotation changed because the feature is optional and no startup/memory comparison demonstrates a need. Verification consisted of checking guide file/section links, rendering the Kubernetes base with kubectl kustomize, and running git diff --check. No live startup benchmark was run.

11. Interview preparation

Developer-level explanation

60-second answer: “Spring bean lazy initialization defers creation of eligible singleton beans until first use. Emerald Housing does not enable spring.main.lazy-initialization and does not mark production beans with @Lazy; normal eager creation remains. It does have a LazyConnectionDataSourceProxy and JPA FetchType.LAZY, but those defer database connection/relationship loading rather than bean construction. Startup also includes Flyway migrations, Society's ApplicationRunner cache warm-up, and AI FAQ vector indexing, so a global lazy flag may not remove those costs. Because no startup or memory benchmark shows a problem, I would first capture process-to-Ready time, memory after equal warm-up, and first-request latency. Then I would test one targeted bean or a staging-only global setting and keep it only if it improves the operational objective without shifting failures or latency to first use.”

Likely follow-up questions

What does Spring do by default for singleton beans?

It normally creates and wires singleton beans during application-context startup, unless laziness or another lifecycle choice defers them.

Does @Lazy always keep a bean out of startup?

No. An eager bean that depends on it can cause it to be created during startup; actual behavior follows the dependency graph.

Is LazyConnectionDataSourceProxy the same feature?

No. It delays obtaining a physical JDBC connection until database work is needed. The Spring datasource bean itself still exists in the context.

Why not turn on global laziness to improve startup?

It may move initialization cost and errors to first use, and migrations/runners or eager dependencies can still perform startup work. Measure both startup and first-request/memory behavior first.

How would you test a lazy experiment?

Compare repeated cold starts, readiness time, startup memory, first-request latency/errors for all routes, and memory after equal warm-up under the same dependencies and workload.

Does an empty AI FAQ index stop the AI Pod from becoming Ready?

Current readiness checks only Spring readiness state. The indexing bean catches runtime indexing errors and logs a warning, so the Pod can be Ready while FAQ retrieval is unavailable.
