Step 1 - Start here

What you need to know first

An app saves and reads information in database tables. SQL is the language used to ask the database for that information. Query optimization is the practice of making those requests focused and efficient.

TableA collection of records, like a spreadsheet tab.
RowOne saved item, such as one member.
ColumnOne field, such as status or created time.
QueryA database request, such as “find active members.”
ORMTool that maps Java objects to database rows; this project uses JPA with Hibernate.
Execution planPostgreSQL's chosen steps for answering a SQL query.
Learning path: learn the words, trace one request, see the project decisions in migration/code order, then learn how to check the database plan. The project already contains query optimizations; this guide is for understanding them.
1 · Basic idea

What does SQL optimization mean?

SQL optimization means asking the database for only the data the application needs, in a form the database can retrieve efficiently. The database still chooses the execution route.

SQL queryA request to read or change rows in database tables.
JPA / Spring DataJava APIs that describe or build database operations.
HibernateThe ORM used by JPA to turn entity/repository operations into SQL and map rows back to Java objects.
Execution planThe steps PostgreSQL chooses to run a SQL query.
ProjectionReturn only selected fields instead of loading a full entity.
PaginationReturn a bounded slice of results rather than every row.
N+1 queriesOne query loads a list, then another query runs for each list item to load related data.
Fetch joinLoad a related object in the same query so the application avoids extra per-row queries.

SQL optimization is already present

Member and Society services already use focused projections, bounded pagination, keyset/cursor pagination, deterministic ordering, separate count queries, and fetch joins for required related data.

Important distinction: these are implemented query-design choices. The repository does not contain saved PostgreSQL EXPLAIN ANALYZE output or automatic query-plan regression checks. The plan commands in this guide show how a developer should review the actual database behavior. No speedup is claimed without a measured plan and workload.
Step 3 - Follow one request

Request-to-SQL flow

HTTP endpoint
Receives filter, page, or cursor parameters.
Service
Checks access and chooses the read operation.
Repository / Criteria API
Describes the query and its bounds/order.
Hibernate
Generates SQL and binds parameters.
PostgreSQL
Chooses a plan and reads the needed rows.
Response mapping
Java returns DTOs and page metadata.

The Java query shape influences PostgreSQL's options; it does not force a specific plan. Indexes from Flyway migrations are available to the planner, which decides whether to use them.

Do not confuse these layers: an efficient-looking repository method does not prove that the resulting SQL is fast. Inspect the generated SQL and the PostgreSQL plan against representative data.

Step 6 - Walk through a real query

Member directory cursor request

The Member Controller exposes a cursor endpoint. The service asks DirectoryQueries.cursor for a bounded batch. That method builds the query with filters, a stable order, and an optional continuation condition.

// Simplified logical SQL shape; Hibernate-generated SQL can differ.
SELECT m.*
FROM members m
WHERE (m.created_at > :lastCreatedAt
       OR (m.created_at = :lastCreatedAt AND m.id > :lastId))
ORDER BY m.created_at ASC, m.id ASC
LIMIT :limitPlusOne;
Build filter
Apply permitted search/status constraints.
Continue from cursor
Skip no prior rows; ask for values after the saved timestamp and ID.
Order consistently
Sort by timestamp then unique ID.
Bound the read
Ask for limit plus one to determine whether another page exists.
Return next cursor
Encode the last returned row as the next bookmark.

Member V5 defines ix_members_cursor(created_at, id) and ix_members_status_cursor(status, created_at, id), which align with the cursor ordering and status-filtered variant. That alignment makes an index path possible; only an actual plan can show the chosen path.

Why the extra row? If the client asks for 20 results, the query can ask for 21. If row 21 exists, the service knows there is another page, drops that extra row from this response, and creates a next cursor from row 20.
Step 7 - Check the execution plan

How to check a query in PostgreSQL

  1. Choose a query that matters: high latency, high call volume, large table, or known expensive endpoint.
  2. Capture the actual SQL and bound values safely. Hibernate's show-sql is off by default in both services (JPA_SHOW_SQL=false); turn SQL logging on only in a safe local/staging environment, and avoid exposing private values in logs.
  3. Run the same SELECT with representative parameters and realistic data in a non-production database.
  4. Inspect estimated rows versus actual rows, scan type, sort nodes, loops, rows removed by filters, shared buffer hits/reads, and execution time.
  5. Change one thing at a time (query shape, projection, index, or pagination), then compare the same workload again.
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, status
FROM members
WHERE status = 'ACTIVE'
ORDER BY created_at ASC, id ASC
LIMIT 21;

This is a representative shape related to the member cursor path and its status/cursor index. The exact Criteria-generated query may include additional predicates, and this guide has not run the statement against a live database.

Index ScanPostgreSQL followed an index to find rows. Check how many table rows it still fetched.
Seq ScanPostgreSQL checked the table rows in sequence. This can be best for small tables or when many rows match.
SortRows had to be put into requested order. An appropriate index may sometimes provide that order.
BuffersShows database page access activity. Fewer physical reads can matter, but buffer counts need workload context.
Actual vs estimated rowsA large mismatch may lead the planner to choose a poor route; statistics or parameter distributions may need investigation.
Execution timeMeasured for this run, data, cache state, and machine. Repeat runs and load tests before drawing conclusions.
Safety: ANALYZE executes the statement. Use it with SELECTs in a non-production environment. Do not casually run EXPLAIN ANALYZE on INSERT/UPDATE/DELETE statements.

Environment limitation: a live PostgreSQL plan could not be captured in this workspace because the Docker daemon is unavailable and no local PostgreSQL client/database is installed. No measured plan or query-speed result is claimed.

Step 8 - Understand the trade-offs

Trade-offs and remaining questions

  • A cursor reduces deep-offset skipping but is not automatically faster for every small dataset.
  • A fetch join avoids repeated lazy reads, but joins can enlarge a result. Fetch only the relationships the response needs.
  • A page total uses a count query, which may be costly at scale. If product requirements allow, consider whether an exact total is essential.
  • Search uses contains-style patterns such as LIKE '%term%'. Ordinary B-tree indexes usually cannot accelerate a leading-wildcard search; check plans and consider specialized search/index options if measured as a bottleneck.
  • A database index helps only if the planner estimates it is cheaper than other paths. More indexes also increase storage and write work.
  • Correctness comes first: do not remove filters, authorization predicates, or ordering guarantees just to make SQL shorter.
Step 9 - Practice explaining it

Explain the approach clearly

Interview answer: “We optimize SQL by starting from real access patterns. In our Spring Boot services, directory queries are bounded, use stable sort keys, and offer cursor pagination for deep traversal. Flat list responses use a DTO projection, and flat directory queries fetch the floor relationship they need to avoid N+1 lazy loads. We maintain indexes through Flyway. To prove a change helps, I capture the generated SQL, inspect PostgreSQL with EXPLAIN ANALYZE and BUFFERS on representative data, then compare plans and latency before and after. I would not claim a speedup from the index definition alone.”

Follow-up questions

Why use a cursor instead of a large page offset?

Large offsets can require the database to walk past many earlier matches. Cursor pagination continues after the last timestamp/ID pair and asks for only a bounded batch.

How does the project avoid N+1 for flat-floor responses?

The Society directory query fetches the floor relationship with the flats in the main query. The response mapper can read the floor number without triggering an extra query per flat.

Does an index guarantee PostgreSQL will use it?

No. The planner estimates cost from statistics and data shape. A sequential scan can be cheaper when few rows exist or many rows match.

Why does a paged query also run a count?

The API returns page metadata including the total count. The implementation uses a separate count-only query; exact totals trade an additional query for that metadata.

What do you need before saying a query is optimized?

Generated SQL, representative data and parameters, an execution plan, and repeatable before/after measurements under a relevant workload.
