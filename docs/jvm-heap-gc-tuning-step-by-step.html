1. Learn the memory model first

The Java heap holds most Java objects. The garbage collector reclaims heap objects that the application can no longer reach. GC can pause application threads or use CPU concurrently; the exact behavior depends on the selected collector, heap size, object lifetime, and workload.

Process memory is larger than the heap. A container's resident memory also includes class metadata, JIT code cache, thread stacks, direct/native buffers, JNI/native libraries, JVM structures, and other process allocations. Therefore, a heap maximum must stay below the container's memory limit with enough room for non-heap usage.

A container memory limit is a hard cgroup boundary. If total process memory exceeds it, the container can be OOM-killed even if the Java heap has not reached its maximum. Kubernetes memory requests help scheduling; the limits set the per-container ceiling.

Beginner rule: don't increase -Xmx just because an app has high memory use. First distinguish live heap, allocation churn, GC behavior, native/direct memory, and container RSS under representative load.

5. Read the evidence before deciding what to tune

Signal patternQuestions to ask before changing a flag
Heap stays near its maximum and old-generation occupancy remains high after GCIs the live set legitimately large, is there a retention leak, or is the workload/data volume different from expected? A larger heap may defer pressure but consumes more of the container limit.
Frequent young collections with high allocation rateWhich allocation sites dominate in JFR? Can repeated temporary object creation or oversized payload copying be reduced before changing the collector?
Long GC pauses align with latency spikesWhich GC events and pause durations occurred, how often, and under what allocation/heap conditions? Does the application actually miss a latency objective?
Container RSS approaches limit while heap is moderateInspect thread count/stacks, direct buffers, native libraries, metaspace/code cache, and sidecar accounting. Increasing heap percentage could make OOM risk worse.
High CPU in GC or allocation samplingConfirm the recording overlaps steady-state load and identify whether the bottleneck is allocation, live-set traversal, application CPU, or another dependency.
Heap appears mostly idle but service is slowLook at blocking/network/database waits, connection-pool saturation, CPU throttling, and downstream latency. GC tuning may not address the bottleneck.

Spring Boot's metrics endpoint exposes Micrometer metrics, and the annotated app pods are discoverable by the optional Prometheus overlay. The repository does not define a JVM-focused Grafana dashboard; operators may query available jvm.memory.*, jvm.gc.*, and process metrics directly if the relevant binders are present in the runtime scrape.

6. Make one safe, reviewable change

  1. Save the baseline: service/image tag, JVM version/options, resource request/limit, workload profile, GC/heap metrics, JFR artifact, latency, throughput, errors, and pod restarts.
  2. Write a specific hypothesis, for example: “The measured steady live set plus allocation headroom is exceeding the 75% heap ceiling, while native memory remains safely below the container limit.”
  3. Change one option at a time. If changing heap sizing, keep the maximum heap below the container limit and account for native memory. The current value is set in each service Dockerfile; a Kubernetes JAVA_TOOL_OPTIONS override can supersede the image value for a controlled experiment.
  4. Only select an explicit collector or pause goal if the profile and objective support it. No GC collector change is prescribed by this guide.
  5. Rebuild/redeploy or apply the controlled environment override in a non-production environment, then confirm the effective JVM flags and container limits.
  6. Repeat the same representative load. Compare p50/p95/p99 latency, throughput, error rate, heap after GC, allocation rate, GC count/pause duration, RSS, CPU, and OOM/restart events.
  7. Keep the change only if the measured outcome improves the relevant objective without moving risk to native memory, latency, or another service. Record rollback instructions.
Current project baseline: all four app Dockerfiles use the same 75% container-aware heap ratio. Kubernetes can override JAVA_TOOL_OPTIONS per workload, and the JFR script uses a temporary override for capture. The normal tuning baseline remains in each Dockerfile.

7. Operate and compare a profile

  1. Choose one service and a non-production cluster. Read its Deployment memory limit and image tag.
  2. Prepare representative traffic and an explicit latency/error objective. Start the load before running the JFR script as its guide instructs.
  3. Capture the same duration and workload shape for each baseline/candidate run. Remember that the script restarts the selected Deployment when enabling and removing JFR.
  4. Inspect the resulting file with JDK 21 jfr summary, jfr print, or Java Mission Control; correlate events with metrics and load-generator output.
  5. Make one change and repeat. Do not compare a warm-up run with a steady-state run or different load profiles as if they were equivalent.
jfr summary .\artifacts\jfr\<pod>-emerald-member-service.jfr
jfr print --events jdk.GarbageCollection,jdk.GCHeapSummary,jdk.ExecutionSample .\artifacts\jfr\<pod>-emerald-member-service.jfr

JFR event names and availability depend on the JDK recording configuration. Check the recording summary before building queries around an event that was not recorded.

8. Current gaps and limits

  • No profile-derived change to heap size or GC policy is present in this repository.
  • No JFR recording from representative service load is checked in; the recent local JFR smoke run only verified that Java 21 could start and summarize a recording.
  • The 75% value is a configured baseline, not a production-validated optimum. The approximate remaining 25% may or may not fit actual native/process use.
  • No explicit collector, GC pause target, or GC log configuration is set in the app images.
  • No JVM/GC-specific Grafana dashboard was found. Prometheus collection depends on the optional overlay and pod annotations; AI Service currently lacks the scrape annotations used by the other app workloads.
  • JFR sampling and a short test do not replace a representative soak test, heap-retention analysis, or peak-memory evaluation.
  • Changing JVM options restarts the service. A change that helps one process can move memory pressure to Kubernetes or dependencies.

10. Interview preparation

Developer-level, interview-ready explanation

60-second answer: “Our Java 21 app images use -XX:+UseContainerSupport and -XX:MaxRAMPercentage=75.0, so the maximum heap is derived from the container memory limit instead of a fixed -Xmx. The Kubernetes limits are 512 Mi for Gateway, 640 Mi for Member and Society, and 1 Gi for AI, giving approximate 75% heap ceilings of 384, 480, 480, and 768 Mi. The remaining memory must cover native JVM and process use. We have an opt-in JFR capture workflow, but there are no representative deployment recordings or measured GC tuning results checked in. Therefore I would not claim that 75% is optimal or select a collector by guess. I would capture JFR and metrics under repeatable load, identify heap versus native pressure, change one option, and compare latency, throughput, GC, RSS, and restarts under the same workload.”

Likely follow-up questions

Why not set a fixed -Xmx?

A fixed heap can be appropriate when measured and deployed with known container limits, but a hard-coded maximum can diverge from per-service limits. This project uses a percentage so the JVM derives the ceiling from container memory.

Does 75% mean the JVM always uses 75% of memory?

No. It configures a maximum heap sizing ratio. The live heap can be smaller, and total process memory includes non-heap/native usage.

What collector does the project use?

The repository does not explicitly select one. The Java 21 runtime uses its built-in ergonomics/default collector; report the runtime's effective flags if an exact collector answer is needed.

When would you choose ZGC or tune a pause target?

Only after a repeatable profile shows GC pause/latency behavior is a material bottleneck, and a controlled benchmark demonstrates the desired latency improvement without unacceptable throughput or memory costs.

How can an app be OOM-killed before the heap is full?

The container limit applies to total process memory, not only Java heap. Native buffers, thread stacks, metadata, code cache, libraries, and other memory also count.

What would you compare before and after?

Use the same image except for the intended change, same limits and load profile, then compare throughput, p50/p95/p99 latency, errors, heap after GC, allocation, GC event frequency and pauses, RSS, CPU, and restarts.

What is the evidence gap in this repository?

The baseline flags and resource limits are checked in and the JFR capture procedure exists, but no representative deployment recording or measured result justifies a heap or collector change.
