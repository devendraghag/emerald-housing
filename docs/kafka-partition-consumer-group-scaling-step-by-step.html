Kafka partitions and consumer groups, from zero

Start with the vocabulary, inspect the current one-partition flows, then learn how to read lag and throughput before scaling. This guide distinguishes what the repository already configures from a future scale change that should wait for measured need.

1. Learn the basics first

  • A topic is a named stream of Kafka records.
  • A partition is an ordered slice of that stream. Kafka assigns partitions, not individual records, to consumers in a consumer group.
  • A consumer group is a set of consumers sharing work for a topic. Each partition is assigned to at most one active consumer in that group at a time.
  • Concurrency is the number of listener consumers a service starts for a listener container.
  • Consumer lag is the count of records between a group’s committed offset and the topic’s current end offset.

For one group, adding consumers helps only while there are unassigned partitions and enough work to keep them busy. If a topic has one partition, only one consumer in that group can actively process its records, even if the deployment has several pods.

Repository status: the measurement foundation exists after the prior lag work: a scheduled AdminClient gauge, Prometheus scrape, and Grafana panels. The topics are still one-partition and listener concurrency is one. No checked-in production measurement demonstrates that more partitions are needed, so this task does not increase partition count or replicas.

Each topic has a separate consumer group. Scaling one group does not redistribute the other topic’s partitions. The @KafkaListener(groupId=...) annotations define the actual notification groups; spring.kafka.consumer.group-id is a general default and does not override those explicit annotation group IDs.

KAFKA_LISTENER_CONCURRENCY configures listener concurrency and defaults to one. The Kubernetes Member Service Deployment runs two replicas initially, and its HPA allows two to three replicas based on CPU. With one partition per notification group, extra pods do not increase active consumer parallelism for that group.

The event-topic builders specify replicas(1) as well as partitions(1). Partition count controls possible consumer parallelism. Replication factor controls broker copies and availability; increasing replication is a durability/availability decision and does not itself add consumer parallelism.

If the topic had three partitions, one consumer group could assign up to three partitions concurrently. If it had one partition, adding ten consumers still leaves one active partition owner. Across the two different event flows, each group has its own assignment; total active work can therefore include one consumer for each topic.

Member Service replicas are also web/API replicas. Each process starts both listener containers. Kafka group coordination assigns partitions across those pods. The lag metrics component independently reads group offsets from each pod, and Grafana collapses the duplicate group/topic lag series with a max by (group, topic) query.

4. Measure before changing partition count

Use several signals together, over a representative time window:

  • Lag level and slope: is kafka.consumer.lag repeatedly rising or failing to return to baseline?
  • Input versus output rate: compare successful outbox send rate (kafka.messages.sent) with first-time consumed rate (kafka.messages.consumed). Check the same flow and window.
  • Outbox waiting rows: distinguish a producer/backlog problem from a consumer-side lag problem.
  • Consumer failures and DLT: more partitions will not fix poison messages or broken database writes.
  • Member Service and PostgreSQL capacity: CPU, DB pool saturation, query latency, lock waits, and pod count show whether the listener or its dependency is actually constrained.
  • Producer batch/latency signals: compare request batching and send throughput before deciding Kafka partitioning is the bottleneck.

A single lag value is not enough. Lag is a record count, not message age, and it can rise during bursts and then drain. No workload benchmark or sustained production lag history is checked into this repository, so the safe decision today is to retain the current one-partition configuration.

Important measurement detail: all Member Service replicas report the same group offsets. Use the dashboard’s aggregation, not a sum across pods, or the same lag will be counted multiple times.

5. Step-by-step scaling decision

Step 1 — confirm the affected flow

Use the group and topic tags to identify whether notices or lost-and-found is behind. Check its outbox sent rate, consumed rate, failures, and database work.

Step 2 — establish sustained demand

Capture lag and throughput over multiple polling and scrape intervals under normal and peak traffic. Distinguish a temporary burst from a persistent input/output rate gap.

Step 3 — rule out the consumer’s downstream bottleneck

Both listeners execute recipient-selection queries and write notification rows. If PostgreSQL is saturated, adding partitions can create more concurrent DB work without increasing completed throughput.

Step 4 — estimate useful parallelism

Choose a partition count based on measured required concurrency, key distribution, retention, broker capacity, and ordering needs. A target of N active consumers for one group requires at least N partitions for its topic.

Step 5 — align listener concurrency and deployment replicas

Set KAFKA_LISTENER_CONCURRENCY no higher than the useful partition count and ensure the number of group members can use those partitions. More pod replicas also run API traffic and increase possible DB concurrency.

Step 6 — change topic partitions deliberately

Topic partition counts cannot be reduced. Adding partitions may remap keys and changes ordering behavior across the topic. Apply and verify a Kafka-side partition increase rather than assuming a source-code topic declaration changes an existing topic.

Step 7 — load-test and compare

After rollout, verify group assignments, lag slope, consume rate, notification correctness, ordering assumptions, database headroom, and failure/DLT rates. Keep the change only if it improves throughput safely.

6. A safe scale procedure

Current source declares one partition directly in each topic configuration class; the partition count is not an application property today. A scale change should therefore include an explicit operational topic change or a reviewed source/configuration change, followed by confirmation of the actual broker state.

For a deliberate partition increase, use the cluster’s approved Kafka administration path. The Kafka CLI shape is:

kafka-topics.sh --bootstrap-server <broker:port> \
  --alter --topic community-notices.events --partitions <new-count>

kafka-topics.sh --bootstrap-server <broker:port> \
  --describe --topic community-notices.events

kafka-consumer-groups.sh --bootstrap-server <broker:port> \
  --describe --group community-notice-notifications

Repeat only for a flow whose measurements justify the change. The project’s local Kafka container uses the Apache Kafka image, whose CLI tools are under /opt/kafka/bin; production clusters may use a different administration workflow and credentials.

Then configure listener concurrency through KAFKA_LISTENER_CONCURRENCY and deploy enough Member Service replicas for the intended assignments, considering the HPA’s CPU-based scale range. Re-check the group after a rebalance. Do not set concurrency above available partitions in expectation of more parallel processing.

7. Ordering, keys, and replication are separate concerns

Publishers use the entity ID (notice or report ID) as the Kafka key. With one partition, each topic has one total order. With multiple partitions, ordering is guaranteed within each partition, not across the whole topic. Same-key records normally route together for a stable partition count, but increasing the partition count can change the key-to-partition mapping; old records for a key may be in one partition and new records in another.

Before increasing partitions, decide whether consumers rely on ordered events for the same notice/report and whether a partition-count change is acceptable for in-flight entities. Event ID deduplication prevents repeated effects, but it does not reorder events or make stale events safe.

Replication factor is different. Current topics use one replica, and the local compose broker is a single-node cluster. A production durability plan should review broker count, replication factor, minimum in-sync replicas, producer acknowledgements, and recovery objectives. Do not mistake more replicas for more consumer threads.

9. Limits and non-goals

  • The topic builders hard-code one partition and one replica; there is no partition-count property in application configuration.
  • The lag gauge is sampled and reports retained offset distance; it is not time lag.
  • The Member Service HPA scales on CPU, not consumer lag. There is no lag-based autoscaler or alert in the checked-in configuration.
  • The current Prometheus gauge is queried independently by every Member Service pod; dashboard aggregation handles duplicates but collection work scales with pod count.
  • Increasing partitions cannot be rolled back by reducing the count, and can affect key partition mapping and order.
  • One partition per flow caps active consumer parallelism at one regardless of HPA replicas. Changing that safely requires measured demand and Kafka/database capacity testing.
  • The local Kafka compose environment is one broker with one replica; it cannot validate production replication or high availability.
  • No load test or production throughput evidence is included in this repository. This guide does not assert that scaling is currently necessary or that a specific partition count is correct.

10. Interview preparation

60-second explanation

“In this project, each notification topic currently has one partition and one replica. Each listener uses a stable, separate consumer group, and listener concurrency is configurable but set to one. The Member Service has multiple replicas, but one partition means only one replica can actively consume each flow’s partition; CPU-based HPA scaling alone does not increase that group’s consumer throughput. We now measure group lag from Kafka offsets and compare it with sent/consumed rates, outbox depth, failures, and database capacity. Since no sustained lag or benchmark evidence is checked in, we leave partition counts unchanged. If measurements justify scaling, we would add partitions, align concurrency and replicas, then validate ordering, rebalances, database capacity, and lag under load.”

Likely follow-upAnswer
Why can’t ten consumers read one partition in parallel?Kafka assigns a partition to one consumer in a group to preserve ordered processing for that partition. Extra group members are idle until more partitions exist.
Does the HPA scale Kafka processing?It can add Member Service pods based on CPU, but active consumption for a group is still bounded by that topic’s partition count. The HPA does not use lag.
How many partitions should be added?Use measured input rate, per-consumer processing capacity, target lag/recovery time, key distribution, broker and database headroom, and ordering requirements. The repository has no benchmark from which to name a correct number.
What happens to ordering after adding partitions?Ordering remains per partition. Increasing partition count can remap keys, so events for one key may cross partitions across the change unless the migration strategy handles it.
What is the difference between partitions and replicas?Partitions expose parallel work and partition-local ordering. Replicas copy partition data for availability/durability; they do not create additional group work.
How would you know the change helped?Under comparable representative load, verify lower/rising-slower lag, higher completed consume rate, stable notification correctness and ordering, and acceptable broker/DB resource use.
