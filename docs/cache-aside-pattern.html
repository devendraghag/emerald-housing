Step 1 | Learn the idea

What is cache-aside?

Cache-aside is a pattern where the application controls the cache. On a read, it checks the cache first. If the value is missing, the application reads the database and places the result in the cache. On a write, the application changes the database and then removes or refreshes the affected cache value.

Simple analogy: before looking up an apartment in the official ledger, check the front-desk copy. If the copy lacks that apartment, look it up in the ledger and add it to the copy. When the ledger changes, discard the old copy.
  • Cache hit: value is already present, so database read is skipped.
  • Cache miss: no cached value; load from the source database.
  • Cache fill: store the database result for later reads.
  • Invalidation: remove old cached data after a successful write.
  • TTL: expiration safety net if invalidation is missed.
Step 2 | Memorize the normal flow

One read, two possible paths

RequestCaller asks for data
Cache checkTry Redis using a key
HitReturn cached response
MissRead database and fill Redis
value = cache.get(key)
if value exists:
    return value
value = database.load(key)
cache.put(key, value)
return value

Spring's @Cacheable implements this common flow around a method. The annotated method acts as the loader: Spring returns a cached value without running it on a hit; on a miss, it calls the method and caches the result.

This is still called cache-aside even though Spring hides the explicit get/put calls. The application chooses cacheable methods and owns write invalidation.
Step 3 | Establish the project status

Already implemented for selected Society reference reads

This pattern is present in Society Service through Redis and Spring Cache. It is not a global cache for every endpoint or every service. Redis cache policy is centralized in SocietyCacheConfiguration; service methods declare which reads can use it.

Step 4 | Follow a real request from the start

Example: GET /api/v1/flats/by-floor/2

HTTPFlatController.byFloor(2)
ServiceFlatService.listByFloorNumber(2)
Spring CacheLook in societyFlatsByFloor using key 2
Redis or DBHit returns; miss loads rows

The controller delegates to the service. The service method has @Cacheable(cacheNames=FLATS_BY_FLOOR, key="#p0.toString()", condition="@societyAccess.staff()", sync=true). This means only staff callers use this shared list cache. The method body loads floor/flat rows and maps them to response DTOs; on a Redis hit, Spring skips this body.

Key fit matters: floor 2 and floor 3 represent distinct values, so the floor number is part of the cache key. If the key omitted the floor, the cache could return the wrong floor's flats.
Step 5 | Inspect what protects a cache miss

Loader, metrics, and stampede control

On a miss, the service body executes and queries PostgreSQL. The load is wrapped by SocietyCacheMetrics.recordDatabaseLoad(...), which records database-load count and duration. The configured cache wrapper records cache hit/miss/error and lookup time.

Cache loading uses Spring's synchronized cache behavior plus a custom Redis per-key load lock. After acquiring the distributed lock, the wrapper checks Redis again before loading. That second check prevents multiple pods that waited on the same miss from all querying PostgreSQL. Once loaded, Spring stores the result in Redis with the configured TTL.

Miss in Redis
  -> acquire per-key Redis load lock
  -> check Redis again (another pod may have filled it)
  -> still missing: run service method / PostgreSQL query
  -> put result in Redis
  -> release lock

There is a separate 30-second negative cache for missing flat IDs. It stores a short marker, not a fake flat response, and is cleared when that flat changes or is created.

Step 6 | Trace a write and refresh

Database first, cache invalidation after commit

Write methodPersist flat/floor change
CommitTransaction succeeds
InvalidateRemove affected Redis keys
Next readMiss reloads fresh DB data

Flat writes publish FlatReferenceChangedEvent. FlatCacheInvalidationListener handles it with @TransactionalEventListener(AFTER_COMMIT), deleting the by-ID entry, the all-flat entry, relevant floor-list entries, and the negative key. If a flat moves floors, both old and new floor lists are evicted. Floor create/update methods use @CacheEvict for related lists.

Evicting after commit avoids removing a good cache value when the database transaction rolls back. Redis keys are shared, so a deletion by one Society pod affects later reads on every pod.

Step 7 | Understand which reads should stay separate

Do not cache data under an incomplete key

Cache keys must include every input that changes the result, including identity/authorization scope where relevant. The project uses staff-only conditions for shared flat lists. It leaves dynamic page/search/cursor endpoints uncached because their result depends on page, sort, search, status, floor, and potentially caller access; a safe cache key would need to model all of that and may have poor reuse.

GET /api/v1/flats/{id} also has an explicit uncached path for authority SERVICE_MEMBER_FLAT_READ. Its service comment says assignment validation must read the primary to avoid replica-lag false negatives. Do not route that case through a cached result.

Other service reads (members, memberships, transactional/audit data, notice target options) have no cache-aside annotations. The code gives no measured reuse/consistency case for adding caching there, so this guide does not claim they are cached.

Step 8 | Find the configuration

Redis and cache manager responsibilities

  • application.yml configures Society Redis host/port, password, 500 ms connect/command timeout, and Lettuce pool.
  • Kubernetes maps SOCIETY_CACHE_REDIS_HOST=redis-cache; cache service is separate from the generic redis endpoint.
  • SocietyCacheConfiguration declares cache names, typed JSON serializers, TTLs, jitter, null behavior, versioned prefix, transaction awareness, and statistics.
  • Key prefix is society:cache:v2:; declared cache names include floors, flat-by-ID, flats-by-floor, and all-flats.
  • SocietyCacheWarmup optionally primes the small floor list at startup. This is a warmup shortcut; request-time behavior remains cache-aside.
Redis is a cache, not the authoritative store. The checked-in Kubernetes cache Redis is one ephemeral pod; loss of cache should mean slower DB-backed reads, not lost business records.
Step 9 | Know failure and consistency behavior

What if Redis is slow or unavailable?

Cache access errors are recorded. Society Service uses a local five-second Redis bypass after failures and limits fallback DB loads to 16 concurrent operations per pod by default. The Redis cache uses a 128 MB limit and allkeys-lru eviction in Kubernetes. Eviction/invalidation failure can leave old values until their TTL expires, so consistency is eventual, not strong.

  • Do not report cache as the source of truth.
  • Do not assume DB commit plus Redis eviction is atomic.
  • Direct SQL changes bypass service invalidation and may stay stale until expiry.
  • High cache hit rate does not alone prove API latency improved; compare Redis, database, and endpoint timings.
Step 10 | Observe cache-aside behavior

Use existing metrics

SocietyCacheMetrics publishes counters for cache lookups by cache and outcome, timers for cache lookup latency, and separate counters/timers for database fallback loads. Redis failures, lock timeouts, negative lookups, warmups, and fallback rejection are also observable through Micrometer/Actuator and Prometheus.

Hit ratio over a time window is hits divided by hits plus misses. Exclude errors and explicit bypasses. Compare cache-hit lookup duration to database-load duration and endpoint latency. The Grafana overview currently has no dedicated cache panel, although Prometheus metrics are exposed.

Counter nuance: cache read after distributed-lock wait is not separately counted, so lookup hit rate is an operational estimate rather than a count of every internal Redis read.
Step 11 | How to operate and improve it

Repeatable developer checklist

  1. Confirm the data is read often, relatively stable, and safe to share for the selected caller scope.
  2. Define a key that includes every result-changing input; define TTL and max acceptable staleness.
  3. Keep PostgreSQL authoritative; implement cache-aside read and database-load metrics.
  4. Invalidate after successful writes, including all dependent list keys and negative entries.
  5. Test hit, miss, write/eviction, rollback, Redis-unavailable, and authorization paths.
  6. Measure hit/miss duration, DB load reduction, endpoint latency, and stale-data incidents before broadening caching.

For this project, standardization already comes from one Society cache manager/wrapper and explicit service annotations. Apply the same rules only to another stable, shared Society reference read after proving it is safe. Do not put paging/search results or caller-specific data in a shared cache without a complete key and authorization-safe design.

Step 12 | Be precise about limitations

What cache-aside cannot promise by itself

  • No automatic consistency if a write bypasses the owning service.
  • No atomic transaction spanning PostgreSQL and Redis.
  • Cache misses still incur database work; a miss storm can load the DB if lock protection is unavailable.
  • TTL bounds cache lifetime but does not guarantee a hard freshness SLA when Redis/DB are unavailable.
  • Adding many query/result combinations can create key-cardinality and memory problems.

For reliable cross-service invalidation, a transactional outbox or CDC could be considered if another writer is introduced. Neither is part of this feature's current implementation.

Step 13 | Interview explanation

Say it clearly

“In Society Service, cache-aside is implemented with Spring Cache over Redis for selected floor and flat reference reads. PostgreSQL stays authoritative. On a hit, Spring returns the cached DTO and skips the loader method; on a miss, the service queries PostgreSQL and the result is stored with a per-cache TTL. Keys distinguish flat IDs, floor lists, and global lists. A distributed Redis load lock reduces duplicate misses across pods. Successful writes evict affected keys after database commit, so the next read reloads fresh data. Dynamic paginated/search results and caller-specific reads remain uncached because their result scope and keys are different. The consistency model is eventual; TTL is a fallback if invalidation is missed.”

Follow-up questions

Why not update the cache on every write?

Eviction is simpler and avoids building a potentially incorrect cache value. The next read recomputes it from the source database.

What happens on a cache hit?

Spring returns the cached result without executing the annotated service loader method.

What if Redis is empty?

The service loads PostgreSQL, returns the result, and fills Redis.

Why invalidate after commit?

So a rolled-back database write does not unnecessarily erase a still-correct cache entry.

Why not cache every GET?

Some responses depend on caller identity, filters, pagination, or require primary-database validation. A wrong/incomplete key can expose or return incorrect data.

Is this strongly consistent?

No. It is eventual; there is a brief commit-to-eviction window, and TTL handles missed invalidation.
