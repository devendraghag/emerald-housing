1. What to know first

Before reading the implementation, know four terms:

  • Database transaction: a group of database changes that commit or roll back together.
  • Kafka: a broker that stores messages for consumers.
  • Dual write: updating a database and publishing to Kafka as two independent operations.
  • At-least-once delivery: a message can be delivered more than once, so consumers need duplicate protection.

The outbox is a database table used as a durable handoff point. Business data and an event row are committed in one database transaction. A separate worker later publishes that row to Kafka.

Current project status: Outbox publishing is implemented for community notices and lost-and-found events in the Member Service. This guide documents existing behavior; it does not add or change runtime code.

2. The failure problem the pattern solves

Suppose an API changes a notice to published and must notify other parts of the system. If it commits the database first and crashes before Kafka publish, the database says “published” but no event exists. If it publishes first and the database rolls back, consumers observe an event for a change that never committed.

Writing the outbox row in the same transaction as the business change removes that gap: either both database changes commit, or neither does. Kafka publication happens after commit and can be retried from the durable row.

Important: this is not a single transaction spanning PostgreSQL and Kafka. The outbox makes the database side atomic and the background publisher retries delivery; duplicates remain possible around acknowledgement and deletion.

4. Follow one event, step by step

Step 1 — a business action creates an event

A service operation decides an event should be emitted. For example, changing a community notice to PUBLISHED creates a CommunityNoticeEvent; lost-and-found service operations create corresponding report events. Event construction and call sites are in the service classes listed in the code map.

Step 2 — write the outbox row inside the transaction

The publisher’s publish method is annotated @Transactional and inserts event identity, entity ID, event type, actor, occurrence time, schema version, event timestamp, and correlation ID. It participates in the business transaction under Spring’s default REQUIRED propagation.

Step 3 — a scheduled job finds eligible work

@EnableScheduling activates publisher scheduling. Each dispatcher uses a configurable fixed delay (default 1,000 ms), selects rows that are unclaimed or whose lease has expired, orders by creation time, and claims at most 50 rows.

Step 4 — claim prevents workers from taking the same row

A PostgreSQL CTE uses FOR UPDATE SKIP LOCKED and assigns a random claim token plus a 180-second lease. This supports multiple service instances: concurrent dispatchers skip rows another transaction has locked/claimed. The lease lets a later poll recover rows left behind by a crashed worker.

Step 5 — serialize and publish synchronously

For each claimed row, the publisher serializes the event and calls kafka.send(...).get(). The Kafka key is the notice ID or report ID, preserving key-based partition ordering when a topic has multiple partitions; current topic configuration is single-partition.

Step 6 — acknowledgement decides whether to delete

Only after the send future completes successfully does the publisher delete the row, matching both event ID and claim token, and increment kafka.messages.sent. If send/serialization fails, it increments the row’s attempts, clears claim/lease so it is eligible again, increments kafka.messages.failed with stage outbox, and logs the error.

At-least-once consequence: a process could publish successfully and fail before deleting the row. Once its lease expires, it can publish again. The consumers use event IDs and processed-event records to deduplicate effects; the publisher itself does not guarantee exactly-once delivery.

5. Transaction and schema: what is persisted

The table schemas originate in Flyway migrations V14__lost_found.sql and V16__community_notices_and_audiences.sql. V17__kafka_delivery_reliability.sql adds fields used by resilient publishing: schema version, event timestamp, correlation ID, claim token, lease expiry, and claim indexes.

Each row includes an event ID, target entity ID, event type, actor, occurrence timestamp, attempts count, creation timestamp, and later-added event metadata and claim state. These records are not a long-term event archive: after successful broker acknowledgement, the row is deleted.

The durable guarantee depends on the business change and outbox insert sharing the same transaction and database. A publisher call made outside the intended transaction would weaken that guarantee; inspect its service call site when adding a new event.

6. Claim, publish, acknowledge: implementation details

  • Polling: @Scheduled(fixedDelayString=...) waits the configured delay after the previous dispatch method finishes, rather than firing at a fixed wall-clock rate.
  • Batch size: hard-coded to 50 in each SQL claim query.
  • Claim lease: hard-coded to 180 seconds.
  • Concurrency: SKIP LOCKED and token-guarded delete/update protect work across concurrent database workers.
  • Publish wait: sends are awaited sequentially with .get(); the next event in the batch waits for the current send result.
  • Failure policy: outbox producer attempts are not capped in these publisher classes. Failed rows are immediately eligible for a later poll; there is no per-row exponential backoff or dead-lettering for outbox-send failures.

Do not confuse this publisher retry loop with the consumer listener retry/DLT configuration. Consumer failures are handled separately by Kafka listener configuration and DLT topics.

8. Monitor backlog and publishing throughput

The publishers register the following Micrometer meters. Prometheus can scrape the Member Service at /actuator/prometheus; the Kubernetes Prometheus configuration scrapes annotated pods every 15 seconds.

MeterKind / tagsInterpretation
kafka.outbox.waitingGauge; flow=community-notices or flow=lost-foundCurrent count of rows in that outbox table, including rows currently claimed.
kafka.messages.sentCounter; flow tagSuccessful outbox sends observed by the publisher since process start. Use a rate over time to estimate publishing throughput.
kafka.messages.failedCounter; flow and stage=outboxOutbox publish attempts that threw an exception. Consumer/DLT failures use a different stage.

How to read the signals together

  • Backlog near zero and sent rate steady: the publisher is generally keeping up.
  • Backlog rising while sent rate remains low: demand is exceeding effective publishing capacity, Kafka/DB may be unhealthy, or the publisher is stalled.
  • Backlog positive with failed counter increasing: inspect Kafka reachability, serialization errors, logs, and DB health.
  • Backlog drops while sent rate rises: queued work is draining. Compare both flows independently.

Micrometer’s Prometheus naming convention typically maps these meters to names such as kafka_outbox_waiting and kafka_messages_sent_total. Confirm the exact exposed names and tags at /actuator/prometheus in the running version before saving production queries. A useful conceptual PromQL expression is sum by (flow) (rate(kafka_messages_sent_total[5m])); adapt it to the actual exported name and label names.

Observability boundary: repository code defines backlog depth and sent/failed counters. It does not define a dedicated outbox dashboard/alert, oldest-row age, send-duration histogram, batch-size metric, or explicit backlog-drain SLO. The counters provide throughput only after calculating their rate. A stable count alone does not prove freshness.

9. Operational runbook

  1. Confirm Member Service targets are up in Prometheus and inspect /actuator/prometheus for the three meters and flow tags.
  2. Graph backlog gauge by flow beside the rate of successful sends and rate of outbox failures.
  3. If a backlog grows, correlate the time window with publisher error logs and Kafka broker health; also verify PostgreSQL availability and connection capacity.
  4. Check whether the backlog is actively claimed: claim leases last 180 seconds. A worker crash may leave rows claimed until expiry.
  5. Inspect outbox row age and attempts directly in PostgreSQL when diagnosing an old/stuck backlog. Use a read-only query and the actual schema names; the built-in gauge does not expose age.
  6. After fixing the dependency, verify backlog declines and sent rate resumes. Since failed rows remain eligible for later polls, no manual replay is normally needed for those rows.

For consumer dead letters and manual event replay, see Kafka notification operations. That runbook covers consumer DLTs, which are distinct from outbox publisher failures.

10. Tests and what they prove

CommunityNoticeKafkaIntegrationTest runs with Testcontainers Kafka and PostgreSQL. It inserts an event via the publisher, confirms its outbox row exists, manually dispatches, checks the row is removed after broker acknowledgement, and reads the event back from Kafka to compare it with the original.

This is a valuable happy-path end-to-end test for the community notice publisher. It does not load-test throughput, verify the lost-and-found publisher end to end, force broker failures, test lease expiry/recovery, assert concurrent-claimer behavior, or validate metric values/alerts. The current evidence therefore confirms basic publication, not production capacity or failure-path completeness.

11. Limits and risks to understand

  • No exactly-once transaction: a send can be acknowledged and then the process can fail before deleting the row; duplicate publication is possible.
  • Sequential worker: waiting synchronously for each send limits batch throughput and ties up the scheduler thread during broker latency.
  • Fixed batch and lease: 50 rows and 180 seconds are constants, not externally configurable.
  • Retry amplification: failed rows become eligible again on the next polling cycle; no exponential delay or cap is implemented, so an extended Kafka outage can cause repeated attempts and logs.
  • Metrics are incomplete for diagnosis: no age/lag distribution or publish latency metric is defined; count and counter-rate can hide a small set of very old rows.
  • Counter lifecycle: counters are process-local and reset on restart; monitoring should use Prometheus counter rate functions, which handle resets.
  • Topic scale: one partition limits parallel consumer throughput and ordering is only per partition; scale strategy needs workload evidence.

Any tuning should use observed arrival rate, drain rate, database load, broker latency, and acceptable event delay. Increasing batch size or shortening polling can raise database and broker pressure; this repository does not include a load-test result that justifies a particular production setting.

12. Interview explanation and likely follow-ups

60-second answer

“The Member Service uses the transactional outbox for community notice and lost-and-found events. The business operation writes the event row into PostgreSQL in the same transaction as its domain update. A scheduled dispatcher claims up to 50 eligible rows using a lease and FOR UPDATE SKIP LOCKED, publishes each to Kafka, and deletes it only after broker acknowledgement. On failure it increments attempts, releases the claim, and retries on a later poll. This avoids losing events in the database-to-Kafka dual-write gap, but is at-least-once, so consumers deduplicate by event ID. Micrometer exposes per-flow backlog gauges and send/failure counters; there is no built-in age metric or dedicated dashboard.”

Likely follow-up questions

QuestionAnswer
Why not publish to Kafka inside the database transaction?PostgreSQL and Kafka do not share an ordinary local transaction here. The outbox makes the database update and event intent atomic, then publishes asynchronously.
Can an event be published twice?Yes. If Kafka acknowledges and the process fails before deleting the row, lease expiry can lead to another send. Consumers deduplicate using event identity.
How are concurrent service replicas coordinated?The claim query selects eligible rows with FOR UPDATE SKIP LOCKED, assigns a UUID claim token and lease, and later mutates only rows matching that token.
How do you detect that the publisher is falling behind?Graph kafka.outbox.waiting per flow and compare it with the rate of kafka.messages.sent; watch outbox-stage failures. Age metrics would improve detection of stale rows but are not currently exposed.
How is throughput computed?Use a rate function over the successful-send counter over a useful window, per flow. Validate actual Prometheus-exported meter and label names first.
What happens during a prolonged Kafka outage?Rows stay durable, each failed attempt increments attempts and releases the claim, and future polls try again. There is no backoff/cap in the outbox dispatcher, so repeated attempts can increase load.
What would you improve next?Add tests for both flows, failure and lease recovery, instrument send duration and oldest pending age, alert on sustained backlog growth/staleness, and consider bounded exponential retry/backoff after measuring workload.
