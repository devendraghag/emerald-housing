1. Learn the basics first

Traditional blocking I/O ties up the calling thread while it waits for a socket, database, or other resource. With non-blocking I/O, the thread can do other work while the operation is pending; a completion signal resumes the next step.

In this Gateway, Reactor is the async composition model:

  • Mono<T>: a deferred operation that can produce zero or one value, or an error.
  • Flux<T>: a deferred sequence that can produce zero or many values.
  • map: transform a value synchronously.
  • flatMap: compose another asynchronous operation that returns a publisher.
  • onErrorResume/onErrorMap: recover from or translate an error without blocking for a result.
  • Subscription: the WebFlux/Gateway runtime subscribes to controller/filter publishers and drives the work.

Reactive is not a synonym for “every method runs on another thread.” It is a way to represent and compose asynchronous work without holding an event-loop thread waiting for I/O.

Current status: API Gateway is built on Spring Cloud Gateway’s WebFlux server starter, WebFlux security and session APIs, Reactor return types, and reactive HTTP/Redis components. There is no .block() or manual subscribe() in the Gateway’s production Java code inspected for this guide.

At the Gateway boundary, a response can remain asynchronous while the upstream service is processing it. The upstream service itself can still use MVC, blocking database access, and its own thread pools. The Gateway and services are separate applications and can have different programming models.

Gateway routes are configured in application.yml for Member, Society, and AI service URLs. Route filters apply authenticated-admin Redis rate limits. Global filters add correlation/error handling, remove untrusted internal headers, and count rate-limited responses.

4. Trace a proxied API request step by step

Step 1 — accept and decorate the exchange

CorrelationAndErrorFilter validates or creates an X-Correlation-ID, adds it to the request/response, and starts timing. The filter returns a Mono<Void> representing the downstream chain.

Step 2 — remove untrusted internal headers

InternalHeaderSanitizingFilter removes gateway/service authentication and identity headers from the incoming request before forwarding. It also returns the filter chain’s Mono.

Step 3 — authenticate and authorize

GatewaySecurityConfiguration permits public/login/health routes, protects /api/v1/**, configures CSRF and session behavior, and denies unmatched exchanges by default.

Step 4 — match a route and apply rate limiting

Spring Cloud Gateway matches the configured path predicates. The route’s RequestRateLimiter asks Redis through the reactive limiter; the key resolver derives a stable authenticated-admin key, or uses the unauthenticated bucket.

Step 5 — proxy the request upstream

The Gateway HTTP client uses configured connect and response timeouts. Reactor Netty performs network I/O without a servlet request thread waiting synchronously for the upstream response.

Step 6 — map errors and finish instrumentation

CorrelationAndErrorFilter translates timeout, unavailable, and not-found failures into JSON responses when the response is not already committed. Its doFinally logs status and duration for completion, error, or cancellation signals.

5. Trace login and session validation separately

Authentication is also composed reactively, but it follows a local controller flow rather than a Gateway proxy route:

  1. AuthController.login asks the reactive Redis login limiter for a decision.
  2. When allowed, it calls AdminAuthenticationManager.authenticate, which returns a Mono<Authentication> from a WebClient request to Member Service.
  3. The credential response is validated and mapped to an authenticated principal. HTTP 401 is mapped to invalid credentials; other errors become an authentication-service-unavailable response.
  4. The controller changes the session ID, saves the security context and clears the old CSRF token through reactive session/repository operations.
  5. /api/v1/auth/me and /internal/auth/session compose session reads with a reactive call to Member Service for current account information.

Connect and response timeouts are configured for the credential WebClient. The session cookie and CSRF policies are configured in the reactive security configuration. Reactive session state is backed by Spring Session Redis.

6. Read Reactor code without losing the flow

Use this mental model on the login method:

rateLimiter.isAllowed(...)
  .flatMap(rate -> rate.isAllowed()
      ? authenticate(request, exchange)
      : loginRateLimited(exchange))
  .onErrorResume(error -> serviceUnavailableResponse(error))

Nothing is synchronously extracted from the publisher. Each flatMap composes another asynchronous result; error recovery returns another publisher. The framework subscribes when it handles the request.

Tests sometimes call .block() to get a result in a synchronous JUnit assertion. The inspected production Gateway code does not. A production .block() on a Reactor Netty event-loop thread would undermine the non-blocking design and can cause starvation or runtime blocking warnings.

Likewise, do not call subscribe() inside a request handler to “start” work and return early. That detaches errors and completion from the HTTP response lifecycle. Return and compose the publisher instead.

When troubleshooting, correlate the Gateway request ID across Gateway and service logs. Separate connect timeout from response timeout, inspect Redis/session/rate-limiter availability, and check whether the upstream service itself is slow. A Gateway timeout tells you the boundary stopped waiting; it does not prove the backend stopped its work.

8. What is not reactive in this repository?

Member Service and Society Service use Spring MVC and imperative patterns such as RestClient, JDBC, and JPA. Their own request threads may block while performing downstream or database I/O. The Gateway’s reactive proxy cannot change those execution models automatically.

The Gateway also contains a small synchronous static-resource controller for serving a classpath rental page. It returns a local resource and does not perform remote blocking I/O. Reactive applications can contain short synchronous computation; the concern is blocking an event-loop thread on slow I/O or long-running work.

No broad rewrite was made. A service migration would require separate workload evidence, compatible reactive database/client drivers, transaction and security redesign, tests, and operational comparison. Replacing only the controller return type would not make JDBC/JPA calls non-blocking.

9. Verification and what tests cover

The Gateway Maven test suite passed: 21 tests, zero failures, zero errors, and zero skips. The tests cover route predicates, WebFlux filters, error mapping, dynamic authentication, role/session behavior, service failures, and internal-header sanitization.

Several unit tests use .block() at the test boundary to assert a publisher result. That is test harness behavior, not a production Gateway blocking call.

The suite verifies reactive code paths and response behavior. It is not a load test proving a specific concurrency or memory advantage over a blocking Gateway, nor does it prove downstream MVC services are non-blocking.

10. Limits, trade-offs, and safe evolution

  • Reactive code can still block if a blocking library or explicit wait runs on an event-loop thread.
  • Reactive Gateway backpressure does not guarantee upstream service capacity, database capacity, or low latency.
  • Session, rate limiter, and authentication flows depend on Redis and Member Service availability; timeouts and error mapping define the failure response.
  • Gateway response timeout and upstream service timeout budgets should be coordinated. A Gateway timeout can happen while backend work continues.
  • Every service boundary requires independent telemetry. Gateway p95 alone cannot identify whether delay is in routing, Redis, Member Service, Society Service, or the database.
  • Reactive composition can be harder to debug if code detaches publishers or loses context. Keep return types composed and propagate correlation/tracing context.
  • No performance benchmark in the repository supports converting the MVC services to reactive programming.

11. Interview preparation

60-second explanation

“The API Gateway is built on Spring Cloud Gateway’s WebFlux server and Reactor Netty. Its route filters, WebFlux security, login/session controllers, Redis rate limiting, and Member credential calls compose through Reactor publishers such as Mono; the production Gateway code does not block or manually subscribe. The Gateway proxies requests to separate Member, Society, and AI services, which remain Spring MVC applications. So I describe the Gateway boundary as reactive, not the whole system. We keep connect/response timeouts, Redis-backed sessions and rate limits, correlation IDs, and error translation. The Gateway test suite passes, but we have not benchmarked a broad service rewrite, so there is no evidence to do that.”

Likely follow-upAnswer
Does returning Mono make blocking code non-blocking?No. A blocking call still blocks the thread it runs on. Reactive composition helps only when the I/O client and participating libraries are non-blocking or blocking work is isolated appropriately.
Are the backend services reactive?No. Member and Society use Spring MVC/imperative persistence. The Gateway forwards to them over HTTP.
Why use flatMap in login?Authentication, session changes, and security-context persistence return asynchronous publishers; flatMap composes their results without waiting synchronously.
Why is .block() acceptable in a test?The test is a synchronous boundary that needs an assertion value. Production handlers should return/compose the publisher rather than block an event-loop thread.
What are the main risks?Accidentally blocking event loops, detached subscriptions, missing timeouts, unbounded concurrency, and assuming reactive Gateway behavior gives downstream services unlimited capacity.
What evidence would justify a broader migration?Profiling that shows thread scarcity caused by blocking I/O, representative load tests, reactive replacements for database and client access, and before/after latency/resource/error measurements.

12. Code map: learn in this order

  • api-gateway/pom.xml — WebFlux Gateway, WebClient, security, session and reactive Redis dependencies.
  • application.yml — WebFlux routes, timeouts, Redis session and route limits.
  • GatewaySecurityConfiguration.java — reactive security chain, CSRF, sessions, authorization.
  • AdminAuthenticationManager.java — reactive WebClient credential/current-account calls.
  • AuthController.java — CSRF, login, session setup, current-admin request flow.
  • InternalSessionValidationController.java — reactive internal session validation.
  • GatewayRateLimitConfiguration.java and RateLimitMetricsFilter.java — reactive key resolution and rate-limit metrics.
  • CorrelationAndErrorFilter.java and InternalHeaderSanitizingFilter.java — reactive global filter chain.
  • GatewayRoutesTest.java and related Gateway tests — route and reactive behavior checks.
Learning order: learn Mono/Flux and subscription → inspect WebFlux Gateway dependency → follow route configuration → trace one proxy request → trace login and session flow → inspect timeout/error filters → compare Gateway with MVC services → review tests and telemetry.

Repository-grounded guide. Reactive behavior is scoped to the API Gateway; upstream service implementations and performance characteristics remain separate.
