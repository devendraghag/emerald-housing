Step 1 | Learn the words

Pagination from zero

Pagination splits a long matching list into smaller batches. If there are 50,000 membership records, an API should not load and send all of them just to show 20 on a screen.

CollectionEvery record that matches
BatchA limited group, for example 20
ContinueAsk for another group only when needed
  • Offset: the number of matching rows to skip before the requested batch.
  • Cursor: a bookmark describing where the previous batch ended.
  • Stable order: a predictable sort, so the bookmark identifies a precise boundary.
  • Keyset pagination: cursor paging that compares sort-key values instead of skipping an offset.
  • Index: a database structure that helps locate/order data for a query. Flyway creates it; the database keeps it updated as rows change.
Analogy: offset says, "walk past 10,000 people in line." A cursor says, "continue after this named person."
Step 2 | Understand the performance issue

Deep offset compared with a bookmark

Page 500 with 20 rows per page means offset 10,000. The database may need to walk over earlier matching rows before returning the next 20. A cursor instead says, "return rows after the timestamp and ID of the last row I already saw."

Offset pageSort; skip 10,000; return 20
Cursor pageContinue beyond a known timestamp and ID
Trade-offCursor is good for sequential browsing, not jumping to page 500
A cursor alone does not guarantee a fast query. The filter, sort, useful index, and query plan still matter. Measure with realistic data.
Step 3 | Inspect what was there before

Cursor paging was partly implemented

Member and flat directories already had cursor routes. They reused CursorCodec and CursorPage, ordered by creation time and ID, and fetched one extra row to determine whether another batch existed.

Membership histories had numbered page routes, but no cursor route:

GET /api/v1/members/{memberId}/flats/page?page=0&size=20
GET /api/v1/flats/{flatId}/memberships/page?page=0&size=20

These page routes are still useful for shallow numbered navigation and total-page information. Deep pages may incur more offset work, so the missing feature was a cursor alternative for each history direction.

Step 4 | What was coded and configured

Implementation progression

  1. Controller contract: added cursor routes accepting limit (default 20) and optional after.
  2. Service layer: added methods to MembershipService; existing member/flat access checks remain.
  3. Entity access: exposed createdAt from FlatMembershipEntity for the cursor sort key.
  4. Query: MembershipWriter filters by memberId or flatId, then adds the keyset boundary predicate.
  5. Stable ordering: sort descending by createdAt and then ID, so equal timestamps have a deterministic order.
  6. Bounded response: validate limit 1-100 and fetch only limit + 1 rows.
  7. Continuation: encode the last returned row's createdAt/ID and the access/query scope as nextCursor.
  8. Database indexes: Flyway V18 creates composite indexes for each resource filter plus timestamp/ID order.
  9. Test coverage: added persistence assertions for order, continuation, invalid scope, and invalid limit.
Step 5 | Follow the full request

Example: first batch of one member's flat history

GET /api/v1/members/123e4567-e89b-12d3-a456-426614174000/flats/cursor?limit=20
1. GatewayRoutes /api/v1/members/** to Member Service
2. ControllerMemberController reads memberId, limit, after
3. ServiceMembershipService applies member access rule
4. WriterMembershipWriter validates the limit and cursor
5. JPABuilds criteria filter, order, and max-results query
6. DatabaseReturns bounded rows; service maps response DTOs

The controller does not fetch every history row and trim a Java list. The query layer asks the database for at most 21 rows when the requested limit is 20. The flat-history route uses the same path, filtering on flatId. Resident flat-history reads are additionally restricted to the resident's own member ID.

Step 6 | See how the cursor becomes a query

Timestamp plus ID is the bookmark

Two rows can share a timestamp. Adding ID as a tie-breaker prevents an ambiguous boundary. For descending order, the next query looks for smaller keys:

ORDER BY created_at DESC, id DESC
WHERE created_at < :lastCreatedAt
   OR (created_at = :lastCreatedAt AND id < :lastId)

This is the SQL idea. MembershipWriter expresses it with JPA Criteria; Hibernate generates dialect-specific SQL. Cursor mode does not call setFirstResult (offset). It applies the boundary predicate and setMaxResults(limit + 1).

Why fetch one extra row?

When limit is 20, query up to 21. If 21 rows are found, return the first 20 and set hasNext=true. The hidden extra row proves another batch exists. Build the next cursor from the 20th returned row.

What is inside the cursor?

CursorCodec encodes timestamp, UUID, and a SHA-256 digest of the scope as URL-safe Base64. It is opaque-looking, but not encrypted or signed. It is a continuation value, not a secret or authorization proof.

Step 7 | Understand the database configuration

Flyway creates indexes for the query

Migration V18__index_membership_cursor_order.sql adds:

CREATE INDEX ix_memberships_member_cursor
    ON flat_memberships (member_id, created_at DESC, id DESC);

CREATE INDEX ix_memberships_flat_cursor
    ON flat_memberships (flat_id, created_at DESC, id DESC);

The first column matches each query's equality filter. The following columns match cursor ordering and continuation. Flyway applies this as part of the member-service schema migration. PostgreSQL maintains index entries when data is inserted or updated; application code does not edit them.

How to confirm the index helps: in a suitable environment, run EXPLAIN (ANALYZE, BUFFERS) for representative queries and check the actual plan. An index existing does not guarantee the planner will choose it.
Step 8 | Try the endpoints

First request, then continue

GET /api/v1/members/{memberId}/flats/cursor?limit=20
GET /api/v1/members/{memberId}/flats/cursor?limit=20&after={nextCursor}

GET /api/v1/flats/{flatId}/memberships/cursor?limit=20
GET /api/v1/flats/{flatId}/memberships/cursor?limit=20&after={nextCursor}

Leave out after for the first call. Send the response's nextCursor unchanged on the next call. Stop when hasNext is false. Limit must be 1 through 100.

Step 10 | Verification and limits

What was verified

Member-service Maven tests passed: 106 tests, 0 failures, 34 skipped. The new persistence test is in a Testcontainers-backed class that was skipped because Docker was unavailable. The Java changes compiled, but the new database assertions and Flyway migration have not been run against PostgreSQL in this environment.

  • Run the persistence test with Docker available to verify order, continuation, permissions, and migration.
  • Compare plans and latency with realistic data before claiming a production speedup.
  • This is not a snapshot: new records inserted before the current cursor may not appear in an ongoing traversal.
  • Scope digest is not encryption or signature. Authorization checks still decide access.
  • Indexes use storage and add write work; measure this cost too.
  • Other offset routes such as account, owner, and family pages remain candidates if observed deep-page performance warrants it.
Step 11 | Interview practice

Explain it from implementation

"Offset pagination can make deep pages expensive because the database may pass many earlier rows. Member and flat directories already had cursors, but membership histories had only page-number routes. I added cursor routes by member and by flat. The JPA criteria query filters on that resource, orders by createdAt and ID descending, and uses the last returned pair as the next boundary. It fetches limit plus one to determine hasNext without counting the full result. I added Flyway composite indexes matching the resource filter and ordering. Existing authorization remains, and the cursor is scope-bound. I also added persistence coverage, but Docker was unavailable, so those database assertions and the migration still need a Docker-enabled run. I would inspect execution plans and measure realistic data before claiming a speedup."

Follow-up questions

Why both createdAt and ID?

Timestamps can tie; ID gives a deterministic order and continuation boundary.

Why not return totalPages?

Cursor navigation answers whether there is another batch without calculating the total. It also does not support jumping to a page number.

Does the index guarantee a faster query?

No. It matches the filter and order, but the planner and data distribution decide whether it helps. Inspect the plan and measure.

Does cursor scope replace permission checks?

No. It prevents reuse across contexts, while method security still authorizes the requested member or flat.
