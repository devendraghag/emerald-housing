Database query caching

Learn query caching from zero, distinguish database/ORM caching from Spring result caching, and follow the project’s existing Redis-backed read paths. Then learn the order to use before considering more caching: optimize the SQL and indexes, measure the plan, and only cache if repeated database work remains a proven cost.

Step 1 | Learn the basic idea

What is database query caching?

Database query caching means reusing the result of a previous read instead of asking the database to execute the same query again. “Query caching” can mean different things depending on which layer stores the result. The project must identify that layer before claiming a feature.

  • Query: a request to the database, such as “list flats for floor 2.”
  • Query result: rows or response objects returned by that request.
  • Cache key: identifies which result can be reused, including relevant query inputs.
  • Invalidation: remove cached result when source data changes.
  • Execution plan: PostgreSQL’s chosen steps for running SQL.
Analogy: a librarian can look up a book in the catalog each time, or keep a photocopy of the answer to a common question. The photocopy saves repeated lookup work, but must be refreshed when the catalog changes.
Step 2 | Separate the three things people call “query cache”

They are not interchangeable

LayerWhat is reused?Project status
PostgreSQL buffer cacheDatabase pages already in memory; SQL still executesDatabase internal behavior; not configured by this application feature.
Hibernate query cacheORM query result identifiers/values, alongside Hibernate cache configurationNo Hibernate query-cache settings or query-cache hints found.
Spring application result cacheReturned Java DTO/list for a selected service method and keyImplemented for selected Society floor/flat reads using Redis.

A Spring @Cacheable method cache can avoid running its repository query on a hit. That is application-level result caching; it does not mean Hibernate's query cache has been enabled.

Step 3 | Inspect the actual feature status

Partly included: selected query results are Redis-cached

Society Service uses Spring Cache and a RedisCacheManager for a small set of repeatable reference reads. PostgreSQL remains authoritative. The cached result is generally a serialized response DTO/list, not a global cache of all database queries.

Service methodResult cachedDefault lifetime
FloorService.getFloors()Ordered floor response list, key all10 minutes

The Redis cache wrapper records hit/miss/error and lookup time. Database loads have separate count and duration metrics. A distributed per-key lock reduces multiple pods loading the same missing result concurrently.

Step 5 | See the query that runs on a miss

Cache does not replace query design

The floor list method calls FlatRepository.findByFloorIdOrderByFlatNumberAsc after resolving the floor. Migration V3__index_flat_floor_order.sql creates ix_flats_floor_flat_number(floor_id, flat_number) to support the floor filter and flat-number order. On a cache miss, PostgreSQL still executes SQL and still benefits from appropriate query design/indexing.

Other query paths use projections, fetch joins, paging, and cursor/keyset logic. The SQL optimization guide notes that these are implemented choices, but saved PostgreSQL EXPLAIN ANALYZE outputs or automatic query-plan regression checks are not in the repository. Do not claim measured plan improvement without collecting actual plan and workload data.

Important sequence: use SQL shape, indexes, bounds, and execution-plan evidence to make each database read efficient. Then ask whether the same optimized result is requested often enough to justify caching it.
Step 6 | Why query and index tuning comes first

Fix unnecessary work before avoiding the work

1. Find slow pathTrace endpoint to SQL
2. Inspect planEXPLAIN (ANALYZE, BUFFERS)
3. Improve query/indexReduce rows, sort, or scans
4. Measure againUse representative data
5. Cache if neededOnly repeated result still costly

A poor query hidden by a cache is still poor on cache miss, after expiry, after invalidation, during Redis bypass, or under cold start. Query/index improvements benefit every execution. Caching is an additional choice when the same result is requested repeatedly and data freshness can be bounded.

For example, the floor/flat composite index helps the uncached path. Redis can skip that query on a hit. These are complementary optimizations, not alternatives.

Step 7 | What the project does not enable

No Hibernate query cache configuration found

Repository inspection did not find settings such as hibernate.cache.use_query_cache, query-cache hints, or a Hibernate query-cache provider configuration. JPA uses ddl-auto: validate and disables Open Session in View, but neither setting enables query caching.

The project has Spring Cache and Redis dependencies and custom SocietyCacheConfiguration. It declares selected application caches, serializers, TTLs, versioned key prefix, metrics, lock handling, and error handling. Therefore the accurate status is:

  • Selected application-level query result caching: implemented.
  • Hibernate query cache / global database query result cache: not configured.
  • Saved real execution-plan evidence/automatic plan checks: not checked in.
Step 8 | Decide whether more caching is worthwhile

Evidence checklist

  1. Identify the exact SQL and endpoint from traces/logs.
  2. Check current indexes and use EXPLAIN (ANALYZE, BUFFERS) against representative, safe data.
  3. Fix query shape/index/pagination first; compare before/after plans and timing.
  4. Measure repeated calls, Redis hit/miss ratio, cache lookup latency, DB query duration, and endpoint latency.
  5. Confirm the key captures every filter, sort, page, tenant, and authorization dimension that changes the result.
  6. Document acceptable staleness and all write paths that must invalidate the result.
  7. Add caching only if repeated DB work remains material and the benefit exceeds Redis, invalidation, and serialization costs.

Existing metrics include society.cache.lookups, society.cache.lookup, society.reference.database.loads, and society.reference.database.load. They help evaluate the current app cache, but do not substitute for an execution plan or prove a new cache layer will help.

Step 9 | Understand the tradeoffs

Every cached result needs a correctness plan

  • Stale results can be returned until eviction or TTL expiry.
  • Many query variants create many keys and memory pressure.
  • Page/search/cursor results have high key cardinality and low reuse unless measured otherwise.
  • Caller-specific results require identity-safe keys and must not leak between users.
  • Redis failures and cold caches send work back to PostgreSQL; fallback capacity matters.
  • Hibernate query caching can add invalidation and entity/query cache coordination; enabling it globally is not a safe shortcut.

The existing Society write paths evict selected Redis entries after changes. Direct SQL writes outside those paths are not automatically known to the cache and can leave old values until TTL.

Step 10 | Explain it in an interview

Developer-level answer

“We distinguish database buffer caching, Hibernate query caching, and application result caching. In this project Hibernate's query cache is not configured. Society Service does use Spring Cache backed by Redis for selected repeatable floor and flat reads. On a Redis hit, the cached DTO/list is returned and the repository query is skipped; on a miss, the service runs its indexed query and fills Redis with a TTL. Flat and floor writes invalidate related cache entries. Before considering more query caching, I inspect generated SQL and PostgreSQL execution plans, tune indexes/query shape, and measure repeated reads, DB time, cache time, and endpoint latency. The repository has query optimizations and indexes but no saved EXPLAIN ANALYZE benchmark, so I would not claim measured speedup or enable Hibernate query cache globally without evidence.”

Likely follow-ups

Is @Cacheable Hibernate query caching?

No. It caches the method's returned value through Spring Cache. Hibernate's own query cache is a different feature and is not configured here.

Does an index make query caching unnecessary?

No. An index makes each database execution cheaper; a cache can skip repeated executions. Measure whether both are useful.

Why tune SQL before caching?

A cache miss still executes the query. A better query helps every miss and avoids masking a bottleneck.

What invalidates a cached query result?

In this project, write paths evict known affected Redis entries after commit; TTL is a backup. External database writes may not trigger that eviction.

Would you enable Hibernate query cache globally?

No. First identify a measured repeated query, verify its plan, check cacheability and invalidation correctness, then benchmark a targeted approach.
