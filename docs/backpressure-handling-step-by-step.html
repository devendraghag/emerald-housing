1. Learn the basics first

Backpressure is how a system prevents a faster producer from overwhelming a slower consumer. In a push stream, the consumer can signal how much work it is ready to receive. In Kafka, consumers pull records with poll(); records not yet committed remain in Kafka, so lag acts as the backlog signal.

Backpressure is different from dropping data. A safe design slows or bounds intake while preserving work in a durable queue. Here, PostgreSQL outbox tables preserve events before Kafka, Kafka stores published events, and the consumer group advances offsets as records complete.

What was already present: durable outbox tables, 50-row publisher batches, Kafka consumer groups, record-level acknowledgement, single-partition topics, consumer lag measurement, and Gateway rate limiting. The Member Service had no explicit cap on records returned in one Kafka poll. This task adds a configurable cap of 25 records per poll.

If processing is slow, the listener stops making progress at its own rate and Kafka retains the remaining records. The lag gauge lets operators see the gap.

4. Follow what happens when consumers fall behind

Step 1 — event intent is persisted

The business operation commits its domain change and an outbox row together. If Kafka is unavailable or slow, the database outbox remains the durable publication backlog.

Step 2 — publisher work is bounded

Each publisher claims at most 50 rows, sends those records, and waits for acknowledgements before deleting rows. Failures release the row for a later poll. This bounds each dispatch batch, while retries and Kafka producer buffers remain additional limits.

Step 3 — Kafka holds published work

Each event topic has one partition. Kafka stores records until its retention policy removes them; the consumer group’s committed offsets indicate progress.

Step 4 — listener asks for a bounded poll batch

The Member Service Kafka consumer now caps a poll at 25 records by default. One partition and listener concurrency one mean one active consumer per flow in the current design.

Step 5 — records are processed and acknowledged

Auto-commit is disabled and acknowledgement mode is record. The listener performs database work transactionally; completed records are acknowledged through the container. A failed record follows the configured retry/error-handler path rather than being silently discarded.

Step 6 — lag reveals whether intake exceeds service rate

If records arrive faster than the listener completes them, committed offsets advance more slowly than the log end offsets. Lag rises. Lowering the poll cap bounds each delivery batch but does not increase processing capacity; use lag and database health to choose a safe value.

6. Observe pressure and tune from evidence

The existing observability path exposes kafka.consumer.lag by group/topic, kafka.messages.consumed by flow, publisher sent/failed counters, and outbox waiting depth. Grafana shows lag beside consumed rate. Compare trends across multiple samples rather than reacting to one poll.

  • Lag rising, database healthy, consumer rate below input: inspect per-record processing time and consider a measured increase to poll size or partition count, with a load test.
  • Lag rising with high DB latency or pool saturation: increasing the poll cap may create a larger burst of DB work; reduce pressure or improve the database/listener path first.
  • Outbox depth rising but Kafka lag is low: investigate publisher/broker delivery rather than consumer capacity.
  • Failures/DLT increasing: address poison events or dependency/database errors; a larger poll does not fix failures.
  • Lag steady or falling: the consumer is keeping up or draining a backlog over that interval.

The Gateway’s Redis rate limit protects ingress at the HTTP edge. It is a separate control from Kafka consumer polling and should not be presented as Kafka backpressure.

7. Operational steps

  1. Identify the affected group/topic from the lag metric and Grafana panel.
  2. Compare lag slope with the event send and consume rates; inspect outbox waiting depth to locate whether pressure is before or after Kafka.
  3. Check the relevant listener logs, DLT rate, Member Service CPU, PostgreSQL query latency, connection pool pressure, and active pod count.
  4. If records are safe and the database has headroom, adjust KAFKA_CONSUMER_MAX_POLL_RECORDS gradually and test representative bursts. Keep the value bounded.
  5. If sustained lag remains and a single partition is the throughput ceiling, review partition scaling separately; increasing consumer concurrency above partition count is ineffective.
  6. After each change, validate lag recovery, consumed throughput, database resources, and notification correctness. Roll back if downstream pressure rises without a throughput improvement.

Consumer handlers process records sequentially within each listener container. If processing a returned poll batch takes longer than Kafka’s max.poll.interval.ms, the group may rebalance. That setting is not overridden here; measure worst-case poll-batch processing time before substantially increasing the cap.

8. Guarantees and limitations

  • The poll cap bounds record count per poll, not total bytes, total lag, or end-to-end work in every internal layer.
  • Kafka is the durable queue for published records; lag can grow until consumer capacity recovers, but retention eventually limits how long records remain available.
  • There is no adaptive pause/resume controller, automatic concurrency scaling, lag-triggered autoscaler, or global token bucket for consumers.
  • The current 25-record default is a conservative starting point and has not been load-tested against production event distributions.
  • One partition and concurrency one limit active consumer parallelism per group. A larger poll batch can smooth work but cannot make one listener process records faster.
  • Outbox batch size 50 and Kafka producer batching are separate producer-side bounds.
  • Retries/DLT, consumer deduplication, and outbox leases preserve reliability but do not guarantee exactly-once delivery.

9. Verification performed

A focused Member Service test loads application.yml with Spring’s YAML property loader and asserts that the consumer poll cap is present with its environment-variable override. The test passed. This validates the checked-in configuration shape.

No broker saturation or load test was run. The existing lag-calculation tests validate offset math, not actual consumer throughput, pause behavior, or a production backpressure threshold.

10. Interview preparation

60-second explanation

“Backpressure is how we avoid letting producers overwhelm consumers while preserving work. Our events are durable in PostgreSQL outboxes and then Kafka. The consumers pull records and commit progress record by record; lag is the backlog signal. I added an environment-configurable max.poll.records cap of 25 so one poll cannot hand an arbitrarily large batch to the Member Service listeners. The existing topics have one partition and concurrency one, so the listener processes serially and Kafka holds the remaining records. We tune the cap from lag, consume rate, and database headroom; it bounds delivery bursts but does not increase processing capacity or provide automatic scaling.”

Likely follow-upAnswer
Does a poll cap drop messages?No. It limits how many records are returned in one poll. Unconsumed records remain in Kafka until consumed or expired by retention.
Is 25 a proven optimal value?No. It is a configurable starting bound. We need representative load tests and observed lag/DB capacity to tune it.
Why not increase listener concurrency?Each flow topic has one partition. A group cannot actively assign one partition to multiple consumers, so extra concurrency would not increase useful parallelism.
What if the consumer is slower than event arrival?Lag rises in Kafka. We inspect processing latency, failures, and database health, then either reduce pressure, improve processing, or scale partitions/consumers when measurements justify it.
How is this different from a reactive backpressure operator?Kafka is a pull-based durable log with consumer offsets and lag. Reactive Streams communicates demand between publishers and subscribers in-process. They are related flow-control ideas but not the same mechanism.
What can fail after increasing the cap?More records may be in flight per poll, increasing memory and DB burst size; batch processing time can approach max.poll.interval.ms, causing a rebalance.
