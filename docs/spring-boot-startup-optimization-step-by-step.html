Spring Boot startup, from zero

Learn what “startup time” means, follow what each service does before it becomes Ready, and see which delays the repository already tolerates. Startup optimization is optional: this guide shows how to measure it first and why no speculative lazy-loading or initialization change was made.

1. Learn the startup terms first

Process start is when the container launches the Java process. Application startup includes Spring configuration, dependency and bean creation, database migrations, optional initialization work, and web-server startup. Ready time is when Kubernetes considers a Pod ready to receive Service traffic.

Those times are different. A JVM can be running while Spring is still building beans; the HTTP server can answer a health check while an application runner is still executing; and a Pod can remain unready while a dependency health check fails.

Startup optimization reduces a measured delay without breaking required initialization, migrations, cache behavior, readiness guarantees, or the first user request. It is not the same as merely allowing a slower startup probe to pass.

Start with the operational question: Are rollouts, autoscaling, crash recovery, or deployments too slow because a Pod takes too long to become Ready? If not, speculative startup changes can add complexity without solving a problem.

Member Service

Spring starts the MVC service, configures databases and Flyway, and creates beans. The Kubernetes startup probe waits on the liveness endpoint. Readiness additionally requires Spring readiness state, database, and Redis health. The probe allowance is long enough to tolerate a slower first boot; it does not tell us the actual boot duration.

Society Service

Flyway and bean initialization run, then SocietyCacheWarmup runs as an ApplicationRunner. It attempts to read floors and store them in cache. If Redis/database access throws the handled exceptions, it records a failed warm-up, logs a warning, and continues so floors can load on demand. Readiness checks application state and database.

AI Service

The FAQ catalog is loaded as a bean. The vector-store bean builds an in-memory SimpleVectorStore and adds catalog documents using the embedding model. The embedding/index call can affect startup. The caught indexing failure logs a warning and leaves an empty store; FAQ retrieval then remains unavailable until a restart after the provider recovers. AI readiness checks only Spring readiness state, not the provider or FAQ index.

API Gateway

The reactive Gateway starts its WebFlux server and connects its Redis-backed session/rate-limit behavior. Kubernetes readiness includes Spring readiness state and Redis health. There is no database migration or startup runner shown in the inspected Gateway configuration.

The approximate tolerance is based on periodSeconds × failureThreshold; actual timing depends on probe scheduling and when the container starts. A startup probe protects a slow-starting process from premature liveness restarts. Readiness controls whether a Pod receives Service traffic; it is a separate signal.

All four app configurations expose Actuator health. The services use graceful shutdown settings too, but shutdown behavior is distinct from startup optimization.

5. Measure the baseline before changing startup

  1. Define the interval: container process start to first successful startup probe, or Pod creation to Ready. Use one definition consistently.
  2. Capture repeated cold starts using the same image, node/resource conditions, database state, Redis state, and configuration.
  3. Record Pod creation/start times, readiness transition, restart count, startup probe failures, and application log timestamps (including Spring's final “Started …” line).
  4. Compare services and runs. Separate fixed JVM/Spring initialization from Flyway migration duration, cache warm-up, and AI embedding-provider latency.
  5. Use the existing JFR capture workflow if a JVM startup profile is useful. It restarts the target Deployment and records from JVM startup; handle its operational impact and artifact security.
  6. Only pursue optimization if startup time is affecting rollout availability, scale-out response, recovery objectives, or developer workflow.

The repository's Prometheus scrape interval is 15 seconds and application readiness probe configuration is not a high-resolution startup tracing system. Do not infer exact startup durations from coarse scrape samples alone.

7. Operate during rollouts and restarts

  1. Inspect rollout status and Pod events to tell slow initialization from probe failure, dependency unavailability, image pull, or crash loop.
  2. Read application logs from the same Pod and correlate the last completed startup task with readiness.
  3. Check whether a failed startup probe restarts the process or a readiness dependency merely keeps it out of service.
  4. For Society warm-up, look for the warm-up outcome metric and warning log; the code can skip the warm-up and continue.
  5. For AI, check the FAQ indexing warning and whether the embedding provider is reachable. A healthy readiness endpoint does not prove FAQ retrieval is available.
  6. Record measured timings before changing startup behavior or probe budgets.
Key distinction: `startupProbe` decides when liveness/readiness probing may begin; readiness decides whether Kubernetes sends traffic; liveness decides whether Kubernetes restarts a stuck process. They are not interchangeable optimization switches.

8. Limits and risks

  • No startup timing benchmark, cold-start baseline, or user-facing startup objective was found.
  • No explicit lazy initialization, AOT/CDS, or native-image configuration is present.
  • Probe windows are configured tolerance, not measurement results or a performance target.
  • Society cache warm-up and AI FAQ indexing are startup-time work with different failure behavior.
  • AI readiness does not check external provider availability or index completeness.
  • JFR recording at startup provides JVM events but does not directly assign all wall time to Spring bean phases.
  • Optimizations can defer work to first requests or weaken readiness if dependency checks are removed.

10. Interview preparation

Developer-level explanation

60-second answer: “The app images launch Java 21 with the normal Spring Boot eager bean initialization path. Member and Society run Flyway migrations at startup; Society also has an ApplicationRunner that warms the floor cache and can skip that warm-up on handled Redis/database errors. AI creates its in-memory FAQ vector store and calls the embedding model during bean initialization; if indexing fails, the service starts with an empty FAQ index. Kubernetes startup probes allow roughly 120 seconds for Gateway, 180 seconds for Member/Society, and 300 seconds for AI, while readiness checks differ by service. We found no startup timing baseline or lazy/AOT optimization. I would measure process-to-Ready time and each initialization step first, then optimize only the demonstrated bottleneck while preserving migration and readiness correctness.”

Likely follow-up questions

Does a long startup probe mean startup is slow?

No. It sets how long Kubernetes tolerates failed startup checks before restarting the container. It does not report the actual time needed to become ready.

Why not enable lazy initialization everywhere?

It can reduce startup work but shifts bean creation and failures to the first request. That can worsen first-request latency and make readiness less representative.

What startup work is service-specific here?

Flyway migrations run for Member and Society; Society warms a cache through an ApplicationRunner; AI indexes a fixed FAQ catalog with provider embeddings during bean creation.

Can AI be Ready while FAQ retrieval is unavailable?

Yes. Its readiness group checks Spring readiness state only. The code catches indexing errors and allows the app to start with an empty vector store.

How do you prove an optimization worked?

Repeat the same cold-start conditions and compare Pod creation-to-Ready and process-to-Ready timings, then verify first-request latency, dependency checks, migrations, and steady-state behavior.

What is the difference between readiness and liveness?

Readiness controls traffic eligibility. Liveness tells Kubernetes whether to restart a process. Startup probes delay those checks until startup has had time to complete.
