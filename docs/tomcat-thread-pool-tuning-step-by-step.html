1. Learn Tomcat terms first

Embedded Tomcat accepts HTTP connections and assigns servlet request work to worker threads. A request worker can be occupied while application code runs or waits on a database, remote HTTP service, lock, or other blocking call.

  • Maximum worker threads bounds the number of request tasks Tomcat can process concurrently.
  • Maximum connections limits the number of open connections the connector manages; it is not the worker count.
  • Accept count controls the incoming connection backlog when the server cannot accept/process work immediately. It can smooth a short burst, but a large backlog can turn overload into long waits.

These limits interact with database pools, downstream bulkheads, CPU, memory, and replicas. More request workers can increase the number of requests waiting for a smaller database pool without improving useful throughput.

Do not apply Tomcat properties to a reactive server. The API Gateway uses WebFlux/Reactor Netty; it does not use Tomcat's servlet request-worker pool.

6. Change the right property only after evidence

  1. If Member workers are saturated and downstreams have headroom: test a small change to MEMBER_HTTP_MAX_THREADS in a controlled environment. Keep the 500 connection and 50 accept-count limits in view.
  2. If Society workers are the measured bottleneck: there is no project-specific worker environment variable today. Configure server.tomcat.threads.max (or its Spring Boot environment equivalent) for that workload, record the value, and test it before rollout.
  3. If AI is the measured bottleneck: first collect its own evidence; it currently relies on embedded-server defaults and has different resource limits and downstream behavior.
  4. If connection/backlog saturates: evaluate connection and accept settings independently from worker threads.
  5. If DB or Society capacity saturates: tune that dependency or reduce admitted load; increasing Tomcat threads is not the fix.

Change one setting at a time. Compare throughput, p99 latency, errors, server queue/wait metrics, CPU, memory, DB pool wait, and downstream rejections. Keep a rollback value and confirm the effective runtime setting after deployment.

Replicas multiply local capacity. A Member limit of 100 workers per pod can represent up to 200 configured workers at two replicas or 300 at three replicas. That is only a theoretical sum; it does not mean the database or Society service can sustain that concurrency.

7. Run a controlled exercise

  1. Select one MVC service and non-production environment. Confirm the active Kubernetes context, current replica count, image, CPU/memory limits, and DB pool sizes.
  2. Prepare the representative request mix and load generator. Set a safe maximum concurrency and stop condition before starting.
  3. Record a no-change baseline: effective Tomcat settings, throughput, latency percentiles, errors, CPU throttling, memory, thread/connection metrics, DB pool occupancy, and dependency signals.
  4. Ramp load gradually. Observe whether busy threads approach the cap before latency rises, and whether work is waiting on DB/downstream pools.
  5. Change one tested boundary. Repeat the same scenario with the same data and warm-up.
  6. Stop load and verify queues drain, latency recovers, and the service remains healthy. Record the result and rollback procedure.

  • Only Member has an explicit maximum worker-thread value; Society and AI use server defaults.
  • Society and Member have explicit connection/backlog values; AI does not.
  • Gateway is reactive and needs event-loop diagnosis, not Tomcat worker settings.
  • Actuator endpoint exposure does not guarantee every Tomcat metric is available or Prometheus is currently scraping it.
  • There is no dedicated Tomcat thread-pool Grafana panel in the inspected dashboard configuration.
  • Static YAML values do not prove the live Pod's effective settings; verify runtime configuration after deployment.
  • Increasing workers can amplify DB contention, downstream calls, memory use, and context-switching overhead.

10. Interview preparation

Developer-level explanation

60-second answer: “Member, Society, and AI use Spring MVC with embedded Tomcat; Gateway uses reactive WebFlux/Reactor Netty. Member explicitly sets a 100-worker maximum, 500 connections, and a 50-request accept backlog. Society sets 500 connections and a 50 backlog but leaves worker sizing to Tomcat's default; AI also uses defaults. Those settings are not yet validated by a representative load test. I would measure busy workers, backlog, request tail latency, DB pool waits, downstream bulkhead/retries, CPU, and memory, then change one boundary and repeat the same workload. Increasing the worker cap is useful only if workers are truly the constraint and dependencies have capacity.”

Likely follow-up questions

Are max threads and max connections the same?

No. Worker threads run servlet requests; max connections limits managed sockets. The server can have connections that are not actively consuming a worker at that moment.

What does accept-count do?

It bounds incoming connection requests waiting when the server cannot accept/process them immediately. It trades short burst absorption against queueing delay.

Why doesn't the Gateway use these Tomcat settings?

Its build uses Spring Cloud Gateway WebFlux and a reactive server. Its execution resource is the Reactor Netty event-loop model.

What would make you increase Member's max threads?

Load evidence that Tomcat workers are saturated while CPU and downstream pools have headroom, followed by a controlled test showing improved useful throughput or tail latency without excess memory or errors.

Why could more workers make things worse?

They may all wait for a smaller DB pool or downstream service, multiplying in-flight work, memory use, and contention without increasing the constrained dependency's throughput.

Does this repository prove the default thread number for Society?

No project setting specifies it. The framework/server default applies, and the live effective value should be checked from runtime configuration/metrics rather than inferred as a project-tuned value.
