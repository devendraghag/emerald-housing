Step 1 | Understand asynchronous work

What changes when work becomes asynchronous?

In synchronous processing, a caller waits for the work to finish before receiving a response. In asynchronous processing, the caller records or publishes work and a separate worker completes it later. This can shorten the request path and decouple work rates, but the result is eventually consistent and failures need durable recovery.

In Emerald Housing, the HTTP request still performs and commits its business database update. The notification fan-out is deferred. The caller does not wait for every recipient notification row to be written.

The response means the main business change and its event-to-be-published were saved. It does not mean every consumer has already created its notification rows.
Step 2 | Learn the parts

Event, broker, consumer, and outbox

  • Event: a fact that a business action occurred, such as a notice being published.
  • Producer: publishes the event to Kafka.
  • Topic: named stream that stores events for consumers.
  • Consumer group: one logical subscriber identity; Kafka distributes topic partitions among group members.
  • Outbox: database table written in the same transaction as business data, so the event record is not lost if Kafka is temporarily unavailable.
  • Idempotent consumer: records processed event IDs so a duplicate delivery does not repeat database effects.
  • Dead-letter topic (DLT): stores a record after configured listener retries fail.

Kafka delivery and database commits are not one atomic transaction here. The outbox and deduplication table make recovery safe with at-least-once delivery.

Step 3 | Identify what is asynchronous

Two event flows, both for in-app notifications

Community noticePublished status creates an outbox event; consumer fans out notice notifications.
Lost and FoundPublish, resolve, claim, or qualifying reassignment creates an outbox event; consumer fans out in-app notifications.

Both producers and consumers are in Member Service. Kafka carries event envelopes; listeners query current members/roles/memberships to determine recipients and store notification rows in PostgreSQL.

This is not an email, SMS, WebSocket, or push-notification pipeline. It is not a general job queue for all business operations. The Kafka events describe domain actions; consumers derive recipient rows.

Step 4 | Understand the transactional outbox

Commit business state and pending event together

A naive flow could update PostgreSQL and then send directly to Kafka. If the database commit succeeds but Kafka is down, the business change exists with no event. If the event is sent first and the database rolls back, consumers may observe an action that never committed.

Here the service changes the business row and calls its publisher's publish(event), which inserts an outbox row. Both execute within the business database transaction. A rollback removes both; a successful commit leaves both business state and pending event durable.

HTTP request
  -> update notice/report state
  -> INSERT event row into matching outbox table
  -> database transaction commits
  -> HTTP response can complete
  ... later ...
  -> scheduled dispatcher publishes event to Kafka

Community notices enqueue an event when a notice changes to PUBLISHED. Lost-and-found enqueues on relevant workflow transitions such as publication, resolution, claim submission, and qualifying flat reassignment for published reports.

Step 5 | Follow the scheduled publisher

Durable rows are dispatched in batches

@EnableScheduling is enabled in Member Service. Each publisher has a scheduled dispatcher, polling every 1 second by default. It claims up to 50 unclaimed or expired-claim rows using PostgreSQL FOR UPDATE SKIP LOCKED, assigns a claim token and 180-second lease, then processes the batch.

For each event, the dispatcher serializes the envelope and calls KafkaTemplate.send(...).get(). That waits for the broker send result in the scheduled worker. On success it deletes the outbox row using the event ID and claim token. On failure it increments attempts and clears the claim so a later poll can retry.

Multiple Member Service replicas can poll safely because SKIP LOCKED and claim tokens prevent them from intentionally taking the same live row. There is no maximum outbox attempt count or exponential retry delay in the shown dispatcher; failures become eligible for the next scheduled poll.

The HTTP request path is decoupled from Kafka delivery. The background dispatcher itself does synchronously wait for each send result, one event at a time within the batch.
Step 6 | Trace consumer work

Listener stores notification rows transactionally

The @KafkaListener methods consume the JSON event payloads in separate groups: community-notice-notifications and lost-found-notifications. Each listener begins a database transaction and first inserts (flow,event_id) into kafka_processed_events with ON CONFLICT DO NOTHING.

If the key already exists, the listener counts a duplicate and returns. Otherwise it selects eligible enabled administrators/residents based on event type, notice audience/report flat, active membership, and actor exclusion rules, then inserts notification rows. Notification primary keys and ON CONFLICT DO NOTHING provide further duplicate protection. The processed-event row and notification writes commit together.

If the listener throws before commit, the database transaction rolls back and Spring Kafka's error handler retries delivery. If the database commits but the offset is not committed before a crash, Kafka may redeliver; the processed-event key prevents repeating notification effects.

Step 7 | Learn delivery and failure behavior

At-least-once with duplicate protection

  • Producer: Kafka producer uses acks=all, idempotence enabled, up to 10 producer retries, and a 120-second delivery timeout. The publisher waits for send completion before deleting the outbox row.
  • Outbox failure: failed sends retain the row, increment attempts, clear claim, and are retried by later polling.
  • Consumer: auto commit is disabled and listener ack mode is record. A successfully handled record can be acknowledged by the container after listener completion.
  • Listener failure: DefaultErrorHandler uses a fixed 1-second backoff with 2 retries after the first delivery (up to 3 listener executions); then a recoverer publishes to the topic's .DLT.
  • DLT record: retains the original key and JSON value and adds original-topic and error headers. If DLT publishing fails, the recoverer throws instead of silently discarding the record.
  • Duplicate: event ID dedupe makes repeat delivery safe for the notification database effects.

Producer idempotence reduces duplicate broker writes within producer semantics; it does not make a database transaction and Kafka send atomic. The outbox plus consumer dedupe cover that cross-system boundary.

Step 9 | Operate and observe

Check outbox age, failures, and DLTs

Member Service exposes these Kafka signals through Micrometer:

  • kafka.outbox.waiting gauge by flow: number of rows still in each outbox.
  • kafka.messages.sent counter by flow: successful outbox sends.
  • kafka.messages.failed counter by flow/stage: outbox send or consumer-to-DLT failures.
  • kafka.messages.consumed counter by flow: successfully processed unique events.
  • kafka.messages.duplicate counter by flow: consumer duplicate event IDs.

Operationally, inspect outbox backlog and its age, send-failure rate, DLT growth, consumer lag, and notification-row creation. A nonzero outbox gauge can be normal during a short broker interruption; a steadily growing backlog signals a dispatch or broker problem. DLT records require inspection and deliberate replay; docs/kafka-operations.md describes commands and replay guidance.

Step 11 | Know what should stay synchronous

Use asynchronous processing only when the contract allows delay

Good candidates are independent side effects that can complete after the primary state transition, such as notification fan-out, email delivery, audit export, or analytics aggregation. Keep the write and outbox record in one transaction, define the event schema, make consumers idempotent, and decide how operators will replay failures.

Keep work synchronous when the caller needs its result to decide whether the main operation can commit: validation, authorization, inventory/eligibility checks, or data that must appear in the immediate response. In this project, Member calls Society synchronously to validate flat details before membership work; that dependency is not turned into a fire-and-forget Kafka event.

  • Current consumers only create in-app notification rows. No email/SMS/push adapter is implemented in these Kafka flows.
  • There is no schema registry shown; event records carry schemaVersion 1 in their JSON envelope.
  • Outbox retries are unbounded and poll-based; there is no maximum-attempt quarantine or exponential outbox backoff.
  • Topics are declared as one partition and one replica; scaling and broker fault tolerance need a production-specific design.
  • Outbox send uses blocking Future.get() on the scheduler, sequentially within a batch.
  • There is no atomic commit across PostgreSQL and Kafka; delivery is at least once, with event-ID deduplication.
Step 12 | Interview practice

Developer-level explanation

“Member Service uses Kafka for eventual in-app notification fan-out from published community notices and lost-and-found workflow events. The business update and event envelope are stored together in PostgreSQL through an outbox, avoiding a dual-write gap. A scheduled publisher claims rows in batches with SKIP LOCKED, sends them to Kafka, waits for broker acknowledgement, and deletes only the claimed row after success. Separate Kafka listener groups create recipient notification rows transactionally and deduplicate by flow plus event ID. Consumer failures get two fixed one-second retries, then go to a DLT. Producer idempotence, the outbox, and consumer dedupe make the flow resilient to retries, but delivery is at least once, not a distributed exactly-once transaction. The HTTP request waits for its database transaction, not for notification fan-out; the publisher itself blocks on each send in the background. The implementation is used for notification side effects, not synchronous validation.”

Likely follow-up questions

Why use an outbox instead of sending Kafka inside the database transaction?

PostgreSQL and Kafka do not share one atomic transaction here. The outbox row commits with business state, so a later dispatcher can retry a broker failure without losing the event.

Can the same event be delivered twice?

Yes. For example, a process can send successfully and crash before deleting the outbox row. Consumers dedupe with flow and event ID, so notification writes do not repeat.

Is this exactly once?

No cross-system exactly-once guarantee is implemented. It is at-least-once delivery with idempotent database effects.

Does the API response wait for Kafka?

No. It waits for its business database transaction, which includes inserting the outbox row. Scheduled dispatch and recipient notification generation happen later.

What happens after consumer failure?

The listener gets the original delivery plus two retries with one-second fixed backoff. Persistent failure sends the original JSON/key to the corresponding DLT with diagnostic headers.

Why not make flat validation asynchronous?

The membership operation needs the validation result before deciding whether to write. That is part of the synchronous business contract, unlike notification fan-out.

What is a production scaling concern?

Topics currently have one partition and one replica. Consumer parallelism and broker durability are therefore limited; production topology should be sized from throughput and recovery requirements.
