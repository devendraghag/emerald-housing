1. Learn the terms first

A thread pool limits or manages concurrent work using worker threads. A server request worker can block while it waits for a database or downstream HTTP call. A pool that is too small can leave requests waiting; one that is too large can create many blocked threads competing for memory, CPU, database connections, and downstream capacity.

A queue/backlog holds accepted work waiting for a worker. A queue can smooth short bursts, but a long queue raises latency and consumes resources. Connections and request-processing threads are separate limits: an open socket does not necessarily occupy one request worker at every moment.

A reactive event loop uses a small set of threads to advance many nonblocking connections. Blocking an event-loop thread can stall unrelated requests. It is not tuned like a servlet request-worker pool.

Pool sizing is a capacity decision, not a standalone number. Request workers, DB pool size, remote-call bulkheads, CPU/memory limits, and replicas constrain one another. Increasing one cap can simply move the queue downstream.

4. Follow what happens when a pool saturates

  1. Requests arrive at the Gateway. Its reactive event loops progress nonblocking work; slow/blocking work can still consume event-loop capacity if code blocks.
  2. Routed MVC requests reach a service's embedded Tomcat server. Member can assign work to up to its configured maximum request workers; Society/AI use their server defaults.
  3. If all workers are busy, additional connections/work may wait in connection/backlog queues subject to configured limits and server behavior.
  4. A worker may then wait for a DB connection, downstream call, Redis response, or lock. The next resource pool can become the real bottleneck.
  5. In Member-to-Society calls, at most the configured bulkhead concurrency is admitted per process; excess work with zero wait fails fast rather than building a bulkhead wait queue.
  6. When load stops, observe whether worker utilization and queues drain and whether latency returns to its prior range.

6. Tune one boundary at a time

Case A — servlet workers are saturated and dependencies have headroom

Test a small increase in Member's MEMBER_HTTP_MAX_THREADS, or configure the appropriate service's server thread setting if measurement shows its default is the constraint. Re-run the same load and watch DB pool wait, memory, CPU, and p99 latency.

Case B — workers are mostly waiting for the database

Do not simply add request workers. Check query latency and Hikari pool occupancy/size first. More servlet workers can create a larger crowd waiting for the same DB connections.

Case C — outbound Society calls saturate

Inspect bulkhead rejections and remote latency. The current Member bulkhead is 12 concurrent attempts per process with zero wait. Adjust only after testing Society capacity and total replica concurrency; remember retries can create repeated attempts.

Case D — Gateway is saturated

Investigate nonblocking route latency, connection metrics, CPU, and event-loop blocking. Gateway is WebFlux/Reactor Netty; changing Tomcat worker settings will not tune it.

Case E — load exceeds one pod's useful capacity

Evaluate horizontal scaling against measured CPU, memory, and downstream budgets. The checked-in HPAs target 70% average CPU, but scaling out still increases total DB and downstream concurrency.

For each experiment, write down the hypothesis, change only one control, keep a rollback value, and compare throughput, tail latency, errors, queue/rejection counts, dependency waits, CPU, and memory. A larger thread count is not automatically an optimization.

7. Operational walkthrough

  1. Identify which service has rising latency and determine whether it is Gateway, MVC request workers, database wait, or downstream wait.
  2. Confirm current runtime values and replica count. The source manifest is not proof of the effective configuration in a running Pod.
  3. Use a non-production environment and a repeatable load profile with gradual ramp-up and stop conditions.
  4. Capture Actuator/Prometheus metrics, JFR/thread evidence, and load-generator results for each phase.
  5. Change only the measured bottleneck's control. Avoid tuning multiple pool sizes at once.
  6. Stop load and observe recovery. Verify there is no growing backlog, resource leak, restart, or sustained downstream rejection.
  7. Record effective setting, image/version, test parameters, before/after results, and rollback plan.
Capacity relationship to remember: per-pod caps multiply across replicas. For example, a Member bulkhead of 12 per pod means 24 concurrent calls at two replicas and 36 at three replicas. The Society server/DB must tolerate aggregate traffic, not just one pod's local setting.

8. Limits and gaps

  • No representative load result or thread-pool tuning benchmark is checked in.
  • Only Member's Tomcat request-thread maximum is explicit; Society and AI use embedded-server defaults.
  • Gateway event-loop sizing is framework-managed and not explicitly tuned in application config.
  • No dedicated thread-pool Grafana dashboard or checked-in alert for active workers, queue depth, or executor rejection was found.
  • Actuator exposure does not prove that every desired metric is registered or scraped; inspect the running endpoint and target health.
  • Tomcat max connections, accept count, request threads, DB pool size, Kafka listener concurrency, and outbound bulkhead are distinct controls.
  • Virtual threads reduce the cost of waiting threads but do not increase database or remote service capacity.
  • HPA CPU scaling and thread-pool tuning solve different problems; either can amplify load on constrained dependencies if configured without a capacity budget.

10. Interview preparation

Developer-level answer

60-second explanation: “Emerald Housing has different execution models. Member, Society, and AI use Spring MVC/Tomcat; Gateway uses reactive WebFlux/Reactor Netty. Member explicitly caps Tomcat workers at 100, connections at 500, and accept backlog at 50. Society caps connections and backlog at 500/50 but leaves worker count to the server default; AI also uses defaults. Member's outgoing Society client uses a dedicated virtual-thread-per-task executor, while a Resilience4j bulkhead limits concurrent calls to 12 per process with zero wait. These are separate boundaries from Hikari pools, Kafka concurrency, and the Gateway event loop. I tune from a controlled load test by observing busy workers, backlog, tail latency, dependency waits, CPU, memory, and rejections. There are no checked-in load results or thread-pool dashboard panels, so I would not claim the existing values are optimal.”

Likely follow-up questions

Why not set every service to 100 Tomcat threads?

Each service has different CPU, blocking behavior, memory, and dependency capacity. A uniform number is not supported by measurements and can overwhelm a smaller DB pool.

What is the difference between max connections and max threads?

Connections cap sockets accepted/managed by the server. Threads cap request-processing workers. A connection can be open without continuously occupying a worker.

How is Gateway different?

It is reactive WebFlux/Reactor Netty, which uses event loops to progress nonblocking work. Servlet/Tomcat worker settings do not apply to that execution model.

Do virtual threads make the downstream service more scalable?

No. They make waiting tasks cheaper in thread resource terms. The Society service, database pool, bulkhead, and remote limits still constrain useful concurrency.

How can a thread pool be too large?

More workers can consume memory and scheduling overhead, increase contention, and let more requests wait simultaneously for a constrained dependency.

What evidence would justify changing the pool?

Under repeatable load, the relevant pool remains saturated while CPU and dependencies have headroom, and a controlled change improves throughput or tail latency without increasing errors, waits, or resource pressure.
