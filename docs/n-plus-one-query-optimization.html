N+1 query optimization

Step 1 | Learn the basic words

What are an entity and a relationship?

An entity is a Java object mapped to a database table. A relationship connects one entity to another. In Emerald Housing, a flat row has a floor_id and its Java entity has a relationship to the floor entity.

  • Lazy loading: related data is not loaded until code asks for it.
  • Query: one request from the application to the database.
  • N+1: one query loads a list, then another query is made for each list item to load its related data.
  • Fetch join: ask the database for the main entity and its related entity together in one query.
  • DTO projection: ask the query to construct response data directly, often selecting the related value in the same query.
Analogy: you ask a librarian for 20 flat records, then walk back to the desk 20 separate times to ask which floor each flat is on. N+1 is those repeated trips.
Step 2 | Understand the performance issue

Why the name N+1?

If the first query loads N flats and the code then reads each flat's lazy floor, the database may execute one floor lookup per flat. With 20 flats:

Query 1Load the 20 flats
Queries 2-21Load one floor for each flat
Total1 + 20 = 21 queries

The query count grows with returned rows. If several flats share a floor, ORM/session caching may change the exact count; repeated relationship access is still a signal to inspect.

Important: lazy loading is not automatically bad. It can save work when related data is not needed. The problem is repeatedly using lazy relationships while building a collection response.
Step 3 | Identify the real relationship

Flat to floor is the relevant example

FlatEntity maps the flats table. Its floor property is a @ManyToOne(fetch = FetchType.LAZY) association. The floor number is included in FlatResponse.

FlatEntity flat
  -> flat.getFloor().getFloorNumber()
  -> FlatResponse.floorNumber

If a list query loaded only FlatEntity and the mapper called getFloor() once per flat, that list could cause N+1 queries. The repository code already fetches floor in the page and cursor directory queries.

Finding: N+1 prevention is already present for the principal flat directory page, filtered page, and cursor flows. This guide explains the existing behavior instead of adding a duplicate fix.
Step 4 | Trace an actual request

Example: GET the flat directory page

GET /api/v1/flats/page?page=0&size=20
1. ControllerFlatController.page reads page, size, sort, and filters
2. ServiceFlatService.searchPage validates and delegates
3. Query layerDirectoryQueries.page builds a Criteria query
4. DatabaseContent query includes each flat's floor
5. MapperReads floor number and builds response

The response mapper calls flat.getFloor().getFloorNumber(). The floor is fetched with the content query, so this access does not need one extra select per flat. Page metadata uses a separate count query; that one additional query is not N+1 because it does not repeat for each result row.

Step 5 | See how the project avoids it

Fetch floor with the flats

In services/society-service/src/main/java/com/emerald/society/api/DirectoryQueries.java, both page and cursor queries include:

root.fetch("floor", JoinType.INNER);

This tells JPA that each returned FlatEntity needs its floor too. Hibernate can generate a join query so floor data is available before the response mapper reads it.

Without fetchSelect flats, then lazy floor query per flat
With fetchSelect flats joined to floors
MappingRead floorNumber without extra per-row selects

The page content query and page count query have different purposes. The count query only counts matching flats and does not need to fetch floor entities.

Conceptual SQL shape

SELECT flat columns, floor columns
FROM flats flat
JOIN floors floor ON floor.id = flat.floor_id
WHERE filters...
ORDER BY ...
LIMIT ... OFFSET ...

This illustrates the idea. Hibernate creates the actual database-specific SQL from JPA Criteria; the project does not hard-code this exact SQL for that endpoint.

Step 7 | Understand configuration and operation

Catch accidental lazy access

The society service has spring.jpa.open-in-view: false. Web response serialization therefore should not silently trigger lazy database loads after service work. SQL logging is controlled by JPA_SHOW_SQL and defaults to false.

  • For local diagnosis, enable SQL logging through the project's normal environment configuration.
  • Request a page with several flats; check that the content query joins floors and there are no repeated floor selects.
  • For a reliable count, use Hibernate statistics, a datasource query counter, or database tracing in a test environment.
  • Avoid verbose SQL logging by default in production; it is noisy and can expose query parameters.
Expected page pattern: one content query with a floor join plus one count query, rather than one extra floor query per flat.
Step 8 | Verify it yourself

How to prove query count behavior

  1. Use a database with several flats, ideally with more than one flat on a floor.
  2. Reset a query counter before calling /api/v1/flats/page.
  3. Call the endpoint and count SQL statements for the request.
  4. Confirm the content query includes the floor join and query count does not grow by one per returned flat.
  5. Check the response contains the correct floorNumber for every flat.
  6. Repeat for cursor and filtered page routes.

Repository inspection confirms the fetch in relevant criteria queries. I found no dedicated query-count assertion in the inspected tests, so measurement is a useful verification step rather than a claim that this guide added such a test.

Step 9 | Understand the limits

What fetch joining does and does not solve

  • The fetch is for the floor relationship required by the flat response. It does not eagerly load every association.
  • Fetching multiple to-many collections can multiply result rows and complicate pagination. Fetch only the data the response needs.
  • The page content query and count query are separate by design; two queries for a page are not an N+1.
  • If a future response accesses another lazy association per item, inspect it and add a targeted fetch or DTO projection.
  • Actual SQL count and query plans should be measured with realistic data; code inspection is not a latency benchmark.
Step 10 | Interview practice

Developer-level explanation

"I inspected the JPA relationships and collection response mappings. FlatEntity has a lazy many-to-one relationship to FloorEntity, and FlatResponse includes the floor number. That could cause N+1 if each flat separately loaded its floor. In the directory query path, DirectoryQueries fetches floor in both page and cursor queries, so the response mapper can read it without a per-flat query. The unpaged list uses a DTO query joining floor, and the by-floor list loads the floor once and reuses its number. The optimization was already implemented for these paths, so I documented it rather than adding duplicate code. I would still use query-count instrumentation to confirm runtime SQL."

Likely follow-up questions

Why is it called N+1?

One query loads the list, then up to N more queries load a related record for each of N results.

What does fetch join change?

It loads the needed floor together with each flat result so mapping does not issue a separate select for each flat.

Is the count query an N+1?

No. It is one additional page-total query, independent of the number of returned rows.

Why disable Open Session in View?

It discourages hidden lazy queries during web response serialization. Required data should be loaded intentionally inside service/query boundaries.

Can fetch joins cause problems?

Multiple to-many fetches can duplicate rows and interfere with pagination. Fetch only what is needed, then inspect generated SQL.
