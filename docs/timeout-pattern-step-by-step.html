Step 1 | Learn the idea

What is a timeout?

A timeout is a limit on how long one operation may wait. It converts a stalled dependency or saturated resource into a bounded failure, so callers can release resources and report an error instead of waiting indefinitely.

  • Connect timeout: maximum time to establish a network connection.
  • Read/response timeout: maximum wait for response data, as defined by that client library.
  • Pool acquisition timeout: maximum wait to borrow a database connection.
  • Transaction timeout: a bound on transaction execution; it is not the same as an HTTP deadline or query timeout.
  • Retry: repeats a failed operation. Every attempt and the delay between attempts consume time.
  • Outer budget: the time available to a request at a layer above its internal operations.
Think of a trip with a total travel allowance. A 3-minute limit for each train connection does not mean the whole trip takes at most 3 minutes; transfers and retries also consume time.
Step 2 | Know the rules before reading settings

Timeout values only make sense in context

  1. Identify which operation the timeout wraps: one socket, one dependency attempt, a database borrow, a transaction, or the full HTTP request.
  2. Find whether retries are inside or outside that timeout. A per-attempt timeout can repeat.
  3. Add retry delays, connection establishment, authentication/session validation, application work, and other downstream calls when estimating an end-to-end path.
  4. Compare that estimate with the caller's timeout. The caller should usually allow enough time for the inner operation to return a useful error.
  5. Separate a designed budget from a measured guarantee. Scheduling pauses, DNS, queueing, cancellation behavior, and proxy semantics can affect elapsed wall time.
Important vocabulary: â€œthe HTTP read timeout is 3 secondsâ€ means a single client request is bounded by that setting. It does not claim that every user-visible request in the whole system has a universal 3-second deadline.

Step 5 | Follow one service-to-service call

Member Service calling Society Service

SocietyRestClientConfig constructs a JDK HttpClient with a configurable connection timeout and a Spring JdkClientHttpRequestFactory with a configurable read timeout. The defaults in Member Service's application.yml are 2 seconds and 3 seconds. Kubernetes' shared app ConfigMap supplies the same values to the Member deployment.

Member business operation
  -> SocietyClient.getFlat(flatId)
  -> decorate operation with CircuitBreaker and Bulkhead
  -> issue GET /api/v1/flats/{flatId}
  -> attach internal service token + correlation ID
  -> RestClient / JDK HTTP transport
       connect timeout: 2s
       read timeout:   3s
  -> parse and validate response
  -> map timeout to SocietyDependencyException 504

SocietyClient handles timeout-shaped transport failures separately from ordinary connection failures: timeouts become a 504 dependency exception with code SOCIETY_SERVICE_TIMEOUT; a non-timeout connection failure becomes 503. The exception handler in Member Service serializes dependency errors for the caller. Society's separate session-validation client also has configurable 2-second connect and 3-second read defaults.

The gateway's own correlation/error filter maps recognized gateway-layer timeout exceptions to HTTP 504 and a safe GATEWAY_TIMEOUT error body. Correlation IDs are propagated so operators can connect logs across services.

Step 6 | Add retry and capacity behavior

Retries multiply time; circuit breakers stop futile calls

SocietyResilienceConfiguration wires three resilience controls for flat lookups and the notice flat directory:

  • Retry: defaults to at most 3 total attempts, with exponential random backoff starting at 200 ms, multiplier 2, jitter 0.2, and configured maximum interval 1 second. Only retryable dependency errors are repeated.
  • Circuit breaker: observes failures and slow calls. It opens after configured thresholds, waits 15 seconds by default, then permits limited probe calls.
  • Bulkhead: allows 12 concurrent downstream operations and has zero wait by default, so excess work fails fast rather than building a queue.

In SocietyClient.executeResilient, retry wraps the circuit-breaker/bulkhead operation. Each retry attempt therefore obtains a fresh breaker evaluation and bulkhead permit. A 503/504 from a transient dependency may be retried; input errors and permanent validation failures are not.

Estimate for a slow dependency: three read-timeout-sized attempts consume about 9 seconds, plus two backoff intervals. If each attempt also reaches the connect timeout before failing, use a deliberately conservative envelope of roughly 15 seconds plus backoff. Either estimate is below the 28-second Gateway response limit; it is an engineering budget calculation, not a real-time SLA.

Step 8 | Walk through end-to-end budget reasoning

Does the synchronous API budget fit?

  1. Start at the public edge. NGINX upstream read/send is 32 seconds.
  2. Look inside at Spring Gateway. Its routed HTTP response timeout is 28 seconds, with a 2-second connect limit. That leaves roughly four seconds between the configured response limit and NGINX's read limit after upstream connection.
  3. Expand Member's downstream work. Society calls have 2-second connect and 3-second read timeouts per attempt. Retry permits at most three attempts and adds bounded delays. A conservative attempt envelope of connect plus read gives 15 seconds across three attempts, before retry delays.
  4. Add other sequential work. Session validation may take up to its own configured connect/read bounds. Normal application processing, database pool wait, query/transaction work, and response serialization also consume time.
  5. Compare sums with the outer limit. The Member-to-Society and session-validation ceilings do not establish the whole budget: the 30-second service transaction default is longer than the Gateway's 28-second routed response timeout. A request can spend time in validation and retries before entering database work, so not every full-path combination is proven to fit.
  6. Check other route types separately. Login credential lookup has a 2-second connect and 3-second response timeout. Direct Society/AI routes have different internal paths and downstream behaviors.
What this proves: the configured nominal timers are ordered so the Gateway's 28-second routed response should expire before the edge's 32-second upstream-read timeout, and the documented Member-to-Society retry envelope by itself is smaller than 28 seconds. What it does not prove: validation + retry + application/database work fits the same 28-second request budget, a global absolute deadline is propagated through every service, a SQL statement is forcibly cancelled at a precise wall-clock instant, or production latency always stays within those limits.
Step 9 | Operate and diagnose

How to interpret a timeout in practice

  1. Capture the HTTP status, error code, route, timestamp, and X-Correlation-ID.
  2. Search Gateway and backend logs using the same correlation ID. Gateway logs include status and durationMs; service logs include correlation and trace identifiers.
  3. Determine which layer ended the wait: edge proxy, Gateway route client, Member's Society client, session validation, Hikari pool, Redis, or transaction manager.
  4. For Society dependency timeouts, inspect emerald.society.flat.lookup.timeouts, lookup duration, resilience4j retry/circuit-breaker/bulkhead metrics, and Member request errors.
  5. Check the dependency's own health and latency before increasing a limit. Longer timeouts can retain request threads/resources and allow queues to grow.
  6. After a dependency recovers, repeat a harmless request and confirm the call succeeds; circuit-breaker state and timeout errors should recover without a pod restart.

Actuator exposes health, metrics, and Prometheus endpoints in the services. Prometheus scrape annotations and observability resources are present in the repository; available dashboards and exact metric names should be checked in the deployed environment.

Step 11 | State the limits accurately

What is and is not implemented

  • Timeouts are configured at several individual boundaries; there is no universal propagated deadline header or single request-budget object.
  • Spring Gateway's 28-second timeout applies to its routed outbound HTTP response path, not every internal route/controller or background job.
  • Member's retry policy allows three attempts. The calculated envelope uses configured values; network runtime behavior and scheduling can add variance.
  • Hikari connection timeout bounds pool acquisition, not SQL execution. Transaction timeouts are manager/resource dependent and do not automatically guarantee database statement cancellation.
  • NGINX's 32-second read/send limits are configured as policies; effective runtime behavior depends on the installed NGINX Gateway API controller and policy attachment status.
  • Focused tests establish client/filter behavior in isolation. They do not establish a live deployment's full-path wall-clock maximum.
  • The AI service has its own provider/network behavior; this guide does not infer a universal AI request timeout from the API Gateway configuration.

Likely follow-up questions

Why should an outer timeout be longer than an inner timeout?

The inner layer needs time to detect the failure and return a meaningful error. If the outer proxy expires first, it may cut off the response and hide the application's controlled error.

Is three attempts the same as three seconds?

No. Each attempt can spend time connecting and reading, and delays occur between attempts. Here the read limit alone can contribute up to about 9 seconds across three attempts.

Does a circuit breaker enforce a request timeout?

No. The HTTP client timeouts bound individual network waits. The breaker tracks failures and slow calls and can reject later calls while open.

What does a bulkhead do?

It caps concurrent calls. With zero wait, excess calls fail fast rather than accumulating in a queue; it does not make an individual call faster.

Does Hikari's connection timeout stop a slow query?

No. It bounds waiting to borrow a pooled connection. Query execution needs its own database or statement timeout if that guarantee is required.

How would you prove a real deployment fits the budget?

Run a controlled delayed-dependency test through the edge, capture elapsed time and correlation IDs at each layer, inspect actual policy attachment and runtime config, and confirm the expected status/error before the outer proxy expires. Repeat for each materially different route and fault type.

Why not set every timeout to the same value?

Different layers wrap different operations. Equal limits can cause outer layers to cut off inner error handling, and a per-attempt limit needs room for retries and backoff.
