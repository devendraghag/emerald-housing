Retry pattern: safe recovery without load storms

Step 1 | Learn the fundamentals

What does a retry do?

A retry repeats an operation after a failure that may be temporary. It can recover from a short network interruption or brief dependency overload without asking the caller to resubmit manually.

But retries create more work. If many callers retry at once, they can add traffic to the same service that is already struggling. A retry policy needs a small attempt limit, selective failure rules, delay between attempts, and a way to cap concurrent downstream work.

Simple example: one request that fails once and then succeeds costs two downstream requests. Three total attempts means up to three times the ordinary work for a single logical call.
Step 2 | Ask whether the operation is safe to repeat

Retry semantics come before retry settings

  • Read-only operation: repeating a GET normally does not create another business record.
  • Idempotent write: repeating the same operation has the same effect as doing it once, often enforced with an idempotency key.
  • Non-idempotent write: a retry may create duplicates or repeat side effects if the first attempt succeeded but its response was lost.
  • Ambiguous outcome: a timeout does not prove the server did no work. The server might have committed and the response might have been lost.

Only retry errors likely to be transient. Do not retry caller mistakes or expected business outcomes. Keep the number of attempts small and include backoff so repeated traffic is spread over time.

A transport timeout on a POST is especially ambiguous: the caller cannot infer whether the server committed. Safe automatic retry needs an idempotency contract or a way to reconcile the result.
Step 3 | Find the retry feature in the project

Two Society Service GET operations are retried

In Member Service, SocietyClient wraps these operations in the same named Resilience4j retry instance:

  • getFlat(UUID) calls Society Service to read flat details.
  • noticeFlatOptions() reads a minimal directory for notice audiences.

Both use HTTP GET, carry the internal service token and correlation ID, and do not ask the retry layer to repeat a write. Other application calls are not automatically retried by this configuration. In particular, do not read this as a global HTTP retry policy.

In this code, safety comes largely from operation semantics: the retried Society calls are reads. The separate idempotency-key path for member creation supports client replay of a write; it is not the Resilience4j retry used by SocietyClient.
Step 4 | Follow each attempt

How one logical lookup becomes physical requests

Business operation calls SocietyClient
  -> Retry checks whether the previous error is retryable
       -> CircuitBreaker admits or rejects this attempt
            -> Bulkhead admits or rejects this attempt
                 -> RestClient issues one HTTP GET
  -> map response or transport error to SocietyDependencyException
  -> on retryable error, wait using configured backoff and try again
  -> stop on success, non-retryable error, open breaker, or final attempt

Retry wraps the breaker, which wraps the bulkhead. A fresh physical attempt therefore gets another breaker and bulkhead decision. The bulkhead permit is held during the attempt and released before the retry delay; waiting in backoff does not hold that permit.

The wrapper is in SocietyClient.executeResilient. The two public lookup methods call it. Error mapping happens inside each physical operation so the retry predicate can make a deliberate decision from the resulting exception.

The settings are injected in SocietyResilienceConfiguration.societyRetryRegistry from Member Service application.yml. Kubernetes supplies matching defaults in kubernetes/config/application-config.yaml. Tune the environment variables there for a deployment override.

Step 6 | Calculate how retries can amplify traffic

Attempt caps reduce, but do not erase, extra load

If every call fails with a retryable error, one logical lookup can issue up to three physical GET requests. A burst of 100 logical lookups could therefore cause up to 300 physical attempts before circuit-breaker and bulkhead effects are considered.

The bulkhead limit is 12 concurrent downstream operations per Member Service process, with zero wait. The Kubernetes Member HPA allows 2 to 3 replicas. That means the configured aggregate concurrent-attempt ceiling is normally up to 36 across three pods; a rolling update can add one surge pod, temporarily allowing up to 48. These are theoretical limits from checked-in deployment settings, not observed traffic.

Backoff jitter helps prevent synchronized retry waves. The breaker eventually stops attempts on a pod after enough qualifying outcomes. Neither feature prevents all amplification: retries are still extra requests before the breaker opens, and each pod learns independently.

Step 7 | Review failure selection and load controls

What retries, and what stops retrying?

The retry predicate accepts only a SocietyDependencyException whose isRetryable() flag is true. In SocietyClient, timeouts and connection failures are marked retryable. Mapped 502/503/504 dependency responses are also considered transient and retryable. Expected 400, 404, and 409 outcomes are not retried. Malformed response parsing and other permanent errors are not marked retryable.

Three neighboring controls complement retries:

  • HTTP timeouts: Member-to-Society connect is 2 seconds and read is 3 seconds per attempt, so an attempt does not wait forever.
  • Circuit breaker: records qualifying failures/slow calls; once open it rejects attempts locally instead of reaching Society.
  • Bulkhead: caps concurrent attempts at 12 per process and fails excess calls immediately.

The code registers retry, breaker, and bulkhead meters through Micrometer. SocietyClient also records lookup-attempt duration and timeout counts. These signals help spot amplification and downstream degradation.

Step 8 | Separate service retries from write idempotency

What protects repeated client requests?

Member creation has an optional Idempotency-Key contract. MemberController forwards the key and actor identity to MemberService.createIdempotent, which stores a request fingerprint and response for replay. A matching repeat can return the prior result; reusing the key with a different payload is rejected.

This is distinct from the SocietyClient retry. The retry wraps only downstream GET calls. The Idempotency-Key handles a client repeating a state-changing member-creation request. It does not cause Resilience4j to replay arbitrary writes, and should not be interpreted as a blanket guarantee for all write endpoints.

For a new automatic retry around a write, first verify the server-side operation supports idempotency and that the key remains stable across attempts. Never infer safety from the fact that a timeout occurred.
Step 9 | Review existing tests

What the tests prove

  • SocietyClientWireMockTest.retriesTransientNoticeDirectoryFailureAndThenSucceeds returns 503 once, then success, and verifies exactly two GET requests.
  • SocietyClientWireMockTest.doesNotRetryPermanentNoticeDirectoryClientError returns 400 and verifies there was exactly one request.
  • SocietyClientResilienceTest builds its retry with maxAttempts(1) to isolate breaker and bulkhead tests from retry behavior.
  • Other client tests verify response mapping, timeouts, and malformed response handling.
Coverage verdict: the repository proves one transient failure can retry and recover, and a permanent client error is not retried. Those tests use the client convenience constructor's test retry policy (three attempts and 1 ms interval), not the production retry bean.

Important coverage gaps

  • No test verifies the production retry property binding or configured jittered backoff.
  • No test verifies the maximum three-attempt count when every attempt fails.
  • No concurrency/load test measures retry amplification under many callers.
  • No test verifies that timeouts and each transient status are all retried exactly as intended.
  • No end-to-end test measures combined retries, breaker, bulkhead, Gateway timeout, and pod replicas.
Step 10 | Measure retry behavior

What operators can observe

TaggedRetryMetrics binds retry meters alongside circuit-breaker and bulkhead meters. Member Service exposes Actuator Prometheus, and the Kubernetes deployment is annotated for Prometheus discovery. Look at retry attempts/successes/errors and compare them with Society request volume, breaker state, bulkhead availability, timeout counter, and lookup-attempt duration. Confirm exact exported metric names and tags from the running /actuator/prometheus endpoint.

Use attempt-level and logical-operation signals together. The custom emerald.society.flat.lookup timer measures each flat lookup attempt, not all retry time as one overall duration. The timeout counter similarly represents timed-out physical flat attempts, not a count of logical requests that eventually failed.

No dedicated retry dashboard or alert was found in the checked-in Grafana configuration. Metrics are registered and scrapes are configured, but teams still need useful queries, panels, thresholds, and runbooks to operate them.
Step 11 | Be clear about limitations

What this retry design does not guarantee

  • At most three attempts bounds one logical invocation; many callers can still each make three attempts.
  • Bulkhead is per process, so total downstream concurrency grows with replicas and rollout surge.
  • Retry backoff is jittered but there is no global retry budget or token bucket that caps total retry traffic over time.
  • Circuit-breaker state is local to each Member pod, so a pod may continue retrying while another pod is open.
  • Only SocietyClient's configured read operations use this retry policy; other clients and writes do not inherit it.
  • The transient classification is application code. When new remote statuses are introduced, maintain the retryable mapping intentionally.
  • Existing tests demonstrate selected outcomes but not production policy binding or behavior under a traffic surge.
Step 12 | Explain it in an interview

Developer-level answer

“Member Service retries only two Society Service GET operations: flat lookup and notice flat directory. The Resilience4j policy allows three total attempts with exponential random backoff, starting at 200 milliseconds, multiplier two, 20 percent jitter, and a one-second interval cap. SocietyClient marks timeouts, connection failures, and selected 502/503/504 dependency failures retryable; 4xx business outcomes and permanent response errors are not retried. Since these are reads, replay does not create duplicate business writes. Retry wraps the circuit breaker and a bulkhead, so each physical attempt gets protection, but one logical call can still create up to three downstream requests. The bulkhead caps 12 concurrent calls per pod, and the HPA allows three replicas, so that is up to 36 active attempts normally at max scale, or 48 with one rollout surge pod. Metrics and tests exist for selected retry paths, but there is no global retry budget, load test, or dedicated retry dashboard. Writes rely on explicit idempotency support where provided.”

Likely follow-up questions

Why retry GET but not arbitrary POST?

GET is expected to be read-only and safe to repeat. A POST may commit before its response is lost, making replay create duplicate effects unless the endpoint enforces idempotency.

What is the maximum retry amplification here?

Three physical attempts per logical invocation. Under a burst, many invocations each reach that maximum, so total traffic can still multiply by three.

How does jitter help?

It varies retry delays so callers that failed together are less likely to all retry at the same instant. It does not lower the maximum attempt count.

Does the bulkhead cap all Member pods together?

No. The limit is instantiated in each process. With three pods at 12 each, the deployment can allow 36 concurrent physical attempts.

What does the circuit breaker add?

It can stop attempts locally after failures or slow calls cross thresholds. It reduces continued traffic after a pod has observed trouble, but it is local to that pod.

How would you improve confidence?

Add tests for production configuration, persistent failure attempt counts, retryable timeout/status cases, and bounded jitter. Then run a controlled concurrent load test while measuring downstream request rate, attempts per logical call, bulkhead rejections, and breaker state.

Does an idempotency key make every retry safe?

No. It protects only endpoints that implement and persist that key correctly, and callers must reuse the same key and payload. It is not a blanket property of every endpoint.
