Chapter 1 - Start here

Learn the idea before the code

A database table stores real records. An index is an extra lookup guide that may help find some records faster.

TableA collection of similar records, such as all flats.
RowOne saved item, such as one flat.
ColumnOne field on each item, such as floor number.
QueryA request asking the database to read or change data.
SchemaThe database blueprint: tables, fields, links, and rules.
IndexA separate guide that points toward matching rows.
Keep this in mind: the table is the source of truth. The index is a shortcut. It can help reading, but it also takes space and must be maintained.

2. Picture it: a filing cabinet

Imagine every flat or member is a paper form in a large cabinet. Without an index, a clerk may open drawers one by one. An index is an alphabetized card catalog: it points to the drawer and position. The forms remain the source of truth; the catalog is a shortcut.
Drawer A
Flats 101 to 120
Drawer B
Flats 201 to 220
Drawer C
Flats 301 to 320
Drawer D
Flats 401 to 420
Drawer E
Flats 501 to 520
Without an index, the clerk checks drawers until finding flat 407.

Yellow drawers were checked; green marks the result. This is a teaching model. PostgreSQL uses page and tree structures, not literal drawers.

3A · Flyway and indexes

Who creates, uses, and maintains an index?

Flyway applies planned database changes. Hibernate maps Java objects to database rows. PostgreSQL chooses whether an index helps a query and maintains that index as rows change.

PartWhat it doesWhat it does not do
FlywayRuns versioned SQL migrations and tracks them in flyway_schema_history.Does not choose an index for each query or run on each API request.
JPA / HibernateMaps entities and repository operations to SQL; this project uses ddl-auto: validate.Does not own production index changes in this project.
PostgreSQL plannerChooses a plan for each query using SQL shape, statistics, and estimated costs.Is not forced to use an available index.
PostgreSQL engineExecutes SQL and maintains index entries when rows are inserted, updated, or deleted.Does not need Flyway to rerun when a row changes.

Create an index through a migration

A first migration might create the table:

-- V1__create_employee_table.sql
CREATE TABLE employee (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255),
    department VARCHAR(100)
);

A later migration adds its index:

Example only: a service needs lookup by email. Put the SQL in that service’s migration folder using its next unused version. The project currently has separate Member and Society migration streams.

-- Example assumes V20 is the next available version; use the service's actual next version.
-- V20__index_employee_email.sql
CREATE INDEX idx_employee_email
    ON employee (email);

Example folder layout:

service/src/main/resources/db/migration/
  V1__create_tables.sql
  V2__add_email_index.sql
  V3__add_department_index.sql

JPA repository method example:

public interface EmployeeRepository
        extends JpaRepository<Employee, Long> {
    List<Employee> findByEmail(String email);
}

Hibernate generates SQL for the method. PostgreSQL decides whether the email index is a useful path.

Commit migration SQL→Build service artifact→Deploy to environment→Flyway applies pending version once→Database records success

On the first run, Flyway applies pending migrations in order and records them. On later starts, successful versions are skipped. Adding an index does not make Flyway run for every query; PostgreSQL can use it for matching queries whenever its planner considers it useful.

What does Flyway remember?

Flyway stores one record per migration in flyway_schema_history. It checks that history at migration time; a migration already recorded as successful is skipped on later starts.

VersionDescriptionSuccessStartup behavior
V1Create employee tabletrueAlready applied; skip
V2Create email indextrueAlready applied; skip
V3Create department indextrueAlready applied; skip
V4New index migrationNot yet recordedPending; apply once
Application starts→Flyway reads history→Runs only pending versions→Records success→Hibernate validates mappings

Example Spring Boot configuration:

spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
spring.flyway.validate-on-migrate=true
spring.jpa.hibernate.ddl-auto=validate

Production hardening note: this example omits Clean; the current Member and Society YAML files set clean-disabled: false. Review that setting before production use and disable Clean in deployed environments.

What about @Table(indexes = ...)?

JPA annotations describe entity mapping metadata. With ddl-auto: validate, Hibernate validates mappings but does not create production indexes. In this project, put index changes in Flyway migrations so they are versioned and reviewed.

4. Check what is present

Flyway migrations define indexes beside schema changes. JPA uses ddl-auto: validate, so Hibernate validates schema compatibility instead of creating or changing indexes at runtime. Existing indexes align with repository access paths: key lookups; filters by floor, member, or status; ordered pages and timelines; active-row rules; and business uniqueness.

Review scope: migration SQL and repository/query code were inspected. No production-like dataset was available to measure latency or real planner choices.

Follow the new search-index work step by step:
  1. Read the predicates in Member and Society DirectoryQueries: each lower-cases the searched column and uses a leading-wildcard pattern.
  2. Compare that shape with existing B-tree indexes. The floor/order index helps a different access path and cannot efficiently seek into an arbitrary substring.
  3. Add pg_trgm and GIN indexes over the matching lower(column) expressions in new Flyway migrations: Member V19 covers full name, mobile, and email; Society V10 covers flat number.
  4. Let the database integration tests apply Flyway, then run EXPLAIN with sequential scans disabled to check that the PostgreSQL planner recognizes each trigram index for a compatible LIKE predicate.
  5. For production decisions, still run EXPLAIN (ANALYZE, BUFFERS) using realistic table size and search values, then measure write and storage overhead.

The forced-plan test checks index compatibility, not normal planner preference or a latency improvement. The Testcontainers tests have been authored but were skipped because no Docker engine was reachable in this environment.

Chapter 5 - Coding timeline

How the implementation grew

Use the Flyway migration versions to see how indexing evolved along with the application.

1. Create core tables
V1 creates societies, floors, flats, members, and memberships. Primary keys and uniqueness rules establish the first lookup structures.
2. Support common lookups
The initial migrations add indexes for floor/member lookups and member contact fields.
3. Match a real sort
Society V3 replaces the floor-only flat index with (floor_id, flat_number), matching the common list query.
4. Support page bookmarks
Society V4 and member V5 add created-time/ID cursor paths and filter variants.
5. Support history and features
Member V4 indexes membership history by member/flat and descending start date; later migrations add audit, rental, notice, notification, and outbox indexes.

JPA uses ddl-auto: validate: Hibernate checks the schema mapping, while Flyway migrations are the source of the database index definitions.

Chapter 6 - One complete code-to-database example

Request: show flats on floor 4

  1. The browser calls GET /api/v1/flats/by-floor/4.
  2. FlatController.byFloor(4) passes the request to FlatService.listByFloorNumber(4).
  3. The service finds the database ID for floor 4, then asks the repository for that floor's flats, ordered by flat number.
  4. Hibernate turns the repository request into SQL, roughly:
    SELECT ...
FROM flats
WHERE floor_id = ?
ORDER BY flat_number;

    The ? is the floor's database ID, not necessarily the number 4.

  5. Before this request, Flyway runs the migration that defines the index:
    -- The common floor listing filters by floor_id and orders by flat_number.
-- The composite index serves both operations and replaces the narrower index.
DROP INDEX IF EXISTS ix_flats_floor;

CREATE INDEX ix_flats_floor_flat_number
    ON flats (floor_id, flat_number);
    • The comments explain the query pattern the index is designed to support.
    • DROP INDEX IF EXISTS removes the old index on floor_id if it exists. It removes no flat rows.
    • The new composite index is ordered by floor_id first, then flat_number. PostgreSQL can use it to find a floor's flats and read those matches in flat-number order.
    • Because floor_id is the first column, the index can also support lookups that filter only by floor_id.
  6. PostgreSQL's planner decides whether this index is the best route for the query, then returns the rows. The index makes that route available; it does not guarantee PostgreSQL will choose it.

7. General request flow

HTTP request → Controller/service → Spring Data / Criteria query → PostgreSQL planner → Index or table scan

The index makes an access path available; PostgreSQL chooses whether it is worthwhile using statistics and estimated cost. Its existence does not guarantee use. Directory cursor queries order by created_at, id and continue after that pair; matching indexes support stable keyset traversal.

8A · Index type guide

Twelve common index designs and methods

This list mixes two kinds of labels: design/purpose (such as composite or partial) and PostgreSQL access method (such as B-tree or GIN). They overlap: a composite index can be unique and use B-tree.

# / TypeWhat it meansPostgreSQL exampleGood fit / limit
1. Single-columnOne indexed column; commonly a B-tree.CREATE INDEX ... ON employee(email);Equality/range searches on that field. Example: find an account by email.
2. CompositeOne index with multiple keys in a defined order.CREATE INDEX ... ON orders(customer_id,status);Put common equality filters first, then range/order keys. Leading key matters; SQL WHERE condition order usually does not.
3. UniqueRejects duplicate indexed key values.CREATE UNIQUE INDEX ... ON employee(email);Enforce business uniqueness safely under concurrent writes. Resolve existing duplicates first. PostgreSQL normally permits multiple NULLs.
4. Primary-key indexPostgreSQL creates a unique B-tree index for a primary key.id BIGINT PRIMARY KEYDo not add a duplicate index on the same key without a demonstrated reason.
5. PartialIndexes only rows matching a predicate.CREATE INDEX ... ON orders(customer_id) WHERE status='PENDING';Smaller index for a subset. The query must imply the predicate for planner use.
6. Functional / expressionIndexes a computed expression.CREATE INDEX ... ON employee(lower(email));Can support compatible expression searches. Query expression must match the indexed expression.
7. Covering / INCLUDEStores extra output columns in a B-tree index without making them search keys.CREATE INDEX ... ON orders(customer_id) INCLUDE(status,amount);May allow index-only scans, but PostgreSQL visibility checks mean this is not guaranteed.
8. B-tree methodBalanced sorted keys; PostgreSQL’s default method.CREATE INDEX ... USING btree(salary);Equality, range, and ordered retrieval. Not a universal answer for every query.
9. Hash methodHash buckets for equality lookups.CREATE INDEX ... USING hash(token);Equality only; no range or ordering support. Benchmark against B-tree before choosing.
10. GIN methodInverted index maps component values to rows.CREATE INDEX ... USING gin(features);Arrays, JSONB operators, full text, and trigram search with suitable operator classes. Often has higher write/storage cost.
11. GiST methodExtensible search tree for operator classes such as geometry and ranges.CREATE INDEX ... USING gist(location);Spatial/overlap/nearest-neighbor queries when the data type and extensions support them.
12. BRIN methodCompact summaries for ranges of physical table blocks.CREATE INDEX ... USING brin(created_at);Very large tables where values correlate with physical row order; less precise than B-tree.
Not an exhaustive list of PostgreSQL methods: PostgreSQL also provides SP-GiST. The “twelve” above are the learning categories in this guide, not twelve mutually exclusive internal structures. MySQL has different index methods and syntax; check its engine/version documentation before translating examples.

Composite index: column order in plain terms

CREATE INDEX ix_order_customer_status
    ON orders (customer_id, status);
customer_id first→status second within each customer
  • WHERE customer_id = 101: a natural candidate because the first key is constrained.
  • WHERE customer_id = 101 AND status = 'PAID': both keys may help.
  • WHERE status = 'PAID' alone: do not assume this index is efficient; check the plan and PostgreSQL version/statistics.
  • WHERE status = 'PAID' AND customer_id = 101: changing predicate text order does not change the index key order.

One index is reused; PostgreSQL decides

Many repository methods may send queries that can use the same index. Developers normally do not name an index in a Spring Data method. PostgreSQL evaluates predicates, joins, ordering, table size, statistics, and costs; it may choose a sequential scan even when an index exists.

A single-column email B-tree is a possible candidate. Verify with EXPLAIN.

9. Verify whether it helps

  1. Find actual SQL from repository methods or safe SQL logging. Note predicates, joins, ordering, and pagination.
  2. Use representative data in non-production and inspect with EXPLAIN (ANALYZE, BUFFERS). ANALYZE executes the query, so use a read-only SELECT.
  3. Review estimated/actual rows, scan type, sort nodes, rows removed by filters, buffers, and duration. A sequential scan can be correct for small or low-selectivity tables.
  4. For B-tree composites, equality keys generally precede range/order keys. Consider leftmost-prefix behavior and whether query predicates imply a partial-index predicate.
  5. Compare plans, validate migration on fresh and upgraded databases, and measure write cost as well as read benefit.
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, flat_number, floor_id, status
FROM flats
WHERE floor_id = '00000000-0000-0000-0000-000000000001'
ORDER BY flat_number
LIMIT 50;

This is an example plan check for ix_flats_floor_flat_number; it is not a measured result from this repository’s runtime.

10. How developers ship index changes

  • Add a new numbered migration under the owning service’s src/main/resources/db/migration. Never edit an applied migration; Flyway tracks checksums.
  • Explain non-obvious target query/index choices in SQL comments.
  • For large live tables, consider PostgreSQL CREATE INDEX CONCURRENTLY to reduce write blocking. It cannot run inside a transaction, so configure Flyway migration transaction behavior deliberately.
  • For small project datasets, ordinary transactional creation is simpler. Production planning should consider lock duration, disk, replica lag, and recovery.
  • Every index costs storage and adds insert/update/delete/vacuum work.

11. Learn the trade-offs

  • Directory substring search uses leading-wildcard LIKE '%term%'. A regular B-tree generally cannot accelerate it. Trigram GIN indexes now cover the current search expressions in both services. Patterns with fewer than three useful characters may not benefit, and broad/common terms may still favor a sequential scan. Confirm selectivity and write/storage cost with representative query plans before claiming a production speedup.
  • Index usefulness depends on data distribution, statistics, and parameters. A migration or unit test does not prove production speed.
  • Composite column order matters; one composite does not support every permutation. Partial/expression indexes need compatible query predicates/expressions.
  • PostgreSQL does not automatically index every referencing foreign-key column. Add one when joins, deletes/updates, or measured workload justify it.
10A · Production scenarios

Index and Flyway interview questions from real incidents

Use these answers as a troubleshooting order: measure first, inspect SQL and plan, make a small reviewed change, then verify both reads and writes.

1. A production API is slow. How do you decide whether it needs an index?

Use monitoring to find which component uses the time. Capture the SQL and parameters safely, inspect the plan and existing indexes, and compare estimated/actual rows with representative data. Add a Flyway index only when it matches a real filter/order pattern, then measure latency and write cost.

2. How do you check whether PostgreSQL uses an index?

Use EXPLAIN for the planned route, and EXPLAIN (ANALYZE, BUFFERS) for an actual read-only query in a safe environment. Look for Index Scan, Index Only Scan, Bitmap Heap Scan, or Seq Scan, and compare actual rows, buffers, filters, sorts, and time. A sequential scan can be correct.

3. Why might an existing index not be used?

The query may use a function or leading wildcard, the composite leading keys may not match, most rows may match, the table may be small, or statistics may be stale. Check the actual SQL and plan before adding a second index.

4. What if someone creates an index on every column?

Reads may not improve, while each insert/update/delete must maintain more index structures. Disk, cache, I/O, and vacuum work also grow. Keep indexes tied to measured query or integrity needs.

5. When do you choose a composite index over single-column indexes?

Use query patterns. If a common query filters by customer and status together, (customer_id,status) can support that combined path and possibly customer-only searches. Separate indexes can serve independent patterns; compare plans and write/storage cost.

6. What is a covering index?

A covering index contains the search key and included output fields. PostgreSQL may use an index-only scan when visibility information allows it; do not assume table access is always avoided.

7. How do you identify unused PostgreSQL indexes?
SELECT relname AS table_name, indexrelname AS index_name, idx_scan
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;

Review a representative statistics period and account for resets, constraints, infrequent jobs, and seasonal reports before removing anything. Create a new Flyway migration to remove an index.

8. How do you add an index on a large live PostgreSQL table?

Consider CREATE INDEX CONCURRENTLY. It permits ordinary writes during much of the build, but takes more work, can run longer, uses CPU/I/O, and still waits on transactions. A normal index build blocks writes until it finishes. Rehearse and monitor either approach.

MySQL comparison: For some supported InnoDB secondary-index operations, ALTER TABLE orders ADD INDEX idx_orders_customer_id (customer_id), ALGORITHM=INPLACE, LOCK=NONE; may allow reads and writes during most of the operation. Support depends on the exact operation and version; brief metadata locks and resource impact can still occur. Verify before relying on it.

9. A Flyway migration fails during deployment. What do you do?

Pause rollout, inspect logs and Flyway history, and inspect actual schema/data. Determine whether the database rolled back or partial changes remain. Reconcile the database first; repair history only if needed, then migrate/validate and resume only after verification.

10. Concurrent index creation fails. What might be left behind?

PostgreSQL can leave an invalid index that the planner ignores but that may still use storage and add write overhead. Inspect pg_index.indisvalid and indisready; under a reviewed plan, drop the invalid index concurrently and retry.

SELECT indexrelid::regclass, indisvalid, indisready
FROM pg_index
WHERE indrelid = 'orders'::regclass;
11. What if an already-applied versioned migration is edited?

Validation usually reports a checksum mismatch; Flyway does not rerun that V migration. Restore the original file and add a new versioned migration for the change. Repair only deliberately for verified metadata alignment; it does not alter the table.

12. What do migrate, validate, repair, info, baseline, and clean do?

migrate applies pending changes; validate compares resolved migrations with history; repair corrects history metadata; info shows status; baseline records a starting point for an existing schema; clean drops objects in configured schemas and should be disabled in production.

13. If multiple app pods start together, will the same migration run twice?

Instances sharing Flyway’s database/history configuration use Flyway locking to coordinate migration work. Startup can still wait or fail from configuration/database problems. A dedicated migration job before app rollout gives the release an explicit migration gate; the current project’s service deployments run Flyway as part of application startup.

14. How would you arrange an index change in CI/CD?

Commit the migration with the service, review and test it against a fresh schema and an upgrade with existing rows, build one artifact, run the database migration step with protected credentials, stop on migration failure, then deploy compatible app code and monitor health/query behavior.

15. Should Hibernate or Flyway create production indexes?

Use JPA annotations for mapping metadata if useful, but this project manages database indexes with Flyway SQL and sets Hibernate to ddl-auto: validate. Hibernate validation does not comprehensively verify every index definition.

16. A unique index fails because old rows contain duplicates. What next?

Find duplicate keys, agree on data cleanup with the business/data owner, preserve records as required, and prevent new duplicates during remediation. Then retry index creation. Never delete production rows just to make the migration pass.

SELECT email, COUNT(*)
FROM employee
GROUP BY email
HAVING COUNT(*) > 1;
17. Why did inserts become slower after an index was added?

Every row change may need to update the table and relevant indexes. Measure write latency and workload; remove redundant indexes only with evidence and a versioned migration.

18. How do you make a schema change compatible with a rolling deployment?

Use expand-and-contract: add a compatible nullable field, deploy code that can work with both shapes, backfill in controlled batches, switch reads/writes, then remove the old field in a later release after old pods and consumers are gone. See the project’s Flyway Lesson 8.

19. How do you remove a problematic PostgreSQL index?

Create a new forward migration such as DROP INDEX CONCURRENTLY idx_orders_status; and configure that specific migration not to execute inside a transaction. Do not expect rolling back Java to undo an applied database migration.

20. How do you monitor a long index build?

Use pg_stat_progress_create_index and monitor phase, blocks, CPU, disk I/O, free space, locks, replication lag, API latency, and errors. The displayed block progress is phase progress, not necessarily percent of total work.

SELECT pid, relid::regclass AS table_name, phase,
       blocks_total, blocks_done
FROM pg_stat_progress_create_index;

PostgreSQL concurrent index migrations with Flyway

CREATE INDEX CONCURRENTLY cannot run inside a transaction block. For a supported Flyway version, the migration can have a per-script config file such as V20__create_orders_index.sql.conf with:

executeInTransaction=false

Flyway’s PostgreSQL transactional advisory lock may also need session-level locking for this operation:

flyway.postgresql.transactional.lock=false

Use the setting only after checking the Flyway and PostgreSQL extension version used by the service. A failed concurrent build can leave an invalid index; inspect it and recover deliberately before retrying.

12. Explain it in an interview

Short answer

“We manage PostgreSQL indexes through versioned Flyway migrations, based on query patterns in Spring Data and directory queries. Flats are listed by floor and sorted by flat number, so we have a composite index on (floor_id, flat_number). Cursor APIs traverse by (created_at, id), with matching indexes for stable keyset pagination. Membership history puts the member or flat equality key before descending start date. Partial unique indexes enforce active-only rules atomically. We validate candidates with EXPLAIN (ANALYZE, BUFFERS) on representative non-production data because the planner decides whether an index is useful.”

Likely follow-ups

Why composite instead of separate indexes?

A composite can support the leading equality filter and subsequent ordering in one path. Separate indexes can require bitmap combination and sorting and cost more storage; verify with a plan.

What is keyset pagination?

The next page starts after the prior (created_at,id) pair instead of skipping a growing offset. A matching index can seek to that point; the ID tie-breaker stabilizes equal timestamps.

Does an index guarantee speed?

No. For small tables, low-selectivity filters, or queries returning many rows, a sequential scan may be cheaper.

What about substring search?

A standard B-tree generally cannot serve a leading wildcard. Benchmark trigram indexing, including extension and write costs, or change search semantics deliberately.

Why partial unique indexes?

They enforce uniqueness atomically only for rows in the relevant active state, without applying the rule to history.

What is the cost of too many indexes?

More disk, write amplification, and maintenance. Add indexes for demonstrated query/integrity needs and check existing coverage.
