Chapter 1 - Start here

Learn the idea before the code

A database table stores real records. An index is an extra lookup guide that may help find some records faster.

TableA collection of similar records, such as all flats.
RowOne saved item, such as one flat.
ColumnOne field on each item, such as floor number.
QueryA request asking the database to read or change data.
SchemaThe database blueprint: tables, fields, links, and rules.
IndexA separate guide that points toward matching rows.
Keep this in mind: the table is the source of truth. The index is a shortcut. It can help reading, but it also takes space and must be maintained.

2. Picture it: a filing cabinet

Imagine every flat or member is a paper form in a large cabinet. Without an index, a clerk may open drawers one by one. An index is an alphabetized card catalog: it points to the drawer and position. The forms remain the source of truth; the catalog is a shortcut.
Drawer A
Flats 101 to 120
Drawer B
Flats 201 to 220
Drawer C
Flats 301 to 320
Drawer D
Flats 401 to 420
Drawer E
Flats 501 to 520
Without an index, the clerk checks drawers until finding flat 407.

Yellow drawers were checked; green marks the result. This is a teaching model. PostgreSQL uses page and tree structures, not literal drawers.

3. Database words in everyday English

Database indexA fast lookup guide, like a book index pointing to pages about a topic.
Row / recordOne saved item, such as one flat or member. Like one form in the cabinet.
QueryA question to the database: “Show flats on floor 4, sorted by number.”
Migration / FlywayA numbered recipe for changing the database. Flyway remembers which recipes have run.
Query plannerPostgreSQL's route chooser. Like a clerk deciding whether to use the catalog or walk the shelves.
Index scanUse the lookup guide to jump near matching records. Helpful when only a small part is needed.
Sequential scanCheck records one after another. This can be best for a small cabinet or when nearly every form is needed.
Composite indexOne guide sorted by multiple fields. Like sorting cards by building, then flat number.
Partial indexA guide containing only records matching a rule, such as active memberships.
Unique indexA guide that also prevents duplicates, like allowing one active card for each member-flat-relationship combination.
Cursor / keyset paginationA bookmark saying “continue after this item,” instead of counting and skipping earlier items.
SelectivityHow many rows a filter matches. One flat is selective; every flat is not.
PredicateThe filter condition, such as floor_id = 4 or status = 'ACTIVE'.
EXPLAINAsk the database to show the route it plans to use for a query.
EXPLAIN ANALYZERun a query and report what happened and how long it took. Use a safe read-only query and test data.
Write amplificationExtra work keeping guides updated when records change. More guides can speed searches but slow filing.
Finding: implemented already. Both PostgreSQL-backed services use versioned Flyway migrations for primary/unique, composite, cursor, partial, and expression indexes. This review did not add an index: repository code alone provides no measured plan evidence that another index would help, and speculative indexes add write and storage costs.

4. Check what is present

Flyway migrations define indexes beside schema changes. JPA uses ddl-auto: validate, so Hibernate validates schema compatibility instead of creating or changing indexes at runtime. Existing indexes align with repository access paths: key lookups; filters by floor, member, or status; ordered pages and timelines; active-row rules; and business uniqueness.

Review scope: migration SQL and repository/query code were inspected. No live production-like dataset was available to measure plans or assert a latency improvement.

Chapter 5 - Coding timeline

How the implementation grew

Use the Flyway migration versions to see how indexing evolved along with the application.

1. Create core tables
V1 creates societies, floors, flats, members, and memberships. Primary keys and uniqueness rules establish the first lookup structures.
2. Support common lookups
The initial migrations add indexes for floor/member lookups and member contact fields.
3. Match a real sort
Society V3 replaces the floor-only flat index with (floor_id, flat_number), matching the common list query.
4. Support page bookmarks
Society V4 and member V5 add created-time/ID cursor paths and filter variants.
5. Support history and features
Member V4 indexes membership history by member/flat and descending start date; later migrations add audit, rental, notice, notification, and outbox indexes.

JPA uses ddl-auto: validate: Hibernate checks the schema mapping, while Flyway migrations are the source of the database index definitions.

Chapter 6 - One complete code-to-database example

Request: show flats on floor 4

Now connect the URL, Java, SQL, table rows, index, and database execution. This example follows the existing Society Service code.

1. Browser
GET /api/v1/flats/by-floor/4
2. Controller
FlatController.byFloor(4)
3. Service
FlatService.listByFloorNumber(4)
4. Repository
Find the floor ID, then find its flats in number order.
5. PostgreSQL
Use the matching index when its plan estimates that is best.
Pause here: Java does not call the index directly. Java asks for data. Hibernate turns the repository request into SQL. PostgreSQL receives that SQL and decides whether to use an index created earlier by a Flyway migration.
A. Earlier: prepare database
Flyway runs V3 and creates ix_flats_floor_flat_number in PostgreSQL.
B. Request arrives
GET /api/v1/flats/by-floor/4 reaches the controller.
C. Java methods call Java methods
Controller calls service; service calls repository.
D. Hibernate makes SQL
The repository method becomes a SELECT with WHERE and ORDER BY.
E. PostgreSQL chooses
The planner sees available indexes and picks an execution plan.
F. Rows return
Hibernate maps rows to Java objects; service builds response DTOs.

Simple picture: Flyway builds the card catalog before the search. The request does not rebuild it. Hibernate writes the search slip (SQL). PostgreSQL's planner decides whether the existing catalog helps.

What the developer wrote

The controller maps the URL and passes the floor number into the service:

@GetMapping("/by-floor/{floorNumber}")
public List<FlatResponse> byFloor(@PathVariable int floorNumber) {
    return flatService.listByFloorNumber(floorNumber);
}

The service resolves the floor number to its UUID. Then it asks the repository for the flats belonging to that UUID, ordered by flat number:

var floor = floors.findByFloorNumber(floorNumber)
        .orElseThrow(() -> new FloorEntityNotFoundException(floorNumber));

return flats.findByFloorIdOrderByFlatNumberAsc(floor.getId())
        .stream()
        .map(flat -> response(flat, floorNumber))
        .filter(this::visible)
        .toList();

The repository method name describes the query: findByFloorIdOrderByFlatNumberAsc(UUID floorId).

Which table and columns are involved?

FlatEntity maps to PostgreSQL table flats. The relevant database columns are id, floor_id, flat_number, and other flat data. The floor lookup happens first; it gets the UUID used by the flat query.

id (short example)floor_idflat_number
f-403floor-4-uuid403
f-407floor-4-uuid407
f-501floor-5-uuid501

These short IDs and sample rows are illustrations, not seeded database values.

SQL shape the repository method represents

SELECT id, society_id, floor_id, flat_number, status,
       created_at, updated_at, version
FROM flats
WHERE floor_id = :floorId
ORDER BY flat_number ASC;

Hibernate may select a slightly different set of columns. The important operations are the floor filter and flat-number ordering.

Where the index fits - it already exists in the database

Existing index: ix_flats_floor_flat_number ON flats (floor_id, flat_number)

Flyway migration V3 created the index before this request. Its entries are sorted first by floor UUID, then by flat number within that floor. The request SQL does not name an index. PostgreSQL can match the WHERE and ORDER BY to this stored structure and choose it as a shortcut. One index supports both filtering and sorting.
What does “pointer to the record” mean in practice? PostgreSQL's index keeps the indexed values plus a row-location pointer (a table page and a position on that page). It does not copy the whole flat record into this index.
Sorted index entry (simplified)Pointer to the full row
(floor-4, 401)(table page 12, position 3)
(floor-4, 407)(table page 45, position 1)

The sample floor IDs and page/position addresses above are made up to illustrate the idea. PostgreSQL stores its own internal row locations.

1. Search the guide
Find the index entries whose first value is this floor UUID.
2. Follow the pointer
For flat 407, use its row location to find the full row in flats.
3. Return the result
Hibernate maps the row to a Java object; the service maps it to FlatResponse.

That is the shortcut: instead of testing every flat row to discover which floor it belongs to, PostgreSQL can use the index to locate the matching rows directly. Without a useful index, it has to check rows another way and may also need to sort them.

floor_id = floor 4→matching index entries→flat rows in number order→FlatResponse list

What happens during execution?

  1. The gateway routes this API path to Society Service.
  2. The controller calls the service with floor number 4.
  3. The service checks access and its Redis cache. Staff requests use cache flats-by-floor; when an entry exists, the service can return it without running the flat SQL. The configured default cache lifetime is five minutes.
  4. On a cache miss, the service queries the floor table to get the floor UUID, then calls the flat repository.
  5. PostgreSQL plans the flat query. It may use ix_flats_floor_flat_number; the planner can choose another plan based on table size and statistics.
  6. The repository returns entities in flat-number order. The service maps them to response DTOs and applies visibility filtering; the controller returns JSON.
Important accuracy note: the SQL above is the logical query shape represented by the repository method, not a captured Hibernate SQL log. No live EXPLAIN ANALYZE output is available here, so we do not claim the planner actually selected this index or measured a speedup.

Same request: with versus without the ordered index

For staff, Redis may answer from cache. On a cache hit, PostgreSQL does not run the flat query and this index is not consulted. The comparison below is for a cache miss, or a caller that does not use the staff cache.

Exact query: this endpoint calls findByFloorIdOrderByFlatNumberAsc. It filters by floor and sorts by flat number. It returns the whole floor list; there is no page-size limit. Resolving floor number to floor UUID is a separate query.
With ix_flats_floor_flat_number
  1. PostgreSQL seeks to this floor UUID in the B-tree.
  2. It reads the matching index entries in flat-number order.
  3. The entity needs other columns too, so PostgreSQL follows row pointers to fetch each full flat row.
  4. The service maps rows to responses and applies visibility rules.
The index can help find matching rows and may avoid a separate sort.
Without a matching ordered index
  1. PostgreSQL still must find rows for this floor.
  2. It may scan the table, or use another index that helps find the floor rows.
  3. If that route does not return flat-number order, PostgreSQL sorts the matches.
  4. The service maps rows to responses and applies visibility rules.
More rows may need checking and a sort may be needed; the actual route depends on data and available indexes.
With index: seek floor→read ordered matches→fetch full rows→return list
Without matching index: find matches→scan or use another index→sort if needed→return list

Project detail: Society V4 also defines ix_flats_floor_cursor(floor_id, created_at, id). If the flat-number index were absent, PostgreSQL might use this other floor-leading index and then sort, or choose a sequential scan. “Without this index” does not necessarily mean “without any index.”

Does the index always make this request faster? No. For a small table or a floor containing most flats, scanning and sorting can cost less. The PostgreSQL planner decides using statistics. This repository has no measured plan output for this example, so compare plans on representative data before claiming a speedup.

7. General request flow

HTTP request → Controller/service → Spring Data / Criteria query → PostgreSQL planner → Index or table scan

The index makes an access path available; PostgreSQL chooses whether it is worthwhile using statistics and estimated cost. Its existence does not guarantee use. Directory cursor queries order by created_at, id and continue after that pair; matching indexes support stable keyset traversal.

9. Verify whether it helps

  1. Find actual SQL from repository methods or safe SQL logging. Note predicates, joins, ordering, and pagination.
  2. Use representative data in non-production and inspect with EXPLAIN (ANALYZE, BUFFERS). ANALYZE executes the query, so use a read-only SELECT.
  3. Review estimated/actual rows, scan type, sort nodes, rows removed by filters, buffers, and duration. A sequential scan can be correct for small or low-selectivity tables.
  4. For B-tree composites, equality keys generally precede range/order keys. Consider leftmost-prefix behavior and whether query predicates imply a partial-index predicate.
  5. Compare plans, validate migration on fresh and upgraded databases, and measure write cost as well as read benefit.
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, flat_number, floor_id, status
FROM flats
WHERE floor_id = '00000000-0000-0000-0000-000000000001'
ORDER BY flat_number
LIMIT 50;

This is an example plan check for ix_flats_floor_flat_number; it is not a measured result from this repository’s runtime.

10. How developers ship index changes

  • Add a new numbered migration under the owning service’s src/main/resources/db/migration. Never edit an applied migration; Flyway tracks checksums.
  • Explain non-obvious target query/index choices in SQL comments.
  • For large live tables, consider PostgreSQL CREATE INDEX CONCURRENTLY to reduce write blocking. It cannot run inside a transaction, so configure Flyway migration transaction behavior deliberately.
  • For small project datasets, ordinary transactional creation is simpler. Production planning should consider lock duration, disk, replica lag, and recovery.
  • Every index costs storage and adds insert/update/delete/vacuum work.

11. Learn the trade-offs

  • Directory substring search uses leading-wildcard LIKE '%term%'. A regular B-tree generally cannot accelerate it. If it becomes slow, benchmark PostgreSQL trigram GIN indexing or deliberately change search semantics.
  • Index usefulness depends on data distribution, statistics, and parameters. A migration or unit test does not prove production speed.
  • Composite column order matters; one composite does not support every permutation. Partial/expression indexes need compatible query predicates/expressions.
  • PostgreSQL does not automatically index every referencing foreign-key column. Add one when joins, deletes/updates, or measured workload justify it.

12. Explain it in an interview

Short answer

“We manage PostgreSQL indexes through versioned Flyway migrations, based on query patterns in Spring Data and directory queries. Flats are listed by floor and sorted by flat number, so we have a composite index on (floor_id, flat_number). Cursor APIs traverse by (created_at, id), with matching indexes for stable keyset pagination. Membership history puts the member or flat equality key before descending start date. Partial unique indexes enforce active-only rules atomically. We validate candidates with EXPLAIN (ANALYZE, BUFFERS) on representative non-production data because the planner decides whether an index is useful.”

Likely follow-ups

Why composite instead of separate indexes?

A composite can support the leading equality filter and subsequent ordering in one path. Separate indexes can require bitmap combination and sorting and cost more storage; verify with a plan.

What is keyset pagination?

The next page starts after the prior (created_at,id) pair instead of skipping a growing offset. A matching index can seek to that point; the ID tie-breaker stabilizes equal timestamps.

Does an index guarantee speed?

No. For small tables, low-selectivity filters, or queries returning many rows, a sequential scan may be cheaper.

What about substring search?

A standard B-tree generally cannot serve a leading wildcard. Benchmark trigram indexing, including extension and write costs, or change search semantics deliberately.

Why partial unique indexes?

They enforce uniqueness atomically only for rows in the relevant active state, without applying the rule to history.

What is the cost of too many indexes?

More disk, write amplification, and maintenance. Add indexes for demonstrated query/integrity needs and check existing coverage.
