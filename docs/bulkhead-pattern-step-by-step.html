Bulkhead pattern: protecting downstream capacity

Start with the isolation idea, then follow the existing Member-to-Society concurrency limiter through its configuration, call flow, error behavior, tests, Kubernetes replica math, and operational signals. This guide distinguishes a focused concurrency test from a real deployment load validation.

Step 1 | Understand the problem

Why isolate concurrent work?

A service can accept more requests than a dependency can safely handle. If every incoming request starts a remote call, slow responses can leave many calls in flight, consuming threads, sockets, memory, and downstream capacity.

A bulkhead places a concurrency cap around a dependency operation. When all permits are in use, new calls are rejected or made to wait according to the configured policy. Compartments in a ship isolate damage so one section does not flood every other section.

A bulkhead does not make Society Service faster. It limits concurrent work from this process and fails excess work predictably.
Step 2 | Learn the terms

Permits, waiting, rejection

  • Concurrent call: one operation currently inside the protected section.
  • Maximum concurrent calls: available permits.
  • Maximum wait: time to wait for a permit after capacity is full.
  • Fail fast: zero wait means reject immediately when no permit is available.
  • Per-process limit: every application instance owns a separate limiter unless coordination is added.

This is Resilience4j's semaphore-style Bulkhead, distinct from ThreadPoolBulkhead, which uses a bounded executor and queue.

Step 3 | Find the implementation

Member-to-Society lookup calls

Member Service injects one bulkhead named societyFlatLookup into SocietyClient. Both the flat details lookup and notice flat directory lookup use it and share its capacity within that process.

This is not a global limit for every Society call. Gateway traffic to Society, other HTTP clients, and Society's own cache/database fallback limits are separate paths.

The Member Deployment starts at 2 pods and the HPA maximum is 3. The setting of 12 is per pod, not a cluster-wide total of 12.
Step 4 | Follow one request

How the permit wraps the remote call

Business operation
  -> SocietyClient.getFlat(...) or noticeFlatOptions()
  -> Retry wrapper
       -> Circuit breaker admission
            -> Bulkhead permit
                 -> Society RestClient HTTP GET
            <- release permit when attempt returns or fails
  -> success or mapped dependency error

Retry is outside the circuit breaker and bulkhead. Each physical attempt gets a breaker and permit decision. A permit covers one HTTP attempt; it is released before a retry delay, and a subsequent attempt must acquire a permit again.

This caps active outbound attempts. It does not cap incoming Member requests waiting in Tomcat or the number of logical callers that may take turns using permits.

TaggedBulkheadMetrics registers the bulkhead with Micrometer alongside retry and circuit-breaker metrics.

Step 6 | Calculate deployment capacity
One pod12 active attempts
Two steady pods24 active attempts
HPA maximum3 × 12 = 36
Rollout peak3 desired + 1 surge = 48

The Member Deployment has 2 replicas and maxSurge: 1. Its HPA scales from 2 to 3 on CPU. Thus the theoretical aggregate active-attempt cap is 36 at HPA maximum, or 48 with one rollout surge pod. These are configured ceilings, not observed traffic or proof Society can sustain that concurrency.

The same per-pod pool is shared by flat and notice-directory lookups. Every pod has its own semaphore, so cluster capacity is the sum of active pod limits.

Capacity planning: compare this aggregate with Society Service throughput and its database/cache limits. Scaling Member replicas also increases potential Society concurrency.
Step 7 | See over-limit behavior

Excess work fails fast with 503

When no permit is available, Resilience4j throws BulkheadFullException. SocietyClient.executeResilient maps it to a SocietyDependencyException with status 503 and code SOCIETY_CAPACITY_EXCEEDED.

The rejected operation does not issue an HTTP request. The mapped exception uses the default non-retryable flag, so the retry predicate does not retry a capacity rejection. That avoids turning local saturation into immediate extra load.

Step 8 | Review existing evidence

What is already validated

SocietyClientResilienceTest.fullBulkheadRejectsAdditionalDependencyWorkWithoutQueueing sets a test bulkhead limit of one and delays a WireMock response. While the first call holds the permit, a second call gets SOCIETY_CAPACITY_EXCEEDED. WireMock verifies only one downstream request; then the first call completes.

This proves semaphore saturation, zero-wait rejection, error mapping, and no downstream request for rejected work. It does not test the production value of 12.

The Postman collection describes a controlled concurrent membership scenario exceeding SOCIETY_BULKHEAD_MAX_CONCURRENT, expecting 503 and no membership saved. It explicitly warns against a single request or production traffic. The collection description documents a procedure; it is not evidence that the procedure was run.

Evidence found: one deterministic concurrent unit test and a manual over-limit scenario. No sustained load result, saturation curve, or deployment-level validation of the configured 12-per-pod value is recorded.
Step 9 | Validate under load safely

A staged exercise

  1. Use a non-production environment and a controllably slow Society stub or test setup.
  2. Confirm the runtime values for SOCIETY_BULKHEAD_MAX_CONCURRENT and SOCIETY_BULKHEAD_MAX_WAIT.
  3. Increase simultaneous calls gradually: below 12, at 12, then above 12 per pod. Keep rate and duration controlled.
  4. Measure accepted/rejected calls, actual Society request count, status/error code, permit availability, latency, CPU, and memory.
  5. Confirm no more than 12 Society attempts are active on a pod at once, and excess calls fail promptly without reaching Society.
  6. Repeat for expected replica count and rollout surge if that peak matters to capacity planning.
  7. Stop traffic and check permits recover and later harmless lookups succeed.

Do not run the Postman over-limit scenario against production. Its description specifically requires controlled concurrent load.

Step 10 | Observe and operate

Keep pod-level signals visible

TaggedBulkheadMetrics binds the bulkhead to Micrometer. Member Service exposes /actuator/prometheus; Kubernetes annotations enable Prometheus pod scraping. Inspect the running endpoint for the societyFlatLookup instance and confirm exact meter names and tags in the deployed version.

Useful signals include available concurrent calls and max allowed calls, plus the mapped capacity-error count, Society lookup-attempt latency, downstream errors, retries, breaker state, and service resource use. Capacity rejections should not correspond to additional Society HTTP requests.

Inspect each pod because the semaphore is local. Preserve pod dimensions when aggregating, or one saturated replica may be hidden by healthy peers. No dedicated Grafana bulkhead panel or alert was found in the checked-in configuration.

Step 11 | Understand trade-offs

What this does not guarantee

  • It limits concurrency in each Member process, not across the cluster or all Society callers.
  • It does not guarantee request throughput or downstream response time.
  • Zero wait favors fast rejection over queueing; bursts can receive 503 even if a permit frees moments later.
  • It does not limit incoming requests already accepted by Member Service.
  • Flat and notice-directory traffic share permits, so a hot operation can consume capacity used by the other.
  • More Member replicas mean more aggregate permits and more potential Society concurrency.
  • The test uses a limit of one and proves mechanics, not production performance at 12.
  • Metrics are registered, but no dedicated Grafana bulkhead panel or alert rule was found.
Step 12 | Interview practice

Developer-level explanation

“Member Service uses a Resilience4j semaphore bulkhead around Society flat and notice-directory GET calls. It permits 12 concurrent attempts per process with zero wait, so calls arriving after capacity is full fail fast. SocietyClient maps that to HTTP 503 with SOCIETY_CAPACITY_EXCEEDED; the rejected operation does not reach Society and is not retried. Retry sits outside the breaker and bulkhead, so each physical attempt competes for a permit. There are two initial Member pods, an HPA maximum of three, and one rollout surge pod: theoretical active attempt capacity is 24 initially, 36 at max replicas, and 48 with surge. A focused test proves rejection at a test limit of one; a Postman scenario documents a manual over-limit check, but sustained load validation at the configured limit is not recorded.”

Likely follow-up questions

Why fail fast instead of waiting?

Zero wait avoids a queue that retains work and increases latency. The trade-off is prompt capacity errors during bursts.

Is 12 the deployment-wide limit?

No. It is per pod. Three pods can allow 36 active calls; one surge pod can temporarily raise that to 48.

Does rejection count as a Society failure?

No Society request was sent. It is mapped as a separate capacity error and is non-retryable.

Can retry bypass the cap?

No. Each retry attempt must acquire the same semaphore. It releases during backoff, and the next attempt competes for a permit again.

How would you choose the right value?

Load test with realistic Society latency, measure its sustainable throughput and resource use, and calculate aggregate concurrent limits at replica maximum plus rollout surge.

What would improve confidence?

Add a test using the bound production configuration, a staged concurrent load run at and above 12, and a dashboard showing per-pod available permits and capacity errors.
