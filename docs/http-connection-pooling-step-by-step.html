Step 1 | Understand the connection cost

Why reuse an HTTP connection?

Opening a network connection costs time and resources: DNS lookup, TCP connection establishment, and sometimes TLS negotiation. If a service repeatedly calls the same dependency, a reusable HTTP client can keep connections available and reuse them for later requests.

Connection pooling is distinct from a thread pool, request timeout, or bulkhead. A connection pool controls reusable network connections and possibly callers waiting to acquire one. A thread pool schedules work. A timeout bounds waiting. A bulkhead limits concurrent operations.

Analogy: instead of hiring a new taxi for every trip to the same building, keep a managed fleet of reusable taxis. A fleet that is too small queues riders; one that is too large wastes resources and may overload the destination.
Step 2 | Learn the terms

Reuse, idle connections, and limits

  • HTTP client instance: the owner of transport settings and, for many clients, a connection pool.
  • Connection reuse: later requests reuse an open keep-alive connection when protocol and server permit.
  • Maximum connections: cap on simultaneously managed connections, often scoped per host or provider.
  • Pending acquire: callers waiting for an available connection when the pool is full.
  • Idle lifetime / eviction: how long unused connections remain before removal.
  • Pool metrics: active, idle, total, and pending connection information, depending on the transport.

Creating a new HTTP client for each request often prevents reuse. Creating one long-lived client per dependency is a common pattern. Defaults can pool connections even when an application has not chosen explicit maximums.

Step 4 | Follow Member-to-Society

The most explicit synchronous client

SocietyRestClientConfig declares three Spring beans: a dedicated executor, a Java HttpClient, and a RestClient. They are singleton beans by default, so application calls reuse this client rather than constructing one for each request.

SocietyClient business lookup
  -> injected Society RestClient
  -> JdkClientHttpRequestFactory
  -> singleton Java HttpClient
       -> connection reuse managed by the JDK client
       -> dedicated virtual-thread executor for HTTP tasks
  -> Society Service

Configuration sets the connect timeout to 2 seconds and read timeout to 3 seconds. It does not set an application-specific maximum connection count, idle pool size, or pool-acquire timeout. The executor is a new virtual thread per task executor; it is not a cap on active HTTP connections. The separate Resilience4j bulkhead limits Society lookup concurrency to 12 per Member process, but that is an operation limit, not a connection-pool setting.

The client and executor have explicit Spring destruction methods. The test checks that they terminate when the application context closes.

Step 5 | Review session-validation and AI clients

Long-lived clients, default pool settings

Member Service, Society Service, and AI Service each construct a Java HttpClient and JdkClientHttpRequestFactory once in a Spring singleton component for Gateway session validation. AI Service's SocietyMaintenanceClient builds another client for its Society read.

These clients set connect and read timeouts through environment-backed properties, but do not set custom connection pool sizing. Because their components are reused, the same client instances can reuse their transport connections. Their pools are separate from the Member-to-Society client pool and from one another.

Timeout configuration does not imply pool configuration. The repository gives session-validation calls finite connect/read bounds but does not separately cap their idle or total connection count.
Step 6 | Review gateway outbound clients

Reactor Netty-managed reuse

Spring Cloud Gateway routes through its WebFlux HTTP client. The gateway configuration sets a 2-second connect timeout and 28-second response timeout. There are no checked-in settings for max connections, pending acquire count, idle lifetime, or pool-acquire timeout.

AdminAuthenticationManager creates a Reactor Netty HttpClient.create() with connect and response timeouts, then uses it in a singleton WebClient for Gateway-to-Member credential/account lookups. The project does not pass a custom ConnectionProvider, so pool sizing and lifecycle follow Reactor Netty/framework defaults for the resolved dependency version.

Reactor Netty documentation describes HttpClient.create() as using a shared default ConnectionProvider. The exact defaults should be checked against the version resolved by this build before changing capacity.

Step 7 | Trace a request and its connection

Next callclient may reuse it

Reuse depends on a fully consumed/closed response body, keep-alive support, compatible protocol and destination, and the server not closing the connection. In this application, Spring's synchronous client methods consume response bodies into objects or strings, allowing the request factory to finish response handling before the call returns.

When all pool connections are busy, behavior depends on the transport: it may open another connection up to its limit, queue an acquire, or fail. This project does not configure custom acquire queue limits for these service clients.

Step 9 | Tune from measurements

A safe review process

  1. Inventory each client and destination. Count client instances per process and replicas; do not combine separate pools into one number.
  2. Measure requests per second, concurrent in-flight calls, response time, connection establishment rate, connection reuse, and downstream capacity.
  3. For Reactor Netty, inspect active, idle, total, and pending acquire metrics if enabled. For JDK HttpClient, gather transport/JFR/network evidence because the project has no pool meter currently.
  4. Compare observed maximum concurrent calls to the Society bulkhead (12 per Member pod) and Gateway workload. Pool capacity should support intended concurrency without multiplying beyond what dependencies can handle.
  5. Include Kubernetes replica maximum and rollout surge when calculating aggregate connections to each dependency.
  6. Set a per-client max, pending acquire limit, idle/lifetime policy only if supported and justified by evidence. Preserve connection/read timeouts and define behavior when acquire capacity is exhausted.
  7. Load test below, at, and above the target concurrency. Compare latency percentiles, errors, connection churn, pending wait, and downstream CPU/connections.
  8. Roll out gradually and retain metrics that tell whether the pool is undersized, oversized, or simply facing a slow dependency.
Step 10 | Check current tests and observability

What repository verification establishes

SocietyRestClientConfigTest checks that the Spring context creates the Society HttpClient and RestClient, that the configured dedicated executor is attached to the client, and that the client/executor close with context. Another test sends a successful request and verifies a configured 500 ms read timeout fails against a delayed WireMock response.

These tests validate client wiring, executor lifecycle, and timeout behavior. They do not verify that an existing TCP connection is reused, that pool limits are correct, or that pool saturation recovers under load. No service-client pool metrics or pool-specific dashboard were found. Gateway route metrics and standard HTTP request metrics do not by themselves prove connection reuse.

Testing distinction: a client can be pooled without a test asserting reuse. A timeout test proves a timeout configuration, not a maximum connection count.
Step 11 | State the current limits accurately

What this review does and does not establish

  • Service clients are long-lived singleton instances, and the JDK/Reactor transports can reuse connections according to their own pooling behavior.
  • The repository does not define explicit max connections, pending-acquire limits, or idle eviction settings for the service-to-service clients.
  • The JDK HttpClient pools are not one shared pool across all components; each client instance owns its own pool behavior.
  • The Member Society bulkhead is a 12-concurrent-operation limit. It is not a configurable HTTP pool maximum.
  • There is no evidence in checked-in configuration that clients are rebuilding an HttpClient per request. The component constructors create them once.
  • There are no pool occupancy metrics, connection-reuse tests, or recorded load measurements to justify numeric tuning in this change.
  • Reactor Netty pool defaults depend on the exact resolved dependency version; do not assume documentation for a newer release exactly matches the deployed build.
Step 12 | Interview practice

Developer-level explanation

“The project uses long-lived service-client instances, so connection reuse is available through the underlying transports. Member-to-Society uses a singleton Java 21 HttpClient through JdkClientHttpRequestFactory and a dedicated virtual-thread executor; its connect and read timeouts are configured, but the application does not set a max connection pool size. The session-validation and AI service clients similarly create one JDK HttpClient in singleton components with timeouts and default pool behavior. Spring Cloud Gateway and its credential WebClient use Reactor Netty; the credential client has timeouts but no custom ConnectionProvider. The Society bulkhead caps concurrent operations per Member pod, but it is not a connection pool. Existing tests validate client wiring, executor shutdown, and read timeout, not actual connection reuse or pool saturation. We need traffic and pool measurements before choosing explicit connection limits.”

Likely follow-up questions

Does this project have connection pooling?

Connection reuse is supplied by the long-lived JDK and Reactor Netty clients. What is absent is explicit application-level pool sizing for most clients.

Why not create a new HttpClient per call?

JDK HttpClient pools are associated with a client instance. Recreating it per operation usually prevents connections from being reused effectively.

Is the virtual-thread executor the connection pool?

No. It schedules HTTP task work. The JDK client owns connection reuse; the Resilience4j bulkhead separately limits concurrent Society operations.

What evidence would you need to tune max connections?

In-flight call concurrency, latency, connection reuse/churn, pending acquire time, downstream sustainable connections, replica maximum, rollout surge, and error/latency objectives.

What happens if a pool limit is too low?

Calls may wait to acquire a connection or fail, increasing latency and timeouts even when the remote service could handle more work.

What happens if it is too high?

The client may create more simultaneous connections than the dependency or its own database can handle, increasing resource use and contention.

What do current tests prove?

They prove the Member Society client is wired with its executor and that a configured read timeout fails on a delayed response. They do not prove connection reuse or a pool capacity value.
