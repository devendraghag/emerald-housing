Virtual threads, from zero

Learn what virtual threads are, then follow the one scoped use in this repository: a dedicated executor supplied to the blocking Society HTTP client. Understand what the tests prove, why the whole application is not switched to virtual threads, and what evidence is still needed before making a wider default change.

1. Learn the basics first

A platform thread is an operating-system-backed Java thread. A virtual thread is a lightweight Java thread scheduled by the JVM over a smaller set of carrier platform threads.

Virtual threads are useful when many tasks spend time waiting on blocking operations such as network I/O. They reduce the cost of representing waiting tasks. They do not make the remote service faster, remove network latency, or make CPU-heavy work faster.

Virtual threads are still threads: they need concurrency limits around databases and downstream services, and code must handle timeouts, cancellation, errors, and resource cleanup as before.

Short status: virtual threads are already used for the JDK HTTP client’s dedicated executor in Member Service. They are not enabled as the application-wide Spring/Tomcat default.

Important distinction: MembershipService.assign makes a synchronous call to societyClient.getFlat. The request handler’s caller is still executing in the application’s normal MVC request model. The custom virtual-thread executor is supplied to the JDK HttpClient; it does not by itself turn every Tomcat request thread into a virtual thread.

Step 1 — create a dedicated executor

The bean uses Executors.newThreadPerTaskExecutor(Thread.ofVirtual().name("society-http-", 0).factory()). Each submitted executor task receives a named virtual thread.

Step 2 — supply it to JDK HttpClient

The societyHttpClient bean calls HttpClient.newBuilder().executor(executor) and applies a connect timeout. The executor is scoped to this client rather than replacing Spring’s general executor.

Step 3 — adapt it for Spring RestClient

The RestClient bean uses JdkClientHttpRequestFactory with that JDK client and applies the read timeout. SocietyClient uses this RestClient for flat lookups and the notice flat directory.

Step 4 — protect the dependency

SocietyClient keeps synchronous request semantics and applies timeout/error mapping, retry, circuit breaker, and a bulkhead. The default bulkhead maximum is 12 concurrent calls, so using lightweight threads does not imply unbounded Society traffic.

Step 5 — close resources in dependency order

The executor bean declares destroyMethod="close"; the HTTP client also declares close and depends on the executor. The tests verify both are terminated when the Spring context closes.

5. What the tests prove

SocietyRestClientConfigTest contains four checks:

  1. The Spring context creates the Society RestClient and its JDK HttpClient uses the configured executor.
  2. Eight tasks submitted to that executor run on virtual threads; after context close, HttpClient and executor report terminated.
  3. A finite task source completes on the executor, keeping the test submission bounded.
  4. A WireMock-backed ready request succeeds, while a deliberately slow endpoint exceeds the configured read timeout and raises ResourceAccessException.

The transport test uses a 2-second read timeout and a 4-second delayed response. This test-only window was widened from 500 ms/1.5 seconds after the fast localhost request was cancelled on the test host before the intended timeout assertion. Production defaults remain 2 seconds connect and 3 seconds read.

Evidence boundary: these tests prove virtual task execution, dependency wiring, resource closure, and timeout behavior. They do not compare virtual threads with platform threads under realistic traffic or prove that the Society HTTP dependency has more capacity.

6. Evaluate the workload before widening scope

To decide whether to enable virtual threads more broadly, benchmark representative blocking workloads and compare:

  • throughput and p50/p95/p99 request latency under the same load;
  • platform/carrier thread count and virtual-thread task count;
  • CPU use, heap use, allocation, and garbage collection;
  • DB connection pool saturation, Society bulkhead rejections, retries, timeouts, and downstream saturation;
  • thread pinning and blocking behavior using Java Flight Recorder or thread dumps.

Use realistic concurrency and failure scenarios, including slow Society responses. Virtual threads make blocked tasks cheaper to represent; they can also allow more work to wait at once. Keep bulkheads, timeouts, rate limits, connection pools, and downstream capacity controls in place.

There are no measurements checked into this repository that justify enabling Spring Boot’s global virtual-thread mode or changing Tomcat defaults. The safe current state is the existing scoped executor plus controlled downstream concurrency.

7. Limits and risks

  • Only the Society JDK HttpClient is explicitly given the virtual-thread executor in the inspected configuration.
  • The Spring MVC request thread is not shown running as a virtual thread by this configuration.
  • Virtual threads do not speed CPU-heavy tasks or the Society Service itself.
  • Connection pools, DB pools, bulkheads, and remote service capacity remain the actual resource constraints.
  • Blocking operations that pin carrier threads can reduce the benefit; inspect with JFR for the real workload.
  • Retries can multiply downstream calls. The Society bulkhead and retry policy still matter when concurrency rises.
  • The automated tests are functional, not a performance benchmark. No production rollout comparison or benchmark is documented.

8. Interview preparation

60-second explanation

“The application targets Java 21 and uses virtual threads in a narrow place: Member Service creates a dedicated virtual-thread-per-task executor and supplies it to the JDK HttpClient behind its synchronous Society RestClient. The rest of the Spring MVC/Tomcat model is not switched globally. The client still has connect/read timeouts, circuit breaker, retries, and a 12-call bulkhead, so lightweight threads do not mean unlimited downstream concurrency. Tests confirm tasks on that executor are virtual, the HTTP client is wired to it, resources close with the context, and slow responses time out. We have not run a representative platform-versus-virtual-thread benchmark, so we would not enable the global Spring setting without measurements.”

Likely follow-upAnswer
Do virtual threads make blocking I/O non-blocking?No. The code can still block. Virtual threads reduce the cost of waiting by letting the JVM unmount/schedule many waiting tasks efficiently in supported blocking operations.
Does this make Tomcat request threads virtual?No. The custom executor is dedicated to the Society JDK HttpClient. Global Spring virtual threads are not enabled, and Tomcat has its own configured platform-thread pool.
Why use a dedicated executor?It scopes the experiment to one blocking HTTP client and avoids replacing Spring’s general executor. The bean is not a default candidate for general injection.
Can the executor handle unlimited calls?Virtual thread creation is lightweight, but downstream resources are finite. The Society bulkhead caps protected concurrent calls at 12 per instance, and the HTTP/database pools and rate controls remain relevant.
What does the test establish?It establishes virtual-thread execution for tasks submitted to the configured executor, client wiring and lifecycle, and timeout behavior. It does not establish a throughput or memory improvement under production traffic.
When would you enable Spring’s global virtual-thread mode?After comparing representative workloads, checking libraries for pinning/ThreadLocal assumptions, reviewing scheduler behavior and resource limits, and observing latency, CPU, memory, and downstream pressure in a controlled rollout.
