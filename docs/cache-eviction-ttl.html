Step 1 | Learn the terms

What are TTL and eviction?

A cache stores a copy to make repeated reads faster. That copy can become old when the database changes. Two mechanisms remove old copies:

  • TTL (time-to-live): a deadline; Redis expires an entry after its configured lifetime.
  • Eviction/invalidation: application code actively deletes a key when it knows the source data changed.
  • Cache key: the address of one cached value, such as a flat UUID or floor number.
  • Stale data: cached data that no longer matches the database.
  • TTL jitter: small random variation in expiry time to avoid many entries expiring together.
Analogy: TTL is a milk carton expiry date. Eviction is the shopkeeper removing the carton immediately after learning it was recalled. The date is a backup; the recall is the immediate action.
Step 2 | Understand why the project uses both

Eviction for quick freshness; TTL as a safety net

ReadRedis has a value until expiry
Successful writeApp deletes affected key after commit
Next readCache miss reloads PostgreSQL
If deletion missedTTL eventually expires it

Eviction can make the next read fresh immediately after a normal service write. TTL bounds how long a missed or external invalidation can leave a cached copy. Neither mechanism makes Redis and PostgreSQL one atomic system.

Step 4 | Follow TTL configuration into Redis

How the code attaches an expiry

SocietyCacheConfiguration.redisCacheManager(...) creates named cache configurations. Each calls cacheConfig(ttl, ttlJitter, serializer). That method uses Redis's per-entry entryTtl function and subtracts a random jitter value from the configured TTL.

actual lifetime = configured TTL - random(0..jitter)

Example:
flats-by-floor TTL = 5 minutes
jitter = up to 30 seconds
an entry expires after about 4m30s to 5m

Startup validation rejects a non-positive TTL, negative jitter, or jitter greater than or equal to the TTL. Null values are not cached. Typed JSON serializers store floor/flat response DTOs. Cache names are predeclared; unrecognized names cannot silently create a new Redis cache.

Redis cache deployment has a separate memory eviction rule (allkeys-lru at 128 MB) for memory pressure. That is not the same as each entry's TTL or application invalidation: Redis may remove a key early if memory pressure triggers LRU eviction.

Spring's @Cacheable checks Redis before executing the service method. A hit returns without running the database loader. After expiry Redis no longer has the entry; the next request is a miss and fills a fresh copy. A distributed per-key lock reduces simultaneous pod misses, then rechecks Redis before loading.

Step 6 | Follow a flat write

Which flat keys are removed?

WriteCreate/update/deactivate flat in PostgreSQL
CommitTransaction finishes successfully
Event listenerEvict flat ID and all-flat keys
Related listsEvict prior/current floor list keys
Next readReload from PostgreSQL

Flat mutations publish FlatReferenceChangedEvent. FlatCacheInvalidationListener listens with @TransactionalEventListener(phase=AFTER_COMMIT). It removes the negative key, by-ID entry, all-flats entry, and the previous/current floor lists. If a flat changes floor, both affected lists are evicted.

Activation uses a broad @CacheEvict(allEntries=true) on the by-ID/all-flat/by-floor caches. TTL remains a backup for missed eviction.

Step 7 | Follow a floor write

Creation and rename have different invalidation breadth

  • Create floor: clears the floor list and all cached flat lists by floor. A new floor changes the floor directory and list universe.
  • Update/rename floor: clears floor list, all by-floor flat lists, all-flat list, and flat-by-ID entries. The floor number appears in flat response data, so broader invalidation avoids stale floor labels.

These rules live on FloorService.create and FloorService.update through @CacheEvict(allEntries=true). The Redis cache manager is transaction-aware so cache operations from annotated transactional writes are coordinated with transaction completion.

Step 8 | Understand negative-cache expiry

How a missing ID is remembered

FlatService.getCached(id) checks a separate SocietyNegativeCache marker before its database loader. If PostgreSQL confirms the flat is missing, the service writes a simple marker in Redis with a 30-second default TTL. Repeated requests for the same missing ID can fail without repeating the database lookup.

When a flat is created or changed, the after-commit listener deletes the marker for that ID. A marker also disappears automatically at TTL expiry. This is called negative caching; it is separate from caching a successful FlatResponse.

Step 9 | Know freshness and failure limits

What can still be stale?

  • There is a short interval after PostgreSQL commit and before eviction where a concurrent request can see the old value.
  • If Redis is unavailable during eviction, the old cache value may remain until Redis returns or its TTL expires.
  • A direct database write outside Society Service does not publish its event; expiry is the fallback.
  • Redis itself may evict entries early under memory pressure using allkeys-lru.
  • Redis cache is disposable and the Kubernetes cache instance is ephemeral; entries can be lost and reloaded from PostgreSQL.

So the strategy is prompt best-effort invalidation for known service writes plus a finite TTL fallback, not a strict freshness SLA.

Step 10 | Operate and tune the policy

How a developer should review it

  1. Find the cached method and write paths that can change its result.
  2. List every key family affected by each mutation; include old and new relationship keys when records move.
  3. Choose TTL from data-change frequency and acceptable staleness, then add jitter.
  4. Watch hit/miss rate, cache lookup latency, database fallback count/duration, Redis errors, and load-lock timeouts.
  5. Exercise create/update/deactivate/floor-change and confirm the next read reloads the changed value.
  6. Test expiry with a shortened test TTL or controlled clock; verify Redis outage fallback separately.

The project exposes cache and database-load metrics through Micrometer/Actuator/Prometheus. Grafana currently has no dedicated cache eviction/TTL panel; use metrics and Redis inspection in the target environment.

Step 11 | Interview practice

Answer in developer language

“Society Service assigns a TTL to every declared Redis cache: floors live about ten minutes, flat-by-ID two, and flat lists five, with up to thirty seconds of jitter. A separate negative flat lookup marker lasts thirty seconds. TTL is the safety net; normal writes actively evict keys after successful changes. Flat events invalidate the ID, global list, affected floor lists, and negative marker after commit. Floor create/update uses cache eviction annotations, with a wider eviction on floor rename because floor numbers are present in flat responses. The Redis cache manager is transaction-aware and uses versioned keys and typed JSON values. If an invalidation is missed or Redis fails, stale data can remain until TTL, so this is bounded eventual consistency, not strict consistency.”

Likely follow-ups

Why use both eviction and TTL?

Eviction refreshes quickly after known writes. TTL limits staleness when invalidation is missed or a write occurs elsewhere.

Why add TTL jitter?

It spreads expiration times so many entries are less likely to expire and reload at once.

What happens if a flat moves floors?

Both old and new floor-list keys are deleted along with its by-ID and all-flats entries.

Does Redis eviction mean the same thing as cache invalidation?

Application invalidation deletes a key because data changed. Redis allkeys-LRU removes keys under memory pressure. TTL expires by age. They are three distinct removal mechanisms.

Is the cache always fresh immediately after a database write?

No. The listener runs after commit, leaving a small interval; failed invalidation can leave stale data until TTL.

How do you decide a TTL?

Balance read frequency, source change frequency, acceptable staleness, and refill cost, then verify through metrics and real workload.
