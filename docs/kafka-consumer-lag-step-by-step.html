1. Learn the basics first

Kafka stores records in ordered partitions. A consumer group tracks the next offset it has committed for each partition. The broker’s end offset tells us how far the partition has advanced.

Consumer lag is the number of records between the group’s committed position and the current end of the log. It is a useful signal that consumers may be falling behind, but it is a record count, not a time duration.

More consumer threads do not automatically mean more throughput. In one consumer group, a partition can be actively assigned to only one consumer at a time. Effective parallelism is bounded by partition count and by the work each consumer can complete.

What changed in this task: the repository had Kafka listeners and Prometheus scraping but no consumer lag calculation or dashboard panel. It now has scheduled lag measurement for both Member Service event groups, an explicit listener concurrency setting, a Grafana lag/consumption view, and focused calculation tests.

2. What was already present, and what was missing

Already present were two Kafka listener groups, two single-partition event topics, Prometheus scraping of Member Service Actuator metrics, a service overview dashboard, and a consumed-record counter by flow. No measurement of committed offsets versus log end offsets was found, and the dashboard had no Kafka panels.

The current topic definitions use one partition each. The new listener setting is therefore explicitly set to one by default. This documents and preserves the effective parallelism today; raising concurrency without adding partitions would create idle consumers, not additional processing capacity.

4. Understand the lag math

For each partition, the metric uses:

partition lag = max(0, log end offset - next committed offset)
group/topic lag = sum(partition lag for the topic)

Kafka’s committed offset is the next record position the group will read. For a group that has not committed an offset for a partition yet, this implementation uses the partition’s beginning offset. That matches the configured auto-offset-reset: earliest behavior for a new group. If retention has advanced past a stale committed offset, the calculation uses the current beginning offset so lag counts only records still retained. A partition missing from the end-offset response is skipped rather than guessed.

The metric is refreshed periodically, so it is a sampled estimate. If AdminClient cannot query Kafka, a poll-failure counter increments and the gauge keeps its last successful value. Until the first successful measurement, it is -1 to represent “unknown”; do not interpret that sentinel as negative backlog.

Lag is not age: 500 records could represent a short delay on a fast topic or a long delay on a slow one. To estimate time behind, combine lag with observed arrival/consume rates or add oldest-record timestamp measurement.

5. Follow one measurement, step by step

Step 1 — the scheduled job wakes up

@EnableScheduling is already active in MemberServiceApplication. The new component runs with kafka.consumer-lag.poll, defaulting to 15 seconds.

Step 2 — discover the topic partitions

The AdminClient asks Kafka to describe the configured topic. It constructs one TopicPartition for each current partition rather than assuming a permanent partition count.

Step 3 — fetch offsets

For each partition it fetches latest and earliest offsets. It also reads the consumer group’s committed offsets. Each AdminClient wait is bounded to 10 seconds.

Step 4 — calculate the aggregate

For committed partitions it subtracts the committed offset from the latest offset. For partitions without a commit it subtracts the earliest offset. Negative results are clamped to zero and partition results are summed into one group/topic gauge.

Step 5 — export and display

Micrometer exposes kafka.consumer.lag with bounded group and topic tags. Prometheus scrapes /actuator/prometheus. Grafana displays lag next to the rate of kafka.messages.consumed.

Step 6 — investigate before tuning

Compare lag trend with consume rate, error/DLT activity, database health, and event arrival rate. A rising lag with flat consumption points to a bottleneck or failure; a temporary spike followed by a decline can be healthy recovery.

6. Tune in the right order

  1. Confirm sustained lag. Ignore a single short spike; use a time window that covers multiple 15-second measurements.
  2. Compare input and output. Compare the lag trend with the existing consumed-event counter rate. If incoming traffic is unknown, instrument producer/arrival rate before guessing.
  3. Find the slow stage. Listener work writes notification rows with recipient-selection SQL. Check DB latency, connection pool saturation, errors, and DLT rate before changing Kafka consumer settings.
  4. Check partitions first. Current topic has one partition; concurrency above one cannot raise parallelism for its group. A scale-out plan starts with partition count and ordering/partition-key review.
  5. Set listener concurrency no higher than useful partitions. Use KAFKA_LISTENER_CONCURRENCY. At current settings, one is the useful default.
  6. Reassess downstream capacity. More partitions and active consumers also increase concurrent database work. Load-test notification writes and PostgreSQL before increasing replicas or partitions.
  7. Validate after each change. Check lag declines under representative load, consume rate increases, errors remain controlled, and database latency stays within its target.

Do not “tune” by blindly increasing max.poll.records or thread count. Batch size can increase per-poll work and memory, and the consumer must still complete work within poll/session constraints. This implementation does not dynamically auto-scale listener concurrency based on lag.

8. Dashboard and Prometheus queries

The Grafana service overview now includes consumer lag by group/topic and consumed events per second by flow. With Micrometer Prometheus naming, the gauge is expected as kafka_consumer_lag and the counter as kafka_messages_consumed_total; verify actual names at the running endpoint before relying on saved queries.

# Group-level lag, collapsed across Member Service replicas
max by (group, topic) (
  kafka_consumer_lag{namespace="emerald-housing"}
)

# Successful unique event processing rate
sum by (flow) (
  rate(kafka_messages_consumed_total{namespace="emerald-housing"}[5m])
)

Prometheus scrapes every 15 seconds. Since both application polling and scraping are 15 seconds, short bursts can occur between samples; use trends instead of interpreting one sample as an exact instantaneous value.

kafka.consumer.lag.poll.failures counts failed measurements. On failure, logs include group and topic; the metric itself intentionally has no high-cardinality labels.

9. Operational runbook

  1. Open Grafana’s Emerald Housing Service Overview dashboard and inspect lag by consumer group/topic together with consumed events per second.
  2. If lag remains elevated or rises, check the Member Service Prometheus target and the kafka.consumer.lag.poll.failures counter. Confirm the gauge is not still at its initial -1 state.
  3. Review Member Service logs for lag collection failures and consumer processing errors. Check Kafka broker health and topic partition/offset state.
  4. Compare the consume rate with arrival rate and inspect DLT activity. A falling lag means the group is catching up; a flat lag with no consume rate suggests the listener is not making progress.
  5. Inspect PostgreSQL latency and pool pressure because each event may query recipient membership and insert notification rows.
  6. Only then change concurrency or partition count. Keep concurrency aligned with partitions and validate event ordering, database headroom, and lag after rollout.

Lag can be high for an inactive group that has not started consuming, or temporarily high after a restart. Interpret group activity, retention, and topic throughput with the numeric gauge.

10. Verification performed

A focused JUnit test verifies that lag is summed across partitions, that partitions without a committed offset use their beginning offset, and that an offset race cannot produce negative lag. The Member Service module compiled and the test passed.

The calculation test does not start a live Kafka broker or prove the AdminClient polling loop against a deployed cluster. The dashboard and config still need runtime validation in the target Kubernetes environment by checking the emitted series and Grafana panel results.

11. Limits and cautions

  • Measurement is scoped to the two known Member Service groups/topics, not arbitrary Kafka consumers.
  • Every Member Service replica creates an AdminClient and independently queries the same group offsets every poll interval; the dashboard aggregates identical lag values.
  • Admin query timeouts are 10 seconds per awaited operation. Poll failures preserve the last known value, so operators should watch the failure counter too.
  • Lag counts retained offsets/records, not elapsed time or business impact. If committed offset is older than log start because of retention, only currently retained records count.
  • The topics currently have one partition; adding concurrency alone does not scale a group.
  • No automatic lag-triggered scaling policy or alert rule was added. HPA behavior is not wired to this gauge.
  • Concurrency changes can increase database pressure and should be load-tested. The repository has a unit calculation test, not a consumer load test.

12. Interview preparation

60-second explanation

“We measure Kafka consumer lag by comparing each group’s committed offset with the broker’s latest offset for every partition, then summing the differences. A scheduled AdminClient poll records a Micrometer gauge per topic and consumer group, which Prometheus scrapes and Grafana displays alongside consume rate. New groups use beginning offsets because the consumers are configured for earliest. Both topics currently have one partition, so concurrency is explicitly one; scaling throughput requires more partitions and enough downstream database capacity, not merely more listener threads. The metric is sampled record count rather than message age, and collection failures are tracked separately.”

Likely follow-upAnswer
Is lag a time measurement?No. It is a count of records between committed and end offsets. Estimate age by combining it with rates or measure record timestamps.
Why include beginning offsets?A new group may have no committed offset. Here auto-offset-reset is earliest, so beginning offset represents its starting position.
Why not increase consumer concurrency now?Each topic has one partition. A single group cannot process one partition concurrently in multiple consumers, so extra threads would be idle.
How do you know whether the consumer is catching up?Observe lag slope and compare it to consumed throughput and incoming event rate. Declining lag means processing exceeds arrivals over that interval.
What can distort the signal?Sampling interval, inactive groups, retention moving the beginning offset, scrape failures, and a stale last-known gauge after AdminClient errors.
How would you scale safely?Review ordering/key requirements, increase partitions, align listener concurrency, verify consumer group assignments, load-test notification database work, and watch lag plus DB resources.
