Step 1 | Learn the words first

What is a cache?

A cache stores a copy of data that is expensive or frequent to read. Redis is a separate in-memory service used here so different Society Service pods can share cached values.

  • Cache hit: requested value is already in Redis.
  • Cache miss: Redis has no value; the service loads it from PostgreSQL.
  • TTL: time-to-live, after which Redis expires the value.
  • Eviction/invalidation: remove a cached value because the underlying data changed.
  • Negative cache: briefly remember that a lookup was not found, avoiding repeated database checks for the same missing ID.
  • Cache stampede: many requests miss the same key and all try to load the same database value at once.
Analogy: keep a frequently used building directory at reception. Most people read the copy. When a flat or floor changes, replace or invalidate the copy so it does not keep showing old information.
Step 2 | Understand what caching changes

Read path before and after Redis

Without cacheRequest -> PostgreSQL -> response
Cache hitRequest -> Redis -> response
Cache missRequest -> Redis miss -> PostgreSQL -> Redis fill -> response

A cache can reduce repeated database reads and latency. It adds another service, data serialization, invalidation rules, and the risk of serving stale values. This project uses it for selected Society reference reads rather than every API response.

Step 4 | Trace one request from code to response

Example: fetch all floors

GET /api/v1/floors
1. ControllerCalls FloorService.getAll
2. Cache advice@Cacheable checks societyFloors/all
3. Redis hitReturn serialized FloorResponse list
4. Redis missLoad FloorRepository rows
5. FillStore response in Redis with TTL

FloorService marks the method @Cacheable with key all and synchronized loading. CacheResolver chooses a wrapped Redis cache; the wrapper measures access and adds a distributed per-key load lock for value-loader misses. The repository work runs only when Redis has no value or the cache is bypassed.

Example: get a flat by ID

FlatService.getCached(id) first checks the short-lived negative cache for a known-missing flat, then uses @Cacheable for societyFlatById. On a miss it loads the flat and floor from PostgreSQL and caches the response. If PostgreSQL says the flat does not exist, the service records a negative entry for 30 seconds.

Step 5 | Understand Redis configuration

Connection, serialization, and expiry

Society Service connects to Redis using environment-configurable host, port, password, connect timeout, command timeout, and Lettuce pool settings. Checked-in defaults include 500 ms connect/command timeouts, pool max-active 12, max-idle 8, min-idle 1, and max-wait 500 ms.

SocietyCacheConfiguration builds a RedisCacheManager with explicit cache names and typed JSON serializers for FlatResponse and FloorResponse values. Null values are disabled. Cache entries are transaction-aware so puts/evictions align with transaction completion.

Cache TTLs, TTL jitter, load-lock wait/lease/retry, negative TTL, and Redis fallback concurrency are configurable. Defaults include 2-second lock wait, 30-second lock lease, 25-millisecond retry, and at most 16 concurrent database fallback loads per pod.

Step 6 | Learn how stale data is prevented

Mutations evict cached values

Flat and floor write paths evict affected caches. Flat changes evict the by-ID entry, all-flat list, affected floor list, and negative key. A FlatReferenceChangedEvent listener runs after database commit to invalidate related caches.

Write requestUpdate flat/floor in PostgreSQL
CommitDatabase transaction commits
After-commit listenerEvict affected Redis entries
Next readMiss loads the fresh value

Using after-commit invalidation avoids evicting the cache for a database change that later rolls back. Floor service also evicts related flat list caches on floor changes. TTL remains a backup bound on stale values if invalidation fails.

Step 7 | See what happens if Redis fails

Fallback is bounded and observable

Cache get/put/evict/clear errors are caught by the configured handler/wrapper and recorded. A Redis failure activates a local 5-second bypass window for that Society pod, during which cache reads use a NoOpCacheManager and loads go to PostgreSQL. A semaphore limits fallback database loads to 16 concurrent operations per pod; excess loads fail fast and increment a rejection metric.

On cache misses, a Redis lock keyed by cache and key coordinates concurrent loaders across pods. If lock acquisition fails or times out, the service loads without filling the cache and records a timeout. The lease expires automatically if a process dies before releasing the lock.

Scope: failure bypass state and fallback semaphore are per process/pod, not shared cluster-wide. Redis keys and load locks are shared through Redis.

Metric nuance: initial cache get calls are counted. After a distributed load-lock wait, the wrapper rechecks Redis without recording a second cache lookup. Thus this is an operational lookup hit ratio, not a perfect count of every cache read made internally.
Step 9 | Operate and interpret the metrics

What to check during a load test or incident

  1. Group lookups by cache name; compare hit and miss rates during the same workload.
  2. Check hit-rate denominator is nonzero and exclude errors/bypass from hit-rate interpretation.
  3. Compare hit and miss lookup durations; high cache-hit latency may indicate Redis/network/pool pressure.
  4. Compare miss counts with database-load counts and database-load duration.
  5. Check Redis failures, load-lock timeouts, fallback rejections, and negative-cache counters.
  6. After flat/floor writes, verify the relevant cache entries are evicted and the next request reloads current data.

Actuator exposes metrics and prometheus. /actuator/metrics is restricted to ADMIN or SOCIETY_ADMIN; Prometheus scrapes the pod's /actuator/prometheus endpoint every 15 seconds.

Step 10 | Understand the limits

What the cache does not promise

  • Only selected Society reference-data methods are cached; member records and all API results are not globally cached.
  • Cache entries can be stale until eviction or TTL expiry. Invalidation is best-effort if Redis is unavailable; TTL bounds the stale period.
  • Redis bypass and fallback permits are per pod, so aggregate fallback concurrency can reach per-pod limit times number of pods.
  • Metrics count instrumented cache accesses. Load-lock rechecks are not counted independently, and scrape intervals can miss short spikes.
  • Current Grafana dashboard has no dedicated cache hit-rate/latency panels, although the metrics are available for Prometheus queries.
  • Redis cache hit rate alone does not prove faster API responses; compare database load, endpoint latency, and Redis latency under the same workload.
Step 11 | Interview practice

Developer-level explanation

"Society Service uses Redis through Spring Cache for selected floor and flat reference reads. CacheManager configures typed JSON values, per-cache TTLs, TTL jitter, and a versioned key prefix. The service methods use @Cacheable and write methods evict affected keys, with flat-reference events invalidating after commit. I instrumented lookups with hit/miss/error counters and a lookup timer; PostgreSQL fallback loads have separate counters and timers. Prometheus scrapes these metrics, so I calculate hit rate as hits over hits plus misses and compare cache lookup time with database-load time. Redis errors trigger a short per-pod bypass and bounded database fallback, and a Redis lock prevents many pods loading the same key simultaneously. The Grafana overview currently lacks cache panels, so metrics are queried directly in Prometheus. The hit ratio is an operational estimate because post-lock rechecks are not counted as separate lookups."

Likely follow-up questions

Why use TTL jitter?

It spreads expirations over time so many entries do not all expire together and create a database load spike.

Why invalidate after commit?

It avoids evicting a still-valid cache value when the database transaction rolls back.

What is the difference between negative cache and normal cache?

The negative cache briefly stores that a flat ID was not found, preventing repeated database reads for the same missing ID.

How do you calculate hit rate?

For a time window, hits divided by hits plus misses. Exclude errors and explicit bypasses, and ensure there were lookups in the window.

What does a high hit rate prove?

It says repeated cache reads are being served from Redis, but not by itself that the API is faster. Compare cache latency, database load, endpoint latency, and correctness.
