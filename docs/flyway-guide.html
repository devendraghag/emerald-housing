1. Start with the idea

A database schema changes as an application grows. Flyway gives those changes a versioned, repeatable history. Instead of asking each developer or deployment operator to make manual database edits, the team stores migration files with the application and applies them in order.

MigrationA change to schema or data, usually expressed as SQL.
VersionThe ordering label in a migration filename, such as V3.
Schema historyFlyway's record of migrations it has applied and their outcomes.
BaselineA declared starting point for an existing schema when a team adopts Flyway; distinct from a normal migration.
Keep this in mind: Flyway coordinates and records database changes. The SQL in each migration defines the actual change.
Repository finding: Flyway is enabled in the Member Service and Society Service. Their migration scripts live under src/main/resources/db/migration. Both configure Hibernate with ddl-auto: validate, so Hibernate checks the mapped schema while Flyway migrations own schema evolution. The checked-in migration streams currently reach Member V19 and Society V10.

3. How Flyway works

  1. Package migration files. SQL files are included in the service classpath in db/migration. The standard versioned naming form is V<version>__<description>.sql, for example V3__index_flat_floor_order.sql.
  2. Connect to the target database. Spring Boot configures Flyway using the application's datasource settings. Member and Society have service-specific writer database URLs and credentials.
  3. Inspect migration history. Flyway creates or reads flyway_schema_history in the configured schema. It compares available migration versions with the successful records.
  4. Choose pending migrations. Migrations that are not yet recorded as successfully applied are selected in version order.
  5. Execute the SQL. Flyway runs the migration script against the target database. Database transaction behavior and DDL support depend on the database and statement; PostgreSQL supports transactional execution for many common DDL statements.
  6. Record the result. Successful execution is recorded in the history table with version, description, checksum, and other metadata. Future startups can see that version is already applied.
  7. Validate the application mapping. Hibernate's configured validate mode checks that the entity mapping is compatible with the schema. It does not replace Flyway's migration history.
Migration SQL in artifact→Flyway at startup→Database schema + history→Hibernate validation

The exact ordering of auto-configuration is managed by Spring Boot. Operationally, a service must not become ready to handle database-backed traffic if required startup migration or schema validation fails.

4. A real project example: flat listing index

The Society Service lists flats by floor and orders them by flat number. The migration history evolves the database to support this access path.

Earlier schema: V1 and V2

V1 creates the society, floor, and flat tables, with keys and constraints. It also creates a narrower index on flats(floor_id). V2 inserts the Emerald society and its configured floors.

Later schema change: V3

-- The common floor listing filters by floor_id and orders by flat_number.
-- The composite index serves both operations and replaces the narrower index.
DROP INDEX IF EXISTS ix_flats_floor;
CREATE INDEX ix_flats_floor_flat_number ON flats (floor_id, flat_number);

Flyway applies V3 after prior migrations when that database has not recorded V3. It removes the old index definition and creates a composite index; it does not delete flat rows. The change becomes part of the database's migration history.

Later still: V10 search support

Society V10 enables PostgreSQL's pg_trgm extension and adds a GIN index on lower(flat_number) for contains-style directory search. This is an example of adding a new versioned migration for a new query pattern instead of editing the already-applied V3 file.

Developer workflow: identify the required schema change, add the next unused versioned migration to the service that owns the database, review it alongside the repository query and entity mapping, then validate both a fresh database and an upgrade from an existing version.

5. System design and deployment view

In this repository, Member and Society have separate service databases and separate migration locations. That is a useful service boundary: each service owns the schema its code reads and writes. A migration in one service should not casually modify another service's database.

Build oncePackage migration resources with the service artifact so the same reviewed migration set moves through environments.
Coordinate startupWhen multiple replicas start, migration execution must be coordinated by Flyway/database locking behavior. Still plan rollouts so application readiness depends on a usable schema.
Use least privilegeWhere operations require it, separate migration permissions from the application's steady-state data permissions.
Support rolling deploysPrefer changes compatible with both old and new application versions while replicas overlap.

Expand and contract pattern

  1. Expand: add a nullable column, new table, or compatible index without breaking the current application.
  2. Deploy compatible code: teach the application to write/read the new shape while old replicas can still operate.
  3. Backfill: populate old rows in controlled, observable batches when needed.
  4. Switch use: move reads to the new representation and verify behavior.
  5. Contract later: remove the old column or constraint only after no running code depends on it.

This staged approach reduces the risk of a single deployment that changes schema and application assumptions incompatibly. It is especially useful for large tables and zero-downtime deployments.

6. Safe migration practices

  • Never rewrite an applied versioned migration. Flyway stores checksums; modifying a script after it has run can make environments disagree or cause validation errors. Add a new migration to correct or extend the schema.
  • Use a unique, increasing version. Coordinate when multiple branches add migrations so two scripts do not claim the same version.
  • Review data effects. Know whether statements preserve, transform, or delete existing data. Take backups and rehearse high-impact changes.
  • Keep large backfills separate. A long update can hold locks and extend deployment time. Consider resumable batches and operational progress tracking.
  • Plan indexes deliberately. Index creation consumes resources and affects writes. For PostgreSQL production tables, consider whether concurrent index creation is needed; that statement has special transaction requirements and needs deliberate Flyway configuration.
  • Make constraints safe to introduce. Existing rows must satisfy new constraints. Clean or backfill data first where required.
  • Review idempotency honestly. Versioned migrations are normally applied once and recorded. Do not assume every SQL statement is safe to rerun after partial failure.
  • Validate on realistic copies. Test data shape, table size, locking, and execution time in a non-production environment before a risky rollout.

7. Failure and recovery

If a migration fails, startup may fail and the application may not become ready. The exact database state depends on which statements completed and whether that database can roll them back in the migration transaction.

  1. Read the application and Flyway error to identify the migration and failing statement.
  2. Inspect flyway_schema_history and the actual schema/data. Do not assume every database engine or statement rolled back completely.
  3. Fix the root cause and determine whether the migration can safely be retried or whether the database needs a deliberate repair procedure.
  4. For an already-applied migration, normally create a new forward migration. Do not silently edit history to hide schema drift.
  5. Use Flyway's repair only for a known history/checksum problem after the database state has been verified. It updates metadata; it does not reverse SQL or restore lost data.
  6. Restore from a tested backup if the data change cannot be safely corrected in place.
Rollback expectation: versioned SQL migrations do not automatically provide a down migration. Design a forward fix or a tested restore strategy. A compensating migration may itself need careful data handling.

8. How this project tests upgrades

The Member and Society upgrade tests use Testcontainers with PostgreSQL 16. Each test migrates a disposable database to version 2, inserts a representative legacy member or flat, then runs the remaining migrations.

  • Member checks the inserted member remains readable and confirms later schema objects exist.
  • Society checks the inserted flat remains readable and verifies a later version column's default.
  • Separate persistence integration tests verify seeded Society data and floors.

This tests the important upgrade path: a populated older schema moving forward. A complete verification strategy should also cover a brand-new empty database and application startup/schema validation.

Current test maintenance: migration files now extend past the versions hard-coded in the upgrade tests' final history assertions. Update those assertions when intended, then run the PostgreSQL-backed tests so the checked-in migration stream and test expectation agree.

9. What Flyway does and does not do

Flyway helps withIt does not automatically guarantee
Ordering and applying versioned migration scripts.That the SQL is correct, fast, or safe for production data.
Recording applied versions and checksums.That all environments have no manual schema drift.
Making schema evolution part of the application delivery process.Zero-downtime compatibility between old and new application versions.
Providing commands and metadata for migration validation/repair workflows.Automatic rollback of arbitrary SQL or recovery of deleted data.

Teams remain responsible for reviewing SQL, testing upgrade paths, planning operational windows, and having recovery procedures.

10. Explain Flyway in an interview

Short answer: "We use Flyway to version database changes alongside the service code. At startup, Flyway checks its schema history table and applies pending versioned SQL migrations in order. In Emerald Housing, Member and Society own separate migration streams, and Hibernate is set to validate rather than create or update the schema. We test both migration behavior and upgrades from populated older schemas. For production, I keep applied migrations immutable, design backward-compatible rollout steps, and plan recovery because Flyway does not automatically roll back arbitrary SQL."

Likely follow-ups

Why not let Hibernate create the production schema?

Explicit migrations make schema changes reviewable, ordered, and reproducible. Hibernate validation can detect mapping/schema mismatch without silently changing production structures.

What does the history table store?

Flyway records migration metadata such as version, description, checksum, execution state, and timing. It uses that record to determine what is pending and validate applied scripts.

What if two application replicas start together?

Flyway coordinates migration execution against the database, but deployments should still ensure only compatible application versions serve traffic and readiness waits for successful initialization.

How do you change a migration that already ran?

Do not edit it. Add a new migration that moves the schema forward, and reconcile any environment-specific drift explicitly.

How do you avoid downtime for a column change?

Use expand-and-contract: add a compatible shape, deploy code that supports both, backfill, switch usage, and remove the old shape in a later release.

Can Flyway roll back a failed migration?

Behavior depends on database transaction support and the statements involved. Flyway does not infer a safe inverse for arbitrary SQL; inspect the state and use a reviewed forward fix or restore plan.
