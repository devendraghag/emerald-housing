Lesson 1 · Start with the problem

Why does a database need careful updates?

A database is where an application keeps important information: members, flats, payments, and more. As the application gets new features, the database structure must change too.

Imagine every developer, test environment, and production operator manually changing tables. Soon the databases differ: one has a new column, another does not, and nobody knows exactly which SQL was run. The application can then fail or use the wrong data.

Without a migration toolDatabase changes are hard to repeat, review, and trace.
With migration filesChanges are saved as ordered scripts with the application code.
With FlywayScripts are applied in order and recorded so successful work is not repeated.
Simple analogy: a migration is a numbered recipe for changing the database. Flyway is the cook that checks which recipes have already been completed.
Lesson 2 · Meet Flyway

What does Flyway do?

Flyway is a database migration tool. Your team writes SQL files that describe changes. Flyway finds those files, checks its history for the target database, runs pending migrations in order, and records what succeeded.

Migration fileA saved SQL change, such as creating a table or adding an index.
VersionThe order label in the filename, for example V3.
History tableflyway_schema_history, Flyway's record of migration runs.
BaselineA starting marker used when Flyway is introduced to a database that already has tables.
Important: Flyway does not decide what your database should look like and does not write the SQL change for you. A developer creates and reviews the migration file.
Lesson 3 · Follow one startup

What happens when the service starts?

  1. Spring Boot starts the service and connects Flyway to its configured database.
  2. Flyway reads the migration files packaged with the service.
  3. Flyway checks flyway_schema_history to see which versions succeeded.
  4. Flyway runs pending versions in order and records each result.
  5. Hibernate can then check that the Java entity mappings match the database schema.
Pack files→Compare history→Run pending SQL→Record + validate

If a migration fails, Flyway normally stops at that version. The service may not finish startup. The exact database changes that remain depend on the database and statements.

Lesson 4 · Understand versions

Will Flyway run V1–V10 every time?

No. A new database runs the available versions in order. After a version succeeds, Flyway records it in history and skips it on later starts. If a database is at V7, Flyway starts with the pending versions after V7.

Choose a state, then select “Show what runs”.

The simulator shows the basic version rule. Validation errors, configured targets, missing scripts, and failed SQL can also stop a real migration.

Migration filename

V<version>__<description>.sql

Example:
V11__add_flat_search_index.sql

The two underscores separate the version from its description. Use the next unused version in that service's migration stream. Member V11 and Society V11 can be different files because the services have separate databases and history.

Does adding a migration file change the database immediately?

No. The file must be included in a deployed artifact or run through a separate migration job. With this project's startup-based setup, Flyway applies pending files when the service starts.

What if V4 fails—can V5 still succeed?

Normally no. Flyway stops at the first failed migration. If V4 fails, V5 and later pending versions do not run in that attempt. Earlier successful versions remain recorded.

Does Flyway generate a migration by comparing entities and tables?

No. Flyway runs migration files you provide; it does not infer your intended changes from entity classes.

Lesson 5 · Make a database change

How do I change a table or index?

Put explicit SQL in a new migration file in the service that owns the database. For a table, that might be an ALTER TABLE. For an index, it might drop an old index and create a new one.

In Society Service, V3 replaces the narrow floor index with a composite index used for filtering by floor and ordering flats by number:

DROP INDEX IF EXISTS ix_flats_floor;
CREATE INDEX ix_flats_floor_flat_number
    ON flats (floor_id, flat_number);

Society V10 later enables PostgreSQL pg_trgm and adds a GIN search index for substring-style flat directory search. That query improvement belongs in a new migration; don't go back and rewrite V3.

1 · PlanCheck the query, entity, existing data, constraints, and index usage.
2 · WriteCreate the next unique versioned SQL migration.
3 · TestCheck an empty database and an upgrade from existing data.
4 · DeployPackage and deploy; Flyway applies the pending version.
Applied migration rule: once a versioned migration has been applied in a shared environment, treat it as immutable. Editing it won't rerun the SQL; validation will usually report a checksum mismatch. Restore the original and make a new migration.
What if it ran only on my disposable local database?

You can usually edit it if nobody else or any shared environment has applied or depended on that version. Recreate the local database so the file can run from a clean state.

Can I rename an applied migration?

Avoid it. The recorded migration and available script can become inconsistent and validation may fail.

Two branches used the same version. What now?

Resolve the collision before shared deployment and assign a unique next version. Never reuse a version that has already been applied in a shared database.

Lesson 6 · Read Flyway's records

What is in flyway_schema_history?

It is Flyway's receipt book for one database. The exact columns can vary by Flyway version and database.

ColumnMeaning
installed_rankThe order migrations were installed. It is not the same as the migration version.
versionThe version label, such as 3 for V3. Repeatable migrations generally have no version.
descriptionA readable description derived from the migration name.
typeMigration type, such as SQL, JDBC, or BASELINE.
scriptThe migration filename or script identifier.
checksumA value Flyway uses to notice changes to an applied script.
installed_byThe database user Flyway used. Different environments may show different users.
installed_onWhen Flyway recorded the migration installation.
execution_timeHow long the migration took, usually milliseconds.
successWhether the migration was recorded as successful.
Managing installed_by: Flyway normally uses the application's datasource. You can set Flyway-specific URL/user/password for a dedicated migration identity, or use a controlled CI/CD migration job. Store secrets securely; grant migration privileges only to the migration identity and limit runtime database permissions.
What does a checksum mismatch mean?

The migration file no longer matches the checksum recorded when it was applied—often because someone edited the file. Restore the original file and put new changes in a new migration. Don't use repair just to hide the discrepancy.

What does success = false mean?

A migration attempt failed. Inspect the actual schema and data; some effects may remain depending on the database and statements.

Can I delete a failed history row by hand?

Don't edit Flyway history manually as a routine fix. Inspect the database and use a deliberate Flyway recovery operation where appropriate.

Does history record each SQL statement?

No. It records migration-level metadata, not a detailed audit of each SQL statement's effects.

Lesson 6A · Understand checksums and V/R migrations

What if a migration file changes after it ran?

Flyway treats versioned migrations as a permanent history. Repeatable migrations have a different job: Flyway runs them again when their content changes.

Learning goal: Recognize a checksum mismatch, explain what repair changes, and choose between a V and an R migration.

1. A checksum is Flyway’s file fingerprint

When Flyway applies a SQL migration, it records a checksum in flyway_schema_history. During validation, it compares that checksum with the migration file currently available to the application. A difference means the applied file and current file no longer match.

1 · Apply V1name VARCHAR(100)
Flyway records its checksum.
2 · Edit V1 latername VARCHAR(200)
The file now has a different fingerprint.
3 · ValidateFlyway reports a mismatch. It does not rerun V1 to alter the database.
WhereWhat it says
History checksumFingerprint from the file when applied, e.g. 123456.
Resolved file checksumFingerprint Flyway calculates from the current file, e.g. 987654.
Actual databaseStill has VARCHAR(100) unless a separate database change altered it.

Values are illustrative. Flyway uses CRC32 for SQL migration checksums. Treat an applied versioned file as immutable, including for cosmetic edits.

2. What does repair do here?

If you run repair after editing V1, Flyway can align the stored checksum with the edited file. That changes migration history metadata only. The actual column remains VARCHAR(100); Flyway does not execute edited V1 SQL.

After repairState
History checksumMay now match the edited file.
V1 fileContains the new definition.
Actual database columnStill has the old definition unless changed separately.
ResultMetadata may align while schema and migration intent still disagree.
Production rule: Don’t use repair to silence an unexpected checksum mismatch. Find out why it changed. The normal fix is to restore the original V1 file and add a new versioned migration. Use repair only as a deliberate, reviewed metadata operation after understanding the database state.

3. Correct path: restore, then add a new V migration

Restore V1 exactly as it was when applied. Add a new migration with the next available version. This project uses PostgreSQL, so the example uses PostgreSQL syntax:

-- V2__widen_product_name.sql\nALTER TABLE product\n    ALTER COLUMN name TYPE VARCHAR(200);

Deploy through the normal release path. Flyway applies V2 once; later starts skip it. Review existing data and application compatibility.

Restore original V1→Add V2 with ALTER TABLE→Review and test→Deploy; Flyway migrates→Validate schema and app

Can R replace a failed V?No. Renaming a failed V to R does not complete or repair that V. Recover the failed migration and its database effects.

5. Why a failed V migration cannot be replaced by R

If V3 adds a column and then fails on a later SQL statement, Flyway stops that migration run; later pending migrations and repeatables don’t bypass V3. Renaming V3__add_stock.sql to R__add_stock.sql changes the migration identity and can leave Flyway’s failed state unresolved.

Inspect the failed migration record and actual database first. Depending on database, SQL, and transaction behavior, earlier statements may remain. Reconcile those changes, correct the migration following team policy, and use repair only if history metadata needs repair. Then rerun migrate and validate. See Lesson 9: production recovery.

6. Quick choice guide

Choose V for structural changesCreating or altering tables, columns, indexes, constraints, and ordered data corrections.
Choose R for replaceable definitionsViews, stored procedures, and functions whose full definition can be safely reapplied.
Before choosing R for dataMake the script idempotent and avoid accidental duplicate or destructive updates.

Interview Q&A

What does a Flyway checksum mismatch mean?

The checksum in history differs from the checksum of the migration file resolved by Flyway. It commonly indicates an applied migration was edited. Validation detects the difference; Flyway does not rerun a versioned migration.

Does repair change my table to match the edited migration?

No. Repair changes Flyway history metadata. It does not execute migration SQL or alter the actual schema or data.

How do you correct an applied V migration that needs a change?

Restore the original applied file, create a new versioned migration with the intended SQL, and promote it through environments. Use repair only if a verified history problem remains and the operation is reviewed.

Why is changing an R migration different?

Repeatable migrations are designed to be reapplied when their checksum changes. Flyway runs changed repeatables after pending versioned migrations. The SQL must be safe to reapply.

Can I rename a failed V migration as R?

No. R is a different migration type, not a recovery mechanism. Inspect and reconcile the failed V migration and its effects first.

7. Flyway Fix Forward · Meaning with an example

Fix Forward means fixing a database issue with a new migration, instead of editing or trying to reverse a migration that already succeeded. The old migration stays as the record of what happened; the new one moves every database to the corrected state.

Example from the Member schema: the original migration defines members.full_name as VARCHAR(160). If the application later needs a wider field, do not change the applied V1 file. If V20 is still the next unused version, create:

-- V20__widen_member_full_name.sql
ALTER TABLE members
    ALTER COLUMN full_name TYPE VARCHAR(200);
Keep applied V1 unchanged→Add a new versioned migration→Review and deploy the service→Flyway applies the pending version once→Hibernate validates the mapping

Update the JPA mapping in the same planned release and check that existing values fit. Promote the same reviewed change through environments. For a risky rename while old and new pods overlap, use the expand-and-contract example in Lesson 8 · Deploy safely.

Fix Forward is a strategy, not a Flyway command. It uses a new migration and the normal migrate operation. It does not restore deleted data; use a recovery/backup plan for data loss.
Why not edit the old migration or run repair?

Editing an applied versioned file does not rerun its SQL and can cause checksum validation to fail. Repair can realign history metadata but cannot apply the intended schema change. Restore the original file and create a later migration.

Is Fix Forward the same as rolling back the application?

No. Application rollback may be part of an incident response, but the database change still needs a safe plan. Fix Forward specifically means applying a new database migration to correct or extend the schema.

8. Flyway Repair: when it helps and when it does not

flyway repair corrects Flyway’s migration-history metadata. It does not run migration SQL, undo a successful migration, remove leftover database objects, or restore data. Before running it, compare the history with the actual database state.

Failed migration example: inspect before repair

Imagine V3__create_employee_email_index.sql contains an index on email_address, but the table column is named email. Flyway reports that V3 failed. Do not assume the history row tells you whether database changes remain.

-- Incorrect V3
CREATE INDEX idx_employee_email
    ON employee(email_address);

-- Corrected V3, only if this failed version has not succeeded
-- in another shared environment and your team approves the retry
CREATE INDEX idx_employee_email
    ON employee(email);
Database matters: Emerald Housing uses PostgreSQL. Many PostgreSQL DDL statements can roll back with a failed migration transaction, but behavior depends on the exact statement and configuration. In MySQL, many DDL statements commit independently, so an earlier statement such as adding salary may remain when a later statement fails. Inspect the real database in either case.
Pause deployment→Inspect logs + history→Inspect schema + data→Reconcile partial changes→Repair only if history needs it→Retry migrate + validate

If the corrected V3 already succeeded in another shared database, do not change V3. Restore its applied contents and create a later migration instead.

Checksum mismatch: repair is not a schema change

If V2 already ran with salary NUMERIC(10,2), then someone edits V2 to say NUMERIC(12,2), repair may align the stored checksum with that edited file. The production column remains NUMERIC(10,2); V2 is not rerun. The usual production fix is to restore original V2 and add a new versioned migration:

-- V3__widen_employee_salary.sql (PostgreSQL example)
ALTER TABLE employee
    ALTER COLUMN salary TYPE NUMERIC(12,2);

If repair was already run against the edited file, restoring the original can create another metadata mismatch. Only realign history through a controlled repair after confirming the schema and intended migration history.

9. Repair vs Recovery vs Fix Forward vs Undo

ApproachPurposeExample
RepairFix Flyway migration history metadata.Remove a failed migration record after checking and reconciling any partial database changes.
RecoveryRestore the actual database to a safe, consistent state.Restore deleted data from a suitable backup or point-in-time recovery.
Fix ForwardFix an issue with a new versioned migration.V3 has a problem; keep it unchanged and add V4 with the correction.
UndoReverse a successful migration using its matching undo script, when supported.Use the U3 script to reverse V3.
Remember: Repair fixes history. Recovery fixes the database state. Fix Forward adds a new change. Undo reverses a successful change when supported and prepared.

Interview question

When do you use Flyway Repair during a production incident?

I first pause deployment and inspect the error, Flyway history, and actual schema/data. I reconcile partial changes or choose a forward/restore plan. If a failed history entry or other verified metadata inconsistency remains, I run repair with the same migration locations as migrate, then migrate and validate. Repair does not repair the actual database. For an edited applied migration, I normally restore the original file and create a new migration.

What is Fix Forward in Flyway, and why is it preferred in production?

Fix Forward means fixing a database issue with a new versioned migration instead of modifying or trying to reverse a migration that already succeeded. For example, if V3 has an incorrect column definition, leave V3 unchanged, create V4 with the corrected SQL, and run flyway migrate. This preserves the applied migration history, avoids checksum mismatches caused by editing V3, and lets each environment apply the correction in order.

Official references: Repair, Migrations and transaction behavior, Undo, Validate, Versioned migrations, and Repeatable migrations.

Lesson 7 · Connect Flyway to Hibernate

No. It checks mapping compatibility and may fail startup; create the required object in a migration.

Lesson 8 · Deploy safely

How do we release a database change safely?

A production release includes both the new database shape and the new application code. During a rolling update, old and new app pods can run at the same time. The database must work with both until the old pods are gone.

Simple rule: Add the new database part first. Move the app to use it. Remove the old database part in a later release.

Example: rename members.full_name to display_name

This is a learning example based on the Member table in this project. It is not a change being made to the application. The current Member migrations go through V19, so V20 would be the next version only if no newer migration exists when the change is created.

Why not rename the column in one step? While the rollout is happening, an old pod may still run SQL that expects full_name. If a migration removes or renames it before that pod stops, old code can fail.
Release 1 · Add

Keep both columns

Add a new column that allows old rows to have no value yet.

-- V20__add_member_display_name.sql
ALTER TABLE members
    ADD COLUMN display_name VARCHAR(160);

Old app pods keep using full_name. New app code can read display_name when it exists and fall back to full_name. During the transition, write both columns.

Between releases · Copy

Fill old rows

Copy existing names into the new column. For a large table, run in small, monitored batches instead of one huge update.

UPDATE members
SET display_name = full_name
WHERE display_name IS NULL;

Check that every required row has a value before making the new column mandatory.

Release 2 · Switch

Use the new column

After all old pods are gone and the data is copied, deploy code that reads and writes display_name. Keep compatibility while rollback to the previous app is still possible.

Update the JPA mapping and any search query or index that uses the old name. In this repository, Member V19 creates a search index on full_name, so account for that dependency in a planned migration.

Later release · Remove

Clean up the old column

Only after no deployed code or other consumer needs full_name, add a later migration to remove it and remove or replace related indexes. Deploy the matching entity/code change.

What this looks like in this project

  1. Add a new versioned SQL file to the Member Service migration folder. Do not edit a migration that has already been applied.
  2. Review the SQL and test both a new database and an upgrade from an existing database with member data.
  3. Deploy the compatible application image. The Member and Society Kubernetes deployments use rolling updates, so old and new pods may overlap.
  4. Check pod readiness, application behavior, migration history, and the copied data before moving to the next release step.
  5. Remove the old column only in a later migration after confirming old pods, rollback versions, queries, and indexes no longer depend on it.
Large or risky changes: Backfills can take time and affect database load. Make them resumable and observable. Review index locks and PostgreSQL transaction requirements before release. Test with production-like data and have a recovery plan.
Lesson 9 · Production recovery

Repair Flyway history or recover the database?

These are different jobs. Repair changes Flyway's history metadata. Recovery fixes actual schema or data problems.

Flyway repairDatabase recovery
Removes failed migration records and can align recorded checksums, descriptions, and types; can mark missing migrations as deleted.Handles partially executed SQL, incorrect schema, or lost/corrupted data.
Changes metadata in flyway_schema_history.Uses inspected SQL changes, corrective migrations, backups, or point-in-time restore.
Does not execute/reverse SQL, drop leftover objects, or restore data.Must match the actual state and data value of the production database.
Use the same target: run repair with the same database, schema, and migration locations as migrate. Never run it automatically at application startup or just to silence an error. See Flyway Repair documentation.

A migration fails halfway: follow the actual state

Imagine V1 and V2 succeeded. V3 contains two MySQL DDL statements. The first adds a column; the next has a typo and fails:

ALTER TABLE product ADD COLUMN stock INT;
ALTER TABLE product ADD COLUMN quantity INTT; -- invalid type

If the first statement succeeded, the stock column may remain even though V3 failed. Flyway stops at V3; later V4 remains pending. Repair can clear a failed history entry, but it does not remove stock. Retrying blindly might hit a duplicate column.

Recovery flow at a glance

Skip database cleanup if inspection confirms nothing changed. Skip repair if history is already correct. Never resume traffic until migration status and application behavior are verified.

Production recovery, step by step

Useful inspection commands include flyway info and a query of the history table. In MySQL, DESCRIBE product; shows columns; use your database client's equivalent schema inspection for PostgreSQL.

SELECT installed_rank, version, description, script, success
FROM flyway_schema_history
ORDER BY installed_rank;

-- MySQL schema inspection
DESCRIBE product;
  1. Stop or pause the deployment. Preserve logs and the database state; take or confirm a recovery point before risky operations.
  2. Identify the failure. Use application logs and flyway info; inspect the matching row in flyway_schema_history.
  3. Inspect real schema and data. For example, use DESCRIBE product; in MySQL or inspect the table definition and rows in PostgreSQL. Determine which statements took effect.
  4. Recover partial effects safely. Remove a partial column only if it is safe and contains no needed data. Otherwise design a forward correction or restore plan.
  5. Correct the failed script only when safe. A failed migration may be corrected only if it has not succeeded in a shared environment. If it succeeded elsewhere, restore its original file and make a new migration.
  6. Repair metadata only if needed. If a failed history entry remains after database reconciliation, run repair with the same target and locations.
  7. Retry and validate. Run migrate, validate, and info; inspect schema/data and test application behavior before resuming the rollout.
flyway info
# Inspect database state and reconcile partial SQL first.
flyway repair    # only if verified and needed
flyway migrate
flyway validate
flyway info

If using Maven, mvn flyway:info, mvn flyway:repair, and similar goals require the Flyway Maven plugin to be configured. The Java API also supports flyway.repair(), flyway.migrate(), and flyway.validate(). Use the same database and locations.

Why the database matters

MySQL 8 with supported InnoDB operations can make an individual DDL statement atomic, but DDL implicitly commits; multiple DDL statements are not one rollbackable transaction. PostgreSQL supports transactions for many DDL statements, but not all operations—for example, CREATE INDEX CONCURRENTLY cannot run inside a transaction block.

References: MySQL atomic DDL, MySQL implicit commits, and PostgreSQL CREATE INDEX.

Does Flyway automatically roll back arbitrary SQL?

No. Database transaction support varies, and Flyway cannot infer a safe inverse. Use a reviewed forward fix or tested restore strategy. Undo migrations require prepared undo scripts and supported Flyway edition/workflow.

Can repair solve a checksum mismatch?

It can align stored metadata to available files, but doing so just to silence a mismatch can legitimize a file that no longer matches the actual database. Normally restore the original applied migration and add a new one.

Should CI/CD automatically repair after a failed migration?

No. A pipeline should stop and request investigation. Repair can change history while partial schema effects remain. Make it a deliberate controlled action after inspection.

Common production problems

A migration works in staging but fails in production. Why?

Production may have different data, table sizes, permissions, or manual schema drift. Compare actual schema/data and reproduce with realistic data before fixing.

Two branches use the same migration version. What do we do?

Resolve the version before shared deployment; use a unique next version in that service's stream.

A migration blocks traffic. How can we reduce risk?

Check locks and runtime. Use resumable batches for large data changes; consider database-specific online index options and rehearse them on production-sized data.

A new constraint fails against old rows. What should happen first?

Identify and repair invalid rows before enforcing the constraint. Stage the rollout and validate existing data.

Old and new replicas disagree about the schema. How can we avoid this?

Use expand-and-contract so both versions work during overlap; remove old schema later.

Flyway cannot connect or alter the schema. What should I check?

Check target URL, secrets, schema selection, network, and the migration account's grants. Keep migration privileges separate from normal runtime privileges where practical.

Production schema differs from migration history. Should I baseline or repair?

First compare history and actual objects/data. Use a reviewed forward reconciliation when possible; baseline/repair only as a deliberate metadata action after verifying state.

Tests pass but production still fails. What could be missing?

Tests may miss production-sized tables, real permissions, fresh installs, old/new version overlap, or the latest migration head. Rehearse operations and keep expected migration versions current.

Lesson 11 · Compare the tools

Flyway and Liquibase: are they the same?

Both tools track and apply ordered database changes. Their goal is similar; teams mainly choose based on how they want to define changes and what extra tooling they need.

AreaFlywayLiquibase
How changes are definedCommonly plain SQL files, e.g. V11__add_column.sql.ChangeLogs in XML, YAML, JSON, or SQL.
ApproachSQL-first and straightforward.Structured change sets with database-aware operations; raw SQL also supported.
Database supportMany databases; SQL often database-specific.Many databases and more database-independent change types; database-specific SQL is possible.
Change trackingflyway_schema_history.DATABASECHANGELOG and a lock table.
RollbackUsually a forward migration or restore plan; arbitrary SQL is not automatically reversed.Rollback mechanisms exist for supported changes but may need to be written and tested.
Schema comparisonApplies and validates migrations; does not infer intended changes from differences.Diff and snapshot features vary by edition and setup.
Learning curve / fitGood for teams that want direct SQL and explicit database-specific control.Good for teams that want structured changes, portability, or schema comparison features.

When can a successful migration run again?

ToolDefault behaviorHow to rerun
FlywayA successful versioned V... migration runs once.Use a repeatable R__... migration. Flyway reapplies it when its checksum changes, after pending versioned migrations.
LiquibaseA successful changeset runs once.Set runOnChange: true to rerun when meaningful contents change, or runAlways: true to run it on every deployment.

For example, a Flyway R__refresh_product_view.sql or a Liquibase runOnChange changeset can maintain a view or stored procedure. They do not rerun every successful script by default. Use Liquibase runAlways only when that operation is meant to run on every deployment.

For Emerald Housing, the services already use Flyway with explicit PostgreSQL SQL. Switching tools means changing the migration workflow; neither tool automatically makes migrations safe.

Lesson 13 · Interview practice

Flyway interview questions and answers

Use these answers as a starting point. In an interview, explain the principle, then connect it to the database and deployment scenario.

Core Flyway questions

1. What is Flyway?

Flyway is a database migration tool. It applies versioned migration scripts in order and records their status in a schema history table.

2. How does Flyway know which migrations to run?

It compares migration files available to the application with successful records in flyway_schema_history. It runs pending migrations and skips versions already applied successfully.

3. Will Flyway rerun V1–V10 every time the application starts?

No. A new database runs the available migrations in order. On later starts, successful versions are skipped. If V11 is added, Flyway applies it when the database has not recorded V11 as successful.

4. What is the standard versioned migration filename format?

V<version>__<description>.sql, such as V11__add_flat_search_index.sql. The version orders the migration; the description makes it easier to identify.

5. Should you edit a migration that has already been applied?

No. Treat applied versioned migrations as immutable. Editing one will not rerun its SQL and usually causes a checksum validation error. Restore the original file and put the new change in a new migration.

6. What does flyway_schema_history store?

Migration metadata such as version, description, script, checksum, installation order, execution time, and success. The exact columns vary by Flyway version and database.

7. What is the difference between Flyway and Hibernate ddl-auto?

Flyway applies explicit versioned changes. Hibernate's ddl-auto controls schema actions based on entity mappings. A common production setup is Flyway enabled with ddl-auto: validate, so Hibernate checks mappings without changing schema.

8. What happens when a migration fails?

Flyway normally stops at the failed migration; later pending versions do not run in that attempt. Earlier successful migrations remain recorded. The database may have partial changes, so inspect its real state before retrying.

9. What does flyway repair do?

It repairs migration history metadata, such as removing failed records or aligning stored migration details. It does not run or reverse SQL, remove leftover objects, or restore data.

10. How would you recover from a production migration failure?

Pause the rollout, inspect logs and migration history, and compare the actual schema/data with the expected state. Reconcile partial database changes first. Use repair only if verified history needs it, then migrate and validate before resuming deployment.

11. How do you make schema changes safer during a rolling deployment?

Use expand-and-contract: add a backward-compatible schema change, deploy code that supports old and new shapes, backfill and switch usage, then remove the old schema in a later release.

12. How does Emerald Housing use Flyway?

Member and Society own separate migration streams and databases. Both enable Flyway and use Hibernate ddl-auto: validate. Migration files are packaged with each service.

+

Lower-environment and production scenarios

13. How do you promote Flyway changes through environments?

Commit migrations with the service, build a reviewed artifact, then promote that same artifact through development, testing, staging, and production. Each database has its own history, so Flyway applies what is pending there.

14. A migration works locally but fails in a lower environment. What do you check?

Check the error, database version, Flyway history, schema/data, and migration-account permissions. Local data may not include the rows or constraints that expose the problem. Reproduce with representative data, fix the cause, and inspect for partial effects before retrying.

15. A migration succeeded in development but has not reached production. Can you edit it?

Treat it as immutable once applied in a shared environment. Editing it can make environments disagree and cause checksum validation errors. Add a new migration for the correction and promote it through the remaining environments.

16. Staging is missing a migration that ran in development. What do you do?

Compare migration files and each database's history. Check the deployed artifact, Flyway locations, target, schema, and database credentials. Apply it through the normal pipeline; do not copy history rows manually between databases.

17. A migration fails in production. What are your first steps?

Pause the rollout, preserve logs and database state, identify the failed migration, then inspect its history row and actual schema/data. Choose a reviewed retry, forward fix, or restore plan based on what actually succeeded.

18. Flyway reports a checksum mismatch in production. Do you run repair?

Not immediately. Find out why the checksum differs and whether the database matches the intended migration. Usually restore the original applied file and add a new migration. Repair changes metadata; it does not make the schema match an edited file.

19. A migration partially changed production before failing. How do you recover?

Inspect objects and data before retrying. Remove partial changes only if safe; otherwise design a compatible forward correction or restore plan. If a failed history record remains after database reconciliation, use repair only when needed, then migrate and validate.

20. Staging succeeded, but a migration takes too long in production. What do you do?

Pause if impact is unsafe. Inspect locks/runtime and compare table sizes. Run large backfills in controlled batches, consider database-specific online index options and their transaction requirements, and rehearse against production-sized data.

21. What if old and new service replicas run during deployment?

Use expand-and-contract. Add compatible schema first, deploy code that works with both shapes, backfill and switch usage, then remove old schema after old replicas are gone.

22. Is a direct production database change ever acceptable?

As an emergency measure to restore service, sometimes. Record the exact SQL, operator, time, and resulting state. Then reconcile through a reviewed migration or deployment step so other environments and future deployments reach the same schema.

23. Two branches create the same migration version. What do you do?

Resolve the collision before shared promotion, assign unique versions within that service's stream, and test the ordered migrations. If a version already ran in a shared database, do not rename or rewrite it casually; coordinate a forward migration.

24. How do you know recovery is complete?

Confirm Flyway history matches migration files, actual schema/data match expectations, the application starts with schema validation, and the affected feature works. Check readiness and database health before resuming traffic.

Interview summary: “We promote the same reviewed artifact through lower and higher environments. Flyway tracks each database independently and applies pending migrations. When an environment fails, I compare its history and actual schema/data, then resolve the cause before retrying. In production, I pause the rollout, inspect for partial changes, and use a forward migration or tested restore plan. I use repair only for verified history problems, never as a substitute for database recovery.”

For any operation with special PostgreSQL transaction or locking requirements, verify the SQL and Flyway behavior for that exact operation. Rehearse it on PostgreSQL 16, check what remains after failure, and plan cleanup/retry before production.
