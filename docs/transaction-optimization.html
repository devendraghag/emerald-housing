Transaction optimization

Learn what a database transaction is, see why its lifetime matters, and follow the membership assignment and end flows before and after the scope change. The goal is to keep database transactions focused on database work.

Step 1 | Learn the basics

What is a transaction?

A database transaction groups database operations that must succeed or fail together. For example, saving a membership and its audit event should be atomic: either both are committed or neither is.

  • Begin: the transaction manager opens a database transaction.
  • Commit: all successful changes become durable together.
  • Rollback: changes are undone when the operation fails.
  • Transaction scope: the code executed between begin and commit/rollback.
  • Lock: a database or Redis coordination mechanism that can make other work wait.
Analogy: keep a checkout counter reserved only while you update the register. Do not reserve it while calling another store to ask whether an item is in stock.
Step 2 | Understand why duration matters

A transaction should not wait on unrelated work

Long transactions can hold database connections and locks longer, increase contention, and make rollback more expensive. A remote HTTP request or waiting for a Redis lock can take much longer than the SQL update itself.

Long scopeOpen DB transaction
Wait elsewhereHTTP call or Redis wait
Then writeFinally update database and commit

Transaction optimization means keeping the atomic database portion together while moving unrelated waits before or after it where correctness allows.

Step 3 | See the original membership flow

Assignment had an outer transaction around HTTP and Redis

MembershipService.assign was annotated transactional. Its work included a member status check, Society Service HTTP call, Redis lock acquisition/wait, and then the membership database write.

MembershipService.assign [outer transaction]
  -> access registry row lock
  -> MemberService.requireActive [database read]
  -> SocietyClient.getFlat [HTTP request]
  -> RedisMembershipLock.withMemberLock [may wait]
  -> MembershipWriter.persist [database write]

MembershipWriter.persist already had its own transaction. Under normal REQUIRED propagation it joined the outer transaction, so the outer transaction stayed open during the external service call and Redis lock acquisition.

Concrete issue: an HTTP delay or lock wait could keep the database transaction and access-control row lock open even though no database write was happening yet.
Step 4 | What the inspection established

Keep correctness checks, move the boundary

The code already had important atomicity protections:

  • MemberService.requireActive is a short read-only transaction.
  • MembershipWriter.persist has a write transaction, locks the access registry row, locks the member row, validates active status and duplicates, saves the membership, and records audit.
  • MembershipWriter.end has a write transaction and records the membership end plus audit.
  • AuditTrail.record uses mandatory propagation so it participates in the caller's write transaction.

The writer methods already form the right database boundary. The optimization removes unnecessary outer transactions from the orchestration layer and keeps registry locks inside the writer transaction.

Step 5 | Follow the improved assignment flow

External work and Redis wait happen before the write transaction

MembershipService.assign [no database transaction]
  -> MemberService.requireActive [short read-only transaction]
  -> SocietyClient.getFlat [HTTP request, no DB transaction held]
  -> validate flat status
  -> RedisMembershipLock.withMemberLock [acquire/wait, no DB transaction held]
       -> MembershipWriter.persist [write transaction begins]
            -> AccessRegistry.lock [DB lock inside transaction]
            -> lock and re-check member active
            -> insert membership and audit
            -> commit
  -> Redis lock released
Quick precheckRead member active
Remote checkConfirm flat is active
Redis coordinationWait for per-member lock
Short DB transactionLock, revalidate, write, audit, commit

The status check in the writer remains authoritative because the member could change after the early precheck. The early check avoids calling Society Service for a missing or inactive member; the final check under transaction preserves correctness.

Step 6 | Follow membership ending and audit

The same boundary principle applies to ending a membership

MembershipService.end now waits for the Redis member lock before invoking MembershipWriter.end. The writer opens the database transaction, takes the access registry lock, locks the member row, updates the membership, records audit, then commits. The Redis lock is released after the writer call returns.

MembershipService.end
  -> Redis lock acquisition/wait (outside DB transaction)
  -> MembershipWriter.end [transaction]
       -> registry lock + row lock
       -> update membership + audit
       -> commit
  -> release Redis lock

The audit record stays in the same transaction as the membership mutation. This prevents a committed membership change without its matching audit event.

Step 7 | Understand the transaction configuration

Timeouts are a safety net, not a substitute for a short scope

Member Service and Society Service configure a default transaction timeout using TRANSACTION_DEFAULT_TIMEOUT, defaulting to 30 seconds. Individual operations can also specify settings, such as the owner write operations with a 15-second timeout. Read methods are often marked readOnly=true.

  • Read-only marks intent and can let the transaction provider optimize reads; it does not mean “no database access.”
  • The assignment and end orchestration methods no longer have an outer @Transactional.
  • The writer persist/end methods retain @Transactional and keep database changes atomic.
  • SocietyClient HTTP timeouts and Redis lock wait/lease settings are configured separately from database transaction timeouts.

Changing a timeout does not fix a transaction that includes unnecessary network waits; boundaries should still be scoped around the work that must commit together.

Step 8 | Verify the change

Checks added and run

A unit test checks the intended annotation boundary: MembershipService orchestration methods have no transaction annotation, while MembershipWriter persistence methods retain it. Existing behavior tests still check that inactive/missing flats or members and Redis lock failures do not persist a membership.

Member-service tests were run with the project Maven wrapper. Report the actual Maven result in the final summary. Database integration tests in Testcontainers may be skipped if Docker is unavailable in the environment.

  1. Confirm no transaction starts at MembershipService.assign/end.
  2. Confirm writer persist/end still run transactionally.
  3. Check the member and flat validation paths stop before persistence on failure.
  4. In an integration environment, verify the registry row lock and member row lock share the writer transaction.
  5. Measure transaction duration and connection-pool wait under load to validate production impact.
Step 9 | Know what this does not change

Transaction design remains operation-specific

  • The remote flat status check can become stale before the write. The writer still locks and revalidates the member, while flat eligibility relies on the remote result and the project's domain rules.
  • The Redis lock still surrounds the database write to serialize same-member changes across instances. It is acquired before opening the DB transaction and released after commit.
  • Other services have their own boundaries. Rental operation handlers use local database work; each should be reviewed based on its actual calls and invariants, not changed mechanically.
  • Transaction timeout does not bound the entire HTTP request or Redis wait; those have separate timeout settings.
  • This change reduces unnecessary transaction duration by code structure; a measured latency/lock-duration improvement still requires runtime metrics.
Step 10 | Interview practice

Explain the refactor

"I found that membership assignment had a transaction around a Society Service HTTP call and a Redis lock wait. The persistence writer already had the correct transaction and row-level validation, so I removed the outer transaction from the orchestration method. The service now performs the read-only member precheck and remote flat validation first, waits for the Redis lock, then calls the transactional writer. I kept the access registry lock, member row lock, final active-member check, membership insert, and audit write inside the writer transaction. I applied the same pattern to membership ending. That keeps the atomic database work together while avoiding holding a database connection/lock during network or Redis waits."

Likely follow-up questions

Why keep the member active precheck if writer checks again?

The early read avoids an unnecessary remote call for an inactive or missing member. The writer repeats the check under lock because state can change before the write.

Why move AccessRegistry.lock into the writer?

It uses SELECT FOR UPDATE and must remain inside the transaction that protects the write. Moving it into the writer keeps the lock but starts holding it only when the database write transaction begins.

Does the writer open a nested transaction?

The service has no active transaction at that point, so the proxied writer method starts its transaction. The writer's audit call uses mandatory propagation and joins it.

Why acquire Redis before the DB transaction?

Redis lock contention can make a request wait. Acquiring it first means that wait does not occupy a database transaction. The writer then commits before the Redis lock is released.

Can we remove the Redis lock too?

Not without replacing its cross-instance same-member serialization guarantee with another proven concurrency control. This change only moves its wait outside the database transaction.
