1. Start with the basics

Idempotent means repeating an operation with the same identity does not repeat its externally visible effect. In event systems, this matters because delivery and processing can be retried.

A Kafka consumer reads a record, calls application code, and advances its offset after successful handling. If processing succeeds but offset progress is not durably recorded (or the consumer restarts before it is), Kafka may deliver the same record again. This is normal at-least-once behavior.

This repository’s application-level idempotency is separate from Kafka producer idempotence. Producer idempotence helps with duplicate writes caused by producer retries. Consumer idempotency uses a database uniqueness constraint to prevent duplicate application effects.

Current implementation: Both the community notice and lost-and-found Kafka listeners use kafka_processed_events, keyed by (flow, event_id). This guide describes existing behavior; it does not add runtime code.

2. Why duplicate processing happens

Imagine a consumer inserts notifications for residents, then the process stops before Kafka considers the record complete. After restart or retry, that record can be delivered again. If the handler blindly repeats inserts or other actions, users may receive duplicate notifications.

There is no ordinary atomic transaction here that commits PostgreSQL writes and Kafka consumer offset together. The standard practical design is to make database effects idempotent using a stable event ID, so replay is safe.

Idempotency does not mean a record is delivered once. It means repeated delivery with the same identity is recognized and does not repeat the protected database effects.

Database uniqueness is the arbiter. It protects against two concurrent deliveries racing as well as ordinary sequential replays. The flow name is part of the key so event IDs are scoped to the event stream.

4. Event identity: what counts as “the same”

The event records (CommunityNoticeEvent and LostFoundEvent) include a UUID eventId. The outbox stores that ID, and the publisher sends the serialized event to Kafka. The listener uses the event’s ID rather than the Kafka offset as its deduplication key.

The processed table schema is introduced by V17__kafka_delivery_reliability.sql:

CREATE TABLE kafka_processed_events (
  flow varchar(80) NOT NULL,
  event_id uuid NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (flow, event_id)
);

Using a stable event ID means a replay to a different Kafka offset is still recognized as the same logical event. Including flow permits independent namespaces such as community-notices and lost-found.

5. Process one event, step by step

Step 1 — Kafka calls the listener

CommunityNoticeEventListener handles community-notices.events; LostFoundEventListener handles lost-found.events. Each method receives the JSON payload.

Step 2 — parse and enter a database transaction

The handler deserializes the payload into its event record. The method is annotated @Transactional, so processed identity and notification inserts participate in one database transaction.

Step 3 — try to claim the event identity

The listener inserts the event’s flow and ID into kafka_processed_events with ON CONFLICT DO NOTHING. If the insert affects zero rows, a row with the same composite key already exists.

Step 4 — duplicate returns without repeating effects

On conflict the handler increments kafka.messages.duplicate for that flow and returns. It does not run the notification recipient query or increment the consumed counter.

Step 5 — first delivery applies effects

If the insert succeeds, the listener selects the eligible recipients and inserts notification rows. Both flows use ON CONFLICT DO NOTHING on the notification write as a second guard against duplicate notification records.

Step 6 — transaction commits, then record handling succeeds

When listener work completes, the database transaction commits. Spring Kafka is configured with record acknowledgement and auto-commit disabled. If listener processing throws, Spring’s error handler retries and eventually routes the record to its dead-letter topic.

Because the event marker and notification effects are in the same DB transaction, a failure during notification writes rolls back the marker too. A later retry can then process the event. This is the key atomicity property of the idempotency mechanism.

6. Transaction safety and the exact guarantee

For a new event, the database transaction performs both actions:

  1. insert the unique processed-event marker;
  2. insert the notification side effects.

If either database operation fails and the transaction rolls back, neither is committed. A retry can try again. If the transaction commits but Kafka redelivers, the unique key detects the existing marker and skips effects.

This makes the database notification effects effectively once per (flow, eventId), as long as all relevant effects stay inside this transaction and use the same identity. It does not make arbitrary external side effects exactly once. If future code sends email or calls another service, that operation cannot be rolled back with this database transaction; it needs its own idempotency or an outbox.

8. Kafka configuration and retry behavior

In Member Service application.yml, consumer auto-commit is disabled and listener acknowledgement mode is record. The error handler in KafkaReliabilityConfiguration uses a fixed 1-second backoff with two retries, then publishes the original record to a topic named {source-topic}.DLT. For example, the community DLT is community-notices.events.DLT.

Consumer retries can deliver the same record more than once, which is why the idempotency guard belongs in the listener’s database transaction. The DLT policy handles records that continue to fail; it is not the deduplication mechanism.

The processed-event table has no cleanup/retention job in the inspected migrations or code. Rows therefore accumulate unless an operator removes them. Deleting a row deliberately permits a replay to apply effects again, so such cleanup is a correctness decision, not merely storage maintenance.

9. Observe and operate it

The listeners expose counters:

  • kafka.messages.duplicate tagged by flow counts deliveries whose event ID already exists.
  • kafka.messages.consumed tagged by flow counts first-time events that completed the listener’s notification logic.
  • kafka.messages.failed tagged with flow and stage records records routed to DLT after retries.

Micrometer exports through Actuator’s Prometheus endpoint, and the Kubernetes Prometheus configuration scrapes annotated Member Service pods every 15 seconds. Check actual names and labels at /actuator/prometheus before writing queries; counters are process-local and should be viewed with rate functions in Prometheus.

A rising duplicate counter can be expected during redelivery or replay; it is not automatically proof of a defect. Compare it with consumed and failed rates, inspect logs by event ID/correlation ID, and verify notification counts for the affected event before taking action.

For deliberate DLT replay and its warning about deleting the processed marker, follow Kafka notification operations. Do not delete processed markers casually: doing so removes the protection against duplicate effects for that event.

Operational limit: the repository exposes a duplicate counter but no dedicated duplicate-rate dashboard or alert. The processed table is durable but has no declared retention policy.

10. Existing test coverage: what it proves and what it misses

FeaturesPersistenceTest directly calls each listener for a normal event and checks recipient visibility. This demonstrates that the consumer logic can create the intended notifications for first delivery.

The checked-in tests do not appear to invoke the same listener twice and assert exactly one set of effects plus a duplicate-counter increment. Nor do they test a transaction rollback after the marker insert, concurrent duplicate deliveries, retention policy, or duplicate delivery via an actual Kafka redelivery. The idempotency mechanism is implemented in code and backed by a database primary key, but these specific guarantees deserve focused automated tests.

11. Guarantees, limitations, and preserving behavior

  • Stable identity is mandatory: retries must reuse the original event ID. Generating a fresh ID on each retry defeats deduplication.
  • Flow label is part of identity: the same UUID in different flow namespaces is treated as a different event.
  • Database side effects only: the transaction protects database writes. Future external effects need an idempotency key or another durable handoff.
  • Marker retention matters: deleting a marker makes a later replay look new.
  • Schema/flow evolution: renaming a flow label changes the deduplication namespace. Plan migrations or compatibility behavior before changing it.
  • At-least-once consumer delivery: this is not Kafka exactly-once processing or atomic DB-offset commit.
  • Metric interpretation: duplicate count reports detection, not necessarily duplicate user-visible notifications; the guard is designed to prevent those effects.

When adding a new flow, define a stable event UUID at event creation, persist and serialize the same ID, choose a stable flow key, insert that marker before effects in one transaction, and add tests for first delivery, duplicate delivery, rollback/retry, and concurrency.

12. Interview preparation

60-second explanation

“The Member Service consumers use a database-backed idempotency key because Kafka delivery is at least once. Each event has a stable UUID. In a listener transaction, the consumer inserts (flow, eventId) into kafka_processed_events, whose composite primary key rejects repeats. If the insert conflicts, the handler increments a duplicate metric and returns before creating notifications. For a new event, it inserts the marker and notification rows in the same PostgreSQL transaction, so a database failure rolls both back. This prevents repeated database notification effects on replay, but it is not an exactly-once transaction across Kafka and PostgreSQL, and it does not cover future external side effects.”

Likely questionInterview-ready answer
Why use the database as the dedupe store?The database is already where notification effects commit. A unique key there serializes concurrent attempts and lets marker plus effects share one transaction.
Why use event ID instead of Kafka offset?Offsets identify a position in one topic partition. The logical event ID remains stable when an event is replayed at a different offset or topic.
What if two consumers process the event at the same time?The primary key on (flow,event_id) lets one insert succeed; the other gets zero rows from ON CONFLICT DO NOTHING and skips effects.
What if notification insertion fails after the marker insert?The listener method is transactional. The marker rolls back with the failed notification insert, allowing a later retry to process the event.
Is processing exactly once?No. Kafka can redeliver. The database effects are idempotent per flow/event ID under the transaction, but Kafka offset and DB commit are not one distributed atomic transaction.
Can a marker be safely deleted?Only when replaying is intended and the side effects have been reviewed. Removing it allows the same event to be treated as new.
What would you add next?Focused duplicate and rollback tests for both listeners, concurrent delivery coverage, a retention policy with safe replay semantics, and dashboards for duplicate and DLT rates.
