Step 1 | Understand the problem

What does rate limiting protect?

Rate limiting controls how quickly a caller can send requests. It protects services from accidental bursts, abusive automation, and traffic that exceeds the capacity a route is designed to handle.

Rate limiting is different from a concurrency bulkhead. A rate limit controls request frequency over time. A bulkhead controls how many operations are active at once. Emerald Housing has both patterns, at different layers.

A rate limit is like a refillable ticket wallet. A caller can spend tickets for requests; tickets return over time. A temporary burst is allowed up to the wallet capacity.
Step 2 | Learn the token bucket

Replenish rate and burst capacity

  • Replenish rate: how many tokens are restored per second.
  • Burst capacity: maximum tokens the bucket can hold.
  • Requested tokens: how many tokens one request costs. These routes request one token per request.
  • Allowed: enough tokens exist; the request proceeds and spends one.
  • Limited: insufficient tokens; the request is rejected, normally with HTTP 429.

At a steady rate, a bucket replenished at 10 tokens per second allows approximately 10 requests per second after any initial burst is spent. A burst capacity of 20 permits a short burst up to 20 requests when the bucket is full. Exact timing depends on Redis token-bucket implementation and request arrival pattern.

Replenish and burst are different knobs. Raising burst accepts larger short spikes; raising replenish allows a higher sustained average rate.
Step 3 | Locate the limiter

Spring Cloud Gateway uses shared Redis state

Gateway route definitions use Spring Cloud Gateway's RequestRateLimiter filter with RedisRateLimiter. The gateway connects to Redis using Spring Data Redis configuration in application.yml. Because bucket state is stored in Redis, gateway replicas can consult shared limiter state rather than keeping independent in-memory counters.

Step 4 | Read the API route policies

Each route requests one token per request. Environment variables set these values in kubernetes/gateway/config.yaml; corresponding defaults are in the gateway's application.yml.

The route policies are independent buckets. A given admin can use the Member, Society, and AI budgets separately. The key resolver returns admin:<adminId> when the authenticated principal is an AdminIdentity; if no matching identity is available, it falls back to unauthenticated. API routes themselves are protected by Gateway security and normally require authentication.

Step 5 | Understand unauthenticated login protection

Login has one shared bucket

AuthController.login calls a dedicated RedisRateLimiter with key parts admin-login and unauthenticated before credential validation. This means all login attempts use the same unauthenticated bucket, not one bucket per username or source IP.

The configured Kubernetes values are 1 token per second and burst capacity 3. The bean defaults in GatewayRateLimitConfiguration are 2 and 5 when environment values are absent. A three-attempt burst can be allowed when the bucket is full; further attempts receive 429 and a Retry-After: 1 header.

Trade-off: one shared login bucket makes distributed username guessing harder, but one client can consume tokens and temporarily affect other users. It is not per-IP, per-account, or per-device throttling.
Step 6 | Walk through a request

Route limiter from input to response

API request
  -> Gateway security authenticates admin session
  -> route predicate selects Member / Society / AI route
  -> RequestRateLimiter calls authenticatedAdminKeyResolver
  -> RedisRateLimiter checks that route + admin bucket
  -> token available: spend one token and forward to service
  -> token unavailable: return HTTP 429
  -> RateLimitMetricsFilter observes 429 and increments route counter

For login, the controller performs its explicit limiter check before calling the authentication manager. A rejected login never invokes password validation. Login uses a fixed bucket key because the caller is not authenticated yet.

Step 7 | Interpret rejection and Redis failures

429 means a bucket is empty

Login rejection is explicitly returned as status 429, code LOGIN_RATE_LIMITED, message to wait, and Retry-After: 1. Login limiter errors are explicitly handled as fail-closed: Gateway returns 503 RATE_LIMITER_UNAVAILABLE and increments emerald.gateway.rate_limiter.errors.

For route-level RedisRateLimiter filters, normal exhaustion produces 429. The repository does not define a separate custom route-level Redis error response handler in the route configuration; confirm the actual Spring Cloud Gateway behavior and error body in the deployed version during operational testing.

429 is different from 401/403 authentication failure and 503 dependency/limiter unavailability. The caller should slow down and retry later rather than immediately replaying a burst.

Step 8 | Find the observability hooks

Rejection counters exist

RateLimitMetricsFilter increments emerald.gateway.rate_limited.requests for Gateway responses with status 429. It uses a bounded route label: route ID when known, otherwise local-handler. Login also increments the same counter with route login in its explicit controller path. The login limiter failure path increments emerald.gateway.rate_limiter.errors.

Gateway Actuator exposes metrics and Prometheus. Kubernetes annotates the gateway pod for scraping, and Prometheus discovers annotated pods. Grafana includes API request-rate and latency panels plus application logs; no dedicated rate-limit dashboard or alert was found.

The global 429 counter measures responses with status 429, which may include another handler returning 429. Treat it as a rate-limited-response signal unless you confirm all 429s come from limiter filters. Login limiter errors are a separate explicit counter.
Step 9 | Tune from observed traffic

A safe tuning workflow

  1. Measure normal request rate, peak burst shape, 429 frequency, service latency, downstream saturation, and traffic by route and admin identity.
  2. Separate expected bursts from sustained demand. A high 429 rate can mean a policy is too tight, a client has a retry loop, or abuse is happening.
  3. Choose replenish rate from the sustainable route throughput. Choose burst capacity from the burst the service can absorb without harming latency or error rates.
  4. Review login separately: because its bucket is shared, assess both brute-force resistance and whether ordinary simultaneous logins can exhaust it.
  5. Adjust one setting gradually in a controlled environment, then compare throughput, p95/p99 latency, 429s, service errors, and Redis health.
  6. Ensure clients respect 429 and back off. Immediate retries can consume the next replenished tokens and sustain the rejection storm.
  7. Check that Redis bucket state is healthy and that gateway replicas use the intended shared Redis deployment.

Use observed traffic and service capacity, not only a desired requests-per-second number. Rate limits are admission policies; they do not create backend capacity.

Step 10 | Review implementation coverage

What is present and what is not proven

  • Member, Society, and AI gateway routes have RedisRateLimiter filters with environment-backed refill and burst settings.
  • An authenticated admin key resolver is implemented and returns the admin UUID-based key.
  • Login has a separate Redis-backed bucket, 429 response, Retry-After header, and explicit 503 behavior if its limiter fails.
  • A gateway filter counts 429 responses, and login limiter errors have a separate metric.
  • Postman descriptions document manual short-burst tests for API routes and login. Functional test cases describe controlled staging checks.
  • No focused automated rate-limiter test class was found in the gateway tests inspected. The existing guidance does not establish that the limits were load-tested or tuned from actual traffic measurements.
Verification boundary: source/configuration inspection proves the feature is wired. It does not prove token behavior against Redis, exact 429 responses in a running deployment, or that current values match production traffic needs.
Step 11 | Know the limitations

Rate limits are not the whole abuse-control strategy

  • API buckets are per authenticated admin and route, not per organization, IP, or global service; a compromised admin can use its full allowance.
  • Login has one shared unauthenticated bucket; it can limit legitimate users during a burst and does not identify source IPs.
  • Redis is required for shared bucket behavior. Login explicitly fails closed with 503 on limiter errors; route-level failure behavior should be verified in the deployed Gateway version.
  • No custom rate-limit response body for route-filter 429s is configured here; login has its own structured body.
  • Configured values may not reflect observed traffic. No traffic study or rate tuning record is checked in.
  • Metrics and scrape setup exist, but a dedicated Grafana panel/alert and automated limiter tests were not found.
Step 12 | Interview practice

Developer-level explanation

“The API Gateway applies Spring Cloud Gateway RedisRateLimiter token buckets to Member, Society, and AI routes. It keys these buckets by authenticated admin ID, with route-specific policies: 10/20 for Member, 20/40 for Society, and 5/10 for AI, where the first number is tokens replenished per second and the second is burst capacity. Each request costs one token. Login has a separate shared unauthenticated bucket configured in Kubernetes at 1 token per second and burst 3; exhaustion returns 429 with Retry-After, while login limiter errors fail closed with 503. Redis gives gateway replicas shared bucket state. Metrics count 429 responses and explicit login limiter errors, and Prometheus scraping is configured. Manual tests are documented, but I found no dedicated automated limiter tests, no dedicated dashboard, and no checked-in traffic study proving the values are tuned.”

Likely follow-up questions

What is the difference between replenish rate and burst capacity?

Replenish rate sets sustained token recovery per second. Burst capacity is the maximum tokens accumulated and therefore controls the short burst allowed when the bucket is full.

Why key API limits by admin identity?

It gives each authenticated administrator an independent allowance and avoids trusting arbitrary client-provided identity headers. It does mean callers behind an admin session share that identity's bucket.

Why is login a shared bucket?

There is no authenticated identity before login. The current implementation uses a fixed unauthenticated key, which is simple but can let one source consume shared login capacity.

What should a client do after 429?

Respect Retry-After when provided and use backoff with jitter. Replaying immediately can keep the bucket empty.

Does Redis failure fail open or closed?

Login explicitly fails closed with 503. The API route configuration has no custom error policy, so verify its behavior with the deployed Spring Cloud Gateway version.

How would you tune these values?

Measure request bursts, sustained route throughput, 429 rate, backend latency and saturation, and Redis health. Adjust refill and burst gradually in staging and compare results.

What is the main testing gap?

Automated tests for Redis token consumption, route key isolation, 429 behavior, and Redis failures, plus a controlled load test validating policy values and metrics.
