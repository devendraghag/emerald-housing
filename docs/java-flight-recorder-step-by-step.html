Java profiling with JFR, from zero

Learn what a profile is, how Java Flight Recorder fits this Java 21 service stack, and how to capture a bounded recording while a representative workload is running. This guide describes the new opt-in Kubernetes workflow and the evidence it does—and does not—provide.

1. Start with the concepts

Profiling means collecting runtime evidence while an application does useful work, then using that evidence to locate where CPU, memory, threads, locks, or latency are spent. A profile is evidence about one build, environment, and workload—not a general performance verdict.

Java Flight Recorder (JFR) is the recording facility built into the Java runtime. A recording is saved as a .jfr file. Java Mission Control can explore it graphically; the JDK's jfr command can print summaries and selected events.

A representative load is a repeatable request or background-job mix that resembles the behavior being investigated: the same endpoint mix, data shape, concurrency, and duration. Profiling an idle service mostly describes startup and waiting.

Before interpreting a recording: note the application image/version, pod, JVM options, time window, load profile, request rate, latency, errors, CPU and memory. Compare recordings only when those conditions are meaningfully similar.

The script first prompts you to start representative load. It then edits the selected Deployment's JAVA_TOOL_OPTIONS and rolls the pods. Each replacement JVM begins its bounded recording at startup while the load remains active. After rollout, the script waits for the configured duration, copies each pod's file, removes the temporary override, and waits for the normal deployment to roll out again.

The target container already has a writable /tmp volume. The JFR file is temporary pod data, so the script copies it before the cleanup restart deletes that pod.

4. Capture a recording step by step

  1. Choose a safe environment. The procedure restarts every pod in the selected Deployment twice: once to enable the profile and once to restore defaults. Use a non-production cluster unless that restart is explicitly acceptable.
  2. Prepare the workload. Agree on the endpoint mix, test data, rate/concurrency, duration, and success/latency targets. Have the load generator ready before starting the capture command.
  3. Run the script from the repository root. Example for a two-minute Member Service profile: 
    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\profiling\record-jfr.ps1 `
  -Deployment member-service `
  -DurationSeconds 120 `
  -Namespace emerald-housing `
  -Context docker-desktop

    -Context is optional; omit it to use the current kubectl context. Supported deployment names are api-gateway, member-service, society-service, and ai-service. Duration is bounded from 15 to 900 seconds.

  4. Start load before the profiling rollout. When the script prompts, launch the prepared workload in another terminal and press Enter. Keep it running through the replacement pod startup and the configured recording window. Each recording starts when its JVM starts, so it includes some startup time; the script waits the full configured duration after rollout to let all files finish.
  5. Collect the output. The script copies each selected pod's /tmp/emerald-<deployment>.jfr into artifacts/jfr/ by default, using the pod name as a filename prefix.
  6. Confirm cleanup. The script removes the temporary JAVA_TOOL_OPTIONS value and waits for the deployment to return to the image's normal JVM defaults.
Don't profile production casually: the command causes a rolling restart and JFR adds runtime overhead. Coordinate the window and assess impact before using a live environment.

5. Read the recording

Use a JDK 21 installation on your workstation. The deployment image is a JRE; the local inspection commands below require the JDK's jfr tool or Java Mission Control.

jfr summary .\artifacts\jfr\<pod-name>-emerald-member-service.jfr
jfr print --events jdk.ExecutionSample,jdk.ThreadPark,jdk.JavaMonitorEnter .\artifacts\jfr\<pod-name>-emerald-member-service.jfr

For a graphical timeline and event navigation, open the file in Java Mission Control. Start with recording duration and event counts, then examine hot methods, allocation, blocking/parking, monitor contention, garbage collection, and thread activity over the load interval.

ObservationWhat to investigate next
Repeated execution samples cluster in one methodTrace that hot path and determine whether the work is necessary, repeated, or CPU-bound.
Many threads are parked or blockedIdentify the resource they wait for: database connections, locks, sockets, or another dependency. Waiting is not itself proof of a bug.
High allocation rate or frequent GCInspect allocation sites, object lifetime, heap sizing, and request data volume; compare with heap/GC behavior under the same load.
Low CPU with slow requestsCheck dependency latency, pool wait, lock contention, and network/database timings; a CPU profile alone may not explain waiting time.

6. Interpret results without overclaiming

JFR helps answer “where did this JVM spend time and allocate?” It does not by itself prove which endpoint caused a sample, explain every external wait, or measure user-visible latency. Pair it with request-level load-generator results and existing service metrics and logs.

  1. Record the exact build, pod, JVM, resource limits, and load-generator settings.
  2. Check that the recording overlaps the representative steady-state period, not only startup or warm-up.
  3. Look for repeated patterns, not one isolated event.
  4. Form one specific hypothesis and make one controlled code/configuration change.
  5. Repeat the same load and compare throughput, p50/p95/p99 latency, errors, CPU, memory, and the relevant JFR events.

Do not infer a speedup from a flame view alone. The measurement should include application behavior and the dependencies that constrain it, such as the database pool or downstream service.

7. Safety, configuration, and limitations

ItemCurrent behaviorOperational implication
JFR settingssettings=profileUses the standard profiling configuration; event volume and overhead depend on workload and runtime.
Recording windowScript default 120 seconds; allowed 15–900 seconds.Recording is bounded, but the workload must overlap it.
DestinationPod-local /tmp; local artifacts/jfr by default.Pod files disappear at restart. Treat local recordings as potentially sensitive and do not commit them.
RestorationTemporary deployment environment override is removed in a finally block.The script waits for the normal deployment rollout even if capture/copy errors occur; if the cluster is unreachable, inspect the Deployment and remove JAVA_TOOL_OPTIONS manually.
ScopeOne selected Deployment at a time; all matching replicas restart and record.Traffic distribution may mean each pod sees different load. The script does not target one pod or synthesize traffic.
Load generationOperator supplies the representative workload.No project-specific traffic is guessed or generated by the capture script.
Artifact transferThe script uses kubectl cp.kubectl cp uses tar in the container; confirm the selected runtime image includes it before the exercise, or use an approved alternative transfer method.

The script preserves the image's existing -XX:MaxRAMPercentage=75.0 and -XX:+UseContainerSupport options while recording. It assumes the selected Deployment inherits those image defaults and does not define a separate JAVA_TOOL_OPTIONS override in its pod spec. Review local deployment customizations before running.

This workflow uses startup recording because the production images are JRE images and the repository did not establish that jcmd is available inside them. It is not an attach-to-running-process feature and cannot begin at an exact point after warm-up.

8. Verification and evidence

The implementation is an operational PowerShell script; there is no Java code change. PowerShell syntax parsing succeeded. A local Java 21 smoke run generated a JFR file and the JDK jfr summary command opened it successfully. The Kubernetes base rendered with kubectl kustomize, and this guide's local file links were checked. These checks validate the local JFR options and repository configuration, not the end-to-end pod capture.

A cluster exercise under representative load was not run, so successful artifact collection from a pod and any performance findings are not claimed. The repository does not contain a checked-in representative workload definition for this script; choose one matching the service and record its profile parameters alongside the resulting JFR file.

9. Interview preparation

Developer-level answer

60-second explanation: “The services run on Java 21, so JFR is available in the runtime, but the repository did not include a capture workflow. I added an opt-in PowerShell script that temporarily adds a bounded StartFlightRecording option to one Kubernetes Deployment, preserves its container-aware heap flags, prompts the operator to start representative load before the rollout, copies each pod's recording from the existing writable /tmp volume, then removes the override and restores the image defaults. It restarts the pods and records from JVM startup, so we use it in a safe environment and keep the load active through pod replacement. JFR helps locate runtime CPU, allocation, GC, and thread-wait patterns; we pair it with latency and throughput measurements and repeat the same workload before claiming an improvement. The workflow is implemented, but a cluster capture/load run has not been demonstrated here.”

Likely follow-up questions

Why use JFR rather than only application logs?

JFR samples and records JVM runtime events such as execution, allocations, garbage collection, thread state, and contention. Logs are useful for application events and errors but generally do not provide that same runtime view.

Does JFR have zero overhead?

No. Its overhead is designed to be practical, but it depends on enabled events and workload. Use bounded recordings and measure the capture impact.

Why is recording enabled at JVM startup?

The checked-in images are JRE-based and the repository did not prove attach tooling availability. Startup options work with the existing launch command and avoid changing images; the trade-off is that the profile includes startup and cannot be triggered at an exact warm steady-state instant.

What makes a load representative?

The endpoint/job mix, data sizes, concurrency, request rate, and duration should reflect the question and target operating conditions. Document them so another run can reproduce the comparison.

Can the JFR file explain slow HTTP response time by itself?

No. It gives JVM evidence. Correlate time windows with endpoint latency, errors, dependency timings, database pool metrics, and load-generator output.

What happens if the script fails?

The finally block attempts to remove the temporary JVM option and wait for the normal rollout. If kubectl cannot reach the cluster during cleanup, inspect the deployment and remove the override when connectivity returns.

10. Source map: read in this order

  1. scripts/profiling/record-jfr.ps1 — parameters, bounded JFR JVM option, rollout, artifact copy, and restoration.
  2. services/member-service/Dockerfile — Java 21 JRE image and baseline JVM options; Society Service and Gateway Dockerfiles follow the same runtime pattern.
  3. kubernetes/member/deployment.yaml — non-root/read-only container and writable /tmp volume; Society and Gateway deployments use the same shape.
  4. kubernetes/society/deployment.yaml, kubernetes/gateway/deployment.yaml, and kubernetes/ai/deployment.yaml — supported target workloads.
  5. services/ai-service/Dockerfile — Java 21 runtime and baseline JVM options for the AI Service.
  6. kubernetes/kustomization.yaml — base deployment resources for the local Kubernetes stack.

Keep the load profile, build identifier, and measurement notes with the artifact. JFR files can contain method names and runtime details; store and share them according to the environment's data-handling rules.
