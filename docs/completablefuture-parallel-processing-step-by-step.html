1. Start with the concepts

A synchronous call starts work and waits for the result before moving on. An asynchronous API returns a handle to work that may finish later. In Java, CompletableFuture<T> represents a result that will complete with a value or an error.

Parallel work is useful only when the operations are independent: neither needs the other’s result, and running them at the same time does not violate ordering, transaction, rate, or resource constraints.

Three ideas to separate:

  • Async: the caller can enqueue work and receive a future before the work completes.
  • Concurrent/parallel: multiple operations can be in flight at once.
  • Fire-and-forget: the caller does not wait for success or failure. That is usually unsafe for durable business work.
Repository status: the outbox publishers use CompletableFuture to overlap Kafka sends within a claimed batch. They still wait for each result before completing that row. No business HTTP endpoint currently fans out to multiple independent downstream requests.

Step 1 — reserve durable rows

The scheduled publisher claims at most 50 eligible rows using PostgreSQL FOR UPDATE SKIP LOCKED, a claim token, and a lease. This is background work, not part of the user’s request thread.

Step 2 — submit all Kafka sends

For each event, code serializes its payload and calls KafkaTemplate.send. That call returns a CompletableFuture<SendResult<String,String>>. The publisher stores each event/future pair and proceeds to enqueue the next event without calling get() yet.

Step 3 — Kafka can batch and overlap network work

Kafka’s producer handles buffering, request scheduling, batching, retries, and broker communication asynchronously. Enqueuing multiple records first gives one topic partition a chance to form batches under the configured batch size and linger window.

Step 4 — wait for outcomes after enqueue

The second loop calls get() on each future. The waits are written sequentially, but the sends have already been submitted and can be completing concurrently. This is not the same as sending one record, waiting, then submitting the next.

Step 5 — make each result durable

On acknowledgement, the dispatcher deletes that exact outbox row only if its event ID and claim token still match, increments kafka.messages.sent, and logs the event. On an enqueue/serialization/future failure it increments attempts, releases the claim, increments the failure counter, and logs. A later poll can retry the row.

4. Why the outbox remains safe

The future is not detached from the persistence lifecycle. The dispatcher retains it and observes completion before deleting the corresponding row. A process crash can still cause a duplicate publish after lease expiry, which is why delivery is at-least-once and consumers deduplicate by event ID.

The Kafka producer uses acknowledgements, retries, idempotence, batch settings, and a delivery timeout. These Kafka settings and the outbox claim lease work together; changing batch size, linger, or event batch size should preserve the relationship between send timeout and the 180-second claim lease.

Both publisher batches are independent from each other at the business level, but the repository does not explicitly configure a multi-thread scheduler for the two @Scheduled methods. Do not assume that their two flows always dispatch in parallel just because individual Kafka sends use futures.

5. HTTP calls and virtual threads: a different kind of concurrency

SocietyRestClientConfig builds a JDK HttpClient using a virtual-thread-per-task executor. This supports many concurrent blocking HTTP requests from different request threads without dedicating a platform thread to each wait. The SocietyClient itself uses synchronous RestClient methods and wraps each individual request with circuit breaker, bulkhead, and retry behavior.

MembershipService.assign first checks the member, then performs one required societyClient.getFlat(flatId) request, then acquires the membership lock and writes. The network call is a prerequisite for the write; there is no second independent remote lookup to overlap.

CommunityNoticeService.flatOptions makes one aggregated directory request. A notice can target multiple flat IDs, but those IDs are not individually fetched from Society Service in a loop; they are stored as audience targets and later resolved in the consumer’s database query.

The Gateway login path uses reactive WebClient and returns a Mono, which is asynchronous I/O for a single identity-validation call. It is not parallel fan-out of multiple independent services.

6. Measure before adding parallelism

The appropriate decision depends on the type of work. For Kafka batching, inspect producer batch size, records per request, compression rate, sent rate, outbox backlog, and publish latency. For a proposed HTTP fan-out, measure per-dependency latency and the total request critical path under representative load.

Do not parallelize operations when:

  • the second operation depends on the first result;
  • the calls share a write transaction, ordering rule, lock, or non-idempotent side effect;
  • the downstream bulkhead, connection pool, rate limit, or database cannot absorb the added concurrency;
  • the latency saved is not material relative to scheduling, aggregation, and failure-handling overhead.

The repository has producer metrics and counters for Kafka flows, but no before/after benchmark demonstrating request-latency improvement from parallel HTTP calls. No measured reason was found to add a new HTTP fan-out.

7. Limits and failure behavior

  • Futures are retained in memory only for the currently claimed batch; PostgreSQL outbox rows remain the durable source of truth.
  • The batch cap is 50. Producer in-flight limits, Kafka broker capacity, partition count, network, and consumer throughput remain separate constraints.
  • The code waits on futures in list order after submitting them. A slow first future can delay completion handling for later already-completed futures, although their network sends were submitted.
  • Each event failure is handled separately in the result loop, but a database error while recording failure can still escape the dispatcher.
  • Async I/O does not automatically reduce total work or downstream load. It can increase simultaneous outstanding sends and memory use.
  • The Kafka integration test exercises one notice event and checks it reaches Kafka and is deleted after acknowledgement. It does not prove multi-event batch overlap, throughput improvement, failure isolation under a burst, or ordering under load.
  • Virtual threads in the Society client provide concurrency across calls; they do not make a single synchronous service method fan out.

8. A safe future design checklist

If a future feature introduces two or more genuinely independent downstream reads, follow this sequence before parallelizing them:

  1. Identify calls that need no results from each other and have no ordering dependency.
  2. Record their individual latency, total endpoint latency, and realistic concurrency under representative traffic.
  3. Confirm both calls are safe to repeat and that partial failure has a defined API response.
  4. Use a bounded, managed executor or a reactive composition consistent with that service; avoid the common pool for blocking HTTP I/O.
  5. Propagate correlation/security context explicitly where necessary, and preserve timeouts, retry budgets, bulkheads, and cancellation.
  6. Join results with an overall deadline. Decide whether one failure fails the whole request or allows a partial response.
  7. Add tests for concurrent start, success, one-side failure, timeout, cancellation, and bounded concurrency; then compare before/after latency and downstream load.
Not implemented here: there is no new CompletableFuture.allOf, parallel stream, or HTTP fan-out in this task. The checklist is guidance for a future measured use case, not a claim about current code.

9. Interview preparation

60-second explanation

“This project already uses CompletableFuture in the Kafka outbox publishers. They claim up to 50 rows, submit every Kafka send before waiting, then await each future and delete only the matching row after its acknowledgement. Failures release their rows for retry. This overlaps producer network work and enables Kafka batching without fire-and-forget delivery. For HTTP, the Society client supports concurrency across requests using a virtual-thread executor, but each reviewed business operation makes one dependent downstream call, so I did not introduce parallel fan-out without measured independent work. The key trade-offs are in-flight memory, downstream capacity, failure semantics, and preserving per-event durability.”

Likely follow-upAnswer
Is calling get() still asynchronous?Each future is awaited eventually, so the dispatcher method remains blocking while it completes the batch. The important difference is that all sends were submitted before the first wait, allowing their producer/network work to overlap.
Why not use parallelStream()?The publisher needs a clear bounded batch, per-event completion, and durable row handling. Parallel streams use the common pool by default and make resource bounds and error collection less explicit.
Why keep a future for every send?Each result maps back to its outbox event and claim token, so success can delete only that row and failure can release only that row.
Does this guarantee exactly once?No. A broker acknowledgement followed by a process crash before row deletion can lead to a replay after lease expiry. Consumers deduplicate by event ID.
Why no parallel HTTP fan-out?The inspected HTTP service operations each make one required downstream request. There are no independent calls to overlap, and no latency measurements justify inventing them.
What do virtual threads do here?They make blocking HTTP requests cheaper to host concurrently across requests. They do not automatically run multiple calls in parallel inside one request.
