A beginner's guide

Emerald Housing Society

Learn how the project grows from two small Java applications into a system with separate databases, service communication, Kubernetes and an API Gateway.

Read one phase at a time. Technical words are explained in everyday language, and diagrams show how the pieces fit together.

Short version: Society Service looks after the building. Member Service looks after people. Each has its own database. Kubernetes runs the applications and gives them stable names. The Gateway is one front door for API calls.

Common section: how to run it

There are two ways to run the current project. Run the Java applications directly on your computer for local development, or run their Docker images in Kubernetes. Do one setup at a time. For local learning, start with Option A.

Important: The current Society and Member code uses PostgreSQL. The databases must exist and be reachable before those applications start. Flyway creates or updates tables inside each database when its application starts.

Prerequisites

  • Java Development Kit 21.
  • PowerShell on Windows, IntelliJ IDEA if you prefer to start apps from the IDE, and the project Maven Wrapper files.
  • PostgreSQL with the databases society_db and member_db, and a PostgreSQL user/password that works on your computer.
  • For Kubernetes only: Docker Desktop, kind, and kubectl.
  • The Postman files in postman/.

The services have separate Maven projects. Their wrappers are under services/society-service/ and services/member-service/. The Gateway project is under infrastructure/api-gateway/. You do not need a system-wide mvn command when using the wrappers, but the wrapper may need network access to download Maven or dependencies the first time.

Option A: run locally from PowerShell

  1. Open the repository: open emerald-housing in IntelliJ IDEA. Set Project SDK, module SDK, and Maven JDK to Java 21. Import the Society and Member Maven projects from their pom.xml files. Keep preview features disabled.
  2. Start PostgreSQL and create the databases: PostgreSQL must be running. If you use one PostgreSQL role called emerald for both services, create that role first if needed. Open psql as the PostgreSQL administrator and run the role commands only if the role does not already exist:
    psql -h localhost -p 5432 -U postgres -d postgres
CREATE ROLE emerald LOGIN;
\password emerald
\q

    Then create each database owned by that role. Run only the database commands for databases that do not already exist:

    createdb -h localhost -p 5432 -U postgres -O emerald society_db
createdb -h localhost -p 5432 -U postgres -O emerald member_db
psql -h localhost -p 5432 -U postgres -d postgres -c "SELECT datname FROM pg_database WHERE datname IN ('society_db','member_db');"

    If createdb is not on PATH, run it from PostgreSQL's bin directory or use pgAdmin. If you use separate application roles, create each database with the matching owner and use those credentials below. Flyway creates tables, not databases.

  3. Open three PowerShell terminals: one for Society, one for Member, and one for Gateway if you want to use Gateway. Environment variables set with $env: apply to that terminal and processes started from it. They do not automatically transfer to an IntelliJ process launched separately from the Start menu.
  4. Start Society Service in its terminal: set Society's DB variables, then run its Maven Wrapper. The default local port is 8081. Keep this terminal open.
  5. Start Member Service in a second terminal: set Member's DB variables and its Society URL, then run its Maven Wrapper. The default local port is 8082. Society must be running for flat assignment validation. Keep this terminal open too.
  6. Optionally start Gateway in a third terminal: after the backend services are running, start Gateway. Its default port is 8080 and its local backend defaults are Society on 8081 and Member on 8082.
  7. Check health: wait for each application's startup to finish; backend startup includes Flyway and Hibernate schema validation. Then run these commands in another PowerShell terminal:
    Invoke-RestMethod http://localhost:8081/actuator/health
Invoke-RestMethod http://localhost:8082/actuator/health
Invoke-RestMethod http://localhost:8080/actuator/health

    Only run the Gateway check if you started Gateway.

  8. Use Postman: import the collection and environment below, select the local environment, and start with Society reads. Create a flat if the database has none, create a member, then assign that member to the flat. To call through Gateway, set gatewayBaseUrl to http://localhost:8080.

Option B: run in Kubernetes (PowerShell commands)

Use this path after Docker Desktop and PostgreSQL are running, and society_db and member_db exist. Run commands from the repository root unless the step says to open another terminal. The detailed explanation of why each resource is applied in this order is in Resource creation order and connections.

  1. Open PowerShell at the repository root:
    cd "D:\Devendra Ghag Interview Preparation\02_Spring\emerald-housing"
Get-Location
  2. Start or check the kind cluster: Docker Desktop must already be running. The script creates the project cluster if needed and checks that kubectl can reach it.
    .\scripts\kubernetes\prepare-kind.ps1
kubectl cluster-info --context kind-emerald-housing
  3. Create the namespace:
    kubectl apply -f .\kubernetes\namespace.yaml
kubectl get namespace emerald-housing
  4. Create the database Secret: enter the actual database credentials when prompted. If the same PostgreSQL role can access both databases, enter it for both services. This creates a Secret in the emerald-housing namespace; it does not create a Secret file.
    $societyUser = Read-Host 'Society DB username'
$societyPasswordSecure = Read-Host 'Society DB password' -AsSecureString
$memberUser = Read-Host 'Member DB username'
$memberPasswordSecure = Read-Host 'Member DB password' -AsSecureString
$societyPassword = [System.Net.NetworkCredential]::new('', $societyPasswordSecure).Password
$memberPassword = [System.Net.NetworkCredential]::new('', $memberPasswordSecure).Password
kubectl create secret generic emerald-db-credentials -n emerald-housing --from-literal="society-username=$societyUser" --from-literal="society-password=$societyPassword" --from-literal="member-username=$memberUser" --from-literal="member-password=$memberPassword"
kubectl get secret emerald-db-credentials -n emerald-housing

    If the Secret already exists, do not create a duplicate. Follow the repository’s manual Kubernetes checklist to update it safely. Keep passwords out of committed files and screenshots.

  5. Build and load the Society and Member images into kind: the kind cluster must exist first because kind load copies images into its nodes.
    .\scripts\kubernetes\build-load-images.ps1
  6. Create the backend ConfigMap:
    kubectl apply -f .\kubernetes\config\application-config.yaml
kubectl get configmap emerald-app-config -n emerald-housing

    It supplies non-secret settings, including POSTGRES_HOST=host.docker.internal and the in-cluster Society URL. This host name is for the repository’s Docker Desktop/kind setup; PostgreSQL must accept connections from the Pod network.

  7. Create backend Deployments and Services:
    kubectl apply -f .\kubernetes\society\
kubectl apply -f .\kubernetes\member\
kubectl get deployments,pods,services,endpointslices -n emerald-housing
  8. Wait for both backend applications: each container starts Spring Boot. Society and Member each run Flyway against their own database, then Hibernate validates the schema. Wait for both Deployments to become ready:
    kubectl rollout status deployment/society-service -n emerald-housing
kubectl rollout status deployment/member-service -n emerald-housing
kubectl get pods -n emerald-housing -o wide

    If a Pod does not become Ready, inspect its logs before continuing:

    kubectl logs deployment/society-service -n emerald-housing
kubectl logs deployment/member-service -n emerald-housing
  9. Build and load images including Gateway: this script option builds and loads all three images using the tags referenced by the manifests.
    .\scripts\kubernetes\build-load-images.ps1 -IncludeGateway
  10. Create Gateway configuration, then its Deployment and Service:
    kubectl apply -f .\kubernetes\gateway\config.yaml
kubectl apply -f .\kubernetes\gateway\deployment.yaml
kubectl apply -f .\kubernetes\gateway\service.yaml
kubectl rollout status deployment/api-gateway -n emerald-housing
kubectl get pods,services -n emerald-housing
  11. Apply NetworkPolicies: these restrict inbound application traffic to the allowed callers. The cluster network plugin must enforce NetworkPolicy for these rules to take effect.
    kubectl apply -f .\kubernetes\networkpolicies.yaml
kubectl get networkpolicies -n emerald-housing
  12. Make the private Gateway reachable from Windows: api-gateway is a ClusterIP Service. That is an internal Kubernetes address: Pods in the cluster can call http://api-gateway:8080, and Kubernetes routes that call to a ready Gateway Pod. Postman on Windows runs outside the cluster, so it cannot normally use that internal address directly. Open a new PowerShell terminal and keep this temporary tunnel running while using Postman:
    kubectl port-forward service/api-gateway 8080:8080 -n emerald-housing

    This connects your computer's localhost:8080 to the Service's port 8080. Use http://localhost:8080 in Postman and press Ctrl+C in the port-forward terminal when finished. This is a local development access method; it does not change the Service to a public endpoint.

  13. Check readiness and send a first request: in another PowerShell terminal:
    Invoke-RestMethod http://localhost:8080/actuator/health
Invoke-RestMethod http://localhost:8080/api/v1/society

    For more status and discovery checks, use kubectl get deployments,pods,services,endpointslices -n emerald-housing. Gateway receives the client request, routes it to a backend Service DNS name, and that Service sends it to a ready Pod.

Inside versus outside the cluster: frontend and backend Pods can call one another through internal Service names, such as http://api-gateway:8080 or http://member-service:8080. A person using a browser or Postman on Windows is outside the cluster and needs a way in. This project uses port-forwarding for local access. An Ingress or NGINX reverse proxy could provide a more stable external entry point in a later phase; neither is configured here.
Database connection note: Flyway creates tables within existing databases; it does not create PostgreSQL databases. If Kubernetes Pods cannot connect to PostgreSQL on Windows, check PostgreSQL listening and host-based authentication settings for the actual Pod source address. Do not use trust authentication as a shortcut.

Postman files and recommended request order

  1. Import postman/Emerald-Housing-Phase1.postman_collection.json.
  2. Import postman/Emerald-Housing-Local.postman_environment.json and select Emerald Housing - Local.
  3. For local direct calls, use societyBaseUrl=http://localhost:8081 and memberBaseUrl=http://localhost:8082. For local Gateway calls, use gatewayBaseUrl=http://localhost:8080.
  4. Get society, list floors, and retrieve or create a flat.
  5. Create a member and copy its UUID into memberId if the collection has not captured it automatically.

If a backend fails during database startup

Check Flyway and the actual database

Connect to the same database named in the startup URL and inspect Flyway history. Use your actual PostgreSQL role:

psql -h localhost -U emerald -d society_db
SELECT current_database(), current_schema();
SELECT installed_rank, version, description, success FROM flyway_schema_history ORDER BY installed_rank;
SELECT to_regclass('public.flats');
psql -h localhost -U emerald -d member_db
SELECT current_database(), current_schema();
SELECT installed_rank, version, description, success FROM flyway_schema_history ORDER BY installed_rank;
SELECT to_regclass('public.flat_memberships');

If a table lookup returns null, verify the database name, schema, credentials, and migration history. Preserve applied migrations; use a new migration for a genuine schema change.

Phase 1 · Foundation

Two separate applications

Different jobs, different ports

A microservice is a small application with one main responsibility. Society Service owns building information. Member Service owns people information. This clear job boundary is called a bounded context.

ApplicationIts jobLocal port
Society ServiceSociety and floors; later flats.8081
Member ServiceCreate, read, update and deactivate members.8082

How an API request moves

A Controller receives the web request. A Service does the job's rules. A DTO is a small data shape used to receive or return information. An exception handler turns errors into a clear response.

Examples: Society has GET /api/v1/society and GET /api/v1/floors. Member has POST /api/v1/members, GET /api/v1/members, update and deactivate operations.

GET reads. POST creates. PUT updates permitted details. PATCH changes part of something. HTTP 200 means okay, 201 means created, 400 means bad input, 404 means not found and 409 means conflict.

Phase 1 used temporary memory. Stop the app and that temporary data is gone. Phase 2 changes storage to PostgreSQL. Phase 1 created separate apps, REST APIs, validation, error responses and health checks.
Phase 2 · Durable storage

Give each service its own database

PostgreSQL · JPA · Flyway

Temporary memory is like a whiteboard: it clears when the app stops. PostgreSQL is like a filing cabinet that keeps information. Society Service uses society_db. Member Service uses member_db. Neither service reads the other's database.

JPA describes database rows using Java objects. Hibernate maps those objects to SQL tables. A repository finds and saves rows. A transaction groups database changes so they succeed or fail as a unit. An index helps locate rows faster.

Society owns society, floor and flat tables. Member owns member and flat-membership tables. Membership stores a flat ID as a reference; there is no foreign key to Society's separate database. Member deactivation keeps its record and status history rather than deleting the row.

Flyway: a numbered instruction book for databases

Flyway applies saved SQL changes in order. Think of a new database receiving a numbered instruction book: first create tables, then insert the building's initial records. Flyway remembers which instructions it has already applied.

  1. Spring Boot starts the service and reads application.yml. With spring.flyway.enabled: true, Spring Boot configures Flyway to run during startup.
  2. The service's datasource tells Flyway which database to connect to: Society uses society_db; Member uses member_db.
  3. Flyway uses its default migration location, classpath:db/migration. It checks flyway_schema_history in that database, creating the history table if this is the first run.
  4. Flyway scans the classpath location for versioned files named like V1__create_tables.sql. The two underscores separate the version from the description. It validates files already recorded, including their checksums.
  5. Any pending versioned migrations run from lowest version to highest. Flyway records each successful migration's version, description, script name, checksum, time and success status in the history table.
  6. Hibernate then uses ddl-auto: validate to check that the Java entity mappings match the database tables. It does not create or update tables here.
How does Flyway find db/migration? The source folder is src/main/resources (resources, plural), a standard Maven resource folder. Maven copies its contents to the application's classpath: for example, src/main/resources/db/migration/V1__create_tables.sql becomes classpath:db/migration/V1__create_tables.sql. When running from an IDE, the IDE also puts the resources folder on the application classpath. Flyway's default location looks for db/migration at that classpath root, so this project does not need a custom spring.flyway.locations setting.
What is flyway_schema_history? Flyway creates this tracking table in each service's own database and records which migration files succeeded. It stores migration metadata and checksums—not the query results, a copy of the SQL's changed data, or business records. If V1 is already recorded as successful, a normal restart skips it. A later V2__... file is applied once and then recorded.

Society files

V1__create_society_tables.sql creates societies, floors, flats, rules and an index.

V2__seed_society_and_floors.sql inserts Emerald Housing Society and floors 1–18.

Member file

V1__create_member_tables.sql creates members and flat memberships with constraints and indexes.

Do not edit a migration that has already run. Add a new higher-numbered migration for a new change. If SQL or the database is broken, Flyway normally makes startup fail so the issue is visible. Each service has its own migration history in its own database.

Phase 2 limit: Member Service can store a flat ID, but it does not yet confirm that the flat exists. Phase 3 adds that request to Society Service.
Phase 3 · Apps communicate

Ask Society Service about a flat

Spring RestClient

Member Service owns people, not flats. For an assignment it asks the flat owner, Society Service, if the flat exists. It never connects directly to society_db.

This is synchronous HTTP: send a question, wait for an answer, then continue. Spring's RestClient performs the request.

  1. Member Service receives an assignment request.
  2. It checks its member and local rules.
  3. SocietyClient asks Society Service for the requested flat.
  4. Only after the flat is confirmed does Member Service save its membership.
SituationResultNew membership saved?
Flat exists and rules passSuccessYes
Member or flat missingNot-found errorNo
Bad requestBad-request errorNo
Society is down/slowControlled dependency error after timeoutNo
Duplicate active assignmentConflict errorNo duplicate

A timeout limits how long Member Service waits. A correlation ID is a tracking label shared by related request logs. This call adds a network dependency: if Society is unavailable, flat assignment must fail safely. The two databases do not share one transaction.

Phase 4 · Stable Kubernetes names

Find services without memorizing Pod addresses

Kubernetes DNS

A Pod can be replaced and get a different IP address, so Member Service must not save or call a particular Society Pod IP. Instead, Member Service calls a Kubernetes Service name that stays the same while the Pods behind it can change.

On your PC:        http://localhost:8081
Inside Kubernetes: http://society-service:8080

There is no project file that creates a DNS record. Kubernetes cluster DNS (normally CoreDNS) automatically makes a DNS name for each Kubernetes Service. The project YAML creates the Namespace, Deployment and Service that Kubernetes DNS uses.

  1. Create the namespace: kubernetes/namespace.yaml declares emerald-housing, the project area in the cluster.
  2. Create labeled Society Pods: kubernetes/society/deployment.yaml asks for two replicas and puts app: society-service on each Pod.
  3. Create the stable Service: kubernetes/society/service.yaml names the Service society-service and selects Pods with app: society-service. It accepts traffic on port 8080.
  4. Kubernetes provides DNS: the Service file kubernetes/society/service.yaml declares metadata.name: society-service and metadata.namespace: emerald-housing. The cluster DNS service, usually CoreDNS, automatically uses that Service name and namespace to provide society-service.emerald-housing.svc.cluster.local. Its parts are: society-service is the Service name; emerald-housing is the namespace; svc marks the Kubernetes Service DNS area; cluster.local is the cluster DNS domain, commonly the default. There is no DNS YAML file to create.
  5. Configure Member to call it: kubernetes/config/application-config.yaml sets SOCIETY_SERVICE_BASE_URL to http://society-service:8080. kubernetes/member/deployment.yaml loads that ConfigMap with envFrom. The Member app's application.yml reads the variable for its RestClient; locally its fallback is http://localhost:8081.
  6. Route to ready Pods: Kubernetes matches the Service selector to Society Pod labels and sends traffic to ready endpoints. When a Pod is replaced, the Service name stays unchanged; its endpoints update.
In short: the Service's metadata.name provides the name; cluster DNS resolves it; its spec.selector finds matching Pod labels; the Deployment creates those Pods; the ConfigMap gives Member Service the URL. Eureka is not used.
Kubernetes setup - this repository

Resource creation order and connections

One complete sequence

Follow this order for the repository's local kind setup. PostgreSQL, Docker, kind, and kubectl must be ready first. The databases must already exist before the backend applications start: Flyway creates tables inside them, not the databases themselves.

  1. Prepare PostgreSQL: start PostgreSQL and create society_db and member_db. Make sure the credentials you will place in the Kubernetes Secret can connect.
  2. Start the kind cluster: run scripts/kubernetes/prepare-kind.ps1. It uses kubernetes/kind-config.yaml. The cluster must exist before image loading because the image-loading script transfers images into the kind nodes.
  3. Create the namespace: apply kubernetes/namespace.yaml. It creates the emerald-housing area inside the cluster.
  4. Create the database Secret: run the documented kubectl create secret command in namespace emerald-housing. It creates emerald-db-credentials; this Secret is created as a Kubernetes object, not from a committed Secret YAML file.
  5. Build and load Society and Member images: run scripts/kubernetes/build-load-images.ps1. This makes the backend images available to the kind cluster.
  6. Apply the backend ConfigMap: apply kubernetes/config/application-config.yaml. It creates emerald-app-config with non-secret settings such as POSTGRES_HOST and SOCIETY_SERVICE_BASE_URL.
  7. Apply backend Deployments and Services: apply the YAML resources under kubernetes/society/ and kubernetes/member/. Deployments request Society 2 replicas and Member 1 replica. Services select their Pods using matching labels. Once the namespace and configuration exist, each Deployment and its Service may be applied in either order.
  8. Kubernetes starts the backend containers: each Deployment creates or updates a ReplicaSet; the ReplicaSet creates Pods; the node's kubelet and container runtime start containers from the images. The Dockerfiles run the packaged applications with java -jar /app/app.jar.
  9. Spring Boot loads application settings: Society reads services/society-service/src/main/resources/application.yml; Member reads services/member-service/src/main/resources/application.yml. Kubernetes supplies ConfigMap values through envFrom and each service's database credentials through secretKeyRef.
  10. Flyway runs during backend application startup: Society connects to society_db and reads services/society-service/src/main/resources/db/migration/V1__create_society_tables.sql, followed by V2__seed_society_and_floors.sql. Member connects to member_db and reads services/member-service/src/main/resources/db/migration/V1__create_member_tables.sql. Flyway checks each database's flyway_schema_history and applies pending migrations. It does not run for each API request.
  11. Hibernate validates each backend schema: after migrations, Hibernate checks that the database tables match the Java mappings. Society and Member own separate databases. Both Society Pods use the same society_db; extra Pods do not create extra databases.
  12. Wait for backend readiness: startup and readiness probes check the applications. When a Pod is ready, its backend Service can route normal traffic to it. A running Pod that has not passed readiness should not receive normal Service traffic.
  13. Build and load the Gateway image: run scripts/kubernetes/build-load-images.ps1 -IncludeGateway after the backend services are ready. This option builds and loads the Gateway image as well as rebuilding and reloading the two backend images with their configured tags. Loading an image does not restart Pods that are already running; a Deployment rollout needs a change to the Deployment Pod template.
  14. Apply the Gateway ConfigMap: apply kubernetes/gateway/config.yaml. It creates api-gateway-config, which the Gateway Deployment reads.
  15. Apply Gateway Deployment and Service: apply the YAML resources under kubernetes/gateway/. The Deployment requests two Gateway Pods. Gateway starts as a separate Spring Boot application and does not connect to a database or run Flyway.
  16. Wait for Gateway readiness: after its readiness probe succeeds, the api-gateway Service can send requests to ready Gateway Pods.
  17. Apply the NetworkPolicies: apply kubernetes/networkpolicies.yaml after the namespace and workloads exist, before the traffic checks. It allows Gateway to reach Member and Society, and Member to reach Society on TCP port 8080. These policies limit incoming traffic only; they do not restrict application egress to PostgreSQL.
  18. Give Postman a way to reach Gateway: the current Gateway Service is ClusterIP, which is private inside the cluster. For local Postman usage, follow the manual Kubernetes checklist and its port-forward step.
  19. Send requests through Gateway: Gateway reads the path rules in infrastructure/api-gateway/src/main/resources/application.yml and forwards Member paths to member-service, and Society, floor, and flat paths to society-service. These Kubernetes Services select ready backend Pods.
  20. For a flat assignment: Member Service uses RestClient over HTTP to call the stable society-service name. Society checks society_db; if the flat is valid, Member saves the membership in member_db.

What it says, why it exists

These are Kubernetes instructions written as YAML. The actual files in this repository use the .yaml extension. Kubernetes reads these fields when you apply the files to the cluster. A field only has an effect when it is under the correct parent such as metadata or spec.

Four different jobs: Namespace groups project resources. Deployment creates and maintains Pods. Service gives selected Pods a stable network name. NetworkPolicy limits which Pods may connect to selected Pods.

Phase 5 · Replicas and replacement

Keep more than one copy running

Scale and self-heal

A replica means one running copy. Society's Deployment requests two copies. Its Kubernetes Service sends traffic to ready copies. The caller still uses the same service name.

If one Pod stops, Kubernetes tries to replace it to reach the requested count. This is self-healing, but it does not promise every request succeeds during a failure.

The X-Instance-ID header can help show which copy answered. Calls may not alternate evenly because HTTP connections can be reused. To request three copies: kubectl scale deployment society-service --replicas=3 -n emerald-housing.

Readiness means a Pod should receive requests. Liveness means the process still appears healthy enough to keep running.

Phase 6 · One API front door

Use Spring Cloud Gateway

Routes by URL

Postman normally needs different addresses for different apps. A Gateway provides one address. It looks at the request path and forwards it to the correct service.

Member paths such as /api/v1/members go to Member Service. Society, floor and flat paths go to Society Service. Actual routes are in infrastructure/api-gateway/src/main/resources/application.yml, lines 11–21.

The Gateway forwards calls; it should not contain member or flat business rules. It is not automatically a login system, so do not assume the APIs are protected just because a Gateway exists.

How the settings reach each application

  1. kubernetes/config/application-config.yaml creates the emerald-app-config ConfigMap. It provides ordinary settings, including POSTGRES_HOST=host.docker.internal and SOCIETY_SERVICE_BASE_URL=http://society-service:8080.
  2. Each backend Deployment loads that ConfigMap using envFrom. It separately maps its own database username and password from emerald-db-credentials using secretKeyRef.
  3. Society's application.yml builds a JDBC URL ending in /society_db. Member's application.yml builds one ending in /member_db. Both connect to the configured PostgreSQL host, but use different databases and credentials.
  4. Each Pod starts its own Spring application and reads those environment variables. The two Society replicas use the same society_db; they do not each get a separate database. Member Service does not connect to society_db.
  5. When Member needs to check a flat, its RestClient calls the stable Society Service name over HTTP. Society Service reads its own database and returns the result.
Simple rule: A Pod is an application copy, not a database copy. Scaling Society from one Pod to two adds another application process; both copies use the same Society database. Member replicas (currently one) use the Member database.

Files to inspect: kubernetes/society/deployment.yaml (2 replicas and Society credentials), kubernetes/member/deployment.yaml (1 replica and Member credentials), kubernetes/config/application-config.yaml (shared non-secret host and Society URL), services/society-service/src/main/resources/application.yml (society_db), and services/member-service/src/main/resources/application.yml (member_db and RestClient URL).

About host.docker.internal: In this repository's local kind/Docker Desktop setup, this configured hostname lets Pods reach PostgreSQL running on the Windows host. It is not a Kubernetes database Service and does not discover PostgreSQL automatically. If PostgreSQL is later moved into Kubernetes, configure the host to use that database's Kubernetes Service DNS name.

Name is required (up to 120 characters). The default mobile format is 10 digits beginning 6–9. Email is optional and validated if supplied. Relationship values are OWNER, TENANT or RESIDENT. An end-membership request uses {"endDate":"2026-10-15"}; the date cannot be before its start date or in the future.

Page sorting is limited to fields supported by the API. Flats support flatNumber, status, createdAt and updatedAt. Members: createdAt, updatedAt, fullName, mobileNumber, email, status. Memberships: startDate, endDate, createdAt, updatedAt, relationshipType. Flat fields are listed in the Society table. Invalid paging and sorting inputs return 400.

Common error shape

{
  "timestamp": "2026-10-15T10:00:00Z",
  "status": 404,
  "error": "Not Found",
  "code": "RESOURCE_NOT_FOUND",
  "message": "Flat not found",
  "path": "/api/v1/flats/example",
  "details": {}
}

The exact message varies with the problem. The stable status and code are more useful to a client than relying on exact wording. Society is not authenticated; these are local learning APIs.

Gateway addresses

Locally the Gateway listens on http://localhost:8080. Through it use the same API paths, such as GET /api/v1/society or GET /api/v1/members. In Kubernetes, Gateway routes to the private names member-service:8080 and society-service:8080.

Manual checklist · run on your own PC

Finish and verify the local Kubernetes setup

Action guide moved here

These actions change your local PostgreSQL and Kubernetes environment. They are instructions only; this page does not run them. Use your own database password. Never commit it or permit database trust authentication from Pod networks.

Check your current state first: this is a manual checklist. Confirm the database, cluster, namespace and Secret before applying commands. The page does not run them for you.

Recommended order

Set a known password for the PostgreSQL application role, create the Kubernetes Secret, start backend Pods, inspect PostgreSQL logs for the source address, then add only the needed SCRAM host rules and reload PostgreSQL. Do not guess a client subnet.

Action 1 · Prepare PostgreSQL access safely

Services default to database role emerald. From an Administrator PowerShell prompt, connect as PostgreSQL administrator:

& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h localhost -U postgres -d postgres

At the psql prompt, confirm the role and set its password without placing it in SQL history:

\du emerald
\password emerald
\q

Open the active pg_hba.conf as Administrator. The previously inspected location was C:\Program Files\PostgreSQL\18\data\pg_hba.conf. If different, run SHOW data_directory; in psql. After a Pod attempts a connection, read the PostgreSQL log and use the client source IP that PostgreSQL reports. Add narrowly scoped rules before broader matching rules:

host  society_db  emerald  <reported-source-ip>/32  scram-sha-256
host  member_db   emerald  <reported-source-ip>/32  scram-sha-256

Repeat for each real source IP shown. Reload PostgreSQL:

& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h localhost -U postgres -d postgres
SELECT pg_reload_conf();
\q

The reload query should return true. Do not use trust for Pod traffic. The source address must be observed from your cluster.

Action 2 · Create the Kubernetes database Secret

From the repository root in PowerShell. Enter the actual database username/password. If both databases share a role, enter the same values for both.

$societyUser = Read-Host 'Society DB username'
$societyPasswordSecure = Read-Host 'Society DB password' -AsSecureString
$memberUser = Read-Host 'Member DB username'
$memberPasswordSecure = Read-Host 'Member DB password' -AsSecureString
$societyPassword = [System.Net.NetworkCredential]::new('', $societyPasswordSecure).Password
$memberPassword = [System.Net.NetworkCredential]::new('', $memberPasswordSecure).Password
kubectl apply -f .\kubernetes\namespace.yaml
kubectl create secret generic emerald-db-credentials -n emerald-housing --from-literal="society-username=$societyUser" --from-literal="society-password=$societyPassword" --from-literal="member-username=$memberUser" --from-literal="member-password=$memberPassword"
kubectl get secret emerald-db-credentials -n emerald-housing

The last command confirms the Secret exists without printing its values. If it already exists, update it using your normal local secret-management procedure rather than creating a duplicate.

Action 3 · Build images and deploy Society and Member

From the repository root build and load backend images, then apply their manifests:

.\scripts\kubernetes\build-load-images.ps1
kubectl apply -f .\kubernetes\config\application-config.yaml
kubectl apply -f .\kubernetes\society\
kubectl apply -f .\kubernetes\member\

kubectl rollout status deployment/society-service -n emerald-housing

Action 4 · Check discovery and flat validation

For direct local checks, run each port-forward in a different terminal:

kubectl port-forward -n emerald-housing service/society-service 8081:8080
kubectl port-forward -n emerald-housing service/member-service 8082:8080

Check the Society APIs and health endpoints:

Invoke-RestMethod http://localhost:8081/actuator/health
Invoke-RestMethod http://localhost:8081/api/v1/society
Invoke-RestMethod http://localhost:8081/api/v1/floors
Invoke-RestMethod http://localhost:8081/api/v1/flats
Invoke-RestMethod http://localhost:8082/actuator/health

Create a flat and member, then assign. The floor must be 1–18:

$flatBody = @{ floorNumber = 1; flatNumber = 'A-101' } | ConvertTo-Json
$flat = Invoke-RestMethod -Method Post -Uri 'http://localhost:8081/api/v1/flats' -ContentType 'application/json' -Body $flatBody
$memberBody = @{ fullName = 'Rahul Sharma'; mobileNumber = '9876543210'; email = 'rahul@example.com' } | ConvertTo-Json
$member = Invoke-RestMethod -Method Post -Uri 'http://localhost:8082/api/v1/members' -ContentType 'application/json' -Body $memberBody
$assignment = @{ flatId = $flat.flatId; relationshipType = 'RESIDENT'; startDate = (Get-Date -Format 'yyyy-MM-dd') } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "http://localhost:8082/api/v1/members/$($member.memberId)/flats" -ContentType 'application/json' -Body $assignment

Try a random UUID for the flat; it should fail and create no membership. Compare the same X-Correlation-ID in the Member and Society logs.

kubectl scale deployment/society-service -n emerald-housing --replicas=3
kubectl rollout status deployment/society-service -n emerald-housing
kubectl get pods -n emerald-housing -l app=society-service -o wide

Inspect X-Instance-ID using separate requests/connections. Traffic is not guaranteed to alternate because connections may be reused. To check self-healing, identify a Society Pod, delete it, and watch Kubernetes replace it:

kubectl get pods -n emerald-housing -l app=society-service
kubectl delete pod <society-pod-name> -n emerald-housing
kubectl get pods -n emerald-housing -l app=society-service -w

Then check that two ready endpoints return and a flat assignment works. A brief request failure during replacement is possible.
