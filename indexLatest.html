1. Spring Boot and backend development

30–45 second answer: “I use Spring Boot for three applications: Member, Society and Gateway. Member and Society expose MVC REST APIs, while the Gateway uses WebFlux. Controllers handle HTTP, services apply business rules and repositories access PostgreSQL. Spring manages dependencies. Validation and exception handlers control bad requests, transactions protect local writes, and Flyway manages schema changes. Actuator supports monitoring, and graceful shutdown helps deployments.”

Simple execution flow: HTTP request → security filters → controller and validation → service and transaction → JPA repository → PostgreSQL → DTO response

3. Security

30–45 second answer: “Credentials use BCrypt hashes, and Gateway login creates a Redis-backed session. State-changing requests require CSRF protection. Services check both the current role and access to the particular record, so residents cannot read another member’s data. Backend validation refreshes current account scope, allowing disablement and revocation to take effect. Internal header sanitization, restricted audit access and network/HTTPS configuration provide additional protection.”

Simple execution flow: Credentials → Redis session → backend session validation → refresh account permissions → role and record checks → result or denial

4. Database design and consistency

30–45 second answer: “PostgreSQL stores the business records using relational models. Local transactions keep changes and audit history together. Membership updates combine a Redis lock, a database row lock and a unique constraint. JPA versions and If-Match detect conflicting edits. Idempotency keys make member-create retries safe. Indexes, DTO projections, pagination and Hikari pools manage query work, while optional replica routing supports selected reads.”

Simple execution flow: Validate → member-scoped Redis lock → database transaction and row lock → enforce constraints → persist business state and audit → commit

5. Redis and caching

30–45 second answer: “Redis supports four jobs: sessions, rate limits, membership locks and Society reference caching. A cache hit avoids a repeated database load; a miss loads PostgreSQL and temporarily stores the result. TTL, jitter, negative caching and coordinated loading reduce repeated work. Changes invalidate caches after commit. Separate Redis deployments and bounded database fallback distinguish cache availability from security and locking requirements.”

Simple execution flow: Cache lookup → hit: return value; miss: coordinate load → PostgreSQL → store with TTL → return; committed change → invalidate

6. Resilience and fault tolerance

30–45 second answer: “Member’s Society lookup uses bounded timeouts, selected retries, a circuit breaker and a bulkhead. Timeouts limit waiting, retries recover selected temporary failures, the breaker stops calls to an unhealthy dependency, and the bulkhead caps simultaneous work. Backoff and jitter spread attempts. Redis rate limits control bursts, security fails closed when identity cannot be validated, and controlled errors explain dependency failures.”

Simple execution flow: Retry → circuit-breaker permit → bulkhead permit → HTTP timeout boundary → response or translated dependency error

Brief key-term definitions — 9 covered topics
TopicBrief definition and use in this repository
Connection/read timeoutsBound how long Member waits to connect to and receive a response from Society.
RetryRepeat selected transient failures within a bounded attempt count.
Exponential backoff and jitterIncrease/randomize retry delays to reduce synchronized retry bursts.
Circuit breakerStop repeated dependency calls when configured failure/slow-call conditions are reached; use limited recovery probes.
BulkheadLimit concurrent Society lookups so the dependency path cannot consume unlimited capacity.
Rate limitingRestrict incoming request rate/bursts using shared Redis state.
Fail-closed securityReject authentication-dependent work when current identity cannot be validated.
Controlled fallbackBypass unavailable cache storage only within bounded database-load capacity.
Error translationConvert timeouts, unavailable dependencies, invalid responses and capacity failures into meaningful API errors.

Limitation: Retries increase traffic and total elapsed time. A safe policy must fit the caller’s budget and must not repeat unsafe writes blindly. Cache fallback is different from bypassing security.

8. System-design reasoning you can discuss

30–45 second answer: “I start with requirements and data ownership, then draw one end-to-end request. I explain local correctness, resident privacy and dependency failures before discussing scale. Measurements such as latency, errors, query plans, cache hits and pool waits guide improvements. Each decision has a cost: services add network coupling, caches add stale-data risk, and more Pods add database connections. I separate implemented behavior from proposed improvements.”

Start here: explain your project in 90 seconds

“Emerald Housing manages society buildings, flats, members and their flat assignments. Society Service owns the building data. Member Service owns people, membership history and application accounts. Each service owns its database, and an API Gateway is the common entry point.

When an administrator assigns a member to a flat, Member Service asks Society Service whether the flat is active. It then uses a Redis lock, a short database transaction and database constraints to protect the assignment. Roles and record checks control access. Audit events are committed with business changes.

Redis also stores sessions, supports rate limits and caches Society reference data. Docker and Kubernetes configuration supports deployment, health checks and scaling. The current scope is one society; maintenance billing is a possible next business phase.”

Technical support for these workflows

How an API request moves

A Controller receives the web request. A Service does the job's rules. A DTO is a small data shape used to receive or return information. An exception handler turns errors into a clear response.

Phase 1 used temporary memory. Stop the app and that temporary data is gone. Phase 2 changes storage to PostgreSQL. Phase 1 created separate apps, REST APIs, validation, error responses and health checks.

Give each service its own database

PostgreSQL · JPA · Flyway

Temporary memory is like a whiteboard: it clears when the app stops. PostgreSQL is like a filing cabinet that keeps information. Society Service uses society_db. Member Service uses member_db. Neither service reads the other's database.

JPA describes database rows using Java objects. Hibernate maps those objects to SQL tables. A repository finds and saves rows. A transaction groups database changes so they succeed or fail as a unit. An index helps locate rows faster.

Society owns society, floor and flat tables. Member owns member and flat-membership tables. Membership stores a flat ID as a reference; there is no foreign key to Society's separate database. Member deactivation keeps its record and status history rather than deleting the row.

Flyway: a numbered instruction book for databases

Flyway applies saved SQL changes in order. Think of a new database receiving a numbered instruction book: first create tables, then insert the building's initial records. Flyway remembers which instructions it has already applied.

  1. Spring Boot starts the service and reads application.yml. With spring.flyway.enabled: true, Spring Boot configures Flyway to run during startup.
  2. The service's datasource tells Flyway which database to connect to: Society uses society_db; Member uses member_db.
  3. Flyway uses its default migration location, classpath:db/migration. It checks flyway_schema_history in that database, creating the history table if this is the first run.
  4. Flyway scans the classpath location for versioned files named like V1__create_tables.sql. The two underscores separate the version from the description. It validates files already recorded, including their checksums.
  5. Any pending versioned migrations run from lowest version to highest. Flyway records each successful migration's version, description, script name, checksum, time and success status in the history table.
  6. Hibernate then uses ddl-auto: validate to check that the Java entity mappings match the database tables. It does not create or update tables here.
How does Flyway find db/migration? The source folder is src/main/resources (resources, plural), a standard Maven resource folder. Maven copies its contents to the application's classpath: for example, src/main/resources/db/migration/V1__create_tables.sql becomes classpath:db/migration/V1__create_tables.sql. When running from an IDE, the IDE also puts the resources folder on the application classpath. Flyway's default location looks for db/migration at that classpath root, so this project does not need a custom spring.flyway.locations setting.
What is flyway_schema_history? Flyway creates this tracking table in each service's own database and records which migration files succeeded. It stores migration metadata and checksums—not the query results, a copy of the SQL's changed data, or business records. If V1 is already recorded as successful, a normal restart skips it. A later V2__... file is applied once and then recorded.

Society files

V1__create_society_tables.sql creates societies, floors, flats, rules and an index.

V2__seed_society_and_floors.sql inserts Emerald Housing Society and floors 1–18.

Member file

V1__create_member_tables.sql creates members and flat memberships with constraints and indexes.

Do not edit a migration that has already run. Add a new higher-numbered migration for a new change. If SQL or the database is broken, Flyway normally makes startup fail so the issue is visible. Each service has its own migration history in its own database.

Phase 2 limit: Member Service can store a flat ID, but it does not yet confirm that the flat exists. Phase 3 adds that request to Society Service.

Ask Society Service about a flat

Spring RestClient

Member Service owns people, not flats. For an assignment it asks the flat owner, Society Service, if the flat exists. It never connects directly to society_db.

This is synchronous HTTP: send a question, wait for an answer, then continue. Spring's RestClient performs the request.

  1. Member Service receives an assignment request.
  2. It checks its member and local rules.
  3. SocietyClient asks Society Service for the requested flat.
  4. Only after the flat is confirmed does Member Service save its membership.

A failed flat lookup is never treated as a valid flat.

Call order: local member check -> circuit-breaker and bulkhead permit -> bounded Society GET -> at most two transient retries with capped exponential randomized delay -> active-flat check -> local membership transaction. Retry is outside the circuit breaker, so the breaker records each physical HTTP attempt. Each Member Pod has its own circuit-breaker state; it is not shared through Redis. Member reads and other operations that use only member_db remain independent of Society availability.

Gateway rate limits, health and shutdown

The WebFlux Gateway uses Spring Cloud Gateway's Redis rate limiter for protected Member and Society routes. The authenticated key comes from the security principal; client-supplied identity headers are not used. Login attempts use a shared Redis bucket and fail closed with 503 if the limiter cannot be reached; an exhausted bucket returns 429 with Retry-After. Default login settings are 2 new tokens/second with burst 5; Kubernetes overrides these to 1/second with burst 3. Member route defaults are 10/second with burst 20; Society route defaults are 20/second with burst 40. These are learning defaults and should be tuned to measured traffic. The unauthenticated login bucket is shared, so all unauthenticated login attempts use the same bucket.

Gateway response timeout defaults to 28 seconds; NGINX upstream read/send timeouts are 32 seconds to leave outer-layer overhead around the Member retry budget and the backend's session-validation call. These are client/proxy wait limits, not a single end-to-end deadline. Member Service has bounded Tomcat threads, connections and accept queue, a zero-wait dependency bulkhead, graceful shutdown with a 20-second phase timeout, and existing Kubernetes readiness/liveness probes. Member readiness checks its local database; Society availability does not control Member liveness. Actuator metrics are exposed by the applications, while Gateway metrics require ADMIN authorization. Resilience4j circuit-breaker, retry and bulkhead meters are bound to Micrometer. The Society client records physical lookup duration and timeout counts; Gateway records 429 responses by fixed route name and login limiter errors. Do not use member IDs, session IDs or idempotency keys as metric labels.

Durable member-creation idempotency

POST /api/v1/members accepts an optional Idempotency-Key (1 to 128 letters, digits, period, underscore, colon or hyphen). Without it, the existing create behavior remains. With it, Member Service scopes the key to the authenticated admin and CREATE_MEMBER, fingerprints the normalized request with SHA-256, and stores the response with the create in one member_db transaction. Repeating the same key and payload returns the stored logical response and Idempotency-Replayed: true; using that key with different input returns 409. A unique database constraint coordinates concurrent submissions, so a repeated request cannot create two members.

The new migration is services/member-service/src/main/resources/db/migration/V3__create_idempotency_records.sql; earlier migrations are unchanged. Records expire after 24 hours by default (IDEMPOTENCY_RECORD_TTL). Expired rows are removed opportunistically during a later idempotent create; no background cleanup job is configured. The stored response can contain member contact fields, so keep the retention short, restrict database access, and account for this data in database backup/retention policy.

Member creation and flat assignment are not automatically retried. Idempotency makes a repeated create safe only when the client deliberately resubmits the same key and payload; it does not justify a Gateway retry. Assignment is a mutation with mandatory live flat validation, so any dependency failure fails the request without persisting membership.

Concurrent means two or more requests happen at the same time. Distributed means the app runs as more than one instance. A local lock can coordinate requests in one instance; a distributed lock coordinates through a shared service such as Redis.

What is the difference between timeout, retry, breaker and bulkhead?

Say it simply: Timeout limits how long one call waits. Retry repeats selected failed attempts. A breaker stops calls to an unhealthy dependency. A bulkhead limits simultaneous calls.

Durable idempotency for member creation

POST /api/v1/members accepts an optional Idempotency-Key containing 1 to 128 letters, digits, periods, underscores, colons, or hyphens. The key is scoped to the authenticated admin and CREATE_MEMBER. Member Service fingerprints the normalized request with SHA-256 and stores the response in the same member_db transaction as the create.

  • Repeating the key with the same payload returns the stored logical response and Idempotency-Replayed: true.
  • Reusing the key with different input returns 409.
  • A database uniqueness constraint coordinates concurrent submissions to prevent duplicate member creation.
  • Records expire after 24 hours by default. Expired rows are removed opportunistically during a later idempotent create; there is no background cleanup job.

Member creation and flat assignment are not automatically retried. Idempotency supports a deliberate client resubmission with the same key and payload; it does not make automatic Gateway retries safe. Assignment always requires live flat validation. The stored replay response may contain contact fields, so retention, database access, and backup policy should account for that data.

What caching means in this project

A cache is a nearby, temporary copy of data that is expensive or repetitive to fetch. The dedicated cache Redis keeps these copies in memory, so a later matching request can return the saved response without repeating the same PostgreSQL query. This is useful for Society reference data because floors and flat descriptions are read often and changed less often than they are viewed.

PostgreSQL remains the permanent record. If Redis is empty, an entry expires, or the cache is bypassed after an error, Society Service reads PostgreSQL. Cache Redis stores temporary copies; it does not replace Flyway, JPA, or either service's database ownership.

Redis in plain English

Redis is a key-value store: an application supplies a key, and Redis stores a value under that key. It is commonly used for fast temporary data, such as cache entries, rate-limit counters, and web sessions. PostgreSQL is the durable relational database in this project. It stores the official Society and Member records and enforces database constraints. Redis cache entries can expire or disappear without losing the official Society records.

The main private redis Service holds Spring Session, Gateway rate-limit, and Member lock data. Society uses the separate redis-cache Service for response caches, negative entries, and per-key load locks. Separate Services have separate processes and memory budgets; the key prefix remains society:cache:. Cache Redis uses allkeys-lru, so it can discard least-recently-used cache keys under memory pressure without evicting session or rate-limit keys.

Runtime caveat: the manifests configure separate Redis Services and expose Society cache-memory metrics, but the cluster has not been applied or load-tested. Redis cache is still a single Pod with temporary storage, so cache data and locks can disappear when that Pod is replaced.

Spring Cache and the important annotations

  • @EnableCaching turns on Spring's cache interception in SocietyCacheConfiguration.
  • @Cacheable checks Redis before running a method. A hit returns the cached DTO; a miss loads the response and stores it in one of societyFloors, societyFlatById, societyFlatsByFloor, or societyFlats.
  • @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) handles flat-change events after the database transaction succeeds. The listener evicts the flat entry, matching negative marker, and affected all-flats and floor-list entries.
  • @CacheEvict and @CachePut are not used. Eviction is performed programmatically after commit; update responses are not written directly into the cache.
  • RedisCacheManager is the cache manager, not an annotation. It configures cache names, key/value serializers, prefixes, TTLs, and cache statistics.

Spring applies caching through a proxy around Spring-managed service methods. Calls from the controller enter that proxy. A method calling another cached method on the same object could bypass that proxy; these cache annotations are on public service entry points, not self-calls.

No Caffeine local cache or Hibernate/JPA second-level cache is configured. Redis is the shared application cache; PostgreSQL remains the source of truth.

Stampede control, negative caching, and warmup

A cache stampede happens when many requests miss the same key together. The cache wrapper now takes a short-lived Redis lock for the specific cache name and key. The owner token ensures a request only releases its own lock. Other Society Pods recheck Redis while waiting up to two seconds; if the lock remains unavailable, a request loads without caching the result, so a slow source cannot hold requests indefinitely. This coordinates the normal miss path across Pods; it is not a correctness lock for database writes.

Unknown flat IDs are remembered as negative entries for 30 seconds on the Admin cached-read path. The API still returns the normal 404 RESOURCE_NOT_FOUND. Member's assignment validation continues to use the uncached authoritative database path. Flat-change events also clear a matching negative marker after commit.

On startup, each Society Pod checks the shared cache and warms only the small floor list when it is absent. This avoids a cold floor-list read for the first Admin request in the usual case. The warmup is configurable with SOCIETY_CACHE_WARMUP_ENABLED; it does not preload the full flat inventory. If Pods start together while the shared entry is missing, more than one small warmup query can still occur.

Security, revocation and attack verification

Read the interview explanation first, then use the original detailed reference below.

Explain security as three separate questions

Who are you?

Authentication validates credentials/session and links the request to a server-side account.

May you do this action?

Role authorization permits administrators to write; committee and residents are read-only.

May you access this record?

Object authorization scopes a resident to their member and currently assigned flats. UUIDs do not grant access.

Why validate identity again inside a service?

Say it simply: The Gateway is the entrance, but each service must enforce its own business authorization.

Explain the reason: Routing and role checks alone cannot decide whether resident A may read member B.

Be ready for: Explain current account refresh, disabled accounts and how service-to-service calls use narrow credentials.

What happens when an administrator revokes a user’s access?

Say it simply: Subsequent backend validation refreshes current account permissions. A disabled account is rejected, and a downgraded role loses its former write permissions.

Explain the reason: Keeping an old cookie must not preserve stale authorization indefinitely.

Be ready for: Revocation does not reverse an already committed action or guarantee cancellation of an in-flight request.

Explain CSRF simply: a browser attaches cookies automatically; a state-changing request also needs the correct CSRF token. The session answers who the user is. CSRF verifies that a cookie-bearing write has the expected token. The existing security lab below shows how to verify these claims.

Authentication and authorization — what we implemented

These ideas work together, but they answer different questions. Authentication asks “Who are you?” Authorization asks “What are you allowed to do?” First the project verifies the admin and creates a session; then it checks the admin role and permissions for each protected operation.

Authentication — prove identity

The client gets a CSRF token, then sends a username and password to the Gateway. Gateway asks Member Service to verify them. Member Service looks up the account in member_db and checks the password with BCrypt. If valid, Gateway creates a session in Redis and returns a SESSION cookie.

In this project: Member Service owns admin credentials. There is no public admin sign-up. The cookie carries a session ID; Redis stores session data.

Authorization — check permission

For a protected request, Gateway finds the session in Redis and checks the ADMIN role. The selected backend independently validates the actual session through Gateway, then applies its own service-layer permission checks.

In this project: protected member and society operations require ADMIN. Member's flat lookup call to Society uses a separate limited service authority, not an ADMIN identity.

Positive flow — what happens in order

  1. Postman manually, or a future frontend automatically, calls GET /api/v1/auth/csrf. Gateway returns a CSRF token and sets the XSRF-TOKEN cookie.
  2. The client calls POST /api/v1/auth/login with credentials, that cookie and matching X-XSRF-TOKEN header.
  3. Gateway checks CSRF and privately asks Member Service to verify the credentials. Member Service checks the BCrypt hash in member_db and returns identity/role only.
  4. Gateway creates the ADMIN session, changes the session ID, stores the server-side session in Redis and returns the HttpOnly SESSION cookie. The client obtains a fresh CSRF token after login.
  5. For a protected request, the client sends SESSION; state-changing requests also send the XSRF cookie and header. Gateway checks Redis and the ADMIN role, then routes by path.
  6. The backend independently validates the real SESSION cookie through Gateway's private endpoint. If valid, its service-layer authorization and business logic run.
  7. For flat assignment, Member uses RestClient and a restricted service credential to ask Society to check society_db. Only a confirmed flat allows Member to save the membership in member_db.
  8. Logout invalidates the Redis session and clears the cookie. The old cookie should then receive 401.
Success: authorized requests reach the owning service and its own database.

Negative flow — where processing stops

  • CSRF missing/invalid: 403; a state-changing operation does not run.
  • Bad username/password: generic 401; no authenticated session is created.
  • SESSION missing/expired/invalid: 401; protected business processing is denied.
  • Permission or role denied: 403. Current provisioning creates ADMIN accounts only; another role must be configured to demonstrate this case.
  • Backend cannot reach session validation: 503; backend fails closed and does not process the protected operation.
  • Flat does not exist: controlled not-found response; no membership is saved.
  • Society is unavailable: dependency error; Member cannot assume the flat is valid and does not save the membership.
  • Old cookie after logout: 401; client must log in again.
Failure: reject safely; do not save data when authorization or flat validation fails.

CSRF and browser cookies

Login creates a cookie-based session, so the application does not turn off CSRF protection at the Gateway. Security limits to understand

  • This implementation uses synchronous internal HTTP calls. The local/Kubernetes examples currently use HTTP. Secrets and NetworkPolicies restrict callers, but they do not encrypt traffic. Use TLS between services and Gateway before exposing this across an untrusted network.
  • Redis is a single ephemeral learning instance, not a highly available session store. Redis loss signs administrators out.
  • Session validation adds a Gateway call for each backend request. Gateway availability is therefore part of backend authentication availability.
  • Postman cookie behavior and CSRF token rotation need manual verification in the actual Postman client.
  • Provisioning is create-if-absent. Password rotation and account-disable administration need a controlled operational process.

  • TLS termination means NGINX decrypts traffic. NGINX-to-Spring-Gateway uses HTTP unless TLS is configured separately for that hop.
  • For production, use a trusted certificate authority, automate renewal, rotate the TLS Secret, and decide whether the internal NGINX-to-Gateway hop also needs TLS.

Load balancing and Gateway Pod recovery

UpstreamSettingsPolicy selects round_robin across API Gateway endpoints. NGINX Gateway Fabric discovers ready endpoints behind api-gateway; no Pod IP is saved in the configuration. When a Pod is unready or replaced, endpoint discovery updates the upstreams. The Deployment replaces a deleted Pod, and the new Pod receives traffic after it becomes ready.

NGINX Gateway Fabric also supports least-connections and randomized approaches such as random two least_conn; without this policy, its documented default is random two least_conn. Keep-alive connections and uneven request durations mean a small sample may not alternate evenly. Gateway API backend weights apply to Service backends; this project has one API Gateway backend, so weights do not select individual Pods. Some in-flight calls may fail during termination; zero downtime is not promised.

Forwarded headers, security and sessions

NGINX supplies X-Forwarded-For, X-Forwarded-Proto, X-Forwarded-Host, and X-Forwarded-Port. It preserves cookies, CSRF headers, and X-Correlation-ID. Kubernetes enables Spring framework forwarded-header handling; local direct runs default to NONE. Spring Security remains responsible for login and authorization.

Trust boundary: do not treat client-supplied forwarding headers as identity or authorize using X-Forwarded-For. If a trusted load balancer is later placed before NGINX, configure only its known addresses before trusting client-IP headers. The application does not rely on RFC Forwarded. Redis sessions remain shared by both Gateway replicas; sticky sessions are not needed for session continuity.

Timeouts, errors and private services

The NGINX policies set a 2-second upstream connection timeout, 8-second upstream read and send inactivity timeouts, a 15-second request-body read timeout, and a 1 MiB body limit. These are separate from Spring Gateway and RestClient timeouts. Read/send settings measure inactivity between I/O, not total request duration. Edge connection failures may return 502 or 504; valid backend responses such as 400, 404, and 409 pass through. No retry policy is configured, so unsafe POST requests are not replayed.

Only /api/ is exposed by this HTTPRoute. Actuator and private /internal/** session-validation paths are not exposed. Society, Member, Redis and PostgreSQL remain internal to the cluster.

Why: cookies authenticate the browser, while CSRF validation prevents a write using only automatically attached cookies. Do not use GET requests to test CSRF: safe reads do not require this header. Postman demonstrates token enforcement, but browser cross-origin behavior needs a browser test.

E. Logout and self-lockout protection

Logout using valid CSRF, then replay the old session cookie on a protected GET: expect 401. Separately, attempt to update your own permissions: expect 409 SELF_PERMISSION_CHANGE. Use administrator A to change B, preserving an administrator for recovery.

Limit: revocation affects subsequent validated requests. It does not undo completed operations or guarantee cancellation of an already running request.

Kubernetes and deployment operations

Find services without memorizing Pod addresses

Kubernetes DNS

A Pod can be replaced and get a different IP address, so Member Service must not save or call a particular Society Pod IP. Instead, Member Service calls a Kubernetes Service name that stays the same while the Pods behind it can change.

On your PC:        http://localhost:8081
Inside Kubernetes: http://society-service:8080

There is no project file that creates a DNS record. Kubernetes cluster DNS (normally CoreDNS) automatically makes a DNS name for each Kubernetes Service. The project YAML creates the Namespace, Deployment and Service that Kubernetes DNS uses.

  1. Create the namespace: kubernetes/namespace.yaml declares emerald-housing, the project area in the cluster.
  2. Create labeled Society Pods: kubernetes/society/deployment.yaml asks for two replicas and puts app: society-service on each Pod.
  3. Create the stable Service: kubernetes/society/service.yaml names the Service society-service and selects Pods with app: society-service. It accepts traffic on port 8080.
  4. Kubernetes provides DNS: the Service file kubernetes/society/service.yaml declares metadata.name: society-service and metadata.namespace: emerald-housing. The cluster DNS service, usually CoreDNS, automatically uses that Service name and namespace to provide society-service.emerald-housing.svc.cluster.local. Its parts are: society-service is the Service name; emerald-housing is the namespace; svc marks the Kubernetes Service DNS area; cluster.local is the cluster DNS domain, commonly the default. There is no DNS YAML file to create.
  5. Configure Member to call it: kubernetes/config/application-config.yaml sets SOCIETY_SERVICE_BASE_URL to http://society-service:8080. kubernetes/member/deployment.yaml loads that ConfigMap with envFrom. The Member app's application.yml reads the variable for its RestClient; locally its fallback is http://localhost:8081.
  6. Route to ready Pods: Kubernetes matches the Service selector to Society Pod labels and sends traffic to ready endpoints. When a Pod is replaced, the Service name stays unchanged; its endpoints update.
In short: the Service's metadata.name provides the name; cluster DNS resolves it; its spec.selector finds matching Pod labels; the Deployment creates those Pods; the ConfigMap gives Member Service the URL. Eureka is not used.

Resource creation order and connections

One complete sequence

Follow this order for the repository's local kind setup. PostgreSQL, Docker, kind, and kubectl must be ready first. The databases must already exist before the backend applications start: Flyway creates tables inside them, not the databases themselves.

  1. Prepare PostgreSQL: start PostgreSQL and create society_db and member_db. Make sure the credentials you will place in the Kubernetes Secret can connect.
  2. Start the kind cluster: run scripts/kubernetes/prepare-kind.ps1. It uses kubernetes/kind-config.yaml. The cluster must exist before image loading because the image-loading script transfers images into the kind nodes.
  3. Create the namespace: apply kubernetes/namespace.yaml. It creates the emerald-housing area inside the cluster.
  4. Create the database Secret: run the documented kubectl create secret command in namespace emerald-housing. It creates emerald-db-credentials; this Secret is created as a Kubernetes object, not from a committed Secret YAML file.
  5. Build and load Society and Member images: run scripts/kubernetes/build-load-images.ps1. This makes the backend images available to the kind cluster.
  6. Apply the backend ConfigMap: apply kubernetes/config/application-config.yaml. It creates emerald-app-config with non-secret settings such as POSTGRES_HOST and SOCIETY_SERVICE_BASE_URL.
  7. Apply backend Deployments and Services: apply the YAML resources under kubernetes/society/ and kubernetes/member/. Deployments request Society 2 replicas and Member 1 replica. Services select their Pods using matching labels. Once the namespace and configuration exist, each Deployment and its Service may be applied in either order.
  8. Kubernetes starts the backend containers: each Deployment creates or updates a ReplicaSet; the ReplicaSet creates Pods; the node's kubelet and container runtime start containers from the images. The Dockerfiles run the packaged applications with java -jar /app/app.jar.
  9. Spring Boot loads application settings: Society reads services/society-service/src/main/resources/application.yml; Member reads services/member-service/src/main/resources/application.yml. Kubernetes supplies ConfigMap values through envFrom and each service's database credentials through secretKeyRef.
  10. Flyway runs during backend application startup: Society connects to society_db and reads services/society-service/src/main/resources/db/migration/V1__create_society_tables.sql, followed by V2__seed_society_and_floors.sql. Member connects to member_db and reads services/member-service/src/main/resources/db/migration/V1__create_member_tables.sql. Flyway checks each database's flyway_schema_history and applies pending migrations. It does not run for each API request.
  11. Hibernate validates each backend schema: after migrations, Hibernate checks that the database tables match the Java mappings. Society and Member own separate databases. Both Society Pods use the same society_db; extra Pods do not create extra databases.
  12. Wait for backend readiness: startup and readiness probes check the applications. When a Pod is ready, its backend Service can route normal traffic to it. A running Pod that has not passed readiness should not receive normal Service traffic.
  13. Build and load the Gateway image: run scripts/kubernetes/build-load-images.ps1 -IncludeGateway after the backend services are ready. This option builds and loads the Gateway image as well as rebuilding and reloading the two backend images with their configured tags. Loading an image does not restart Pods that are already running; a Deployment rollout needs a change to the Deployment Pod template.
  14. Apply the Gateway ConfigMap: apply kubernetes/gateway/config.yaml. It creates api-gateway-config, which the Gateway Deployment reads.
  15. Apply Gateway Deployment and Service: apply the YAML resources under kubernetes/gateway/. The Deployment requests two Gateway Pods. Gateway starts as a separate Spring Boot application and does not connect to a database or run Flyway.
  16. Wait for Gateway readiness: after its readiness probe succeeds, the api-gateway Service can send requests to ready Gateway Pods.
  17. Apply the NetworkPolicies: apply kubernetes/networkpolicies.yaml after the namespace and workloads exist, before the traffic checks. It allows Gateway to reach Member and Society, and Member to reach Society on TCP port 8080. These policies limit incoming traffic only; they do not restrict application egress to PostgreSQL.
  18. Give Postman a way to reach Gateway: the current Gateway Service is ClusterIP, which is private inside the cluster. For local Postman usage, follow the manual Kubernetes checklist and its port-forward step.
  19. Send requests through Gateway: Gateway reads the path rules in infrastructure/api-gateway/src/main/resources/application.yml and forwards Member paths to member-service, and Society, floor, and flat paths to society-service. These Kubernetes Services select ready backend Pods.
  20. For a flat assignment: Member Service uses RestClient over HTTP to call the stable society-service name. Society checks society_db; if the flat is valid, Member saves the membership in member_db.

Keep more than one copy running

Scale and self-heal

A replica means one running copy. Society's Deployment requests two copies. Its Kubernetes Service sends traffic to ready copies. The caller still uses the same service name.

If one Pod stops, Kubernetes tries to replace it to reach the requested count. This is self-healing, but it does not promise every request succeeds during a failure.

The X-Instance-ID header can help show which copy answered. Calls may not alternate evenly because HTTP connections can be reused. To request three copies: kubectl scale deployment society-service --replicas=3 -n emerald-housing.

Readiness means a Pod should receive requests. Liveness means the process still appears healthy enough to keep running.

How the settings reach each application

  1. kubernetes/config/application-config.yaml creates the emerald-app-config ConfigMap. It provides ordinary settings, including POSTGRES_HOST=host.docker.internal and SOCIETY_SERVICE_BASE_URL=http://society-service:8080.

  3. Society's application.yml builds a JDBC URL ending in /society_db. Member's application.yml builds one ending in /member_db. Both connect to the configured PostgreSQL host, but use different databases and credentials.
  4. Each Pod starts its own Spring application and reads those environment variables. The two Society replicas use the same society_db; they do not each get a separate database. Member Service does not connect to society_db.
  5. When Member needs to check a flat, its RestClient calls the stable Society Service name over HTTP. Society Service reads its own database and returns the result.
Simple rule: A Pod is an application copy, not a database copy. Scaling Society from one Pod to two adds another application process; both copies use the same Society database. Member replicas (currently one) use the Member database.

1. What Kubernetes does

Docker packages an application and its runtime into an image. Kubernetes runs those images as containers inside Pods and continually reconciles the cluster toward the desired state written in YAML. The control plane accepts the desired state; worker nodes run the Pods. If one Pod disappears, a Deployment and its ReplicaSet create another. Kubernetes is therefore an orchestrator, while Docker Compose starts a declared group of containers on one Docker host. Compose is useful locally; Kubernetes adds cluster scheduling, Services, rolling updates, self-healing and autoscaling.

6. Probes: startup, readiness and liveness

Society and Member probe /actuator/health/liveness during startup and liveness; their readiness probes call /actuator/health/readiness, whose application configuration includes the database. Gateway uses the same liveness and readiness paths; its readiness group includes Redis. Redis uses authenticated redis-cli ping for all three probes. A startup probe gives an application time to launch (36 checks every 5 seconds for the backends, up to about 180 seconds; Gateway allows 24 checks, about 120 seconds). Readiness keeps an unready Pod out of Service endpoints; liveness restarts a stuck container; startup delays liveness until initialization has had time. Probe values are in each workload’s Deployment YAML.

# Society and Member Deployment probe pattern (Gateway has the same paths)
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: http }
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 36
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: http }
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: http }
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

The application startup path runs Spring Boot and Flyway before readiness can succeed. Society and Member readiness includes PostgreSQL, so Flyway/database initialization must finish before they receive normal Service traffic. Liveness uses the process liveness state, not a remote Society check, which helps avoid restart storms during a dependency outage.

7. Resource requests and limits

Requests are the scheduling baseline and the denominator used for CPU utilization in these HPAs. Limits cap CPU and memory consumption. For example, the Society HPA’s 70% CPU target is relative to its 100m CPU request, not a promise about a specific request rate. The current values are conservative learning defaults, not measured production sizing. Java’s container-aware heap still must fit inside the Pod memory limit after non-heap memory is included. Actual sizing needs runtime measurement; this task did not run the services.

8. Horizontal Pod Autoscaling

Each autoscaling/v2 HPA reads CPU usage and adjusts the matching Deployment between its configured minimum and maximum. Scale-up can add up to 100% or two Pods per 60 seconds. Scale-down waits 300 seconds and is limited to 25% or one Pod per 60 seconds, using the more conservative permitted change. These are learning defaults to reduce oscillation. HPA needs the Kubernetes resource metrics API, commonly provided by metrics-server; no metrics provider is installed by these manifests. 16. Interview practice: explain the scaling plan

  • Scale application replicas: HPA currently uses CPU. It is simple, but request rate or latency may be a better signal for some workloads. The project has not installed a metrics provider or measured a workload.
  • Set replica limits: HPA ranges are Society 2–4, Member 1–3, Gateway 2–4. The maximums should fit cluster capacity and the databases’ connection budgets.
  • Budget database connections: each additional application replica may create another connection pool. Estimate the maximum possible total before increasing HPA limits.
  • Plan Redis availability: one Redis Pod is easy to learn with, but production session continuity and cache availability need persistence and failover planning.
  • Balance cache freshness and load: shorter TTLs reduce how long stale data may remain but cause more database reads. Invalidation can improve freshness but must cover all affected cache entries.
  • Keep retries bounded: retrying a safe read may recover from a brief fault, but retries during an outage add load. Do not retry unsafe writes or multiply retries across Gateway and Member Service.
  • Separate readiness and liveness: readiness controls whether a Pod receives new calls; liveness determines whether Kubernetes restarts it. Making liveness depend on a remote service can cause restart storms.
A useful interview answer: “We use a stable Service name so callers survive Pod replacement. We scale replicas within limits, but CPU scaling can increase database connections, so we need capacity measurements. Flat assignment remains synchronous because it needs authoritative validation; if Society is down, we fail safely instead of saving uncertain data.”

WebFlux and its use in this repository

What is WebFlux, and where do we use it?

Spring WebFlux is Spring's reactive web framework. Nonblocking I/O lets a small set of event-loop threads process other work while network operations are pending. Mono<T> represents zero or one result; Flux<T> represents zero or many results. The main benefit is efficient concurrency during I/O waits, rather than automatically faster queries.

Current implementation: infrastructure/api-gateway/pom.xml declares spring-cloud-starter-gateway-server-webflux. Gateway authentication, session validation and filters return Mono; AdminAuthenticationManager uses reactive WebClient for credential validation. Member and Society declare spring-boot-starter-webmvc and use JPA/JDBC.

Example: while Gateway waits for Member to validate a login, its event-loop thread can handle other connections. Member's database query still executes using blocking database access.

Follow-up: returning a Mono does not by itself make every operation inside it nonblocking. Avoid blocking database calls, sleeps and block() on Gateway event-loop threads.

Graceful shutdown in the current repository

What is graceful shutdown, and how is it configured here?

Graceful shutdown stops accepting new application work and gives requests already being processed a bounded opportunity to finish during normal termination. For example, a member-creation transaction may complete during a rolling deployment before the old process exits.

# Configured in all three application.yml files
server:
  shutdown: graceful
spring.lifecycle:
  timeout-per-shutdown-phase: 20s

# Configured in the Gateway, Member and Society Pod specifications
terminationGracePeriodSeconds: 30

The Spring value is a timeout per lifecycle phase; the Kubernetes value is the Pod's overall termination window. Multiple phases and any termination hooks must fit within the overall budget. Check readiness, routing propagation and real termination behavior when validating deployments.

Limitation: this does not guarantee completion during a crash, power loss, forced kill or work exceeding the available timeout. Transactions, idempotent retries and deployment verification remain necessary.

Evidence: the three application resource files and kubernetes/gateway/deployment.yaml, kubernetes/member/deployment.yaml and kubernetes/society/deployment.yaml.

Spring Boot configures infrastructure such as application startup, the web server and integration with persistence and security libraries. It does not know which resident owns a record, whether a member is active or whether a duplicate membership is allowed. We must encode those policies explicitly.

Read Replica

1. What is a read replica, and why would you use one?

A read replica is a database server that receives replicated changes from a primary database and can serve queries. It can spread read traffic and reduce load on the primary. The replica can lag behind the primary, so it may return older data for a short time. This project supports routing to an external PostgreSQL replica, but does not create or manage that replica.

Interview answer: “We keep writes on the primary and can offload suitable read-only transactions to a replica. We account for replication lag by keeping consistency-sensitive reads on the primary.”

2. How does this project route reads and writes?

Spring's transaction metadata is checked by ReadOnlyRoutingDataSource. A read-only transaction selects the reader; other transactions use the writer. The routing data source is wrapped in LazyConnectionDataSourceProxy so the JDBC connection is requested after Spring has set the transaction's read-only flag.

@Override
protected Object determineCurrentLookupKey() {
    return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
            ? READ_ONLY
            : null; // default target is the writer
}

The same pattern is implemented in both backend services. The reader maps to the writer when replica support is off.

3. How do you mark a service query for replica routing?

Put @Transactional(readOnly = true) on the Spring service method that performs the database read. For example, Society's floor lookup methods use this annotation.

@Transactional(readOnly = true)
public List<FloorResponse> getFloors() {
    return floorRepository.findAllByOrderByFloorNumberAsc()
            .stream()
            .map(floor -> new FloorResponse(floor.getFloorNumber()))
            .toList();
}

Keep write operations in normal read-write transactions. The annotation is transaction metadata used for routing; it is not a guarantee that the database itself is read-only.

4. How do you enable and configure the replica?

Provision PostgreSQL replication separately, then give the service a reachable replica URL and credentials. The app defaults to disabled, so setting only a URL does not activate routing.

# Society Service environment

SOCIETY_DB_REPLICA_URL=jdbc:postgresql://society-replica:5432/society_db
SOCIETY_DB_REPLICA_USERNAME=emerald_reader
SOCIETY_DB_REPLICA_PASSWORD=${SOCIETY_REPLICA_PASSWORD}

# Member Service uses MEMBER_DB_REPLICA_ENABLED,
# MEMBER_DB_REPLICA_URL, MEMBER_DB_REPLICA_USERNAME,
# and MEMBER_DB_REPLICA_PASSWORD.

Use a read-only database account for the replica connection and store its password in a secret manager or Kubernetes Secret, not in committed configuration. Both service application.yml files expose these settings through environment variables.

5. What happens when replica routing is disabled?

The reader data source bean is not created unless its enabled property is true. The routing configuration then uses the writer as the reader target, so read-only transactions continue to work against the primary. In this repository's Kubernetes ConfigMap, both replica flags are currently false.

6. What is replica lag, and how can it affect the application?

Replication is usually asynchronous. After a successful write to the primary, the replica may not have received that write yet. A read routed immediately to the replica can therefore return stale data or report that a newly written record is missing.

Solution: route consistency-sensitive reads to the primary, such as validation immediately following a write. In this project, Society's flat-assignment validation explicitly uses a read-write transaction for that reason:

// Keep this authoritative validation on the primary
@Transactional(readOnly = false)
public FlatResponse validateFlatForAssignment(...) {
    // query the primary before Member saves the assignment
}

For workflows that need stronger guarantees across multiple requests, use an explicit primary-read policy or a database-specific replication-position strategy; do not assume the replica is instantly current.

7. How would you test that routing works?

Unit-test the routing data source with a reader and writer and assert which one is selected when Spring's transaction read-only flag is true or false. This repository has such tests in both services. Then add an integration test with distinguishable databases or connection identities to verify real transaction wiring and proxy order.

TransactionSynchronizationManager.setCurrentTransactionReadOnly(true);
// routing.getConnection() should reach the reader

TransactionSynchronizationManager.setCurrentTransactionReadOnly(false);
// routing.getConnection() should reach the writer

Also verify behavior with the feature disabled and with the configured replica unreachable. Unit routing tests do not prove replication health or replica freshness.

8. What happens if the replica is unavailable?

With replica routing enabled, a read-only transaction is directed to the configured reader. The current implementation does not include health-based failover or retry-to-primary behavior, so replica connection failures can fail the request.

Production improvement: monitor replica connectivity and lag, define a deliberate fallback policy, and test it. If falling back to the primary, make that policy observable and account for the added load; never silently claim that a replica is healthy just because the primary can serve the query.

9. What are the limits of this implementation?

The application supplies optional connection pools and read/write routing. PostgreSQL provisioning, replication setup, lag monitoring, automatic failover, and high availability are operational responsibilities outside this code. The feature is opt-in and currently disabled in the checked-in Kubernetes ConfigMap.

Interview summary: “The routing mechanism is implemented in Society and Member, but a production replica must be provisioned and configured separately. I would enable it only after validating credentials, connectivity, replication lag, failure handling, and query consistency requirements.”

Database Sharding

Project status: Database sharding is not implemented in Emerald Housing. The examples below are interview solution patterns, not existing project code. The services have separate databases and optional read-replica routing; neither distributes one service's records across shards.
1. What is database sharding, and how does it differ from replication?

Sharding splits a dataset across nodes, with each shard holding part of the data. Replication copies the same dataset to another node. Sharding can increase storage and write capacity; replicas often improve read capacity and availability. A system can use both, with each shard having replicas.

2. Why shard a database, and what signs indicate it may be needed?

Sharding can increase write throughput and storage capacity. Consider it after measurements show query/index tuning, vertical scaling, partitioning, or read replicas cannot meet targets. Track write rate, storage growth, latency, CPU, I/O, locks, and connection saturation; load-test alternatives first.

3. How do you choose a shard key?

Choose a stable, high-cardinality field used in common lookups that spreads writes evenly, such as tenant ID for tenant-scoped access. Validate against real query patterns and growth.

Conceptual Java: Shard shard = shardRouter.forTenant(tenantId); then query that shard using both tenantId and the record ID.

4. What makes a good shard key, and what can a poor one cause?

A good key distributes data and traffic while matching common queries. A poor key creates oversized or overloaded shards and cross-shard lookups. A low-cardinality status such as ACTIVE/INACTIVE is usually poor. Choose a higher-cardinality access key, test skew, and avoid mutable keys.

5. What is a hot shard, and how can you prevent one?

A hot shard receives a disproportionate share of requests or writes, often because one tenant dominates or sequential IDs target one range. Monitor per-shard load; improve distribution with hashing or buckets, and isolate unusually large tenants when needed.

6. What are range-based and hash-based sharding?

Range sharding assigns key intervals to shards; it supports range scans but can create hot spots. Hash sharding spreads keys more evenly, but range queries may touch many shards. Choose based on measured lookup and write patterns.

Illustrative syntax: int shardIndex = Math.floorMod(tenantId.hashCode(), shardCount); This fixed-count mapping is simple but changing the count requires data migration.

7. How does consistent hashing help when shard count changes?

Modulo hashing can remap most keys when shard count changes. Consistent hashing generally limits remapping to a subset, and virtual nodes can improve balance. It does not move data by itself: use versioned routing metadata and a controlled migration.

8. How do you route a query to the correct shard?

The application or a database proxy uses the shard key to choose the destination before querying. Keep the key in common repository operations and derive tenant identity from authenticated context.

Illustrative syntax: Shard shard = shardMap.forTenant(authenticatedTenantId); followed by shard.members().findByTenantIdAndId(authenticatedTenantId, memberId);. Do not use a caller-supplied shard name as authorization.

9. How do you handle queries that need data from multiple shards?

A query without a shard key may need scatter-gather: run against many shards and merge results. This increases latency and load. Keep common API queries shard-key-scoped; use an analytics store, read model, or asynchronous aggregation for broad reports.

10. How do you handle joins across shards?

Joins are efficient when related records share a shard key and are colocated. Cross-shard joins require fetching and merging data across nodes. Choose a shared key for commonly joined data, or use a documented read model/denormalization strategy with clear update consistency.

11. How do you enforce uniqueness across shards?

A unique index on one shard cannot guarantee global uniqueness if equal values can land on different shards. Include the shard key in local unique constraints, use globally unique IDs, or coordinate allocation for business identifiers that must be unique everywhere.

12. How do you handle transactions that span multiple shards?

Cross-shard transactions need coordination and can reduce performance and availability. Prefer shard-local transactions. For multi-step workflows use a saga: commit local steps and run compensating actions if a later step fails.

Solution sketch: reserveInventory(); try { chargePayment(); } catch (RuntimeException e) { releaseInventory(); throw e; }.

13. How do you rebalance data when adding or removing shards?

Move data in bounded, restartable batches while tracking writes made during the copy. Verify counts/checksums, switch routing in a controlled step, throttle migration load, and keep a rollback path. Changing the hash map alone does not move records safely.

14. How would you migrate an existing database to sharding?

Identify the shard key, add routing support, provision shards, backfill in batches, capture concurrent changes, and compare counts/checksums. Gradually switch reads and then writes with monitoring and rollback. Keep routing-map and migration versions explicit.

15. How do you handle shard failure and recovery?

Define per-shard health checks, replicas/failover, backups, recovery-point and recovery-time targets, and routing updates. Test restore and failover regularly, and retry only operations designed to be safe to repeat.

16. How do you back up and restore a sharded database?

Back up every shard and preserve a consistent recovery point across shards when workflows span them. Record the routing-map version with backup metadata and regularly test restoring one shard and the whole system.

17. How do you monitor shard health and load balance?

Compare latency, request/error rates, CPU, disk, pool usage, replication lag, and data size by shard. Use bounded shard labels in metrics and avoid customer IDs as labels. Alert on skew and saturation, which cluster-wide averages can hide.

18. How does sharding affect pagination and sorting?

Shard-local pagination is simple; globally sorted pages require merging ordered results from multiple shards. Use a stable cursor and deterministic sort key with tie-breakers. Prefer shard-scoped pagination when the product allows it.

19. How do you manage schema changes across shards?

Use backward-compatible expand-and-contract migrations: add schema, deploy code that supports both forms, backfill, switch usage, then remove old fields later. Track migration status per shard and make migrations restartable.

20. What security and access-control concerns arise with sharding?

Routing must not let callers access another tenant's data. Derive tenant/shard from authenticated identity, enforce tenant predicates, use least-privilege credentials and TLS, and test forged tenant IDs for cross-tenant access.

21. What should you try before introducing sharding?

Review query plans and indexes, pool sizing, vertical scaling, partitioning, caching, read replicas, and workload-specific read models. Shard only when measured bottlenecks remain and the team can operate its migration and failure paths.

22. Does this project need sharding, and how would you explain that in an interview?

There is no evidence in the current implementation that sharding is needed. This repository has separate databases per service and optional read-replica routing, but no shard key or multi-shard router.

Interview answer: “I would not add sharding without workload measurements showing that a service database cannot meet capacity targets after simpler options. If needed, I would choose a stable key aligned with access patterns, keep common transactions shard-local, and plan rebalancing, monitoring, migration, and recovery before rollout.”

Rate Limiting

Project implementation: The Spring Cloud Gateway uses Redis-backed token-bucket rate limiting for Member and Society routes. Authenticated API buckets use the security principal's admin identity; login attempts share an unauthenticated bucket. Current defaults are Member 10 tokens/second with burst 20, Society 20/second with burst 40, and login 2/second with burst 5 (Kubernetes overrides login to 1/second with burst 3). Limits are configurable and should be tuned to measured traffic. Exhausted limits return 429; Redis limiter failures return 503 (fail closed).
1. What is rate limiting, and why use it?

Rate limiting caps how many requests a client or key can make during a period. It protects capacity, reduces abuse, and helps allocate service fairly. It is not a substitute for authentication, authorization, or backend capacity planning.

Project example: Gateway limits authenticated Member and Society API traffic before forwarding requests.

2. What is the difference between rate limiting and throttling?

Rate limiting defines the allowed request budget. Throttling is the action taken when demand exceeds capacity, such as delaying work, queuing it, or rejecting requests. Many APIs implement limiting by rejecting excess requests with HTTP 429.

3. Which rate-limiting algorithms are common?

Common choices are fixed window, sliding window, token bucket, and leaky bucket. Choose based on burst tolerance, accuracy, state cost, and implementation complexity. This project uses Spring Cloud Gateway's Redis rate limiter with token-bucket settings.

4. How does the token bucket algorithm work?

Tokens refill at a configured rate up to a maximum capacity. Each request consumes tokens; if there are not enough, it is rejected. This allows short bursts up to the bucket capacity while controlling the long-term average.

Project settings: replenishRate controls refill per second, burstCapacity is the bucket size, and requestedTokens is normally 1 per request.

5. How does the leaky bucket algorithm work?

Requests enter a queue and leave at a steady rate. It smooths bursts, but a full queue means the system must reject or delay new work. Use it when steady downstream processing matters more than allowing brief bursts.

6. How does a fixed-window counter work, and what is its boundary problem?

It counts requests in fixed time blocks and resets at each boundary. A client can use nearly its whole allowance just before and after a reset, creating a burst close to twice the nominal limit. A sliding window or token bucket can soften that edge.

7. How does a sliding-window algorithm improve on a fixed window?

A sliding window measures requests over the most recent duration rather than resetting all at once. An exact log is accurate but stores more state; a weighted counter uses less memory with an approximation. Choose the accuracy and storage cost the endpoint needs.

8. How would you choose a rate limit for an API?

Measure sustainable service capacity, normal and peak client behavior, endpoint cost, and acceptable latency. Set a refill rate for sustained traffic and burst capacity for short spikes. Start conservatively, monitor 429 rates and backend saturation, and tune via configuration.

Project example: Member and Society have separate configurable values, so their limits can reflect different service capacity.

9. Should limits apply per user, API key, IP, endpoint, or service?

Use the identity that best represents fairness and abuse risk. Authenticated account or API-key limits are usually more reliable than IP alone; endpoint and global limits can protect especially expensive operations and total service capacity. Multiple layers can be combined.

Project behavior: protected route keys come from the authenticated admin principal; login uses a shared unauthenticated key.

10. How do you identify a client safely?

Prefer a verified principal or API key established by authentication. Do not trust client-supplied identity headers. If using IP, trust forwarding headers only when a known proxy removes untrusted incoming values and writes the real client address.

Project solution: the Gateway key resolver derives admin:{adminId} from the authenticated principal rather than an identity header.

11. How do you enforce limits across multiple application instances?

Use shared state or a centralized limiter so each Gateway instance sees the same bucket. A local in-memory counter is per process and can multiply the effective allowance as instances scale. The project uses Redis-backed Gateway rate limiting for shared buckets.

12. Why use Redis, and how do you make updates atomic?

Redis provides fast shared state for multiple Gateway instances. Concurrent requests must update/check tokens atomically; otherwise simultaneous requests can all observe the same remaining budget. Use a limiter's atomic Redis operation or Lua script instead of separate read-then-write commands. Spring Cloud Gateway's RedisRateLimiter supplies this coordination.

13. What happens if Redis is unavailable?

The policy must be deliberate: fail open to preserve availability, or fail closed to protect a sensitive system. This project fails closed for rate-limited login when Redis errors, returning HTTP 503 with a limiter-unavailable response. That prevents unmetered login attempts but makes login depend on Redis availability.

Production fix: monitor Redis, alert on limiter failures, and document whether each route should fail open or closed based on its risk and capacity.

14. How would you return a rate-limit response?

Return HTTP 429 Too Many Requests with a stable error body. Include Retry-After when the retry time is known so clients can back off instead of immediately repeating requests. The project's login response sets Retry-After: 1.

return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS)
        .header("Retry-After", "1")
        .body(error("LOGIN_RATE_LIMITED", "Wait before trying again"));
15. What do HTTP 429 and Retry-After communicate?

429 tells the caller that its request budget is exhausted, not that the server has an internal error. Retry-After gives a delay or date after which retrying may be appropriate. Clients should use bounded exponential backoff and jitter and avoid retrying non-idempotent operations blindly.

16. How do you support different limits for users, plans, or endpoints?

Resolve a stable key and select policy by route, account tier, or operation cost. Keep policies configurable and prevent untrusted clients from choosing a more generous tier. The project already assigns distinct Member, Society, and login bucket settings through Gateway configuration.

redis-rate-limiter.replenishRate: ${GATEWAY_MEMBER_RATE_REPLENISH:10}
redis-rate-limiter.burstCapacity: ${GATEWAY_MEMBER_RATE_BURST:20}
redis-rate-limiter.requestedTokens: 1
17. How do you allow bursts while controlling sustained traffic?

Use a token bucket: set refill rate to the sustained allowance and capacity to the maximum short burst. For example, a refill rate of 10 tokens/second and capacity 20 allows a burst of up to 20 requests when full, then refills at 10 per second.

18. How do you prevent race conditions under concurrent requests?

Do not implement a distributed limiter as separate non-atomic read and write operations. Use an atomic Redis script/primitive, transaction, or a framework limiter designed for concurrent updates. Test with simultaneous requests across multiple Gateway instances, not only sequential calls.

19. How do you monitor and alert on rate limiting?

Track allowed and rejected requests, limiter errors, and Redis latency by bounded route name. Alert on unusual 429 spikes and limiter failures, and compare them with backend saturation. Avoid user IDs, session IDs, or tokens as metric labels because they create high-cardinality and sensitive telemetry.

Project example: Gateway records rate-limited requests by fixed route name and login limiter errors.

20. How do you test rate limiting under concurrent load?

Send controlled requests with the same key to exhaust a bucket, verify allowed/rejected counts and 429 responses, wait for refill, then verify requests are admitted again. Repeat across multiple Gateway instances and check Redis failure behavior. Avoid production load tests without an approved test plan.

21. How do you distinguish abuse from a legitimate traffic spike?

Correlate rate-limit events with authenticated identities, route, request patterns, error rates, and service health. Rate limiting should protect capacity without automatically treating every burst as malicious. Adjust limits, add anomaly detection or challenges, and investigate repeated distributed patterns.

22. How would you explain and improve this project's rate-limiting design?

Interview answer: “We enforce shared token buckets at Spring Cloud Gateway using Redis. Authenticated API requests are keyed by the verified admin principal, while login attempts share an unauthenticated bucket. Exhausted buckets return 429, and Redis failures fail closed with 503. I would tune refill and burst values from traffic measurements, monitor rejection and Redis error rates, and explicitly review the shared login bucket and failure policy.”

The project configuration is an implementation example; its learning defaults should be validated under runtime load before production use.

IDOR (Insecure Direct Object Reference)

Project context: The current Gateway and backend services require an ADMIN role for the exposed Member and Society APIs, and service methods also enforce roles. Membership ending uses a lookup constrained by both membership ID and member ID. If the product adds resident or tenant self-service, every object access must additionally check that the authenticated user is allowed to access that specific member, flat, membership, or file. UUIDs alone do not provide authorization.
1. What is IDOR, and how does it differ from a general authorization failure?

IDOR is a vulnerability where an attacker changes an object reference, such as an ID in a URL, and the server returns or modifies an object the caller is not allowed to access. It is a specific object-level authorization failure: the caller may be logged in and allowed to use the endpoint, but not allowed to use that object.

2. How can an attacker exploit IDOR?

An attacker can substitute another record's ID in a path, query, body, or nested resource reference, then read, update, delete, or associate that record if the server checks only that it exists. The fix is a server-side authorization decision for every referenced object and operation.

3. Why are IDs in URLs and request bodies common IDOR targets?

IDs are easy to observe in browser tools, API responses, logs, and links. Sequential IDs are easy to guess, but unguessable IDs can also be copied or leaked. Treat every client-provided object reference as untrusted and authorize access after resolving it.

4. How is IDOR related to Broken Object Level Authorization (BOLA)?

BOLA describes the broader API security problem where a caller can act on an object without the required object-level permission. IDOR is commonly used for this class of issue when an exposed object reference can be changed. The remedy is not merely to hide the reference; enforce access rules on the server.

5. Why is authentication alone not enough?

Authentication proves who the caller is. Authorization decides what that identity can do and which object it may access. A valid session must not grant access to every record.

Solution: derive the caller identity from the verified security context, then apply ownership, tenant, role, and operation rules to the requested object.

6. How do you authorize each object access?

Check authorization on every read and write, including nested resources, bulk operations, exports, and background actions. Prefer a service-layer policy so controllers cannot accidentally omit it, and keep the object lookup and access predicate together where practical.

// Illustrative Spring pattern; principal comes from verified authentication
@GetMapping("/{memberId}")
public MemberResponse get(@PathVariable UUID memberId, @AuthenticationPrincipal AppUser user) {
    return memberService.getForOwner(memberId, user.userId());
}
7. Should IDOR checks live in controllers, services, or repositories?

Controllers handle HTTP input, services enforce business authorization, and repository queries can constrain the data returned. Use defense in depth: the service decides policy and the query scopes the lookup. Avoid relying only on the UI or one controller check.

8. How do you prevent one tenant from accessing another tenant's records?

Take the tenant identity from authenticated server-side context, not a request parameter, and include it in every data query and mutation.

Repository pattern: Optional<MemberEntity> findByIdAndTenantId(UUID id, UUID tenantId); If it returns empty, treat the object as inaccessible or absent according to the API's disclosure policy.

9. Are UUIDs enough to prevent IDOR?

No. UUIDs make guessing harder but do not prove permission. IDs can be copied, exposed, or obtained through another endpoint. Keep UUIDs for identifier quality if useful, but always perform an authorization check.

10. Where can IDOR appear beyond a path ID?

It can appear in query parameters, request bodies, nested paths, GraphQL arguments, bulk ID arrays, export jobs, and indirect references such as flatId or membershipId. Audit all inputs that select an object, not just route variables.

11. How do you secure object IDs supplied in a request body?

Do not trust fields such as ownerId, tenantId, or role in the body. Bind only fields the caller may set, derive identity and ownership from the authenticated context, and validate referenced objects server-side before saving.

Fix: map a request DTO to an entity explicitly instead of binding client JSON directly to a persistence entity.

12. How do you handle ownership changes and shared resources?

Model the policy explicitly: owner, tenant membership, delegated role, or time-bounded share. Check the current relationship for every operation and define how revocation takes effect. Do not infer access from possession of a URL or object ID.

13. How do you prevent IDOR in file uploads and downloads?

Store file metadata with its owner or tenant and authorize that relationship before returning bytes or changing metadata. Use opaque storage keys only as internal identifiers; a signed URL should be short-lived and scoped to the intended file and action.

14. How do you test for IDOR?

Create two users/tenants and objects owned by each. Authenticate as user A, substitute user B's IDs across read, update, delete, nested, and bulk endpoints, and assert that no data or side effect is exposed. Also verify user A can access allowed records and anonymous requests are denied.

15. What negative authorization tests should you add?

Test wrong-owner, wrong-tenant, missing-object, forged owner fields, revoked sharing, bulk lists containing mixed-owner IDs, and membership IDs paired with the wrong member ID. Assert both the response and that the database was not modified.

Project example: membership operations should verify the membership belongs to the member in the URL; the current repository has a findByIdAndMemberId lookup for ending a membership.

16. How do you avoid leaking whether an unauthorized object exists?

Use consistent response bodies and avoid returning object details before authorization. Some APIs return 404 for both nonexistent and inaccessible objects to conceal existence; others use 403 when disclosure is acceptable. Choose deliberately and keep the policy consistent.

17. When should an API return 403 versus 404?

Return 403 when the caller is authenticated but explicitly lacks permission and revealing the object's existence is acceptable. Return 404 when the object is absent or the API intentionally hides whether it exists. Neither response replaces the authorization check.

18. How can database queries help enforce object-level authorization?

Scope the query by both object ID and authorized owner/tenant, so unauthorized rows are never loaded for accidental use.

// Illustrative repository method
Optional<Membership> findByIdAndMemberId(UUID membershipId, UUID memberId);

Membership membership = repository.findByIdAndMemberId(membershipId, memberId)
        .orElseThrow(MembershipNotFoundException::new);

For updates, use a similarly scoped update and verify the affected-row count.

19. How do you audit and monitor IDOR attempts?

Record denied access attempts with authenticated actor, route, action, and a safe object reference or hash. Avoid logging secrets or sensitive payloads. Alert on repeated cross-owner failures, but do not expose monitoring details to the caller.

20. How would you review this project for IDOR?

Enumerate every endpoint that accepts a member, flat, floor, or membership identifier; trace it through controller, service, and repository; then verify object-level policy and negative tests. Currently the APIs are ADMIN-only, and service methods enforce roles. If self-service users are added, introduce owner/tenant-scoped lookups instead of relying on the ADMIN role or UUID secrecy.

Interview answer: “I would test with two identities and swap every object ID across read and write operations. The server must authorize the specific object on every request, and failed authorization must not reveal data or cause side effects.”

HikariCP pool sizing and connection budgeting

Questions, explanation, and solution

Question: How do you size a Hikari pool and budget connections across replicas?

Answer: Measure database capacity and request concurrency. Count every possible app Pod and each pool, then reserve connections for migrations, monitoring, admin tools, and failover.

Follow-up: What metrics would you use to tune a HikariCP pool?

Answer: Measure active, idle, pending, and timed-out connections along with query latency and database saturation. If callers wait while the database is saturated, adding connections may worsen contention; first find slow queries and calculate the total pool budget at maximum Pod count.

Questions, explanation, and solution

Question: What is N+1, and when can a DTO projection help?

Answer: One query loads a page of parent rows, then one query per parent loads related data. A projection selects the fields needed for the response in one bounded query and avoids loading full entity graphs.

Solution sketch: select new FlatSummary(f.id, f.number, floor.number) from Flat f join f.floor floor where .... Check SQL query counts in tests; do not solve it with an unbounded fetch join on multiple collections.

Follow-up: How do you verify that a DTO projection actually removes N+1 queries?

Answer: Capture SQL or query counts for a representative page and assert the count stays bounded as the number of rows grows. Keep pagination in the database and project only required columns; avoid loading full entity graphs and then mapping them one row at a time.

Composite indexes and query-plan analysis

Questions, explanation, and solution

Question: How do you choose a composite index and verify that it helps?

Answer: Start from real predicates, joins, and ordering. Column order matters; equality filters often precede range/order columns. Use the query plan and representative data to see whether the database uses the index and whether it reduces rows and cost.

Example: CREATE INDEX idx_membership_member_start ON flat_memberships(member_id, start_date DESC); then inspect with EXPLAIN (ANALYZE, BUFFERS) SELECT ... WHERE member_id = ? ORDER BY start_date DESC;. Add indexes for measured queries, accounting for write and storage cost.

Follow-up: What if EXPLAIN shows the database is not using your new index?

Answer: Check predicate and sort column order, data selectivity, stale statistics, implicit casts, and whether the query returns a large fraction of the table. Compare actual rows and buffer reads with and without the index, then keep the index only if measured workload improves.

Redis cache-aside and after-commit invalidation

Questions, explanation, and solution

Question: How does cache-aside work, and why invalidate after commit?

Answer: Read Redis first; on a miss load PostgreSQL and populate Redis. A write commits the source-of-truth change before invalidating or refreshing cached data. Invalidating before commit can let a reader reload old database state and cache it again.

Spring solution: publish a domain event in the transaction and handle it with @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT). For guaranteed delivery across crashes, use a transactional outbox rather than relying only on an in-process event.

Follow-up: What failure can still occur after using an after-commit cache event?

Answer: The process can crash after the database commit but before the in-process event invalidates Redis. Use a transactional outbox if that gap is unacceptable: commit the outbox record with the data, then retry delivery until cache invalidation succeeds.

Cache stampede protection across Pods

Questions, explanation, and solution

Question: How do you prevent many Pods loading the same missing key at once?

Answer: Use a per-key distributed single-flight/lock so one Pod loads the value while others wait briefly, serve stale data if safe, or use a bounded fallback. A JVM-only lock protects only one Pod.

Solution sketch: SET cache-load:{key} {randomToken} NX PX 30000, then release only when the stored token still matches. Bound wait time and database fallback concurrency; a lease can expire while work continues, so protect writes with fencing/version checks where needed.

Follow-up: What should waiting Pods do while one Pod loads a cache key?

Answer: Wait only for a bounded interval, then serve stale data if allowed or return a controlled response. Limit concurrent database fallback loads per Pod and across the fleet; never make every waiter perform the same expensive query when the lock wait expires.

Negative caching and TTL jitter

Questions, explanation, and solution

Question: What are negative caching and TTL jitter?

Answer: Negative caching stores a short-lived “not found” result to reduce repeated lookups for absent objects. TTL jitter randomizes expiry so many keys do not expire simultaneously.

Solution: cache absence briefly and invalidate it when the object is created. Compute ttl = baseTtl + random(0, jitter); keep the base and jitter small enough for the freshness requirement.

Follow-up: Which failures should not be stored as a negative cache result?

Answer: Do not cache timeouts, authorization failures, or database errors as not-found results. Cache only a confirmed absence, for a short TTL, and invalidate it when the object is created so a temporary failure cannot hide valid data.

Cache behavior during Redis outages

Questions, explanation, and solution

Question: What should an application do when Redis is unavailable?

Answer: Decide per Redis use: cache may fall back to PostgreSQL under a bounded concurrency limit; sessions or rate limits may fail closed because bypassing them changes security behavior. Provide timeouts, a short circuit/bypass interval, metrics, and recovery behavior.

Project context: Society has bounded database fallback loads for cache errors. Gateway sessions and shared rate limiting depend on Redis, so outage behavior differs from disposable cache behavior.

Follow-up: How do you keep cache fallback from causing a database outage?

Answer: Use short Redis timeouts, a per-Pod or distributed circuit/bypass window, and a strict concurrency limit for database fallback. Track fallback load and rejected requests. Fail closed for security-sensitive Redis use such as sessions or shared limits when bypassing would weaken policy.

Distributed locking with Redis

Questions, explanation, and solution

Question: What makes a Redis lock safe enough for distributed work?

Answer: Acquire atomically with a unique ownership token and lease, and release only if the token still belongs to the caller. A lease can expire while a slow worker continues; use fencing tokens or database constraints when stale workers must not overwrite newer work.

Solution sketch: SET lock:{resource} {token} NX PX {leaseMs}; release with an atomic compare-token-and-delete script. Redis locking coordinates workers but does not replace database integrity.

Follow-up: When would you prefer a database lock over a Redis lock?

Answer: Prefer a database transaction lock when protecting a database invariant or coordinating a short update to rows in that database. Redis can reduce duplicate work across Pods, but a Redis lease alone cannot guarantee that a stale worker will not later commit an outdated database write.

Pessimistic database locking and unique constraints

Questions, explanation, and solution

Question: When use pessimistic locking, and why keep a unique constraint?

Answer: Lock a row when concurrent changes must serialize around existing data, for example when ending a membership. A unique constraint protects correctness even if application locks are missed, expire, or multiple code paths race.

Spring/JPA pattern: @Lock(LockModeType.PESSIMISTIC_WRITE) on a repository lookup, plus a database UNIQUE(member_id, flat_id, relationship_type, active_key) constraint matching the invariant. Handle constraint violations as a controlled conflict.

Follow-up: How do you reduce deadlocks when transactions use pessimistic locks?

Answer: Keep transactions short, acquire rows in a consistent order, avoid remote calls while holding locks, and retry only recognized deadlock failures with a small bounded policy. Keep unique constraints as the final guard for invariants.

Idempotency keys for safe member creation

Questions, explanation, and solution

Question: How does an idempotency key make a create request safe to retry?

Answer: Store the key, a canonical request hash, and the original result under a uniqueness constraint. Repeating the same key and payload replays the result; the same key with different input returns a conflict. Retain records long enough for client retries.

Solution sketch: UNIQUE(actor_id, idempotency_key); compare storedRequestHash with the retry hash, then replay or return HTTP 409. Write the idempotency record and business result transactionally when possible.

Follow-up: What should be included in an idempotency record?

Answer: Scope the key to the authenticated actor and operation, store a canonical request hash, processing state, expiry, and the response needed for replay. Enforce uniqueness in the database so concurrent requests with the same key cannot both create the member.

Retry, timeout, circuit breaker, and bulkhead

Questions, explanation, and solution

Question: How do these resilience controls work together?

Answer: A timeout bounds one call; limited retries handle transient failures; a circuit breaker stops calls to a dependency that is failing; a bulkhead caps concurrent calls so one dependency cannot consume all resources. The total retry budget must fit inside the caller's deadline, and retries need idempotent operations.

Solution sketch: overallDeadline > attempts × perAttemptTimeout + backoffBudget. Use exponential backoff with jitter and a small attempt count; do not retry validation errors or unsafe writes without idempotency.

Follow-up: How do retries affect downstream load during an outage?

Answer: Retries multiply traffic precisely when a dependency is unhealthy. Bound attempts and total time, add exponential backoff with jitter, retry only transient failures, and combine retries with a circuit breaker and concurrency bulkhead.

Synchronous service-to-service validation

Questions, explanation, and solution

Question: Why validate a flat synchronously, and what if Society is down?

Answer: A synchronous call gives an immediate authoritative answer before Member records an assignment, but it couples availability and latency. Use a short timeout, bounded concurrency, clear error mapping, and fail safely when validation is required; do not save based on an unknown result.

Project flow: Member → Society GET flat → validate → persist membership. If the product can accept eventual consistency, consider an asynchronous workflow with explicit pending/rejected states instead.

Follow-up: How can synchronous validation evolve if request volume or dependency latency grows?

Answer: First measure the call path and keep timeouts, concurrency, and caching of stable reference facts bounded. If the business accepts delayed decisions, move to an asynchronous workflow with explicit pending, confirmed, and rejected states rather than silently accepting an unvalidated write.

Gateway sessions, CSRF, and service credentials

Questions, explanation, and solution

Question: How do session cookies, CSRF protection, and internal credentials work together?

Answer: Gateway authenticates the user and stores the server-side session in Redis; the browser sends an HttpOnly session cookie. CSRF tokens protect cookie-authenticated state-changing requests from cross-site submission. A backend independently validates the session, while service credentials authenticate service-to-service calls and must not be treated as user identity.

Security fixes: use Secure/HttpOnly/SameSite cookie settings appropriate to deployment, rotate sessions after login, keep secrets in Secret storage, scope service credentials narrowly, and use TLS for untrusted networks.

Follow-up: How should internal service credentials be rotated?

Answer: Store credentials in a secret manager or Kubernetes Secret, support overlapping old and new credentials during rotation, update workloads, verify calls, then revoke the old value. Limit each credential to the required service and operation, and never log it.

Kubernetes health probes and graceful shutdown

Questions, explanation, and solution

Question: What do readiness, liveness, and startup probes do?

Answer: Readiness controls whether a Pod receives new traffic; liveness restarts a stuck container; startup gives slow initialization time before the other checks apply. On shutdown, stop accepting traffic, fail readiness, drain in-flight work, then exit before the termination grace period.

Solution: set terminationGracePeriodSeconds longer than the app shutdown timeout plus drain allowance. Avoid making liveness depend on a downstream service outage, or Kubernetes may restart every Pod unnecessarily.

Follow-up: Should liveness fail whenever PostgreSQL or Redis is unavailable?

Answer: Usually no. A downstream outage does not mean the process is dead; failing liveness can restart every Pod and amplify the incident. Use readiness to reflect whether this Pod can safely serve traffic, and reserve liveness for a stuck or irrecoverable process state.

HPA scaling and rolling updates

Questions, explanation, and solution

Question: How can HPA and rolling updates affect database capacity and availability?

Answer: HPA adds Pods from resource metrics, but each Pod may open its own Hikari pool. Budget connections at maximum replicas. Rolling updates temporarily run old and new Pods together, so the connection and resource budget must include surge capacity. Readiness prevents unready Pods receiving requests.

Budget: (replicas + maxSurge) × poolMaxPerPod ≤ databaseConnectionBudget. Tune HPA, pool size, and rollout surge as one capacity plan.

Follow-up: How do you prevent HPA scale-out from exhausting database connections?

Answer: Calculate maximum application Pods including rollout surge, multiply by each Pod pool maximum, and compare with the database budget. Set pool limits and HPA maximums together; consider queueing or a connection proxy if measured concurrency requires more application replicas than the database can serve directly.

Manual canary validation and rollback

Questions, explanation, and solution

Question: How do you decide whether to promote or roll back a canary?

Answer: Send a small controlled portion of traffic to the candidate, then compare error rate, latency, saturation, and key business checks against the stable version. Promote only when the checks pass for a defined observation window; route traffic back and scale down the candidate if a threshold fails.

Operational fix: write down thresholds and rollback commands before rollout, verify the stable version remains healthy, and preserve logs/metrics for diagnosis. Manual canary validation is not a substitute for automated deployment gates.

Follow-up: How do you make canary rollback safe when database schema changes are included?

Answer: Use backward-compatible expand-and-contract migrations so both old and new application versions can run during the canary. Validate rollback before deployment; avoid destructive schema changes until the rollback window has closed.

Correlation IDs, metrics, and distributed tracing

Questions, explanation, and solution

Question: How do correlation IDs, metrics, and traces complement each other?

Answer: A correlation/trace ID links one request's logs; metrics summarize rates, errors, and latency over time; distributed traces show spans and delays across service boundaries. Propagate W3C traceparent or a validated request ID, and keep metric labels bounded.

Example: logger.info("membership created traceId={} memberId={}", traceId, memberId); do not use trace IDs, member IDs, or session IDs as metric labels.

Follow-up: What is the difference between a correlation ID and a trace ID?

Answer: A correlation ID is an application-level identifier used to connect related logs and may cover a business workflow. A trace ID identifies a distributed trace with timed spans. Propagate standard trace context across services and use IDs in logs, not as metric dimensions.

Validated pagination and sorting

Questions, explanation, and solution

Question: How do you make pagination and sorting safe and predictable?

Answer: Bound page size, reject negative page numbers, allowlist sortable fields and directions, and add a stable tie-breaker to ordering. Arbitrary sort properties can trigger expensive queries or expose unintended entity fields.

Solution sketch: size = clamp(requestedSize, 1, MAX_PAGE_SIZE); sortField = ALLOWED_SORTS.getOrDefault(input, DEFAULT_SORT); then order by the chosen field plus a unique ID for deterministic pages.

Follow-up: When would you use cursor pagination instead of page-number pagination?

Answer: Use cursor pagination for large or changing datasets where offset scans become costly or rows shift between pages. Encode a stable sort key and unique tie-breaker in the cursor, validate it, and add a matching database index.
