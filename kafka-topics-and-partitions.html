Topics & Partitions

A simple guide using the Emerald Housing events: lost-found.events and community-notices.events. Learn what the names mean, how messages move, and where the Java configuration fits.

Start with the simple idea

Kafka is like a shared event record book. An application writes events into named sections. Other applications read those events when they are ready.

Topic = named shelfA named place for related messages. Example: lost-found.events stores lost/found updates.
Partition = lane in the shelfA topic is split into one or more ordered lanes. Kafka appends messages to a lane.
Replica = spare copyA replica is another copy of a partition, usually on another broker, to help if a broker fails.

Analogy: Imagine a society notice board with separate binders. One binder is for lost items; another is for community notices. A partition is a numbered page sequence inside a binder. A replica is a photocopy kept in another safe place.

Our two topics

Keep different kinds of events in different topics so the right service can read each kind.

Each topic has its own lane and its own reader group. This separates the two event flows. With one lane per topic, that topic's work is read in order by one consumer at a time within a consumer group.

What does “one partition, one replica” mean?

Partitions: 1Each topic currently has one partition: Partition 0. Messages in that partition have an order (first in, first out).
Replicas: 1There is one copy of that partition. It is the leader copy, and there is no additional Kafka copy to take over if its broker is lost.

Plain English: The current setup is good for learning and local development. It does not provide broker-level copy redundancy, and one partition does not let a consumer group split this topic's records across multiple active consumers.

Imagine adding lanes

With 3 partitions, Kafka could spread records among lanes 0, 1 and 2. A consumer group could process those lanes in parallel. Ordering would be guaranteed inside each lane, not across all three lanes together. Adding partitions later should be planned because it can affect key-to-partition mapping and ordering expectations.

How a message travels

A resident reports a found item.Member Service creates a lost/found event.
The outbox stores it.The database records the event alongside the business change.
The dispatcher publishes it.Spring's KafkaTemplate sends it to lost-found.events.
Kafka appends it.With one partition, it is appended to that topic's Partition 0.
The listener reads it.The lost-and-found listener group consumes it and performs its work.

Code view: declaring the topic

These are simplified versions of the project's Spring configuration classes. Spring Kafka's admin client creates the topic if it does not already exist (and the broker allows topic creation).

// LostFoundKafkaConfiguration.java @Bean NewTopic lostFoundEventsTopic() { return TopicBuilder.name("lost-found.events") .partitions(1) // one lane .replicas(1) // one copy .build(); } // CommunityNoticeKafkaConfiguration.java @Bean NewTopic communityNoticesTopic() { return TopicBuilder.name("community-notices.events") .partitions(1) .replicas(1) .build(); }

Read it line by line: @Bean makes this topic description available to Spring. TopicBuilder.name(...) chooses the topic name. partitions(1) asks for one partition. replicas(1) asks for one copy on the broker cluster.

Docker broker default

KAFKA_NUM_PARTITIONS: 1

This is the broker's default for topics that are created without an explicit partition count. The Java topic beans also declare one partition for these two topics. Explicit topic configuration is easy to see and understand.

Code view: publishing into a topic

The project uses the business object's ID as the Kafka key. For a lost/found report, the report ID is the key; for a community notice, the notice ID is the key.

// Simplified from LostFoundEventPublisher.dispatch() kafka.send( "lost-found.events", // topic event.reportId().toString(), // key json.writeValueAsString(event) // message value ).get();

The key and message body serve different purposes. The key helps Kafka choose a partition and lets related records stay together when there are multiple partitions. The value is the event data itself. Today each topic has only one partition, so all its records go to Partition 0 whatever the key is.

// Simplified listener @KafkaListener( topics = "lost-found.events", groupId = "lost-found-notifications" ) public void onEvent(String message) { // handle the event }

The notice listener subscribes to community-notices.events using group community-notice-notifications. The group name identifies the reader team and keeps its reading position separate from other groups.

System design view

Why separate topics?Different event types can have separate listeners, access rules, retention settings, and failure handling.
Why use an ID as key?When a topic has several partitions, the same ID is routed to the same partition, preserving order for that ID (assuming the partitioning setup stays stable).
Why add partitions?More partitions can allow more consumers in a group to work at once. A group cannot usefully have more active consumers than partitions for a single topic.
Why add replicas?Extra replicas on separate brokers provide copies that can remain available after a broker failure. Replication needs multiple brokers to provide broker failure protection.

Example design choice

SetupGood forTrade-off
1 partition / 1 replicaLocal learning, simple ordering, low setup costNo parallel reads within the group; no spare broker copy
3 partitions / 3 replicas across brokersMore parallel work and stronger availabilityNeeds multiple brokers and careful ordering/scaling decisions

A replica count of 3 needs at least 3 brokers if each replica is to live on a different broker. More copies also use more storage and network traffic.

Quick recap

Topic named event stream   Partition ordered lane   Replica extra copy

  • lost-found.events carries lost-and-found events.
  • community-notices.events carries community notice events.
  • Both currently have one partition and one replica.
  • One partition means simple per-topic ordering, but only one active consumer in a group can read that topic at a time.
  • One replica means no additional Kafka copy if the broker fails.
  • The project publishes from PostgreSQL outbox rows using Spring KafkaTemplate, then listeners read the topic.

One sentence to remember: A topic is the named stream, a partition is its ordered lane, and a replica is another copy of that lane.
